## 零、本分支的边界（先说清楚）

原方案是**全栈**分期（M0–M7 含后端迁移 V44–V50）。本分支不适用。重新划线：

| 项 | 归属 |
| --- | --- |
| uni-app Vue3 客户端（微信小程序 + H5） | **本分支产出** |
| 客户端契约层、类型、错误码映射、定点金额 | **本分支产出** |
| 客户端 E2E / 契约一致性测试 | **本分支产出** |
| `/scm/mall/**` 后端、`UserTypeEnum` 追加、迁移 V44+ | 其它分支 / 工作流 |
| F0-DEBT-01 读侧收口（FA-1/FA-2） | 其它分支 |
| 微信 AppID / 合法域名 / 商户号 | 业主 |

**本分支的输入 = 一份冻结的接口契约；不是后端代码。** 因此本分支的第一个交付物不是页面，而是「契约冻结 + 契约层」。

## 一、现状核实（含对原方案的一处修正）

### 1.1 `xsy-scm-miniapp/` 确为 v1 遗留，且从未构建

实测数据，与原方案一致：

| 核查项 | 实测结果 |
| --- | --- |
| git 跟踪文件 | **69** 个（`src/**` 58 个） |
| 页面 | **11** 个（主包 5 + account 分包 2 + trade 分包 4） |
| 技术栈 | Taro **4.2.1** + React **18** + zustand 4.5.5 |
| 令牌 | 自研请求头 `X-Mall-Token`（`src/services/http.ts:83`） |
| 接口前缀 | `/api/mall/**` |
| 错误码域 | 自成一域 `40070–40074 / 40170–40172 / 40370–40372 / 40470–40473 / 40970 / 50170` |
| 引入提交 | `da1184d feat(mall): integrate cross-platform storefront foundation` |
| 最后改动 | `803a862 feat(v2): establish SmartAdmin SCM baseline and W3 pricing`（随基线冻结） |
| 构建产物 | **无 `node_modules`、无 `dist`，从未构建**（`appid` 仍是 `touristappid` 占位） |

结论不变：**这 58 个文件只能当交互与接口语义参考，不能当"已有基础"估工期。**

### 1.2 ⚠️ 修正：遗留商城后端不是"不存在"，而是"被基线删除、可从历史恢复"

原方案的核实方式是 `grep -ril mall xsy-scm-server`，只命中 4 个顺带命中文件，据此写下
「**没有任何 `module/scm/mall` 目录**」「59 个 Java 文件在 V2 中不存在」。

**路径猜错了，结论因此偏了。** 实测：

```text
实际路径：xsy-scm-server/src/main/java/com/xianshuyuan/scm/mall/
          （v1 的 Spring Security 体系，不是 SmartAdmin 的 module/scm 结构）
文件数：  59 个 Java 文件（controller 6 / service 10 / vo 15 / dto 8 / entity 5 /
          mapper 6 / security 6 / row 2 / test 1）
删除点：  803a862（随整个 v1 后端一起删除，与 xsy-scm-miniapp 同一提交）
```

v1 的商城迁移同样在历史里：

```text
V29__create_mall_customer_foundation.sql   mall_customer_account / mall_customer_session /
                                           mall_customer_address / mall_cart_item
V30__add_mall_order_source_and_address_snapshot.sql  sales_order 来源加 MALL + mall_order_address
```

恢复方式：

```bash
git show 803a862^:xsy-scm-server/src/main/java/com/xianshuyuan/scm/mall/service/MallErrorCodes.java
git show 803a862^:xsy-scm-server/src/main/resources/db/migration/V29__create_mall_customer_foundation.sql
```

**这对本分支的意义（重要）**：接口语义、字段形状、错误码、交互流程不是从零设计，而是
**有一份完整且经过设计评审的 v1 契约可恢复**。它是客户端契约层最好的起点。

**但它不能照搬，因为架构不兼容**（原方案此点判断正确）：

| 维度 | v1 遗留商城 | V2 裁决 |
| --- | --- | --- |
| 认证 | Spring Security + `MallAuthenticationFilter` + 自研令牌 | Sa-Token 1.44.0 多 `userType` |
| 会话 | `mall_customer_session` 表（token_hash） | 不建会话表，交 Sa-Token Redis |
| 账号 | `username` + `password_hash` | 微信 openid 优先 + 手机号兜底 |
| 购物车归属 | `customer_id` | 需按 `account_id`（见 3.3） |
| 地址 | 仅 `region VARCHAR(200)` | 需省市区六列 + `longitude/latitude/geom_crs` |

### 1.4 🔴 新发现：遗留错误码与 V2 已占用码段冲突

V2 scm 域实测已占用：`40000–40090`、`40410–40499`、`40910–40999`、`41000–41109`。
遗留商城错误码落在其中：

| 遗留码 | 含义 | V2 现状 |
| --- | --- | --- |
| `40070` | 购物车为空 | 🔴 已占用 `ORDER_IDEMPOTENCY_KEY_INVALID` |
| `40074` | 未选下单商品 | 🔴 已占用 `ORDER_DELETE_STATE_INVALID` |
| `40970` | 商品价格已变化 | 🔴 已占用 `ORDER_RETURN_ORDER_NOT_CONFIRMED` |
| `40170/40171/40172` | 登录失败/未登录/令牌失效 | ✅ 空闲 |
| `40370/40371/40372` | 账号停用/客户停用/商品不可见 | ✅ 空闲 |
| `40470–40473` | 商品/地址/订单/溯源不存在 | ✅ 空闲 |
| `50170` | 微信登录未开通 | ✅ 空闲 |

**直接后果（本分支必做）**：`src/types/mall.ts` 里的 `MallErrorCode` 表**不能照搬**，
必须整体重排到空闲段，并在契约冻结时与后端一次性对齐。
`src/services/http.ts` 只对 `LOGIN_REQUIRED` / `TOKEN_INVALID` 做硬编码跳转，
这两个码是客户端唯一的行为依赖，**必须最先冻结**。

### 1.5 🔴 新发现：遗留客户端分页参数名与 V2 不符

- 遗留客户端：`PageData { page, pageSize }`，`orderPage({ page, pageSize })`
- V2 `PageParam`：**`pageNum`** / `pageSize`

契约不符，客户端契约层必须按 `pageNum` 定义，并在契约测试里钉死。

### 1.6 遗留契约里另有两处不适合直接继承

| 项 | 遗留做法 | 问题 |
| --- | --- | --- |
| 购物车归属 | `mall_cart_item.customer_id` | 与「集团客户多采购员各自独立采购」冲突，应改 `account_id` |
| 首页装修 | `MallHomeResponse` + `MallHomeSection`（BANNER/FLASH_SALE/NEW_ARRIVAL/…）+ `MallThemeConfig` | 这是**通用装修器**，原方案自己说本期不做；客户端不应为它建复杂模型 |

## 二、遗留客户端复用清单（代码 vs 资产）

**代码不能复用**：Taro + React ≠ uni-app + Vue3。以下按「资产」处理。

| 资产 | 载体 | 处理方式 | 价值 |
| --- | --- | --- | --- |
| 领域类型与字段形状 | `src/types/mall.ts`（282 行） | 转译为 TS interface，**错误码重排** | 高 |
| 定点十进制算法 | `src/utils/decimal.ts`（142 行） | **算法可移植**：纯整数运算、无 BigInt、自带 HALF_UP 与千分位 | 高 |
| 信封优先解析策略 | `src/services/http.ts` | 策略复用（任意 HTTP 码都先解析信封），实现重写 | 高 |
| 幂等键策略 | `src/utils/id.ts` + `services/checkout.ts` | 策略复用：内容签名绑定 key，内容不变则复用 | 高 |
| 页面信息架构与交互 | 11 个页面 | 作为 IA 与交互稿参考 | 中 |
| Mall Theme 视觉变量 | `src/app.css`（109 行，生鲜绿 `#16a34a`） | 色值/圆角/间距转 `uni.scss` | 中 |
| 首页装修 section 模型 | `MallHomeSection` 等 | **砍掉**，本期只做「一组配置 + 一处生效」 | — |

> 定点算法是遗留客户端里最值得保留的一块：它明确禁止 `Number()` 求和，
> 并用整数 `unscaled` + 内部 6 位精度（后端结算 4 位，留 2 位余量）避免浮点误差。
> 这条约束要在新客户端以 **ESLint 规则 + 单测**双重钉死。

## 三、客户端分期（C0–C6，替代原 M0–M7）

原方案的 M0–M7 把后端迁移号当里程碑，客户端无法独立验收。重排为可独立验收的 7 期：

| 期 | 主题 | 产出 | 依赖 |
| --- | --- | --- | --- |
| **C0** | 契约冻结与工程骨架 | 契约文档 + TS 类型 + mock server + uni-app 骨架 | 错误码段裁决 |
| **C1** | 身份与会话 | 微信登录、手机号兜底、令牌存储、401 分流 | C0、AppID（H5 可先走兜底） |
| **C2** | 目录 / 可见性 / 客户价 | 首页、分类、搜索、详情；询价态；有货缺货 | C1 |
| **C3** | 购物车 + 收货地址 | 服务端购物车；地址 + 地图选点 | C2 |
| **C4** | 下单闭环 | preview → fingerprint → submit；幂等；变价负向 | C3 |
| **C5** | 订单查询与履约展示 | 列表/详情；只展示状态，不自建状态机 | C4 |
| **C6** | 商城配置消费 | Banner / 分类 / 活动位 / 新品位（一处生效） | C2 |
| 延后 | 营销、支付 | 营销建议独立立项；支付待商户号 | — |

### C0 契约冻结与工程骨架

- uni-app + Vue3 + TypeScript + Vite，`src/api/` 契约层集中定义请求/响应/错误码
- **mock server 从契约生成**，使 C1–C6 可在后端未就绪时推进（这是本分支解耦的关键）
- 契约测试双向钉死：客户端类型 ↔ 后端 VO 字段；客户端错误码表 ↔ 后端常量
- 分页统一 `pageNum` / `pageSize`

### C1 身份与会话

- 微信登录（`code` → 后端换 openid）优先；手机号验证码兜底（AppID 未就绪时唯一可联调路径）
- 令牌头与 SmartAdmin 一致，**不再用 `X-Mall-Token`**
- 客户端只做一件事：拿到 token 存好、失效时清会话跳登录。**不缓存 profile 作为授权依据**
- 仅 `COOPERATING` 可进入；`SUSPENDED`/`BLACKLIST` 给明确文案

### C2 目录 / 可见性 / 客户价

- 分类树只展示**有可见 SKU** 的分类（服务端过滤，客户端不再二次过滤）
- 价格只展示服务端返回值，`unitPrice` 为 `null` 时展示「询价」，**不得用 `¥0.00` 冒充**
- 可用量口径按 D-9 裁决；客户端**不做** `quantity − reserved_quantity` 运算
- 图片一律静态 URL；**商城 VO 不得出现 `private/` 前缀**（G-1 契约守卫）

### C3 购物车 + 收货地址

- 服务端购物车，跨端一致；数量一律字符串定点
- 地址含省市区六列 + 经纬度，形态与 V40 三张主档地理列一致（配送 L3 排线的前置）
- 「一个账号一个默认地址」
- 归属由服务端从登录身份派生，客户端提交的 `customerId` 一律忽略

### C4 下单闭环

```text
POST /scm/mall/orders/preview  → 明细 + priceFingerprint
POST /scm/mall/orders          → 同一 priceFingerprint + Idempotency-Key
```

客户端职责四条：
1. `Idempotency-Key` 必带，与「商品+数量+地址+价格指纹」签名绑定；内容不变时重试**复用同一 key**
2. 指纹不一致（专用错误码）→ 重新 preview + 提示「价格已变化」
3. 提交按钮 ref 级 in-flight 互斥，防连点
4. 落地状态按 D-3 裁决展示；客户端不假设状态

### C5 订单查询与履约展示

- 只确定**展示口径**（已确认/已分拣/已发货/已签收/实重差异），状态来自主线单据
- **不在客户端自建状态机**，不本地推导状态流转

## 十一、基线替换（2026-09-22 执行）

### 11.1 做了什么

### 11.2 版本升级的真实边界（重要）

"升到新稳定版"不等于"升到最新版"。`@dcloudio/vite-plugin-uni` 的 peer 依赖
**把 vite 精确锁在 `5.2.8`**，且 uni-app 内置 Vue `3.4.21` 编译器，因此：

| 想装 | 实际约束 | 结果 |
| --- | --- | --- |
| `vite@8.3.0` | `peerDependencies.vite === "5.2.8"` | 上不去，用 `5.2.8` |
| `vue@3.5.43` | uni-app 内置 `@vue/compiler-sfc`/`server-renderer` = `3.4.21` | 留在 `3.4.38` |
| `pinia@4.0.3` / `pinia@2.3.1` | peer 要求 `vue ^3.5.11` | 只能 `2.1.7` |
| `vue-i18n@11.x` | 源码零处使用，且 uni-app 内部依赖 `@intlify/shared@9.1.9` | **直接移除** |

升级后的实际版本：`@dcloudio/* 3.0.0-5020620260917001`（2026-09-17 稳定构建，非 alpha）、
`vue 3.4.38`、`vite 5.2.8`、`pinia 2.1.7`、`@dcloudio/types 3.4.31`、`uni-ui 1.5.12`、
`sass 1.104.1`、`eslint 9.39.5`、`prettier 3.9.8`。

顺带处理的两处基线问题：
1. **`build.minify: 'terser'` 但基线未安装 terser** → 已补 `terser@5.51.2`（否则生产构建会失败）
2. **`.eslintrc.cjs` 在 ESLint 9+ 已不被读取** → 迁移为 `eslint.config.js` 扁平配置，
   规则集保持不变以免升级 lint 时顺手改变代码风格要求
3. 移除 `transpileDependencies`（Vue CLI / webpack 选项，Vite 忽略）
4. 移除 webpack-only 的 `sass-loader`，以及 10 个未使用的跨端平台包
   （只保留 `mp-weixin` + `h5`）

### 11.4 契约口径的变更

新基线用的是 **SmartAdmin 约定**，与 v1 遗留商城不同，客户端契约层必须按这个改：

| 项 | v1 遗留商城 | 新基线（SmartAdmin） |
| --- | --- | --- |
| 成功判定 | `code === 0` | **`code === 1`** |
| 响应字段 | `{ code, message, data }` | `{ code, msg, data }` |
| 令牌头 | `X-Mall-Token` | **`Authorization: Bearer <token>`** |
| 令牌失效码 | `40171` / `40172` | **`30007` / `30008` / `30012`** |
| 本地存储前缀 | `mall_` | `xsy_mall_` |

> §1.4 里"错误码段冲突"的结论仍然有效，但**优先级下降**：新基线的错误码处理走
> `smart-request.js` 的 `code !== 1` 分支，商城错误码只需在该分支内做映射。
