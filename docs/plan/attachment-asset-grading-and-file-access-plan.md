## 1. 要解决的问题

F0 已经把「上传白名单」和「按目录前缀的读取守卫」建起来了，但两者之间有一条缝：

```text
写侧  业务表单接受任意 fileKey  →  可以把他人私有附件绑到自己的业务对象上
读侧  业务 VO 展开 fileKey      →  FileService.getFileList() 无用户参数，
                                  FileAccessGuard 完全不参与
```

读侧的入口是 `FileKeyVoSerializer`（`sa-base/common/json/serializer/`），它被
`oa/enterprise`（营业执照等）、`oa/notice`（公告附件）、`support/helpdoc`、`support/feedback`
的 VO/Form 引用，并且是**代码生成器的默认模板**，所以不处理就会持续长出新实例。
商品图片是同一模式的 SCM 实例。

后果不是「越权读一条记录」，而是**数据提升**：只要攻击者对某个业务对象有编辑权，
就能把一个只有他自己看得见（甚至完全不该他看得见）的附件，变成该对象所有查看者可读。

## 2. 分级模型（裁决已定，本节是可执行判定表）

唯一的分级来源是目录前缀，不引入第二套标签体系。

| 目录 | 机密性 | 可读条件 | 典型资产 |
| --- | --- | --- | --- |
| `public/image/` | 公开 | 无需授权，URL 可静态缓存、可匿名 GET | 商品图片、后续商城 banner |
| `public/…`（其他） | 公开 | 同上 | 新增公开资产前必须先在此登记用途 |
| `private/common/` | 私有 | 业务对象权限（FA-2 后） | OA 企业执照、供应商资质、合同 |
| `private/notice/` | 私有 | 同上 | 公告附件 |
| `private/help-doc/` | 私有 | 同上 | 帮助文档图片 |
| `private/feedback/` | 私有 | 管理员或提交人 | 意见反馈截图 |

判定规则：

- 一份资产是否公开，取决于**最终读者是否需要登录**，不取决于「哪个模块上传的」。
- 需要登录才能看的，一律 `private/`，并且必须能回答「凭哪条业务权限可读」。
- 公开目录写入即公开，**撤回成本很高**（浏览器缓存、CDN、被转发），因此放进 `public/` 是
  一个需要显式选择的动作，不能靠上传组件的默认值落到哪算哪。

## 3. FA-1：读侧收口（受控批量读取）

目标：让所有从服务端展开出来的文件 URL 都经过一次授权判断，且不改掉 SmartAdmin 的调用习惯。

- 在 `FileService` 增加带请求者身份的批量入口（形如 `getFileList(List<String> keys, RequestUser user)`），
  逐 key 走 `FileAccessGuard`；无权限的 key **不返回**（不是返回空 URL），避免「存在性」本身成为旁路信号。
  原有无身份签名保留给内部与公开路径调用，但**不允许业务 VO 序列化器继续使用**。
- `FileKeyVoSerializer` 改为经请求上下文取当前用户后调用受控入口；同步修改
  `VOVariableService` 的代码生成模板，否则新页面会继续生成不安全写法。
- 序列化发生在 Jackson 写 JSON 时，拿不到 `RequestUser` 的处境要提前确认：
  如果只能靠 `RequestContext` 线程本地变量，异步导出、`@Async`、定时任务里的序列化路径
  必须显式失败（抛错）而不是静默放行 —— 静默放行等于把洞留在最难发现的地方。
- 商品图在 FA-3 之前仍有一批历史 `private/common/` key：它们属于「有商品查看权即可读」这一类，
  由 FA-1 的判定按业务对象解析，不在此特判。

范围边界：FA-1 不引入关系表，仍按前缀 + 现有 `FileAccessGuard` 规则判定，只是把守卫接到读路径上。

## 4. FA-2：`scm_file_relation` 关系表授权

目标：把「谁能看这个文件」回答成「谁能看挂这个文件的业务对象」。

规划表结构（版本号待重排，暂记 V42）：

```text
scm_file_relation
  id                BIGSERIAL PK
  file_key          VARCHAR(250) NOT NULL      -- 指向 t_file.file_key，不建外键
  biz_type          VARCHAR(50)  NOT NULL      -- 枚举白名单：PRODUCT / SUPPLIER_QUALIFICATION /
                                               -- PURCHASE_CONTRACT / FINANCE_RECEIPT / ...
  biz_id            BIGINT       NOT NULL      -- 该业务对象主键
  created_at / deleted ...
  UNIQUE (file_key, biz_type, biz_id) WHERE deleted = FALSE
```

要点：

- **一张文件可以挂多个业务对象**（同一张回单同时属于多个结算单），这是选择关系表而不是
  在文件表加 owner 列的直接原因。
- 业务权限判定复用各业务模块自己的可见性规则，不新增第三种权限模型：
  `check(key, user)` → 取该 key 的全部活动关系行 → **任一** `(biz_type, biz_id)` 用户可读即放行。
  「任一」而非「全部」，否则一份多方共享的合同会对其中一方不可见。
- 无关系行的 `private/*` 文件视为**不可读**（除管理员按现有 support 权限查询），
  不能退化成「没人绑定所以谁都能看」。
- 生命周期改为两段式：上传进 `private/common/` 的**暂存前缀**（例如 `private/common/scratch/`，
  带 `t_file` 记录但无关系行）→ 保存业务表单时按最终 key 建关系行 →
  由一个低频清理任务回收超过 N 天仍无关系行的暂存件。
  暂存窗口必须显式存在，否则「上传成功但表单没保存」的垃圾永久堆积。
- 删除业务对象时关系行随软删除失效；**不删物理文件**，与 SCM 既有「不静默删数据」一致。
- 不建数据库外键（`AGENTS.md` §8），完整性由 Service 层校验 + 唯一约束保证。

迁移顺序（必须按此顺序，否则读侧会先失效）：
① 建表 → ② 为**存量** `private/*` 业务附件回填关系行（按各业务表已有的 fileKey 字段扫描，
回填脚本要输出「扫到多少 / 建了多少 / 剩下多少孤儿」三个数，孤儿必须人工裁决）→
③ 打开按关系判定的读路径 → ④ 才允许关闭前缀级放行。

## 5. FA-3：商品图片搬运与商城免登录展示

- 用一次性迁移把 `product_image` 中仍指向 `private/common/` 的 key 对应对象**复制到**
  `public/image/`（复制而非 move：历史 key 可能已被外部引用，且失败可重跑），
  再把行的 `file_key` 改到新前缀。迁移必须在事务外可重入，按行幂等。
- 搬运完成后 `product_image` 全部落在 `public/image/`，此时才可以在 Java 侧把
  「新绑定必须公开」的判断升级为数据库 CHECK；在那之前加 CHECK 会把存量数据变成故障。
- 前端商品图不再拼预签名串，URL 直接可缓存；商城 / 小程序（W6-2）免登录展示因此无需新接口。
- 搬运**不能与 FA-1 同期上线**：读侧收口先跑一轮，确认没有把公开资产误判为私有，再动数据。

## 6. 验收判据

- 权限矩阵 IT（新增，`FileAccessGuardPgIT` 或复用 `FileAccessGuardTest` 扩展）：
  对每个前缀 × {超管、有业务对象权、无业务对象权、另一用户自有的私有文件} 断言可读 / 不可读；
  **不可读必须表现为 URL 不出现在响应里**，而不是空字符串。
- 数据提升回归：用户 A 有商品编辑权、有供应商附件查看权、**无**该供应商查看权时，
  把该 fileKey 绑到自己商品上必须被拒（FA-0 已覆盖 SCM 侧，FA-2 要把同一断言扩展到关系表）。
- 序列化路径回归：JSON 展开含无权限 key 的 VO，响应中不得出现该 key 的任何 URL。
- 清理任务：暂存超期件被回收，且**永不**回收有关系行或被业务表直接引用的文件（用测试钉住，
  这类误删是不可逆事故）。
- 存量搬运：迁移前后行数与「非 public 前缀剩余行数」都要断言，重跑一次结果必须相同。
- 前端：`vue-tsc`（SCM 范围）+ `npm run lint`；浏览器验证商品图片正常显示且 URL 为 public 前缀、
  无过期语义；OA / 反馈 / 帮助文档三处附件仍可读。
- 本地存储模式**不作为**权限验证环境（`/upload/**` 静态直出无守卫），权限用例必须跑对象存储模式。

## 7. 门禁与非目标

- **门禁**：在引入任何非管理员业务角色之前，FA-1 与 FA-2 必须完成。当前系统只有 SUPER_ADMIN
  （`administratorFlag` 绕过权限校验），所以洞尚未被真实暴露，**这是唯一的安全窗口期**；
  一旦上线业务角色，FA-0 之后的写侧虽然收紧，读侧仍会让附件互看。
- 非目标：不建 DLP / 水印 / 病毒扫描；不做文件级 ACL（表达成关系表就够）；
  不为兼容旧 `private/common/` 商品图长期保留双前缀放行——FA-3 之后必须回到单一口径；
  不把 SmartAdmin 底座的文件表改造成 SCM 业务表。
