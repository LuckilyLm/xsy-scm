## D-1 存量已签收 / 已收货事实是否回填财务事实

**阻塞阶段**：F1-2 的回填入口（不阻塞 F1-2 主路径）。

### 业务例子

P2 上线后库里已经存在真实的 `SIGNED` 订单与 `CONFIRMED` 收货单（dev 库即有，生产上线后同样会有）。
若不回填：财务页「应收发生额」从上线日 0 起算，而业务方记得「上周已经发过三车货」，
两边第一次对账就会对不上；若回填：这三车货的应收 `event_at` 是上周的签收时刻，
但**生成时刻**是上线日，`finance_operation_log` 的 `created_at` 与 `event_at` 会分离。

### 候选方案

| 候选 | 影响 | 与既有裁决的冲突 |
| --- | --- | --- |
| **A 不回填**（设计稿暂定） | 财务账从上线日起干净；历史往来只能回业务域查 | 无 |
| **B 上线时一次性回填** | 生成器按存量 `SIGNED` / `CONFIRMED` 重放，`event_at` 取历史时点；往来报表窗口口径正确 | 需同时决定**上线前的已批准退货是否补红字**（第二批 Q27 的补生成逻辑只对上线后的签收生效）；回填本身是一次数据修正，需按 V37 的纪律「重放不出来即 RAISE」 |
| **C 提供受权限保护的「历史补生成」命令，分批执行** | 财务可自主控制节奏与范围 | 需要 1–2 个新操作权限点（不属 Q24 禁止的金额权限，但属新增权限）；命令必须幂等（来源唯一索引已保证） |

### 建议重点考虑的问题

1. 上线时点距离 P2 发车上线多久？间隔越短，A 的代价越小。
2. 若选 B/C，**历史退货**要不要一起补红字？不补会出现「历史应收全额挂着、货早已退」的永久偏差。
3. 回填产生的 `operation_log` 行，`operator` 记谁（系统 / 执行人）？

## D-2 「可冲金额」是否扣除已核销额

**阻塞阶段**：F1-2 红字生成的金额校验。**2026-09-25 评审重新打开。**

### 业务例子（评审指定）

```text
正常应收 100
→ 收款 100
→ 核销 100          （此时应收：净额 100、已核销 100、未核销 0、结清）
→ 之后批准退货 20
```

- 若「可冲 = 净额 − 已红字 − **已核销**」：可冲 = 0，红字 20 被拒；
  红字生成在 `OrderReturnService.approve` 的同一事务内，抛错即**整笔退货批准回滚** ——
  财务规则反向阻止了原本合法的订单域动作，评审已明确不可接受。
- 若「可冲 = 净额 − 已红字」（不扣已核销）：红字 20 成功；应收净额变 80、已核销仍 100，
  **未核销 = −20**。这 −20 的业务含义是「客户多付了 20 / 我们欠客户 20」，
  与退款付款（Q19）是两件事：钱当初是作为货款收进来的，不是预收。

### 候选方案

| 候选 | 影响 | 与既有裁决的冲突 |
| --- | --- | --- |
| **A 可冲不扣已核销**（未核销允许为负） | approve 不被阻塞；派生公式需定义负数语义与展示（负未核销 = 多收/应退）；核销校验「本次 ≤ 未核销额」在未核销 ≤ 0 时自然拒绝再核销 | 与 Q17「读时派生」一致；负数语义是新增解释，需写入页面 tooltip |
| **B 可冲扣已核销** | 语义最「干净」，但上例中 approve 被财务阻塞 | **评审已否决**（不得阻止合法 approve） |
| **C 完全不校验红字金额** | approve 永不被阻塞；但少拣场景（见 D-4）可出现累计红字 > 净额 → 应收净额为负 | 与第一批 Q13/Q27「累计红字不得超过可冲金额」字面冲突，需负责人明确放弃该校验 |
| **D 封顶生成 `min(批准额, 可冲)`** | approve 成功；差额不生成财务事实 | 静默丢差额，违反「不建解释不了的账」；除非差额有可见残差，否则不可接受 |
| **E 超额部分生成独立「应退 / 待退」事实** | 差额有归属 | **新增财务对象**，超出 27 条裁决，需新裁决 |

### 建议重点考虑的问题

1. **负未核销额是否可接受**？若接受，它在客户维报表里叫什么（多收款 / 应退未退），属 R1 还是 R2？
2. 上例中客户最终应拿回 20：这笔钱在 R1 里由谁表达 —— 退款付款（Q19）独立登记，还是负未核销本身？
   两者并存会不会被读成「退了两次」？
3. 若选 A，红字与核销**并发**时（同一应收一边在核销一边在红字）锁序已覆盖串行，
   但「谁先谁后结果不同」是否可接受（先核销则未核销更负，先红字则核销额上限更小）？

## D-3 收款 / 付款单录错的纠正路径

**阻塞阶段**：F1-3 的纠错入口（不阻塞登记）。**2026-09-25 评审重新打开。**

### 业务例子

财务把客户 A 的一笔收款 **5,000 登成 50,000**（多一个零），或把客户 A 的款登到了客户 B 名下。
「反向核销 + 重新登记」只能撤销**分配**：错误那张收款单仍挂着 50,000 的待核销余额，
客户 A 的往来页永远多出一笔不存在的钱；对象登错时，客户 B 名下还会凭空多一笔预收。
**登错的单据本身在 append-only 纪律下没有任何纠正手段** —— 这是评审指出的真缺口。

### 候选方案（设计稿 §6.3 已给出形态与六面影响，此处只列取舍）

| 候选 | 影响 | 与既有裁决的冲突 |
| --- | --- | --- |
| **A 收付款增加 `entry_type NORMAL/REVERSE` + `reverse_of_id` + `reason`**，反向前强制「已用额 = 0」（先反向其全部核销） | append-only、与反向核销同形；负待核销不会出现；需新增 2 个权限点（`scm:finance:receipt:reverse` / `scm:finance:payment:reverse`，菜单号追加 1526/1527）与 2 个日志类型 | 与 Q20「破坏性动作需独立权限 + 原因 + 日志」一致；权限点属新增但属 Q20 要求之内 |
| **B 同 A 但允许「已用额 > 0」时反向** | 不必先反向核销，操作更顺；但产生负待核销，语义与展示复杂化 | 与 D-2 的负数语义叠加，两处负数需统一解释 |
| **C 不纠错，登错走数据修正迁移** | 零新机制 | 财务纠错是日常，运维不可接受 |
| **D 允许一次性修改对方 / 金额** | 最省事 | **违反全局不变量 1**（不得修改历史财务事实） |

### 建议重点考虑的问题

1. 选 A 时，「反向前必须已用额 = 0」这条前置是否可接受？它把一次纠错拆成
   「反向核销 N 笔 → 反向收款 → 重新登记 → 重新核销」四步，步骤多但每步都可追溯。
2. 对象登错（A 的款登到 B）用「反向 + 重登」表达后，B 名下会留下「一笔收款 + 一笔反向」的痕迹 ——
   这是否正是财务想要的审计形态？
3. 反向收付款是否需要**第二人审批**？（Q20 已裁不新增审批状态机；若此处要审批，等于局部推翻 Q20，需明确。）

## D-4 少拣时红字超过可冲金额的处置

**阻塞阶段**：F1-2 红字生成的金额校验（与 D-2 同一点）。**2026-09-25 评审重新打开。**

### 业务例子

订单行结算量 5（`actual_quantity = 5`）、分拣少拣实发 3（`SHORT`）、签收后应收 = 3 × 单价 = 30。
客户实际收到 3 件，但事后整行退货获批 5 件 —— **这是合法的**：退货申请量上限是
`actual_quantity`（`OrderReturnService.java:135`），不是实发量。
于是红字请求金额 = 5 × 单价 = 50 > 应收 30。

- 设计稿原暂定「整单回滚抛 41137」→ 退货批准被财务阻塞 → **评审已否决**。
- 差额 20 的业务含义：客户退了 2 件**从未收到**的货。这 2 件在库存账上从未出库
  （`SALES_OUT` 只有 3），在订单账上却结算过 5 —— 偏差源头在订单域与库存域之间，不在财务域。

### 候选方案

| 候选 | 影响 | 与既有裁决的冲突 |
| --- | --- | --- |
| **A 不校验，红字按批准额全额生成** | approve 不被阻塞；该行应收净额 = 30 − 50 = **−20**，负数语义与 D-2 联动 | 与 Q27「累计红字不得超过可冲金额」字面冲突，需负责人明确改为「不得超过结算口径上限」或放弃上限 |
| **B 封顶生成 30，差额 20 不记** | approve 成功；但账上客户仍「欠 20 的货钱」而货已退完 → 永久偏差且不可见 | 静默丢事实，不可接受，除非差额有可见残差列 |
| **C 退货批准时校验 `approved_quantity ≤ 实发量`** | 从源头消除超额 | **改订单域校验**，超出 R1 范围且改变既有业务规则，需单独立项（与「不在 R1 新建采购退货模块」同精神） |
| **D 超额部分生成独立「应退」事实** | 差额有归属 | 新增财务对象，需新裁决（同 D-2 候选 E） |

### 建议重点考虑的问题

1. 「客户退了没收到过的货」在业务上是否真实存在（录错退货量？补发未走补单？）——
   若本质是录错，正确答案可能在订单域校验（候选 C）而不是财务域兜底。
2. 若选 A，D-2 与 D-4 的负数语义必须**一次裁清**：负应收净额、负未核销额、多收款三者如何互相对应。
3. 无论选哪个，红字明细的 `quantity` 记批准量还是记实发量？（记批准量才能与退货单对账，记实发量才能与应收对冲 —— 二者不可兼得，需表态。）

## D-5 收款 / 付款 / 核销三类的行级数据范围

**阻塞阶段**：F1-5 / F1-6 的读侧与权限 IT。

### 业务例子

销售甲只被授权看自己的客户（`customerSellerScope`）。财务登记了一笔客户 A（甲的客户）的预收 10,000。
问题一：将来若财务视图开放给销售（本期不开放，Q24），甲该不该看到这笔预收？
问题二：核销行同时属于「收款（客户维）」与「应收（订单维 `seller_id`）」两个归属 ——
一张应收单的客户是 A、业务员是甲，而用来核销它的收款登记在客户 A 名下；
若甲的范围按订单维收窄、收款按客户维收窄，**同一条核销行在两个列表里的可见性可能不一致**。

### 候选方案

| 候选 | 影响 | 与既有裁决的冲突 |
| --- | --- | --- |
| **A 设计稿暂定**：收款按 `customerSellerScope`；付款的供应商侧不收窄（P0 裁决 7：供应商共享读）、客户侧同收款；核销随 **target** | 实现最简；核销行可见性 = 被核销单据的可见性 | 与 Q23 已裁的应收 / 应付口径衔接自然 |
| **B 收付款不做行级范围，只受功能权限** | 最省 | **与 P0 裁决 2「没有授权范围就查不到数据」相悖** |
| **C 核销随 source 与 target 的交集** | 更严 | 可能让财务在自己可见范围内仍无法核销（source 可见、target 不可见），与「核销主要面向应收单」（第一批 Q4）的操作习惯冲突 |

### 建议重点考虑的问题

1. 本期财务页面只授 `SCM_FINANCE`（Q24），而 `SCM_FINANCE` 已持 1302/1311/1322/1331 ——
   即**当前唯一使用者本来就全范围**，D-5 实际影响的是「将来开放给非全范围角色」时的行为。
   是否接受「本期按 A 实现、将来开放前再复核」？
2. 核销随 target 时，一条核销行在「收款页抽屉」与「应收页抽屉」都可见 ——
   若某角色只看得到收款、看不到应收，抽屉里的核销行要不要裁剪？（属前端展示口径，需与 Q24 一并表态。）
