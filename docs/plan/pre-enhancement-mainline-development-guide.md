# XSY-SCM 主线开发计划

> 基线：当前主线已完成 Finance R0，后续先完成现有业务主链，再进入增强系统需求。
> 本文只定义“做什么”和“做到什么程度”，不包含 AI 执行提示词。

## 1. 开发顺序

```text
P0 基线收口
→ P1 分拣管理
→ P2 物流配送 L3
→ P3 Finance R1
→ P4 Finance R2
→ P5 营销与结算
→ P6 后台补缺 / 订单助手 / 溯源
→ P7 小程序
→ Baseline Complete
→ 再进入增强系统需求
```

---

## 2. P0 基线收口

目标：在继续扩展业务模块前，把现有安全、权限、并发和文档状态收口。

需要完成：

- 关闭 `F0-DEBT-01`
  - FA-1：FileService 读侧统一受控
  - FA-2：建立业务对象与附件的关系授权
  - FA-3：历史文件兼容与迁移收口
- 建立正式非管理员业务角色并验证数据范围
  - 销售
  - 采购
  - 仓库
  - 分拣
  - 配送
  - 财务
- 补库存预留并发测试
- 对 Delivery L0-L2 做最终 E2E 验收
- 同步：
  - `docs/progress.md`
  - `docs/decisions.md`
  - 需求覆盖文档
  - `AGENTS.md`

完成标准：

- 私有附件不存在越权读取
- 正式非管理员角色可用
- 库存预留不存在超卖、重复预留、重复释放
- Delivery L0-L2 主流程稳定
- 项目文档与真实代码状态一致

---

## 3. P1 分拣管理

目标：

```text
销售订单
→ 分拣任务
→ 实际分拣 / 实重
→ 稳定实发事实
→ 交给 Delivery L3
```

首期范围：

- 分拣任务
- 分拣任务明细
- 按客户订单分拣
- 按商品汇总分拣
- 标品数量确认
- 非标品实重录入
- 分拣员
- 分拣状态
- 分拣标签 / 小票打印
- 分拣操作日志
- 权限与数据范围

开工前必须明确：

- 哪些订单可以进入分拣
- 一张订单是否允许多次分拣
- 订单行是否允许拆分分拣
- 非标品实重何时成为最终数量
- 分拣完成后是否允许修改
- 缺货、少拣、替代商品如何处理
- 分拣结果如何关联订单实际履约数量

以上六问连同分拣与配送 / 库存 / 权限模型的衔接口径，已由用户逐条裁决，
见 [`docs/decisions.md`](../decisions.md)「P1 分拣管理裁决（2026-09-24）」第 1–14 条；
实现与验收以该节为准，本节保留范围与完成标准。

完成标准：

- 按订单与按商品视角来自同一套业务事实
- 不直接修改库存余额
- 分拣结果可稳定供 Delivery L3 使用
- 重复生成任务不会生成重复业务事实
- 正式分拣角色可完整使用
- 后端、前端、数据库、权限、测试、E2E 全部通过

---

## 4. P2 物流配送 L3

目标：

```text
已规划线路
→ 发车 / 发货
→ 库存正式出库
→ 配送中
→ 签收 / 异常
→ 配送完成
```

范围：

- 发车
- 发货
- 配送状态
- 出库联动
- 签收
- 异常签收
- 配送完成
- 订单 / 配送 / 出库互相追溯
- 幂等
- 权限
- 操作日志

库存要求：

配送模块不得直接修改库存。

必须通过现有库存领域正式命令产生：

```text
InventoryOutbound
→ inventory_balance
→ inventory_movement(SALES_OUT)
```

必须建立明确关系：

```text
delivery
→ outbound
→ sales order
→ sales order item
```

这条关系是后续利润和成本核算的基础。

开工前必须明确：

- 实发数量来自哪里
- 是否允许部分发车
- 是否允许部分签收
- 拒收如何处理
- 配送取消后库存如何处理

GPS / 轨迹可以拆成后续子阶段，不阻塞 L3-Core。

完成标准：

- 发车 / 出库 / 签收流程闭环
- 重复请求不会重复扣库存
- SALES_OUT 只能由库存领域产生
- 配送与订单、出库均可追溯
- 正式配送角色可使用
- E2E 覆盖完整履约流程

---

## 5. P3 Finance R1

目标：建立真实的经营财务事实。

范围：

- 应收
- 应付
- 收款
- 付款
- 核销
- 财务操作日志
- 财务权限
- 财务明细查询与导出

开工前必须明确：

### 应收形成时点

必须明确由哪个业务事实触发：

- 发货
- 签收
- 配送完成
- 财务确认
- 其他明确规则

### 应付形成时点

必须明确由哪个业务事实触发：

- 收货
- 入库
- 对账确认
- 财务确认
- 其他明确规则

原则：

- 订单金额不能直接当应收
- 采购金额不能直接当应付
- 收款、付款、核销必须是独立可追溯事实
- 金额统一使用定点类型
- 财务写操作必须支持幂等

完成标准：

- 应收 / 应付来源明确
- 收付款可追溯
- 核销关系可追溯
- 退款 / 退货有明确财务处理方式
- Finance R0 报表升级后口径仍一致
- 财务权限通过正向和负向验证

---

## 6. P4 Finance R2

目标：

- 客户利润
- 商品利润
- 订单利润
- 销售毛利
- 应收账龄
- 应付账龄
- 客户对账
- 供应商对账
- 财务分析

前置条件：

必须已经有稳定关系：

```text
销售订单行
↔ 实际出库
↔ SALES_OUT
↔ 实际出库成本
```

禁止使用：

```text
日期 + SKU + 客户
```

之类模糊条件推测成本归属。

完成标准：

- 利润可回溯到真实订单、出库和成本
- 账龄来自真实应收 / 应付余额
- 页面与导出口径一致
- 无成本权限时不泄露成本数据
- 大数据量查询有性能验证

---

## 7. P5 营销与结算

范围：

- 首页运营配置
- 新品推荐
- 限时特价
- 满减
- 满赠
- 优惠券
- 账期支付
- 货到付款
- 在线支付
- 余额支付 / 充值

要求：

- 所有价格必须走统一价格解析服务
- 活动价、协议价、客户价的优先级必须统一
- 支付必须幂等
- 支付回调必须验签
- 支付金额必须服务端校验
- 支付成功必须形成财务收款事实

---

## 8. P6 后台补缺 / 订单助手 / 溯源

### 后台补缺

补齐：

- 采购单模板
- 发货单模板
- 分拣小票模板

优先采用模板配置，不复制多套页面。

### 订单助手

补齐移动端所需稳定 API：

- 订单查询
- 订单编辑
- 改价
- 操作日志
- 权限
- 必要审批

涉及库存动作时必须调用库存领域，不允许直接写库存表。

### 溯源

首期目标：

```text
二维码
→ 商品
→ 批次
→ 采购
→ 入库
→ 分拣
→ 配送
```

只展示真实存在的数据，不伪造检测、温控、GPS 等信息。

## 9. P7 小程序

小程序最后开发。

启动前必须满足：

- 订单稳定
- 库存稳定
- 分拣稳定
- 配送稳定
- Finance R1 可结算
- 营销和支付稳定

第一阶段：

- 登录
- 首页
- 商品分类
- 商品详情
- 搜索
- 购物车
- 确认订单
- 订单列表
- 订单详情
- 再来一单
- 客户价格
- 营销价格

小程序不得重新实现：

- 价格规则
- 促销规则
- 库存算法
- 财务算法
- 订单状态机

全部调用后端统一能力。

---

## 10. Baseline Complete

以下全部完成后，当前主线开发才算结束：

```text
P0 基线收口
P1 分拣
P2 Delivery L3
P3 Finance R1
P4 Finance R2
P5 营销与结算
P6 后台补缺 / 订单助手 / 溯源
P7 小程序核心链路
```

同时必须满足：

- 正式非管理员岗位可用
- 订单 → 采购 → 收货 → 库存 → 分拣 → 配送 → 财务可追溯
- 关键写操作有权限、日志、幂等和并发保护
- 报表可以回到真实业务事实
- 核心指标不存在“名称和真实含义不一致”

达到此状态后，再启动增强系统需求。

---

## 11. Baseline 阶段明确不做

以下统一放到后续增强阶段：

- 自动净采购建议
- 自动创建采购单
- 采购任务 / 采购负责人体系
- 采购净重 / 毛重 / 高级损耗分摊
- 供应商竞价
- 采购实时比价
- 电子秤 / 标签机 / 硬件深度联动
- 司机绩效
- 采购员绩效
- 分拣绩效
- 高级经营驾驶舱
- 自动化采购
- 自动化配送优化

原则：

> 先把真实业务事实链做完整，再做自动化和智能化。
