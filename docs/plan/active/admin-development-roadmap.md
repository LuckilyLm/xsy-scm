## 2. 施工原则

- **只保留一个正式客户商城实现**（2026-10-10 确认）：`xsy-scm-customer-app/` 是主分支唯一正式客户商城目录，不再新建任何商城项目；`miniprogram-dev` 中已实现的页面与组件按文件级**选择性复用**，不整合分支历史、不双线开发。
- 优先复用现有 SCM 的商品、定价、客户、库存、订单、采购、配送、财务和营销领域服务；商城只做独立客户身份和受控业务适配。
- 将管理后台的订单与商城订单归到**同一个销售订单事实**，来源标识 `MALL`；不建立第二套商城订单账、库存账或财务账。
- 价格、可见商品、促销、库存及最终金额以服务端为准；客户端只负责展示、选购、确认、提示和安全重试。数量、单价和金额保留正式领域精度。
- 新 Flyway 只能追加版本；V118/V119 已提交，后续商城变更从 V120 起追加，禁止回改历史迁移。
- 每个阶段都按**页面 / API / 复用表或新增表 / 功能验收**收口，不能仅凭创建文件宣称完成。
- 当前处于开发期：优先实现真实业务流程。运行测试、数据库迁移、构建、提交、推送等按用户当次授权执行；计划本身不代表已经运行。

### 阶段 B：ADM-12 资金业务闭环 — 代码已齐，待运行回归

**已具备**：`PaymentIntentService` 成功派生、`BalanceRechargeSink`、`RefundFundingAllocationService`、比例计算器、退款分摊表 V118。

**补齐内容**：

1. 充值场景按既定“渠道成功即到账”：同步成功、`DELAYED` 等回调、重复回调、恢复重放，Finance 收款与钱包 CREDIT 可对应，不会重复增加余额。
2. 混合及多笔成功交易按**各来源剩余可退本金比例**冻结分摊；余额退回原冻结结算钱包，在线资金对应原交易；尾差与重试顺序固定。
3. 为订单退款详情增加**资金来源分摊**查看、执行或重试入口；展示每个来源的金额、状态、失败原因和结果单据，不只显示一条聚合成功/失败。
4. 对部分来源成功、部分失败、已成功后重试和累计退款上限作独立验证；保持正式订单售后和 Finance 单据关系清晰。

**API**：已有 `POST /scm/payment/refund/funding/execute`、`POST /scm/payment/refund/funding/detail`；复用现有支付回调、退款与余额服务。
**表**：V118 `refund_funding_allocation`，复用 `payment_refund`、`customer_balance_movement`、`finance_payment`。
**完成标准**：至少一张“余额 + 多笔在线资金”的订单完成部分退款、失败重试及查询，资金各来源金额之和等于业务退款额；充值黄金链不再跳过。

## 6. 已确认口径（2026-10-10 负责人确认）

以下三项已裁决，实施时直接遵循，不再作为待裁决事项：

- **混合/多交易退款来源分配**：按原订单各成功资金来源的**剩余可退本金比例**冻结分摊，尾差确定归集；不默认余额优先、在线优先或按时间顺序。V118 已按此实现。
- **商城多采购账号**：一个客户可绑定多个采购账号，由后台管理员开通、停用与重置密码。V119 的一客一号唯一索引需由新迁移（V120 起）放宽为「同客户可多账号、登录手机号全局唯一」。
- **常购返回结构**：以现有后端返回结构为准（`List<MallProductVO>` 裸数组 + `days/limit`），由前端修正请求参数与响应解析，不新增包装 VO 或分页字段。

仍待确认（不阻塞商城主线）：

- **一个账号切换多个企业**（集团/多门店）：属后续独立功能，需另立账号—企业授权模型。
- 首页与报表可见性策略的「负责人归属 ∩ 仓库」口径（见 §4）。
