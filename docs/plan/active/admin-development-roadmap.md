## 2. 施工原则

- **只保留一个正式客户商城实现**（2026-10-10 确认）：`xsy-scm-customer-app/` 是主分支唯一正式客户商城目录，不再新建任何商城项目；`miniprogram-dev` 中已实现的页面与组件按文件级**选择性复用**，不整合分支历史、不双线开发。
- 优先复用现有 SCM 的商品、定价、客户、库存、订单、采购、配送、财务和营销领域服务；商城只做独立客户身份和受控业务适配。
- 将管理后台的订单与商城订单归到**同一个销售订单事实**，来源标识 `MALL`；不建立第二套商城订单账、库存账或财务账。
- 价格、可见商品、促销、库存及最终金额以服务端为准；客户端只负责展示、选购、确认、提示和安全重试。数量、单价和金额保留正式领域精度。
- 新 Flyway 只能追加版本；V118/V119 保留远程表名前缀迁移，退款与商城迁移顺延到 V120～V124。后续变更从 V125 起追加，禁止回改已应用迁移。
- 每个阶段都按**页面 / API / 复用表或新增表 / 功能验收**收口，不能仅凭创建文件宣称完成。
- 当前处于开发期：优先实现真实业务流程。运行测试、数据库迁移、构建、提交、推送等按用户当次授权执行；计划本身不代表已经运行。

### 阶段 B：ADM-12 资金业务闭环 — 代码已齐，待运行回归

**已具备**：`PaymentIntentService` 成功派生、`BalanceRechargeSink`、`RefundFundingAllocationService`、比例计算器、退款分摊表 V120。

**补齐内容**：

1. 充值场景按既定“渠道成功即到账”：同步成功、`DELAYED` 等回调、重复回调、恢复重放，Finance 收款与钱包 CREDIT 可对应，不会重复增加余额。
2. 混合及多笔成功交易按**各来源剩余可退本金比例**冻结分摊；余额退回原冻结结算钱包，在线资金对应原交易；尾差与重试顺序固定。
3. 为订单退款详情增加**资金来源分摊**查看、执行或重试入口；展示每个来源的金额、状态、失败原因和结果单据，不只显示一条聚合成功/失败。
4. 对部分来源成功、部分失败、已成功后重试和累计退款上限作独立验证；保持正式订单售后和 Finance 单据关系清晰。

**API**：已有 `POST /scm/payment/refund/funding/execute`、`POST /scm/payment/refund/funding/detail`；复用现有支付回调、退款与余额服务。
**表**：V120 `xsy_refund_funding_allocation`，复用 `xsy_payment_refund`、`xsy_customer_balance_movement`、`xsy_finance_payment`。
**完成标准**：至少一张“余额 + 多笔在线资金”的订单完成部分退款、失败重试及查询，资金各来源金额之和等于业务退款额；充值黄金链不再跳过。

**已固化的幂等约定（后续商城写命令一律遵守）**：

- **幂等指纹只绑定稳定字段**。带 `version` 等并发控制字段的表单直接参与哈希，会让「同一请求重试」被判成内容不同：第一次成功后版本前进，重试必然哈希不一致。商城入口必须传只含业务稳定字段的指纹（订单/商品标识、数量、原因），客户身份由幂等 scope 里的操作者体现；管理端保持原样。
- **幂等指纹不得包含「重试时会重新读取、且可能已被他人改动」的快照**。下单原实现用整张 `SalesOrderAddForm`（含收货地址内容）当指纹，地址被同一客户的其他采购账号编辑后，同一幂等键重试的哈希就变了，原订单回放不出来。凡引用可变主数据的命令，指纹取**稳定标识**（如地址 ID），不取内容快照；内容快照仍照常冻结进业务单据。
- **指纹容器用 `LinkedHashMap`，不用 `Map.of`**：后者迭代顺序在不同 JVM 之间会变，序列化后哈希漂移，重启后认不出同一个键。数组顺序会被哈希保留，因此涉及多行明细的指纹要显式按主键排序。
- **「先确认是否已成功」的入口要排在所有「会被后续操作改变的前置校验」之前**（`ScmIdempotencyService.peekCompleted`），否则「第一次已成功、重试时外部数据变了」会被误报成业务错误。已踩过两次：排在价格校验之后 → 重试遇变价报「价格已变化」；排在读取收货地址之后 → 重试期间地址被删报「地址不存在」。**预检需要的一切都必须只来自请求体本身**（如地址 ID），不能依赖先读库。只有未成功的新请求才严格按当前数据校验。
- **前端提交守卫必须覆盖服务端下发的阻断信号**，不能只看金额：`preview` 会把不可售行从金额里排除并返回 `unavailableSkuIds`，若前端只更新金额就允许提交，客户会拿「少了钱的金额」下单。凡服务端返回的不可用清单，前端都要同时用于展示原因与禁用提交。
- **同一页面的并发读请求用请求序号丢弃旧响应**（订单列表、结算预览均已如此）：旧响应后到会覆盖新状态，且不能把仍在进行中的最新请求标记为已结束。

每个批次完成时仅更新 [项目状态](../../status.md) 的当次代码事实、必要的 ADR/决策和本路线图中的未完成项；保留对应 Git 提交与已实际执行的验证记录。**没运行的测试写“未运行”**，不得据此宣称失败或通过。功能收口后从本路线图移除历史实施细节，避免长期堆积第二份状态台账。
