## 2. 施工原则

- **只保留一个正式客户商城实现**：现有 `xsy-scm-customer-app/` 已经落地，先以此作为当前集成目标，不再新建第三套；`miniprogram-dev` 是已开发成果的迁入来源。若负责人最终决定沿用原目录，先做差异对照与成果保全，再统一迁移，不进行双线重复开发。
- 优先复用现有 SCM 的商品、定价、客户、库存、订单、采购、配送、财务和营销领域服务；商城只做独立客户身份和受控业务适配。
- 将管理后台的订单与商城订单归到**同一个销售订单事实**，来源标识 `MALL`；不建立第二套商城订单账、库存账或财务账。
- 价格、可见商品、促销、库存及最终金额以服务端为准；客户端只负责展示、选购、确认、提示和安全重试。数量、单价和金额保留正式领域精度。
- 新 Flyway 只能追加版本；V118/V119 是当前本地新增文件，先核对已有迁移与数据约束，禁止回改历史迁移。
- 每个阶段都按**页面 / API / 复用表或新增表 / 功能验收**收口，不能仅凭创建文件宣称完成。
- 当前处于开发期：优先实现真实业务流程。运行测试、数据库迁移、构建、提交、推送等按用户当次授权执行；计划本身不代表已经运行。

## 3. 开发顺序与功能拆分

### 阶段 A：收拢本轮四批已有代码（先做，不重新开发）

**范围**：充值到账、退款分摊、商城后端、uni-app 迁入。

- 逐项核对未提交源码与原 ADM-12 / ADR-009 / ADR-010 的实现边界，修明显的接口、字段、状态和依赖不一致。
- 确认 V118（`refund_funding_allocation`）和 V119（`mall_customer_account`、`mall_wechat_binding`）完整、版本无冲突。
- 建立 `miniprogram-dev` 页面/组件/接口与 `xsy-scm-customer-app` 的迁入对照，标明“已迁入 / 可迁入 / 需重写适配 / 当前不需要”。
- 拆出独立功能提交：① 充值回归，② 资金退款分摊，③ 商城身份与目录，④ 商城前端，不删除旧分支及未迁入成果。

**完成标准**：每个工作包的入口和依赖明确，没有重复商城项目或丢失已有页面；本地变更可单独回顾。

### 阶段 B：ADM-12 资金业务闭环

**已具备**：`PaymentIntentService` 成功派生、`BalanceRechargeSink`、`RefundFundingAllocationService`、比例计算器、退款分摊表 V118。

**补齐内容**：

1. 充值场景按既定“渠道成功即到账”：同步成功、`DELAYED` 等回调、重复回调、恢复重放，Finance 收款与钱包 CREDIT 可对应，不会重复增加余额。
2. 混合及多笔成功交易按**各来源剩余可退本金比例**冻结分摊；余额退回原冻结结算钱包，在线资金对应原交易；尾差与重试顺序固定。
3. 为订单退款详情增加**资金来源分摊**查看、执行或重试入口；展示每个来源的金额、状态、失败原因和结果单据，不只显示一条聚合成功/失败。
4. 对部分来源成功、部分失败、已成功后重试和累计退款上限作独立验证；保持正式订单售后和 Finance 单据关系清晰。

**API**：已有 `POST /scm/payment/refund/funding/execute`、`POST /scm/payment/refund/funding/detail`；复用现有支付回调、退款与余额服务。
**表**：V118 `refund_funding_allocation`，复用 `payment_refund`、`customer_balance_movement`、`finance_payment`。
**完成标准**：至少一张“余额 + 多笔在线资金”的订单完成部分退款、失败重试及查询，资金各来源金额之和等于业务退款额；充值黄金链不再跳过。

### 阶段 C：ADM-16 客户认证与真实商品目录联调

**已具备**：V119、商城账号后台按钮、商城认证和目录 Controller/Service、uni-app 登录与商品页面。

- 客户详情可以开通、停用、重置密码和查看商城账号；首次登录修改临时密码，停用后无法继续访问目录。
- 手机号密码登录、退出、会话恢复、获取当前客户资料的前后端协议统一；客户 ID 只从服务端登录身份取得。
- 商品分类树、搜索分页、SKU 详情、图片、常购列表与正式客户商品可见性、协议价→客户类型价→市场价对齐。
- 商城页面从 mock 切到真实 API；不可售/价格待询/无可见 SKU 时有明确呈现。搜索热词可先为空，不把空热词当主链阻塞。
- 账号首期按 V119 一客一号运行；是否支持多采购账号列为明确后续产品决策。
- **常购返回结构必须先定稿再联调**（`GET /scm/mall/catalog/frequent`）：前端 `getFavorites` 读 `response.data.list` 并传 `pageNum/pageSize`，后端返回**裸数组** `List<MallProductVO>`、参数为 `days/limit`，包装类 `MallFrequentProductVO`（含 `list` 字段）已定义但无任何引用。三者必须统一为一种契约，否则「常购商品」在真实数据下恒为空。定稿方向二选一：① 后端改回包装 `{ list }` 并接受分页参数；② 前端改读数组并改用 `days/limit`。裁决前不新增第三套结构。

**页面**：客户详情商城账号卡；`pages/login/login`、`pages/account/password`、`pages/home/index`、`pages/category/index`、`pages-sub/product/search|detail`。
**API**：`/scm/customer/mall-account/**`、`/scm/mall/auth/**`、`/scm/mall/catalog/**`。
**表**：V119 账号表及微信身份预留表；商品和价格继续复用正式业务表。
**完成标准**：后台开通一个真实客户账号，手机登录后仅看其有权购买的商品与客户价格，切换客户得到不同结果；不将购物车或下单算进本阶段。

### 阶段 D：ADM-16 购物车、收货地址

- 从 `miniprogram-dev` 复用购物车、地址列表/编辑以及数量选择组件；不要按设计图重复手写已有交互。
- 购物车支持加入、修改数量、移除、批量勾选、同商品规格合并；多规格和按斤/千克等小数数量按 SCM 精度处理。
- 地址与商城客户绑定，支持常用/默认地址、配送信息和停用/删除；先核实是否可复用现有客户地址，避免重复建客户主数据。
- 商品停用、客户可见性变化、价格变化后重新获取服务端信息，不信任客户端缓存金额。

**建议 API**：`/scm/mall/cart/**`、`/scm/mall/address/**`；具体方法与入参以实现时冻结的接口契约为准。
**建议数据**：必要时增加 `mall_cart_item`、`mall_customer_address`；若正式领域已有可复用地址事实，则不再建第二套。
**完成标准**：真实客户完成“浏览商品→加购物车→改数量/勾选→选择地址”，数据在重新登录后仍正确，尚不要求创建订单。

### 阶段 E：ADM-16 结算预览与商城下单

- 从 `miniprogram-dev` 选择性迁入结算页、下单成功页和订单列表/详情的基础视图。
- 结算预览按真实 SKU、客户价格、优惠、可售状态、订单来源和正式库存规则计算；提交时重新校验，变价要求客户明确确认。
- 客户订单使用 SCM 现有销售订单创建/确认流程、订单来源 `MALL`、正式库存预留与业务日志，不新建平行状态机。
- 支持已确认的首期账期、货到付款和本地模拟支付方案；钱包余额按 ADM-12 正式资金事实衔接，真实微信支付另立工作包。
- 下单采用幂等键、请求内容约束与可重复安全重试，不能连续点击生成重复订单；非标称重结果由正式分拣、配送事实回读。

**建议 API**：`/scm/mall/checkout/preview`、`/scm/mall/orders` 与订单列表/详情端点；名称可按既有 SCM 接口风格统一。
**建议数据**：优先复用 `sales_order`、`sales_order_item`、订单地址/价格快照及支付/优惠/库存事实；只在真实缺口处追加迁移。
**完成标准**：商城真实客户下单 → 管理后台可接单/履约 → 商城查询到同一订单；价格、数量、金额和订单状态一致。

### 阶段 F：ADM-16 订单履约、售后与客户中心

- 迁入订单列表/详情、配送、实际称重、退货退款、再来一单、常购、地址、优惠券、余额和账期页面中的有效成果。
- 商城订单进度只读取现有销售订单、分拣、配送签收、售后、Finance 和客户余额事实；不复制业务状态。
- 客户能看到已下单量、分拣/实重、配送状态、有效优惠、应付/账期和退款进度；功能依实际已实现的订单合同开放。
- 将 ADM-12 混合资金退款结果以客户能理解的方式展示原路退回和钱包返还。

**建议 API**：`/scm/mall/orders/**`、`/scm/mall/after-sale/**`、`/scm/mall/account/**` 等客户只读或受控命令接口。
**完成标准**：从小程序完成下单、后台处理、手机看履约、发起售后、查看资金结果的业务闭环。

### 阶段 G：ADM-13 推广与商城营销体验

- 业务员专属二维码、推广落地页、首次有效客户绑定、推广归属查询；复用已有客户负责人事实。
- 首页促销、新品、限时特价、优惠券展示与领取接正式营销域，不复制活动计算规则。
- 常购/再来一单优先于复杂零售营销；主题与 DIY 可参考芋道商城的 Vue 3 组件，但不要为了 UI 更换客户端基线。

**数据/API**：若现有客户来源不足以记录码版本、有效期、扫码归属，则增正式推广码与绑定事实；营销读取已有 Promotion/Coupon 服务。
**完成标准**：客户从业务员二维码进入商城并形成可追溯归属；促销在真实订单结算中按已冻结规则生效。

### 阶段 H：ADM-17 员工移动端与 ADM-14 订单助手

- 员工端与客户商城身份和导航隔离，复用后端原有员工、采购、仓库、司机、分拣和配送授权。
- 第一条移动闭环建议：**采购收货任务 → 输入实收数量/重量 → 提交正式收货命令 → 后台查询确认**。
- 后续加分拣任务/电子秤稳定读数确认、配送线路查看、订单签收和操作记录。
- 订单助手提供受控改价、订单编辑与关联入库入口，实际写入仍走已有销售、采购收货、库存领域服务。
- 仅展示计划路线，不增加实时 GPS 采集；遵守 ADR-008、ADR-009、ADR-010。

**完成标准**：员工手机执行至少一条真实作业命令，后台对应单据和库存/履约事实一致；后续按收货、分拣、配送逐条扩展。

### 阶段 I：ADM-15 批次与包装溯源

- 采购实际收货生成批次，记录来源、供应商、商品、保质期/检验等正式事实。
- 包装码生成、拆分、合并、补码、作废及内部查验；扫码公开页只展示确认允许的溯源字段。
- 与收货、入库、分拣、出库的现有记录关联，不为溯源重新实现库存流水。

**完成标准**：批次收货→包装赋码→扫码查到来源及流转记录；拆包/补码/作废历史可回溯。

## 6. 待产品裁决（开工前确认）

以下三项在实现前必须先拿到结论，不得由实现方自行假定：

- **商城多采购账号**：一个客户是否需要多个采购账号分别登录。当前 V119 唯一索引 `uk_mall_customer_account_customer_active` 与 `login_phone` 全局唯一 = 1 客户 : 1 账号；若需多账号，须改唯一约束与账号归属/角色模型。
- **常购返回结构**：裸数组 + `days/limit`，还是包装 `{ list }` + 分页（见阶段 C）。
- **混合/多交易退款来源分配**：余额、在线资金的来源选择与分配规则；不得默认余额优先、在线优先、按比例或按时间顺序。

## 7. 本期明确不作为开发阻塞
