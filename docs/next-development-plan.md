# XSY-SCM 下一阶段开发计划（原始需求 MVP 收敛版）

> 更新：2026-10-19。以 [原始产品功能需求](requirements/产品功能需求基线.md) 和 [负责人确认口径](requirements/2026-09-09-负责人确认口径.md) 为范围基线。原始清单共 13 个业务模块、44 条功能描述（其中有重复项），不代表 44 套独立系统。没有细化的业务流程，只借鉴蔬东坡常见操作，不自动追加其完整产品范围。代码与验证见 [项目状态](status.md)，正式约束见 [业务决策](decisions.md)。

## 一、目标与范围规则

**目标：一家生鲜配送公司能用当前系统完成一天的业务。先满足原始需求的最小可用操作，而非建设完整版蔬东坡。**

- 原始要求明确的功能先做基本版：列表、新建或编辑、操作确认、结果查询/打印；没有说明的细节不自行扩展审批、策略、工作台和数据模型。
- 已有代码先演示和复用，不重新造订单、库存、分拣、财务、商城模块；借鉴蔬东坡用于理解页面及常见业务步骤，不搬运全部能力。
- 权限与数据隔离、幂等、库存和资金不重复记账、数量金额精度属于必须保留的质量底线；**技术正确性不是新增业务范围的理由**。
- 证据分级：有接口或页面＝“已有源码”；隔离环境流程跑通＝“已联调”；真实岗位实际操作通过＝“已业务验收”。不能因代码多或 V158 已完成就声称原始 44 条全部实现。
- 暂停按 Flyway 版本号推进功能。只有原始要求确实无法完成、且真实用户会使用时才补下一项。

## 二、13 个原始模块对照（44 条描述）

“已有基础”仅指存在对应服务、控制器或页面，不代表其每个子功能均已验收；“待核实”也不等于未实现。

| 原始模块 | 代码中已有的基础 | MVP 目标与待核实要点 |
| --- | --- | --- |
| 商品管理（4 条） | 商品/规格/分类/图片、价格与多供应商关联 | 商品分级、批量图片与价格、标品/非标品、默认采购员和供应商能实际操作；先点页面 |
| 客户管理（5 条） | 客户、客户类型、商品可见性、业务员与账期基础 | 客户资料、分类和绑定可用；**集团下属单位独立下单、统一结算**、供应商绑定和推广二维码需核实 |
| 营销管理（4 条） | Promotion、商城首页、常购/购物车、支付入口 | 做最基础活动与优惠展示；**语音下单**是否有入口待核实，不建语音 Agent |
| 订单管理（4 条） | 销售订单、退货、退款、异常与日志 | 商城/后台录单、补单、实重客户展示与消息能实际用；不继续拆出额外订单工作台 |
| 采购管理（3 条） | 采购汇总/订单、正式多次收货 | 人工选时间段生成采购单并可选计算库存；**二维码分享、手机接单、回传价格重量**待核实 |
| 库存管理（3 条） | 入出库、盘点、损溢、转换、预警、成本 | 按实际重量操作、与订单联动、移动平均成本正确；不增加新平行账本 |
| 分拣管理（4 条） | 分拣、称重、打印、任务筛选 | 按客户/商品录实重并打印、误差阈值、标品一键操作；**供应商代分拣**与实时上传效果需核实 |
| 物流配送（3 条） | 线路、地图、司机、发车签收、打印 | 能排线、发货、签收并打印；线路轨迹的**真实记录**待核实 |
| 财务与报表（3 条） | Finance / Report / 利润报表 | 应收应付、收付款、销售/采购/利润查询导出能够对账；不造高级 BI |
| 后台管理（3 条） | SmartAdmin、打印中心、待办和日志 | 权限、单据模板、系统日志和可用帮助入口；优先可操作性 |
| 下单商城（5 条） | uni-app 客户端，目录/购物车/结算/订单/支付等 | 微信小程序最短下单流程、商品汇总、主题、常购/再来一单；语音能力待核实 |
| 订单助手（2 条） | 订单和收货后端已有正式接口，独立手机助手入口未确认 | 手机端能按授权改价/编辑订单、完成要求的入库动作；复用既有 API，不建第二套订单 |
| 溯源（1 条） | V151～V158 批次及独立包装码、发码/绑定/回放 | 一码对应一个实物包装，扫码查基本商品、来源批次和当前确认的去向；**扫码面向员工还是客户需明确**，不要求完整逐码物流账 |

> 基础核对以页面和已授权 API 的真实操作为准。所有“待核实”都先检查已有入口与业务数据，再决定是否补开发；不因控制器名称不存在就宣布功能缺失。

## 三、只分三批推进

### MVP-01：日常业务主链核对（优先）

按真实岗位以一组测试数据走一遍：

1. 管理员建商品规格、供应商、客户和仓库，维护必要价格与角色权限。
2. 客户在微信端选择商品、购物车下单，后台能快速录单或补单，订单状态与价格一致。
3. 采购员按负责人已确认的**人工触发 + 固定时间段**汇总订单、选择“计算库存”或不计算，生成采购单。
4. 采购员多次实重收货，显示超收/少收；按选择执行直接入库或仓库二次确认入库。
5. 仓库按商品/客户分拣、称重打印；司机排线、发货签收。
6. 财务核对应收、已收、应付与付款，管理者查询销售、采购、客户与商品利润。
7. 检查权限、单位、库存、资金和异常提示；只修阻塞日常操作的问题，不为低概率情形新增复杂子系统。

**退出标准：** 各岗位能走通基本流程，记录页面入口、真实数据、问题、通过或未验收状态。V158 的 43/43 定向测试不能替代以上演示。

### MVP-02：只补原始清单的明显基础缺口

先演示，真缺再按业务价值单项实施；不要同时开工：

- **采购单二维码分享 + 手机接单回传**：优先复用正式采购单/收货接口，做能查看任务、填写价格与实重的最简单入口，不建供应商协同平台。
- **订单助手**：复用订单改价、编辑与已有收货/入库命令，按权限提供简洁手机操作，不新建第二套订单系统。
- **业务员推广二维码、集团统一结算、供应商代分拣**：分别确认使用岗位和实际流程，沿用客户、财务和分拣模块做最简功能。
- **语音下单**：如确需做，先语音转文字、匹配商品、用户确认购物车；不能自动下单付款，不接入复杂 Agent。
- **司机轨迹、商城主题与帮助入口**：现有能力若已足够演示原始要求，不为功能丰富度继续扩展。

**退出标准：** 每个补齐项能展示原需求对应的功能与结果；不捆绑复杂审批、多级绩效、额外分析报表。

### MVP-03：基础验收和收口

- 新改动运行对应定向测试，主链跑一次真实浏览器 E2E；云存储组要求 Playwright 进程显式设置 XSY_FILE_STORAGE_MODE=cloud，不得假性跳过。
- 已有数据库升级只在隔离库/开发数据克隆验证；生产升级、真实支付渠道、微信真机、实物秤和打印机由现场单独验收。
- 对 44 条原始描述逐条标记 **已演示 / 有代码待演示 / 缺少基础功能 / 需要负责人一句话裁定 / 非本期**，不以增加的技术任务数计算进度。

## 四、暂停扩展与例外规则

- **TRACE-OUT-01、TRACE-RETURN-02、TRACE-ISSUE-03、V159/V160 不再作为自动下一步。** V151～V158 已有追溯基础先保持稳定。只有最基本“扫码看到真实来源”仍无法满足业务时，再决定是否补少量必要关联。
- 暂停混批/拆包复杂谱系、EPCIS、召回工作台、独立消费者溯源门户、外部监管上报、复杂质检体系。
- 暂停假想的审批引擎、自动询价采购策略、复杂优化排线、ERP 同步、多企业账号平台、语音代理和高级增长归因。
- 不随意删除已完成且正常工作的代码；冻结新功能不意味着破坏已存在的历史流水和数据库结构。
- **例外**：若在演示中发现权限越界、库存/金额错账、严重重复提交或数据泄露，必须修复，这是现有功能质量，不算“继续扩业务”。

## 五、下一轮给开发助手的指令

> 先根据原始 44 条产品描述、负责人 6 条确认口径和当前仓库的正式菜单/API 完成 MVP-01 基础流程核验。优先复用现有页面和服务，不先建 V159、不设计新追溯子系统。找出会阻断日常接单→采购→收货→分拣→配送→结算的真实缺口，形成少量可操作任务。参考蔬东坡时只看最常见的页面和操作顺序，避免复制全部字段和深层规则。只有确认存在缺口后才补代码，保留既有权限、幂等及账本正确性。同步更新 docs/status.md；未经明确要求不推送、不部署、不操作生产库。
