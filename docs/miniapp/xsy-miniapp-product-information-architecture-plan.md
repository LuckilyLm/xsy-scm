### Step 4.5（新增）：mock 契约层

**背景**：核对 `xsy-scm-server` 后确认后端 `/scm/mall/**` **尚不存在**
（只有 `order_source = MALL` 这个枚举值），Step 6 会被数据阻塞。
因此先补一层 mock 契约，作为「假后端」顶住客户端开发。

| 落地物 | 说明 |
| --- | --- |
| `mock/`（**在 `src/` 之外**） | 分发器 / 空实现 / 信封与分页 helper / 假会话 / 假数据 / 按域路由 / 冒烟测试 |
| `src/lib/smart-request.js` 接入点 | 在请求层内部拦截，页面与 `api/mall/**` 零改动；返回真实信封 `{code,msg,data}` |
| `VITE_APP_USE_MOCK` | 仅 `.env.development` 为 `true`；关闭时别名指向 `mock/noop.js` |

**两条硬约束**（踩过坑，务必遵守）：

1. `mock/` 必须留在 `src/` 之外 —— uni-app 会把 `src/` 整棵树镜像进构建产物，
   假数据放在 `src/` 内会直接被打进生产包；
2. 引入标识用 `@mock`，**不能用 `@/mock`** —— uni-app 自带的 `@` → `src/` 别名优先级更高。

已双向验证：生产构建中假数据命中数为 0，`--mode development` 下 mock 存在。
`npm run test:mock` 覆盖认证、分页、分类过滤、搜索、详情字段、价格/非标品契约、回落与登出。

# 4. 核心产品原则

## 4.1 小程序不是 PC 后台手机版

禁止按 PC 菜单进行一比一移动端迁移。

错误示例：

```text
商品
客户
采购
库存
配送
财务
报表
系统
```

直接全部塞到小程序中。

小程序的导航必须围绕客户订货任务设计。

---

## 4.2 高频订货优先于营销展示

首页优先级应当是：

```text
找商品
→ 常购
→ 再来一单
→ 快速加购
→ 下单
```

而不是：

```text
Banner
→ 新品
→ 广告
→ 活动
→ 再找商品
```

营销存在，但不能阻塞订货效率。

---

## 4.3 业务数据以 SCM 主业务为事实源

商城不得重新维护平行业务数据。

禁止复制：

- 商品主数据；
- SKU；
- 客户；
- 客户价；
- 库存；
- 销售订单；
- 收货地址归属；
- 应收；
- 配送状态。

商城是渠道层，不是第二套 ERP。

---

## 4.4 小程序订单进入统一销售订单体系

商城订单直接进入：

```text
sales_order
```

并通过来源字段区分：

```text
order_source = MALL
```

禁止新增：

```text
mall_order
```

作为另一套订单账。

---

## 4.5 价格由服务端权威计算

前端不得自行实现最终价格计算逻辑。

服务端负责：

- 协议价；
- 客户类型价；
- 市场价；
- 特价；
- 活动价；
- 客户专属覆盖价；
- 最终成交价。

前端负责：

- 展示；
- 标注价格来源；
- 展示变价提示；
- 结算确认。

---

## 4.6 商城提交必须满足库存约束

商城正式下单不同于后台人工录单。

商城正式提交必须：

```text
事务内
├── 校验用户
├── 派生客户
├── 校验地址归属
├── 校验商品可见性
├── 校验商品状态
├── 校验价格指纹
├── 校验库存
├── 锁定库存余额
├── 创建库存预留
├── 创建销售订单
├── 创建订单明细
├── 写操作记录
└── 幂等提交
```

禁止：

```text
先查库存
→ 再创建订单
```

这种存在并发超卖风险的实现。

# 6. 一级信息架构

建议底部 TabBar：

```text
首页
分类
购物车
订单
我的
```

即：

```text
┌────┬────┬──────┬────┬────┐
│首页│分类│购物车│订单│我的│
└────┴────┴──────┴────┴────┘
```

---

## 6.1 为什么订单必须作为一级 Tab

XSY 属于 B2B 高频订货场景。

客户常见任务包括：

- 查刚下的单；
- 查今天配送；
- 查是否已出库；
- 查实际称重；
- 查历史订单；
- 再来一单；
- 查异常商品。

因此：

```text
我的
→ 我的订单
```

多走一级没有必要。

订单应作为一级入口。

# 8. 首页结构规划

## 8.1 首页首屏

推荐结构：

```text
┌────────────────────────────┐
│ 上午好，海岸城门店       ⌄ │
│ 配送至：南山区 XXX       ⌄ │
│                            │
│ [ 搜商品 / SKU       🎙 ] │
│                            │
│ 常购商品  再来一单 今日特价 我的账单 │
└────────────────────────────┘
```

首屏核心原则：

- 先识别当前客户 / 门店；
- 明确当前配送地址；
- 搜索框永久高优先级；
- 快捷入口解决高频任务；
- Banner 不应该占据首屏大部分高度。

---

## 8.2 首页楼层

首页建议按以下优先级组织：

```text
1. 用户 / 门店信息
2. 搜索
3. 高频快捷入口
4. 商城公告
5. 分类导航
6. 常购商品
7. 再来一单
8. Banner / 活动
9. 限时抢购
10. 新品推荐
11. 推荐商品
12. 商品列表
```

其中：

```text
常购
再来一单
```

属于 B2B 核心能力，不应被放在很深的位置。

配置：

- 分类；
- 图标；

- 数量；

- 客户历史采购；

# 15. 再来一单

这是核心能力。

流程：

```text
历史订单
    ↓
再来一单
    ↓
重新获取当前商品状态
    ↓
重新获取当前价格
    ↓
重新获取库存
    ↓
处理失效商品
    ↓
重新生成购物车
    ↓
客户修改数量
    ↓
结算
```

禁止：

```text
直接复制历史订单金额
```

---

## 15.1 再来一单异常状态

必须覆盖：

- 商品已下架；
- 商品对当前客户不可见；
- SKU 失效；
- 价格变化；
- 商品无价；
- 库存不足；
- 规格发生变化。

必须逐项向用户解释。

## 17.1 价格指纹

流程：

```text

      ↓

      ↓
用户确认
      ↓

      ↓
```

```text

→ 用户重新确认
```

```text

```

```text
复用同一个 key
```

内容发生变化后：

```text
生成新 key
```

# 18. 订单体系

客户侧订单展示不能机械复制内部 SCM 状态。

应做“客户可理解状态映射”。

例如：

| 客户展示状态 | 内部可能状态 |
|---|---|
| 待确认 | DRAFT / PENDING |
| 已确认 | CONFIRMED |
| 备货中 | PURCHASE / WAIT_SORTING / SORTING |
| 待配送 | READY_TO_DELIVER |
| 配送中 | DELIVERING |
| 已完成 | SIGNED / COMPLETED |
| 已取消 | CANCELLED / INVALID |
| 售后中 | REFUNDING / AFTER_SALE |

具体映射以当前服务端状态机最终实现为准。

---

## 18.1 订单详情重点

客户真正关心：

```text
买了什么
订了多少
最后称了多少
多少钱
什么时候送
送到哪
现在到哪了
有没有缺货 / 换货
```

订单详情 UI 必须突出这些信息。

---

# 19. 实重与非标品

非标品是 XSY 与普通电商的重要区别。

订单详情必须允许展示：

```text
下单重量 / 数量
实际称重
结算重量
单价
最终金额
```

例如：

```text
鲜鲈鱼

下单：2 条
预估：1.30 kg
实重：1.46 kg

¥18.80 / kg
最终：¥27.45
```

不能让用户看到金额变化，却不知道原因。

# 31. 认证方向

当前正式方向应以现有项目最新决策为准：

```text
Sa-Token
+
多 userType
```

客户端不得重新发明第二套与 PC 完全割裂的认证模型。



来决定数据权限。


- 非标品有明确称重提示；

# 44. 总结

XSY 小程序后续的正确方向不是：

> 把旧 Taro 重写成 UniApp。

因为该技术切换已经在当前小程序专用分支完成。

真正要做的是：

> 以当前 `xsy-scm-miniapp` 的 UniApp Vue3 基线为工程基础，删除内部 ERP Demo 的产品信息架构，重新建设一套面向下游客户的 B2B 食材订货商城。

核心要求：

```text
一个移动端工程
一套商城产品
一套主业务数据
一套销售订单事实源
小程序 + H5 双端
商城运营后台驱动前台
高频订货优先于纯营销展示
```

后续 Figma、接口、页面与代码实现均以本文作为产品与架构基线。
