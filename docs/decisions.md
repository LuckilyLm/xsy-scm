# 当前项目决策

最后更新：2026-09-25

这些是当前仓库继续有效的简要边界。详细业务语义优先查阅
[`project-reference-examples/xsy-scm/`](../project-reference-examples/xsy-scm/)；实现约束以根目录 `AGENTS.md` 为准。

## 工程边界

- `xsy-scm-server/` 和 `xsy-scm-web/` 是 V2 正式实现；`xsy-scm-miniapp/` 冻结，只读参考。
- SmartAdmin 是系统底座；SCM 只实现供应链业务域，不复制旧认证、组织和权限实现。
- 后端使用 Java 21、Spring Boot、MyBatis-Plus、PostgreSQL、Flyway 和 Sa-Token；前端使用 Vue 3 + TypeScript。
- PostgreSQL 不使用数据库外键；关系完整性由服务层、事务、唯一约束和检查约束保证。
- 金额使用 `BigDecimal`，库存变化必须有可追溯流水，敏感变更需要审计。
- 不引入微服务、消息总线、Kubernetes 或第二套 UI / 状态 / HTTP 框架，除非另有明确决策。

## 参考与变更

- `project-reference-examples/xsy-scm/` 是需求、旧业务语义和参考页面的主要来源，保持只读。
- 参考内容不能直接覆盖当前 V2 技术栈、权限命名、数据库规则或已批准的业务实现。
- 新需求先在参考项目中定位来源，再在代码和本文件中记录当前项目的取舍；不要重新建立大批镜像文档。
- 验证入口 `verify.ps1` / `verify.sh` 共用 `tools/verify.py`；仅验证工具及其测试纳入 Git 白名单，TS 历史基线保存在 `xsy-scm-web/quality/`。类型门禁要求 SCM 零错误且全局不新增，不代表上游全量类型检查零错误。
- 采购单拆分保留事务编排在 `PurchaseOrderService`；行装配与分配对账共享请求行上下文，暂不继续拆出 Assembler，也不扩展到收货服务重构。
- B1 收货入库采用显式双模式：`DIRECT` 在确认收货事务内写入库存；`WAREHOUSE_CONFIRM` 在确认收货后保持 `PENDING`，由独立 putaway 命令完成物理入库。模式创建时必选，确认后不得切换。
- putaway 是独立生命周期和审计动作；库存流水 `occurred_at` 记录物理入库时刻，因此 `DIRECT` 取收货确认时刻，`WAREHOUSE_CONFIRM` 取仓库确认入库时刻。重复或非法状态统一拒绝，不重复写余额和流水。
- 仓库停用采用严格模式：正库存余额、在途采购单或待入库收货单任一存在即拒绝；停用仓库不能建立新的需求、采购单或收货单引用，既有历史记录仍可查询。
- B1 权限拆分为收货确认入库、仓库启用和仓库停用（菜单 822/823/824），不把三类动作合并到普通编辑权限。
- B2/B3 尚未形成批准方案；后续库存方向（损溢、调拨、单位转换、阈值预警、成本核算）必须另行裁决。
- 出库采用**独立出库单**，不挂在尚未开发的分拣 / 发货模块上：把出库挂上去会让库存能力被一个不存在的模块阻塞。
  发货模块落地后由发货确认去创建并确认出库单即可，无需改表结构。
- 预留**不进 `inventory_movement`**：那张表是物理数量账本（`quantity` 恒为正、方向编码在类型里），
  预留不改变物理数量。预留单独建表，并在 `inventory_balance.reserved_quantity` 上维护活状态计数。
- **出库与预留的可用量门槛**：可用量 = `quantity − reserved_quantity`。出库不得吃掉已预留的货，
  预留不得超出可用量。服务层给可读错误码（41011），DB 的 `ck_inventory_balance_available` 兜底。
- **盘点差异施加到「确认瞬间的账面量」，不是把账面改写成实盘数**（2026-09-19）。
  `delta = 实盘量 − 账面量快照`，`after = 确认瞬间账面量 + delta`。
  理由：保存草稿到确认之间很可能发生收货 / 出库（鲜活品仓里这是常态），直接改写会把那些真实变动
  悄悄抹掉，而抹掉的痕迹在任何报表里都看不出来。用「施加差异」的写法，期间变动被完整保留，
  且当期间无变动时 `after` 恰好等于实盘数 —— 符合直觉。两种量都在单据行上留痕，漂移可审计。
- 盘点**不建零余额行**：记账单位（Q13）只能来自余额行，因此从未入库过的 SKU 不能在盘点里凭空盘盈，
  必须先有入库事实（否则报 41023）。这不是能力缺失，而是刻意不让盘点成为「绕过入库、凭空造库存」的入口。
- 盘点差异为 0 的行**不写流水**：`quantity` 恒为正，写不出「零差异」流水；强行写一条 0 会让
  「一行一流水」的防重索引语义变脏。
- 同一 SKU 在盘点单里出现两次**直接拒绝**（41027），不做静默去重：重复行会让同一份差异被施加两次，
  而结果看起来完全正常（余额确实变了，只是变错了）。
- 盘盈 / 盘亏是**两个**流水类型而不是一个 `STOCKTAKE_ADJUST`：方向必须能从类型本身读出来，
  否则 `ck_inventory_movement_snap` 无法判定 `after` 该加还是该减。数量恒为正，方向编码在类型里。
- **报损报溢单独建表**，不与盘点调整 / 规格转换混在一张表里（参考项目 `t_stock_adjust` 是混的）：
  V2 的盘点是独立模块且状态机不同（`DRAFT/CONFIRMED`），规格转换尚未开发；
  把三种语义塞回一张表会让状态机无法统一。
- **报损报溢有审批状态机**：`PENDING`（创建即待审核）→ `COMPLETED`（写流水、调余额）/ `REJECTED`。
  「新建」与「审批」是**两个独立权限** —— 报损是把货从账上抹掉的动作，由同一人录单并批准就失去了制衡。
  「审批」与「驳回」也是两个独立权限（允许主管审批、由另一角色驳回是常见分工）。
- **报损报溢的 `update` / `delete` 都加状态守卫（仅 PENDING）**。参考项目对这两者没有状态守卫，
  会让「已完成（已写流水）」的单据被改内容或被删掉，账与单从此对不上。这是刻意比参考项目更严的地方。
- **审批用乐观锁**：审批请求必须携带审批人打开单据时读到的 `version`，不符则 40921。
  理由：审批是一道控制，审批人必须批准自己读到的内容；否则「打开 → 审批」之间被静默改掉数量，
  这道控制就形同虚设。而两个人同时改同一张待审核单据属于录单碰撞，与全仓其它单据一致，
  **不**引入乐观锁（保持一致比局部更严更重要）。
- **驳回必须填审核意见**（41037）：本波次没有消息通知，驳回是唯一会把「为什么不行」
  传达给录单人的渠道；允许空意见的驳回等于把沟通成本转移给录单人去反复试。
- **报损报溢不含 `weight`**：Q2 裁决「数量 = 采购单位口径（非标品实重即数量）」，双记账属分拣波次。
- 报损 / 报溢与盘亏 / 盘盈**不合并**成同一组流水类型：两者都改变库存，但业务含义与追责对象不同
  （盘亏是「账实不符」的结果，报损是「对已知损耗的申报」）。合并后「这个月损耗了多少」
  就无法从流水里直接读出来，而那正是报损存在的理由。
- **调拨是两步式（发出 → 在途 → 收货）**，不是一次事务内两边同时改（2026-09-19，V2 原创设计，
  参考项目**没有任何调拨实现**）。两条理由：① 语义正确 —— 货在卡车上时既不在源仓也不在目标仓，
  一步式会让「发出」那一刻目标仓就凭空多出库存，而那正是仓库最不能接受的账实不符；
  ② 并发安全 —— 两步各自只锁**一个仓库**的余额行，既有的「按 `(warehouse_id, sku_id)` 升序锁余额」
  纪律完全不用改；一步式要在同一事务里锁两个仓库的行，锁序规则就得升级为跨仓排序，
  而那是六条既有写入路径都要跟着改的事。
- **在途期间这批货不在任何余额行里**（`inventory_balance` 只表达「在仓库里的货」，没有虚拟在途仓），
  因此全仓总库存会暂时减少。这是两步式的必然结果，不是缺陷；要让它在余额上可见，
  需要引入「在途仓」这个虚拟仓库 —— **属未决事项**，见下方。
- **在途调拨不可取消**：货已经物理离开源仓，账上只能靠一张反向调拨单冲回，
  不能把状态改回草稿再删流水（会被 `trg_inventory_movement_append_only` 拒绝）。
- **调拨占两个来源类型**（`TRANSFER_OUT_ITEM` / `TRANSFER_IN_ITEM`）：这是被迫的 ——
  同一条调拨明细行会产生两条流水，而 `uk_inventory_movement_source_active` 只认
  `(source_document_type, source_document_item_id)`，共用一个来源类型会让第二条插不进去。
  该索引是 V19 冻结的 Q7/Q11 契约，不能为了调拨放宽它。
- **两仓记账单位必须一致**（41044），不做隐式换算：源仓按「箱」记账、目标仓按「kg」记账时，
  把 10 箱加成 10 kg 会得到一个没有物理意义的余额，而错误只会在未来盘点时以「账实不符」暴露。
  换算能力属「单位转换」波次。
- **调拨在途阻塞仓库停用**（41009，第四条停用阻塞条件），源仓与目标仓**都算**：
  源仓的货已经出去了但账上还没落地到目标仓，目标仓则还欠着一批要入库的货。
  草稿调拨不阻塞（还没动过库存，停用后发出会被 41048 拒绝）。
- **预警阈值不放在 `inventory_balance` 上，单独建 `inventory_warning_threshold`**
  （2026-09-19，与参考项目不同）。余额行是**派生状态**：它只能由流水产生，
  `InventoryBalanceDao` 里没有任何「建行 / 赋值」方法。若阈值放在余额表上，
  配置路径就必须为了写阈值而创建余额行 —— 那会造出「没有任何流水支撑的余额行」，
  直接破坏「余额是流水的净和」这条不变量。单独建表后配置路径完全不碰余额表。
  （V19 的契约断言「`inventory_balance` 不含 `warn_min` / `warn_max`」**没有被削弱**，
  它现在的含义更明确了：预警配置刻意不在余额表上。）
- **预警按 (仓库, SKU) 配置，不是只按 SKU**：参考项目的「单仓库」是 G-03 的范围限制
  而非业务规则；V2 已有跨仓调拨，两仓的合理下限本来就可能不同（前置仓 vs 中心仓）。
- **预警状态不落库，读时计算**（参考项目写「余额变动后校验」）。落库就意味着**六条**
  余额写入路径都要顺手维护它，而它完全可以由 `(阈值, 可用量)` 推导 —— 落库只会多出一个
  会漂移的副本。判定规则只在 `ScmInventoryWarningStatusEnum#evaluate` 实现一次；
  列表 SQL 里另有一份**过滤**谓词，两者的等价性由 IT 交叉验证。
- **判定基准是可用量（现有量 − 预留量），不是现有量**。下限的业务含义是「还够不够发货」：
  20 kg 在库但 18 kg 已预留给明天的订单时可用只有 2 kg，必须触发补货预警。
  上限同理：货已经被订走就不算积压。列表同时展示三个数量，用户能看出预警为什么触发。
- **取等号算正常**（「不低于下限」= 恰好等于下限是正常的），边界两侧都有断言钉住。
- **预警列表由配置驱动**：只列配置了阈值的 (仓库, SKU)。没有配置就没有预警 ——
  否则每个 SKU × 每个仓库都会因为「没有余额行 = 0 < 下限」而刷屏。
  配置了阈值却没有余额行时数量按 0 计并预警 —— 这是本能力唯一能表达
  「还没进过货就要补货」的方式。
- **预警不设「已读 / 已忽略」状态**：它只是 `(阈值, 可用量)` 的当前计算结果。
  引入已读会让预警与真实库存脱钩 —— 货补上了那条「已读」记录还在，货又少了它却已被忽略过。
- **本波次不做推送 / 通知**：项目没有任何消息机制，「提醒」落地为「一个随时可查的预警列表」。
  推送采购（补货）/ 销售（积压处理）属未决事项。

### 移动加权成本（V34，2026-09-20）

- **改变 Q3 的既有裁决：`inventory_balance` 新增 `avg_cost`**。Q3 原本定的是
  「成本事实由 `inventory_movement.unit_cost` 承载、余额表不加 `avg_cost`」。这条在只做数量账时成立，
  但移动加权**顺序相关**：均价取决于全部历史出入库的先后，而「出库那一刻的成本」必须在出库时确定。
  事后从流水反推需要重放整条历史，而重放的前提是出库流水都已经带成本 —— 那正是本波次要建立的东西，
  鸡生蛋。因此均价必须有一个**活状态**承载者，那就是余额行。
- **入库（`PURCHASE_IN`）是唯一会改变均价的路径**：
  `newAvg = (旧量·旧均价 + 入量·入价) / (旧量 + 入量)`，四舍五入到 4 位（`HALF_UP`）。
  取 `HALF_UP` 而不是 `HALF_EVEN`：四舍五入是财务口径默认，银行家舍入会让「同一批数据算两遍」
  的结果依赖末位奇偶，对账时无法解释。
- **出库不改变均价**（移动加权平均的性质），但**出库流水必须写当时的均价** —— 这是本波次的核心语义变更：
  出库 / 盘点 / 报损报溢 / 调拨转出 / 转换转出的 `unit_cost` 从 `NULL` 变成有值。
  写的是**出库那一刻**的均价，不是回填、不是当前均价。
- **入库分两类**：**盘盈 / 报溢**（`STOCKTAKE_GAIN` / `GAIN_REPORT`）不带来任何新的成本事实，
  按该 (仓库, SKU) 现有均价入账（等价于均价不变），不凭空创造损益；
  **调拨转入 / 转换转入**（`TRANSFER_IN` / `CONVERT_IN`）是同一批货换了个科目，
  成本必须**跟着货走**，取同一条明细行转出腿的成本，见下一节。
- **存量流水的 `unit_cost` 不回填**（Q7 append-only 禁止改历史行）。上线后历史出库流水的 `unit_cost`
  仍是 `NULL` —— 那**不是缺陷**，而是「该笔出库发生在成本核算上线之前」这一事实的忠实记录。
  对账时要按此解释，不要试图补齐。
- **期初 `avg_cost` 口径**：取该 (仓库, SKU) **最近一次 `PURCHASE_IN` 流水的 `unit_cost`**，
  没有采购入库则为 0。选它的理由：它是唯一有真实采购价格事实支撑的起点，且不需要引入任何新的输入数据。
  副作用是「最近一次采购价」会覆盖更早的价格，对历史库存的估价偏保守（不虚高）。
  业务若要求更精确的期初（如最近一次采购价 × 存量、或财务指定价），需另开一次数据修正迁移。
  **这条口径是本次采用的默认值，属可调整项。**
- **金额（`quantity × avg_cost`）在 SQL 里显式 `ROUND(..., 2)`**：`NUMERIC(18,4) × NUMERIC(18,4)`
  在 PG 里得到 scale 8，而 `BigDecimal` 走 `ToStringSerializer` 原样输出 → 前端会看到 `112.00000000`。
  金额是给对账看的，2 位是财务口径；均价保留 4 位不动（它是计算基数）。
- **`avg_cost` 为 `NOT NULL DEFAULT 0`**，不允许为空：「没有均价」与「均价为 0」在本业务里无法区分，
  而让调用方每次都判空会让八条写入路径都多一层分支。
- **`recomputeAvgCost` 必须在持有余额行锁之后调用**，且只用一次赋值（`updateAvgCost`），
  不做「读-改-写」—— 与 `quantity` 的增量更新同一纪律。

### 调拨 / 转换的成本平移与 0 成本余额修正（V37，2026-09-20）

- **调拨转入的成本取「同一条明细行的转出腿」，不取目标仓均价**。目标是**跨仓不变量**：
  `调出总成本 == 调入总成本`。此前按目标仓均价入账，目标仓**没有**该 SKU 的余额行时
  （行由 `insertOnConflictDoNothing` 现建、`avg_cost` 默认 0）成本会被**整体清零**，
  实测三笔调拨的转出腿 `unit_cost` = 6.20 / 132.00 / 2.60，转入腿全部 0.0000。
- **不新增「源成本快照」列**：转出腿落库时已经携带了 `unit_cost`，转入用
  `(TRANSFER_OUT_ITEM, 明细行 id)` 读回同一条流水即可。加一列等于把同一个事实存两处，
  还要额外规定哪一处是权威。读不到配对流水直接抛 `IllegalStateException` 让整单回滚 ——
  出现即说明有绕过命令层的写入，静默按 0 记账会把这种问题永久埋掉。
- **成本基准在锁行时一次取齐**（`lockCostBasis` 返回 `skuId -> (数量, 均价)`）：同一条明细的
  转入腿可能先于转出腿执行，到腿里再读均价会读到被本单前半段改过的值，两条腿于是不同源、
  总成本不守恒。
- **转换的转入单价 = 转出腿总成本 ÷ 目标腿数量**（`HALF_UP` 到 4 位，与 `avg_cost` 同精度）。
  折算率是人工声明的（一箱是 9.5 还是 10 kg 取决于供应商与批次），跨单位单价必然不同 ——
  **守恒的是总成本，不是单价**。
- **链式转换（A→B 且 B→C）的 B 不能取期初快照**：B 既收又发，真实账本上它的转出腿看到的是
  「进完之后」的加权均价；B 没有期初行时直接取 0，就是「调拨转入清零」的同一个缺陷。
  因此改为按**单据图**预解每个源 SKU 的成本基准：以锁行快照为期初，沿「谁转入到它」递归
  加权（记忆化；同一单据内互相引用时按期初均价收敛且不写缓存）。这类单据本身没有业务意义，
  不为它新增拒绝路径 —— 环上每条明细的两条腿仍共用同一个基准值，总成本依旧守恒。
- **V37 只重算 `avg_cost`，不改任何流水**（Q7 append-only）。`avg_cost` 是派生的活状态而非
  流水的净和，修正它不产生新的成本事实。候选集刻意收窄为 `quantity > 0 AND avg_cost = 0`
  （缺陷症状），逐行重放自己的流水并与重放结果逐行核对；重放不出来的行（转入腿找不到配对
  转出腿、或重放值与库里数量不符）**`RAISE EXCEPTION` 让迁移失败**，而不是按 0 继续 ——
  宁可卡住发布，也不要把一个算不出来的成本写进账。
- **口径**：盘盈 / 报溢转入仍按现有均价（不带来成本事实）；V34 上线前发生的出库腿
  `unit_cost` 为 `NULL`，按 0 参与加权 —— 那是「当时没有成本记录」的忠实重放，不是缺陷。

### 销售订单录入渠道（V35–V36，2026-09-20）

- 后台人工新增使用单一原子命令完成创建与推进：纯标品直接到 `CONFIRMED`；只要包含任一非标品，整单停在 `PENDING`。混合订单的标品由系统写入实数量，非标品等待电子秤或现有实重入口回写，全部实重齐备后再确认整单。
- Excel 导入是一种录入来源 `IMPORT`，不是第二套订单账。一行一个明细，按“导入订单标识”分组；先汇总全文件错误，只有全部通过才在一个事务内创建。任一订单失败，整批回滚。导入权限不隐含人工改价权限。
- 导入只接收模板单工作表，校验表头与实际单元格；空行不改变错误行号，公式/错误单元格不能录入。数量、人工单价读取实际数值而非显示格式；不可售、无价、金额超限等错误定位到行和字段。写入阶段业务失败必须先退出事务并完成回滚，再返回失败订单的行号，不能捕获异常后继续提交。
- 小程序订单本期仅确定接口边界，**未实现**客户端和 mall 后端。未来使用 uni-app Vue3 与 SmartAdmin Sa-Token 多 `userType`；服务端从登录身份派生客户，校验地址归属，通过结算预览返回 `priceFingerprint`，提交携带同一指纹和 `Idempotency-Key`，直接写同一 `sales_order` 并标记 `MALL`，不建 `mall_order` 或同步表。
- 商城提交必须满足可用库存。预览只作提示；正式提交必须在一个事务内锁定余额并建立预留，不能采用“先查询库存、再创建订单”的竞态实现。多仓规则未裁决前沿用唯一启用仓库约束。该商城规则不改变后台/Excel“先接单、再采购”的既有主链。
### 数据大屏（V28 建，V1 视觉版重构，2026-09-20）

- **「今日」必须是北京时间的今天**。`ScreenDataService.todayRange()` 原用 `ZoneOffset.UTC` 的日界，
  实际窗口是「北京时间 08:00 → 次日 08:00」：早上 07:00 下的单会被算进前一天，而 14:00 下的单
  恰好落在窗口内 —— 所以这个 bug 在下午几乎不可见。改为 `Asia/Shanghai` 日界，
  与 `demand_date` 的既有约定（`AT TIME ZONE 'Asia/Shanghai'`）一致。
- **库存健康度的四档互斥、之和等于总数**。设计稿把「缺货」画成与「预警」并列的一段（占比要凑满 100%），
  所以判定顺序是「缺货 → 未配置 → 三档」，而不是把缺货当作「低于下限」的子集另计：
  1. **缺货** —— 可用量 ≤ 0，**优先判定且不要求配了阈值**。理由：把缺货挂在阈值上会让
     「配了阈值但一件都没有」被算成「预警」而缺货段恒为 0；
  2. **未配置阈值** —— 有余额但没配阈值，**单独成档**。塞进「正常」会让健康度虚高
     （大屏看上去一片健康，实际什么都没评估过）；
  3. **预警 / 积压 / 正常** —— 完全交给 `ScmInventoryWarningStatusEnum.evaluate`，**取等号算正常**。
- **`totalSkuCount` 是「参与评估的行数」而不是 `product_sku` 总数**。取后者会让
  四档之和（13）与面板上显示的总数（14）对不上 —— 有一个 SKU 任何仓库都没有余额行。
- **口径单位是「(仓库, SKU)」而不是「SKU」**：阈值按 (仓库, SKU) 配，同一 SKU 在两个仓库
  可以一个正常一个缺货。面板文案写明「(仓库,SKU)」，避免与「SKU 总数」混淆。
- **大屏不自己编健康度算法**。判定只有 `ScmInventoryWarningStatusEnum.evaluate` 一份实现，
  大屏的 SQL 只提供「可用量 + 上下限」三个事实、不参与分类 ——
  一旦 SQL 里也写一份「正常/低于下限/高于上限」，两份规则漂移后大屏的健康度就会和预警列表对不上，
  而那种不一致比没有这个面板更糟。IT 里有交叉验证（大屏异常档 vs 预警列表总数，夹逼关系）。
- **商品排行按 SPU 归并**。原按 `sku_id` 分组，同一商品的多规格 SKU（如「智利车厘子」5 斤装 / 10 斤装）
  会在榜单里出现两条同名行，看起来像数据重复。榜单的口径是「商品」，所以按 `spu_id` 合并金额。
- **趋势接口一次返回全部序列**（`GET /scm/screen/data/trend?range=7d|30d`，8 条等长序列）。
  设计稿明确要求「不要大屏为了 7 张图调用十几个接口」；未知 `range` 兜底 7d ——
  大屏不应因为一个参数笔误而整块空白。
- **环比基数为 0 时显示「—」，不显示 0%**。昨天没营业、今天有 1 万，说「增长 0%」是错的，
  说「增长 ∞%」没有意义。「今日客户」「今日出库」没有同口径的历史序列，
  所以它们**恒显示「—」**而不是拿一个口径不同的数字算出看似合理的百分比。
- **各面板的数量类指标是跨单位求和**（kg + 箱 + 把 + 颗 + 托 + 件）。这是 V28 起的既有口径，
  设计稿也接受，但**不能当作重量或件数解读**，只适合看趋势与相对大小。
- **图表只在必要时用 ECharts**：排行用自定义条形（ECharts 类目轴做不出「序号+名称+金额一行、
  条形另起一行」的排布，10 条柱状图在 420px 面板里标签必然截断）；
  仓库分布用横向条形而不是饼图（饼图外置标签在 420px 下会被截断成「默…」）。
- **供应链地图的抽象网络占位已被真实地图取代**（2026-09-20 V1 用内联 SVG 按数组下标画节点，
  当时三张主档无结构化地理字段；2026-09-21 地图 M0/M1 建好归属列与质心后整体替换，
  上层三列布局未动）。当前口径见下方「地图模块 M0 / M1」。

### 商品中心优化 PCO-1：主档增强与辅助资料（V38–V39，2026-09-20）

- **`master_status` 只收窄「可选范围」，不改任何写入路径**。`DISABLED`（停止引用）的语义是
  「新单据选不到该商品」，落点只有 `ProductSkuOptionDao.options`；订单、采购、库存写入路径一行未动。
  曾考虑在写入侧也校验主档状态，那会让历史单据的补录与改单被自己的主数据挡住，
  属于把「引用控制」误用成「交易控制」。
- **单位字典只做取值来源，业务字段继续存名称快照**。`product_sku.sale_unit`、
  `supplier_sku.purchase_unit`、`inventory_balance.unit` 都是既有事实的组成部分，
  回写成 `uom_id` 会让历史流水的单位随字典变化而漂移。代价是字典必须保证**活动行内名称唯一**
  （`uk_scm_uom_name_active`），否则「按名称记账」会出现两个真值来源；也因此单位**编辑锁定编码与名称**，
  只能改量纲、精度和状态，退役走「停用」而不是删除，被引用的单位更是直接拒绝删除。
- **标签可以改名，停用只挡新绑定**。关系表存 `tag_id`，改名不影响已绑定商品的展示；
  停用标签仍保留历史绑定，所以批量摘标的下拉必须连选中商品已挂的停用标签一起给出（标注「已停用」），
  否则摘不掉。
- **批量维护是一个入口三种命令**（状态 / 分类 / 标签），逐行携带乐观锁版本，
  **预校验不通过整批不写**。半批成功会让运营无法判断哪些商品已改；失败行按行修正后原地重试。
  `failures` 最多回 50 行，超出只报条数，避免整批明细灌进响应。
- **商品删除保护刻意排除 `supplier_sku` 与客户可见性**。这两张是商品自身的辅助绑定，
  随商品一起清理是正当的；订单明细、采购明细、库存流水才是不可再生的业务事实，
  命中即 `40931` 拒绝并引导改用「停用 / 归档」。
- **归档必须下架**：`ck_product_spu_archived_off_shelf` 在数据库兜底，服务层同名校验只为了给出可解释错误。
  `status`（是否在售）与 `master_status`（主数据是否可用）保持正交，不合并成单个枚举，
  因为「下架但仍可引用」和「在售但停止新引用」是两种真实状态。
- **`/options` 类下拉数据源不单独开权限**，复用 `scm:product:query`。否则只读角色连筛选条件都渲染不出来，
  「页面能打开、写按钮被隐藏」这条验收就不成立。
- **本轮不做 Excel 导入导出与图片中心**（归入 PCO-2）：主档字段先稳定，导入模板与图集分组才有确定的列。
- **只读账号夹具拆成 `_read` 与 `_none`**。`_read` 带只读角色（全部页面菜单 + 只读按钮），
  已经无法验证「完全无权限」；`scm-inventory.spec.ts` 的「深链落到 404 + 查询也被拒」改用不挂角色的
  `_none`。两种语义互斥，不能再用同一个伴随账号承担。

### 地图模块 M0 / M1：地理数据地基与大屏真实地图（V40，2026-09-21）

方案与分期见 [`requirements/2026-09-21-地图模块分期实施方案.md`](./requirements/2026-09-21-地图模块分期实施方案.md)；
本节只记取舍，不复述实现。

- **`scm_region` 只做省 / 市两级，不建区县字典**。区县由表单人工选择后按「编码 + 名称快照」直接落库，
  服务端持有区划数据只有两个理由：把存量自由文本地址保守解析到市、按市聚合时取质心坐标，两者都不需要区县。
  多建一级只会带来一份需要长期维护、且与前端选择器可能不一致的数据。
- **种子编码与名称逐字取自前端 `area-cascader` 的静态字典**（GB/T 2260 六位码），质心另取
  DataV.GeoAtlas（拉取日期 2026-09-21）。这样表单选出来的编码与库里的字典必然同值；
  若从统计部门快照导码表，名称写法（简称 / 全称 /「市」后缀）会与选择器对不上，回填即失效。
- **存量地址解析只在迁移里做 SQL 保守整市名匹配，不自研 Java `RegionMatcher`**。
  原方案的「最长前缀匹配 + 三种形态」在真实数据上收益不明显：地址是自由文本，
  激进匹配会造出**看起来可信但错误**的归属（「长沙路」被认成长沙市），而这类错误比空值更难发现。
  规则收窄为「只按市级**完整名称**匹配，全国重名的市必须同时命中省名」，代价是解析成功率下降 ——
  换掉的正是「不猜」，与 M0 的验收口径（失败可见、可人工纠正）一致。
- **不新增区划查询接口**。前端已有静态省市区字典，加一枚接口只会多一个缓存与一致性责任；
  因此 `scm_region` 目前是**后端专用表**，无 CRUD、无菜单、无权限。后续若区县需要校验再议。
- **`longitude` / `latitude` / `geom_crs` 建列但本期不进表单**。没有底图（M2）就没有可信的取点方式，
  提前放开人工录入只会得到一批来源不明的坐标；列与 CHECK 先就位，是为了让 M2 不必再改表。
- **省界 GeoJSON 存档为构建期资产**（`xsy-scm-web/public/screen/china-province.json`，
  576 KB / 35 要素，其中 34 个有名称，第 35 个是无名的南海诸岛要素）。运行时不请求任何外部域名，
  内网与离线部署照常可用；边界数据来自官方来源且**不做删减、不自绘**（合规见方案 §8 R-3）。
- **省级数值在 Java 侧由市级聚合行上卷，不写第二份省级 SQL**。两份各自演算迟早漂移，
  漂移的表现是「省界图例与市级气泡对不上」，而大屏恰恰要靠这两个数字互相印证。
- **底图要素的匹配键是 `adcode`（= `province_code`），不是名称**。字典沿用简称「香港」/「澳门」，
  官方边界数据用全称；按名称匹配时 ECharts 不报错，只是那两省静默不着色。
  这条差异由 `xsy-scm-web/test/screen-geo-contract.test.mjs` 钉成断言，防止匹配键被改回名称。
- **覆盖度必须与地图同时呈现**：面板标题条标出「未归属：客户 N · 供应商 N · 仓库 N」。
  只画分布等于把「有地理归属的那部分」冒充全部业务量。仓库口径与气泡一致，只统计启用仓。
- **`lines` 流向层（供应商 → 仓库 → 客户）本期不做**。没有街道坐标时只能画省 → 省的粗线，
  信息量低于实现代价；等 M2 有真实点位后再评估。

### F0-DEBT-01 裁决：附件资产分级与文件读取权限（V41，2026-09-21）

下一波完整改造的方案见 [`plan/attachment-asset-grading-and-file-access-plan.md`](./plan/attachment-asset-grading-and-file-access-plan.md)；
本节只记裁决本身与其理由。

- **附件按「机密性」分级，不按「哪个业务模块上传」分级**。分级只有一个可执行来源：目录前缀
  （`public/*` 公开可读、`private/*` 需要授权）。若按模块分类，同一个模块内既有机密件又有展示件，
  守卫仍然要逐个文件判断，等于没有分级。
- **商品图片判定为公开资产，落 `public/image/`（新增枚举值 `PUBLIC_IMAGE(5)`）**。商城与小程序的
  商品图本来就要对未登录访客展示；此前挂在 `private/common/` 只是上传表单的默认值带来的历史结果，
  不是业务判断。改到公开目录同时解决两件事：读取不必再逐用户授权，URL 变成静态可缓存地址而不是
  会过期的预签名串。MinIO 侧的匿名读策略与 `public/` 前缀 ACL 早已就位，本次只补了一个枚举值。
- **真正的业务附件（合同、营业执照、财务回单、供应商资质）用 `file_relation` 关系表授权**，
  即「有权看这个业务对象 ⇒ 能看它绑定的文件」，而不是「有权看这个文件记录 ⇒ 能看」。
  否决过的两个替代方案：按 fileKey 前缀细分到 `private/contract/` 之类（前缀粒度表达不了
  「哪一张单据」，同前缀下所有人的合同仍然互看）；在文件表上加 owner 列（表达不了
  一张回单同时归属多个业务对象，且把业务权限模型焊进底座表）。
  代价是上传与绑定要分两步：先入暂存，绑定业务对象时才建关系行；未绑定的暂存件需要回收。
- **写侧的绑定期限权本轮已收口，且比读侧更严重**。`product_image` 的 fileKey 由客户端提交，
  原先只要知道别人的 key 就能把它挂到自己的商品上；商品详情对所有查看者展开图片 URL，
  等于「有商品编辑权就能把他人私有附件晋升为全员可读」。这是数据提升，不是越权读一条记录，
  所以先修它。规则收在 `ProductImageSyncManager`：新增或换绑只能引用 `public/image/` 前缀，
  **但允许行沿用自己原有的 key**——否则 PCO-1 之前落库的私有 key 会让历史商品连改排序都保存不了。
  前缀常量取自上传白名单枚举，不在业务侧另写一份字符串。
- **`product_image.file_url` 列删除（V41），展示 URL 一律按 `file_key` 现算**。预签名地址是带 TTL 的
  派生值，落库即成为一份会漂移、会过期的副本，而页面从来不用它。删列不丢业务信息：
  文件名与 key 仍在。刻意**不在库上加前缀 CHECK**——存量行是合法的私有上传，硬约束会把历史变成故障，
  「新绑定必须公开」是写入语义，归 Java 侧判断。
- **本轮边界（如实声明，不是已完成）**：
  ① 读侧仍未闭合，`FileService.getFileList()` 依旧无用户参数，存量私有商品图和 OA 附件 VO
  走的还是绕过守卫的批量展开路径；② 本地存储模式（dev 常用）把 `/upload/**` 静态映射直出，
  没有任何守卫，因此「私有附件」在本地环境不构成保密性，验证权限行为必须走对象存储模式；
  ③ `public/` 一旦写入即公开，任何将来上传都要先确认目录归类，不能靠默认值落到哪算哪。
  **2026-09-23 更新（只更新事实，不改裁决）**：① 中 VO 展开这一条路径已做**临时收口**——
  `FileKeyVoSerializer` 逐 key 过 `FileAccessGuard.filterReadable`，无身份或依赖未注入时输出空列表；
  但 `FileService.getFileList()` 的无身份批量入口与代码生成模板**未变**，FA-1 仍未完成。

## P0 基线收口裁决：角色模型、SCM 数据范围与 F0 附件收口（2026-09-23）

背景：主线计划 P0 要求「建立正式非管理员业务角色并验证数据范围」并关闭 `F0-DEBT-01`。
以下 15 条是正式裁决，取代此前记在「未决事项」里的开放问题。

### 一、角色与数据范围是两件事

1. **角色只表达「能做什么」，数据范围只表达「能看哪些数据」**。不创建 `角色 × 仓库`
   这种角色实例（「采购员-深圳仓」），也不把仓库当部门用 —— 部门只承担组织架构。
   员工可以有多个角色，**功能权限取并集**。
   理由：仓库集合会随人员调整变化，把它编进角色名会让角色数量随「人 × 仓」膨胀，
   且没有任何一处能回答「这个员工能看哪些仓」。
2. **SCM 数据范围不扩展现有 `@DataScope`**，改为集中解析 + 显式下传的业务数据范围
   （`ScmDataScopeService` / `ScmDataScopeContext`，Service 层算出
   `warehouseIds / employeeId / sellerId / purchaserId / driverId / financeScope` 后
   显式传给 Mapper）。理由有三条实测事实：底座插件对空 id 清单与 `ALL` 返回空串即
   **不加限制（fail-open）**；`ME` 硬编码 `create_user_id`，而 SCM 全库只有
   `created_by VARCHAR(64)`；它的 SQL 改写靠 `where` 关键字字符串切片，对
   `ReportDao.xml` / `DeliveryQueryDao.xml` 的 CTE 语句不安全。
   原则：**没有授权范围就查不到数据，不允许用 `null` 表达「全部」**；
   用户自己传的 `warehouseId` / `sellerId` 只能进一步**缩小**范围，不能扩大。
   解析必须集中在一个入口，不允许每个 Controller 各写一套判断。
3. **「本人」以业务 owner 字段为准，`created_by` 永远是审计字段**，不作为数据权限依据：
   销售订单看 `sales_order.seller_id`、采购订单看 `purchase_order.purchaser_id`、
   线路看 `route.driver_id → driver.employee_id`。
   `created_by` 只回答「谁建的这条记录」，回答不了「这条业务归谁负责」——
   管理员替业务员录单时两者必然不一致。
4. **最终组合规则**：功能权限按角色并集；同一领域的授权范围按显式授权并集；
   用户筛选与授权范围取交集；无任何授权 fail-closed 返回 0 行。
   **不再用数字 `level` / max level 推导 SCM 业务数据范围**（多角色取最大级别的语义
   会把「有仓库 A 范围的仓管 + 有全部范围的财务」算成全部，这是错的并集）。
5. **`administrator_flag` 的底座语义本轮不动**，仍作为 break-glass 超管绕过菜单/API/数据范围。
   但约束是硬的：**普通业务人员禁止 `administrator_flag=true`**，
   正式角色验收必须用 `administrator_flag=false` 的账号，**超管通过不能作为权限证据**。
   本轮不重构 SmartAdmin 超管机制。

### 二、四个业务角色的范围口径

6. **销售**：默认只看 `customer.seller_id = 当前员工` 的客户与
   `sales_order.seller_id = 当前员工` 的订单。`seller_id IS NULL` 定义为**未分配**，
   普通销售不可见，只有销售主管/管理员可查看与分配。新建客户时普通销售的
   `seller_id` **由服务端强制为当前员工**；有分配权的人才可以指定或改派。
   `parent_customer_id` 与 `settle_mode=GROUP` **不自动扩大**可见范围 —— 集团统一结算
   由财务或集团客户管理权限查看，不允许因为同属一个集团就跨业务员看别人的客户。
   普通销售默认可见**不含**采购成本、库存成本与毛利底层成本。
7. **采购**：普通采购员默认只看 `purchase_order.purchaser_id = 当前员工`。
   **必须先把 `purchaser_id` 从「取自表单」改为「普通新建时服务端强制为当前员工」**，
   有采购分配权的主管才可指定/改派；在完成这项修正之前，
   客户端传入的 `purchaser_id` **不得**当作数据范围依据（现在它是个可任意填写的字符串）。
   `supplier` 无 owner 列 → **供应商主档按采购团队共享读取**，
   不为了数据范围给 supplier 强行加 purchaser 归属列。
8. **仓库**：新增员工与仓库的授权关系表（`employee_warehouse_scope`，一人可绑多仓），
   库存余额 / 流水 / 盘点 / 收货 / 出库的 `warehouse_id` 必须落在授权仓内。
   调拨特殊：**查询**是 `from_warehouse` 或 `to_warehouse` 任一命中即可见，
   **发出**要求 `from_warehouse` 权限，**收货**要求 `to_warehouse` 权限。
   普通仓管**可看数量、不默认看**采购价 / `avg_cost` / 库存金额，
   成本经独立成本权限开放给仓库主管与财务（沿用 `scm:report:cost:query` 同一取向）。
   `inventory_movement.created_by IS NULL` 的历史回填行**不影响可见性**，仍只按仓库判定。
   对已存在「录单 + 审批」两个动作的业务**禁止自建自审**，至少报损报溢要求
   `approver != creator`；但不为此给没有审批环节的库存单据凭空加审批状态。
9. **配送**：`delivery_driver` 增加 `employee_id BIGINT NULL`，一个员工最多绑一个活动司机、
   一个司机最多绑一个员工；历史行可以为 null，但正式司机启用前必须绑定。
   普通司机只看 `driver.employee_id = 当前员工` 的线路。
   **「配送调度/线路规划员」与「司机」不是同一个角色**。
   `DeliveryQueryDao.candidates`（全量候选订单）只允许「调度/线路规划权限 + 对应仓库范围」，
   普通司机不得查询全量候选。敏感字段口径：调度员在工作范围内可看完整地址与电话；
   司机只能看**已分配给自己线路**内订单的配送地址与电话；**司机默认隐藏订单金额**，
   未来货到付款确实需要金额时另开独立权限。
10. **财务不等于代码里的全组织可见**：数据范围机制对财务同样存在，
    「总部财务看全部」是**配置出来的范围值**，不能写死 `FINANCE = 全部`，
    否则将来出现分公司财务时要反过来改代码。
    财务的页面查询与 Excel 导出**必须使用同一套数据范围**（能看 A/B 仓就只能导 A/B 仓），
    `scm:report:export` 只代表「允许导出」，绝不扩大查询范围。
11. **分拣角色顺延到 P1**：当前没有分拣实体、页面与权限，P0 不建空壳「分拣员角色」，
    P1 建模块时同时交付权限、角色、数据范围与正式 E2E 账号。不提前造无消费方的权限。

### 三、F0-DEBT-01（附件）四项待裁决的落定

12. **D-1：FA-2 首版同时覆盖 SCM 与现有 OA 私有业务附件**（企业执照等、公告附件、
    帮助文档、反馈附件）。目标是真正关闭这笔债，不留「SCM 安全、OA 继续按目录前缀放行」
    的半成品。因为要跨 OA/SCM 复用，**关系能力放在通用 `support/file` 层**，
    表用中性名（`t_file_relation`），核心列仍是 `file_key / biz_type / biz_id`；
    **不允许 OA 代码依赖 `module/scm`**。
13. **D-3：全员可见的公告附件仍是 `private/`**，不等价于互联网公开。
    「全员可见」= 所有登录员工可见，授权规则是「能看这条公告 ⇒ 能看它的附件」，不迁 `public/`。
14. **D-2：暂存（scratch）回收窗口 7 天、每用户未绑定暂存上限 100 个**。
    上传成功但表单未保存即属暂存；保存业务对象时建关系行、从此不可回收；
    超 7 天仍无任何关系行的清理掉。清理任务必须**再次确认「无关系行且没有任何业务表直接引用」**
    才允许物理删除 —— 误删不可逆，这类双确认要由测试钉住。
15. **D-4：财务回单采用比普通业务对象更严格的附件权限**：
    「能看业务对象 **且** 有财务附件权限」才可读。但关系表**不存任意 `required_permission` 字符串**，
    而是在服务端按 `biz_type` 固定映射（`FINANCE_RECEIPT → scm:finance:attachment:query`），
    普通合同/供应商资料同样走 `biz_type` 的 Policy Registry。
    理由：把权限串写进数据库等于给「改一行数据即可越权」留口子。

**FA 上线顺序（强制，取代此前「FA-3 先于 FA-1」的初步倾向）**：

```text
FA-1 受控 FileService 读侧 → FA-2 通用关系授权 + 存量关系回填
→ 至少跑一轮权限 / 浏览器回归 → FA-3 存量商品图搬 public/image → 删除历史临时前缀兼容
```

禁止：FA-1 与 FA-3 同批上线；FA-2 未回填就开启 relation fail-closed；
FA-3 未完成就删除存量 `private` 商品图的兼容读取。

> 顺序修正的原因：FA-3 是**数据搬运**，搬运本身不修读侧洞，且 `FileService.getFileList(keys)`
> 的无身份批量入口还在，任何新调用方都能绕过守卫；先把守卫接进唯一的读出口（FA-1）、
> 再让「可读」这件事有业务含义（FA-2），最后才动数据（FA-3）。
> 原「先搬运再收口」的取向会把「商品图对非创建人不可见」这个问题留到搬运之后仍然没解决。

## P0 基线收口裁决（第二批，2026-09-24）

第一批的 15 条收口后仍留四条口径由实现方提出、等业务裁决；本节是用户的正式答复，
编号沿用上一节（第 16–19 条），实现基线与差异一律以本节为准。

16. **「一个员工最多绑定一个活动司机」的「活动」= `deleted = false`，不是 `status = ENABLED`**。
    `status = DISABLED` 只表示该司机不能再参与新的配送任务，**不解除员工与司机档案的身份绑定**。
    因此：V54 的 `uk_delivery_driver_active_employee` 保留现有谓词，不需要新迁移；
    要换司机档案必须先软删旧档案再建新绑定；历史线路仍能查询当时那位司机。
    **Why:** 绑定回答的是「这个人是谁的账号」，停用回答的是「今天有没有排班」，
    两者混在一个谓词里会让停用/恢复顺带解绑、换绑，审计上查不到是谁移动的。
17. **正式角色矩阵按以下业务口径收口（V57 增量，V56 已应用不可改）**：
    * 库存数量权限 ≠ 库存成本权限。普通采购员**可以**查库存余额与可用量（用于判断收货与采购需求），
      但默认**不得**看 `avg_cost`、库存金额与销售成本 —— 成本继续由独立的
      `scm:report:cost:query` 控制，缺省时抹成 `null` 而不是 `0`。
    * 销售主管**可以**进入退货 / 退款的业务审批入口（批准、驳回、退款完成），
      但这只代表业务审批，不代表财务付款、资金操作或查看采购成本；
      普通销售员不自动获得任何审批权。Finance R1 的实际退款付款另归财务权限。
    * 财务按「总部统一财务」处理：**默认可见全部仓库**，但必须仍然通过正式数据范围机制表达
      （显式授予 `scm:inventory:scope:all:query`），**禁止**写 `if role == FINANCE then bypass scope`。
      将来出现区域 / 分公司财务时只调授权，不改业务代码。财务的导出范围必须与查询范围完全一致。
    **How to apply:** 这三条都是「授权数据」而不是「代码分支」。新增岗位时先问
    「它属于哪个维度、要不要放宽」，再决定给不给 `*:scope:all:query`，不要在 Service 里按角色名判断。
18. **`receipt.confirm` 的 `DIRECT` 模式取「采购范围 ∩ 仓库范围」交集，失败关闭**，
    不是二选一：采购归属只能证明「你能操作这张采购单」，不能证明「你能向任意仓库写库存」。
    因此普通采购员即使 `purchaser_id = 本人`，没有目标仓授权也不能 DIRECT 入库；
    采购主管能看全部采购单也不能借此绕过仓库范围；仓管有仓库权限但没有对应采购操作权限时，
    同样不能替采购员执行采购动作。`WAREHOUSE_CONFIRM` 模式在 `confirm` 时不写库存，
    所以仓库判定落在 `putaway` 那一步（保持「收货确认 ≠ 库存入账」的既有口径）。
    将来某岗位确实需要跨仓 DIRECT 收货，通过显式仓库授权解决，不写特殊角色 bypass。
    归属维度同时补齐到采购单命令（编辑 / 提交 / 取消 / 少收关单 / 删除）、收货单的创建与编辑、
    以及需求分配的两头（需求归属与目标采购单归属）。
    **Why:** 第一批只收了读侧与 `putaway`，写侧留了一个洞 —— 功能权限在采购团队内共享，
    只有读侧收窄等于「看不到但改得动」。
19. **`GET /scm/warehouse/list` 对非管理员只返回其被授权的仓库**，未授权仓库的 id、名称、地址
    一律不给（通用选择器不得成为绕过仓库范围的旁门）。
    例外是**历史事实**：用户已有权查看的业务单据继续展示该单据行上保存的
    `warehouse_name_snapshot`，即使他当前已经失去该仓授权 —— 那是快照，不是该仓的查询权。
    超级管理员照常返回全部。
    **How to apply:** 需要跨仓选仓的岗位（例如配送调度）通过授权行 / 范围权限解决，
    不要把选择器改回全量。同理，任何「给表单用的 option 列表」在新增时都要问一句
    「它是否隐含了某个维度的可见性」。

## P1 分拣管理裁决（2026-09-24）

主线计划 P1 节「开工前必须明确」的六个问题，加上分拣与既有 Delivery L0–L2、库存、权限
模型的衔接，由用户逐条裁决如下（第 1–14 条）。分拣是**实发事实的产生地**，不是第二套订单、
库存或配送事实。

1. **分拣发生在订单 `CONFIRMED` 之后**（计划选项 A），并且**绝不回写** `sales_order_item.actual_quantity`
   与 `settlement_*`。分拣任务自己保存 `planned_quantity_snapshot`（= 进入分拣那一刻冻结的
   `actual_quantity`）与 `sorted_quantity`；订单侧的实发与结算口径由后续阶段按分拣结果决定。
2. **一张订单允许进入多个任务，但一个 `sales_order_item` 最多属于一条「有效」分拣明细行**：
   未取消的任务占用，已取消的不占用，由**部分唯一索引**在库里强制
   （占用位具体写在明细行上，见补充第 16 条）。
   「按客户订单」与「按商品汇总」两个视角共用同一套事实。
3. **缺货 / 少拣不改订单行**（V13 的 `actual_quantity > 0` 检查保留原样）；`sorted_quantity >= 0`
   合法（允许 0）。每条明细的结果取 `NORMAL / SHORT / OUT_OF_STOCK / OVER`，**非正常结果必须填原因**，
   分拣本身**不自动触发任何下游动作**；是否部分发货由 P2 决定。
4. **P1 不做商品替代**：不引入替代表或替代状态，也不复用 `CONVERT_OUT / CONVERT_IN` 流水；
   需要换货时由人工补单解决。
5. **P1 不设容差阈值**：任何 `sorted_quantity != planned_quantity_snapshot` 都是需要原因的差异，
   不存在「在阈值内自动通过」或「自动重新结算」的分支。
6. **P1 不写库存**：不创建出库单、不动余额与预留、不移动预留的触发点；`SALES_OUT` 仍由
   Delivery L3 / P2 在真正出库时产生。
7. **分拣的数据范围 = `warehouse_id ∈ 授权仓 AND 任务受指派人 = 本人`，失败关闭**（两个维度取交集，
   不互相替代）。分配权 `scm:sorting:assign` 授予**既有** `SCM_STOREKEEPER_LEAD`；
   新增正式非管理员角色 `SCM_SORTER`（使用者必须 `administrator_flag = false`）。
   **不新增第六个「分拣员」范围维度**（复用仓库与员工两个既有维度），也不做供应商自分拣。
8. **打印 = 预览 + 触发 + 计次 / 时间 / 操作人**，绝不改任务状态、不写库存（与配送打印同口径）；
   标签与小票用**固定版式**，可配置模板系统留给 P6。实重**只允许人工录入**（电子设备归设备波次）。
   任务号前缀 `SRT`，序号取**全局非重置序列**（不按日重置）。不记毛重 / 皮重 / 净重，不做单位换算。
9. **`sorting_task` 携带 `warehouse_id` 与 `warehouse_name_snapshot`**，由操作人显式选择、后端校验；
   **不从订单、客户或线路推断仓库**。不给 `sales_order` 增加仓库字段（订单不属于某个仓）。
10. **状态机可编辑性**：`PENDING / SORTING` 可编辑；`COMPLETED` 只能通过**显式 REOPEN** 回退，
    REOPEN 需要独立权限 + 原因 + `version` 乐观锁 + 操作日志，且**该任务已产生真实出库
    （`SALES_OUT`）后禁止重开**（这一半的可实现性受限于模型，见补充第 21 条）。
    被重开的订单必须在 `DeliveryEligibilityPolicy` 里立即变成不合格，
    不允许「已完成分拣 → 已重开」期间还能被当作可发货候选。
11. **配送候选资格改为**：`CONFIRMED` **且该订单全部有效明细行都有终态分拣结果**
    （`NORMAL / SHORT / OUT_OF_STOCK / OVER` 都算已处理）。不引入 P2 语义（不判断部分发货、
    不判断发多少）。P1 上线**不得自动释放或改写**库里已存在的 `ACTIVE` `delivery_route_order` 行。
12. **表只有 `sorting_task` 与 `sorting_task_item`**；操作日志**优先复用** SmartAdmin 通用
    `@OperateLog` / `t_operate_log`，只有能证明通用日志满足不了追溯时才新建 `sorting_operation_log`。
13. **迁移号与菜单号在与远端同步后重扫**：P1 迁移从实际最大号 + 1 开始（当前 max = V59 →
    P1 从 **V60** 起），菜单 id 段先查实际占用再定（1400–1499 只是候选，不作为既成事实）。
14. **P1 明确不做**：库存写入与出库、预留触发点迁移、替代商品、容差阈值、自动重新结算、
    可配置打印模板、设备称重、单位换算、毛重皮重净重、第六个范围维度、供应商自分拣、
    部分发货与发货量决策（P2）、分拣绩效大屏。**完成 P1 即停止，不自动进入 P2。**

**Why:** 分拣处在「订单已确认」与「实际出库」中间，最容易越界的地方就是把实发事实顺手
变成第二套结算、第二套库存或第二套配送状态；裁决把每条边界钉在「只写自己那两张表」。

**How to apply:** 实现时以本节的编号为准，计划文档里的范围描述只是背景。任何「看起来更省事」
的做法 —— 例如回写 `actual_quantity` 让下游少改一处、用 `if role == SORTER` 代替数据范围、
在 COMPLETED 时顺手生成出库单 —— 都是对上述某一条的直接违反，需要重新裁决。

### P1 分拣管理裁决补充（同日第二轮，第 15–22 条）

第 1–14 条落地前还有八处会直接改表结构与状态机的口径，由用户逐条选定；与上文冲突处**以本节为准**。

15. **创建与可见性：主管建单并指派**。分拣任务只能由持 `scm:sorting:assign` 的人（现状即
    `SCM_STOREKEEPER_LEAD`）创建并指派；**未指派任务只对持该权限者可见**。分拣员的任务列表
    恒等于「派给自己的 ∩ 授权仓」，两维取交集失败关闭。
    **不新增** `scm:sorting:scope:all:query` 这类第二个范围权限 —— 跨指派人的可见性由 `assign`
    权本身隐含，因为它表达的就是「谁的任务都由你排」。
16. **`sorting_task` 状态集只有 `PENDING / SORTING / COMPLETED / CANCELLED`**。
    取消即释放占用，**不存在 `RELEASED` 任务状态**（第 2 条列举的「不占用」态实际只有 `CANCELLED`）。
    明细行沿用 `delivery_route_order` 既有形态：占用状态写在明细行自己身上
    （`ACTIVE / RELEASED`），取消任务时在**同一事务**里把该任务全部明细置为 `RELEASED`，
    部分唯一索引 `WHERE deleted = FALSE AND occupation_status = 'ACTIVE'` 因此不需要跨表判断。
17. **COMPLETED 的硬前置：任务内每一条明细都必须已有结果**（`result` 与 `sorted_quantity` 齐备）。
    一张订单需要分多次分拣时，靠「剩余有效明细行另建新任务」实现，而不是靠「带洞完成」。
18. **配送候选资格按「订单全部有效明细行都被 `COMPLETED` 任务覆盖」判定**，
    这是第 11 条「都有终态分拣结果」的等价式选择。选它的理由是可重开性：判定落在任务状态上，
    REOPEN 只需把任务退回 `SORTING`，订单立即不合格，**已录入的分拣量与原因作为事实保留可继续修改**，
    不破坏审计；反之若按「行上有结果」判定，REOPEN 就必须清空明细结果才能让订单不合格。
19. **「按商品汇总」视角在 P1 只读**：跨订单聚合展示与打印，不承载录入。
    分拣量一律在「按客户订单」视角逐行录入。因此 P1 不存在「汇总量如何拆回订单行」这个问题
    （legacy 需求稿 07-01 的未决项在 P1 范围内被绕开，不是被解决）。
20. **已排线（存在 `ACTIVE` 配送占用）的订单允许重开其已完成任务**，接受「订单已在线路上但已不合格」
    这个中间态：P1 **不自动释放占用、不改写线路**（与第 11 条一致），发车时如何判由 P2 决定。
21. **第 10 条里「已产生真实出库则禁止 REOPEN」这一半在 P1 不实现，整条推给 P2**。
    原因不是没做，而是现状没有可用判据：出库单行 `inventory_outbound_item` 不带订单行来源
    （只有仓库 + SKU + 数量），`SALES_OUT` 流水按 `SALES_OUTBOUND_ITEM` 记账，预留虽有
    `SALES_ORDER_ITEM` 维度但 `CONSUMED` 状态全库无生产者。任何实现都只能按
    「仓库 + SKU + 时间窗」近似，会把别的订单的出库算到本任务头上。
    **How to apply:** 不要为了让这条守卫"看起来存在"而引入近似判据；等 P2 的发货出库
    带上订单行来源之后，再把这条守卫补回来。
22. **建单用的「候选订单行」是分拣队列视图，不受订单业务员范围约束。**
    入口只授 `scm:sorting:task:add`（现状即 `SCM_STOREKEEPER_LEAD`），返回列只取队列必需的
    单号 / 客户名 / 商品 / 规格 / 单位 / 订购量 / 实发量，**不含任何价格与金额**。
    **Why:** 仓库岗位默认不持 `scm:order:scope:all:query`，若按 `seller_id` 收窄，
    建单页一个候选行都选不到，第 15 条的「主管建单并指派」直接无法执行；
    而为它放宽订单域全量范围会把订单列表 / 详情一起放宽，代价更大。
    **How to apply:** 这是「option 列表隐含可见性」这条 P0 口径的一个**显式例外**，
    只此一处；将来若出现「按仓分单的区域调度」需求，回到收窄 + 授权行解决，不要在这个接口上加参数开关。

**Why:** 这八条都是「一个字段位置 / 一个状态是否存在的理由」级别的分叉，自行选边会让
P1 的实现里混进未经确认的权限模型（第二条范围权限）、死状态或破坏审计的重开语义。

**How to apply:** 第 16 条是同事务写两表的约束 —— 任何新增的任务状态迁移入口都必须同时维护
明细占用位，否则部分唯一索引会与任务状态漂移；第 18 条要求资格判定与 REOPEN 一起改，
不要只改 `DeliveryEligibilityPolicy` 的 SQL 而忘了 `eligible(order)` 那条服务侧分支。

## P2 物流配送 L3 裁决（2026-09-25）

主线计划 P2 节「开工前必须明确」的五个问题（实发数量来源 / 部分发车 / 部分签收 / 拒收 /
配送取消后库存如何处理），加上与 P1 第 21 条、库存出库与预留模型的衔接，由用户逐条裁决。
配送 L3 是**把已经存在的实发事实变成正式出库事实**，不产生第二套实发量、第二套库存账或第二套订单状态。
本阶段之后的主线顺序是 **P2 → Finance R1 → Finance R2**（与 `docs/plan/finance-reporting-r0-plan.md`
第 56–64 行一致），不跳去 Finance，也不先扩商品 / 采购 / 小程序的业务接口。

1. **实发数量的唯一来源是分拣结果**：出库量 = `sorting_task_item.sorted_quantity`（任务 `COMPLETED`、
   明细占用位 `ACTIVE`）。发车**绝不回读** `sales_order_item.actual_quantity`，也不重新计算或修正分拣量；
   `NORMAL / SHORT / OUT_OF_STOCK / OVER` 在分拣阶段已经成形，配送只消费这个事实。
2. **发车粒度 = 整条线路原子发车，P2 不做部分发车**。一条 `PLANNED` 线路发车时在事务内重查全部
   `ACTIVE` 的 `delivery_route_order`；只要有任何一单因分拣 REOPEN 等原因不再合格，**整条线路拒绝发车**，
   不做「先发能发的、剩下的留着」。状态机因此保持单一出口，不产生「线路半发车」这种无法解释的中间态。
3. **一条线路 = 一张出库单**，出库明细**按 `sales_order_item` 逐行保留来源，同 SKU 不跨订单行合并**。
   由此成立的可追溯链是
   `delivery_route → inventory_outbound → inventory_outbound_item → sales_order_item → sorting_task_item`。
   主线计划第 148–157 行要求的「订单 / 配送 / 出库互相追溯」由这条链承担，它也是 Finance R1 做
   「订单行 → 实发 → 出库流水 → `unit_cost` → 实际销售成本」的唯一可行前提。
4. **库存事实一律由库存领域产生，配送模块不直接改库存**（主线计划第 136–146 行的既有约束）。
   发车调用库存域的一条原子命令，在**同一个事务**里完成：锁预留 → 锁余额 → 归还本订单行的预留 →
   按实发量产生 `SALES_OUT` → 预留置 `CONSUMED`。`module/scm/delivery` 里不得出现任何对
   `inventory_balance` / `inventory_reservation` / `inventory_movement` 的写入。
5. **第 4 条的步骤顺序是数据库强制的，不是风格选择**：`ck_inventory_balance_available
   (reserved_quantity <= quantity)` 逐语句求值，因此**必须先归还预留、再扣减实物**。
   反例：存量 10、本单预留 10、实发 5 —— 先扣实物会写出 `quantity = 5, reserved_quantity = 10`
   并被 CHECK 打回，整个发车事务回滚。
6. **少拣时预留整条 `CONSUMED`，不拆行、不加差额列**。唯一索引
   `uk_inventory_reservation_source_active` 的谓词不含 `status`，一条订单行终身只能有一行预留；
   「预留 5、实发 3」的差额由「`inventory_reservation.quantity` − 对应 `SALES_OUT.quantity`」现算，
   不给同一个事实第二个权威来源。
7. **预留仓库与线路仓库不一致时，整条释放后从本仓扣**：发车事务把该订单行的跨仓预留整条归还
   （那个仓的 `reserved_quantity` 当场回落），实发量全部从线路仓库的可用量扣减。
   **Why:** 预留入口用 `defaultEnabledWarehouse()`、线路仓库由调度自选，两者可以不同
   （dev 库已有两个启用仓，这条路径真实可达）。「拒绝发车并要求先处理」会在调度手里留下死结；
   「跨仓预留原样留着」则让那个仓的可用量被永久压低且没有任何时点会回收它。
8. **无预留的订单从真正可用量扣减**（`quantity − reserved_quantity`，即既有 `41011` 口径），
   多拣（`OVER`）的超出部分同样走可用量；库存不足时**整条线路事务回滚**，一行库存都不扣。
9. **出库单在发车时以 `CONFIRMED` 直生，不经过 `DRAFT`**。`isEditable / isConfirmable / isCancellable`
   三个判定都只认 `DRAFT`，所以直生 `CONFIRMED` 天然让手工出库页无法编辑、重复确认或取消
   一张已经代表真实发货的单据；也不需要在出库单上再加一层「是否被线路占用」的状态。
10. **作废 W6-1 里「无需改表结构」那半句**（本文第 30 行）：当时的判断是「发货模块落地后由发货确认
    去创建并确认出库单即可」，但 `inventory_outbound_item` 实际只有 `outbound_id + sku_id + quantity +
    unit_snapshot`，没有任何订单行来源列 —— P1 第 21 条的守卫也正是因此不具备判据。
    P2 必须给出库单行补来源列。「出库采用独立出库单、不挂在未开发模块上」这个**前半句仍然有效**，
    本次不改，也不把出库单变成配送的附属表。
11. **P1 第 21 条的守卫在本阶段补回**：`REOPEN` 的前置增加「该任务的任一明细行若存在**父单为
    `CONFIRMED`** 的 `inventory_outbound_item`，禁止重开」。只认 `CONFIRMED`：出库单的取消只在
    `DRAFT` 可用且不发任何流水，没扣过库存的出库行不构成「货已出去」的事实。
    仍然禁止使用「仓库 + SKU + 时间窗」的近似判据。
12. **签收是订单级二值终态，不做部分签收**：`delivery_route_order` 新增履约状态
    `PENDING → IN_TRANSIT → SIGNED | EXCEPTION`。发车时该线路全部活动订单进 `IN_TRANSIT`；
    逐单「正常签收」或「异常签收」，**异常必填原因**；全部活动订单进入终态后线路才可
    `DISPATCHED → COMPLETED`。`assignment_status`（在不在线路上）与履约状态（到没到手）正交，
    不合并成一列，也不拿 `RELEASED` 表达签收。
13. **签收不产生任何库存事实**：`EXCEPTION`（含拒收）**不反冲 `SALES_OUT`、不改历史流水**
    （Q7 追加式账本）。退货应由后续退货流程以**新增反向事实**处理。
    主线计划第 165 行的「配送取消后库存如何处理」据此回答：**L3 不处理，只保证不破坏账本**。
14. **发车后线路不可逆**：`DISPATCHED` / `COMPLETED` 线路禁止取消，也禁止改停靠点、增删订单
    （既有 `cancel / update / addOrders / removeOrder / stops reorder` 全部补状态守卫）。
    要纠正只能走后续退货 / 补单，不给「把已发车的线路退回去」留口子。
15. **打印与发车彻底分开**（沿用 P1 第 8 条与 L0–L2 既有口径）：打印只计次，
    不创建出库单、不推进任何状态；发车只由 `POST /scm/delivery/routes/{id}/dispatch` 触发。
16. **权限与角色**：新增 `scm:delivery:route:dispatch`、`scm:delivery:order:sign`、
    `scm:delivery:route:complete` 三个点。发车授 `SCM_DISPATCHER` + `SCM_STOREKEEPER_LEAD`；
    签收授 `SCM_DISPATCHER` + `SCM_DRIVER`（司机继续受既有 `driverScope`「只看绑定到本人的司机档案
    所属线路」约束，读侧不收宽）；完成线路授 `SCM_DISPATCHER`。**不新增第四个范围维度。**
    发车走库存域既有的仓库范围守卫（P0 第二批第 8 条：出库的 `warehouse_id` 必须落在授权仓内），
    因此**调度岗需要与之匹配的 `employee_warehouse_scope` 授权行** —— 这是配置要求，
    不是把守卫放宽的理由。
17. **发车必须 `Idempotency-Key` + `version` 双保护**：它是会产生库存事实的命令。同一键重复请求
    回放原结果；并发两个发车请求只允许一个真正扣库存。签收与完成线路带 `version` 乐观锁，
    与 L0–L2 的 `plan / cancel / print` 同形。
18. **L3 不动销售订单状态机**（`docs/delivery-static-route-implementation.md` 第 26 行的既有约束，
    P1 第 1 条同向）：发车与签收都不写 `sales_order.status`、不写 `settlement_*`、
    不新增订单操作日志类型。履约事实在配送域自己的表上，跨域追溯靠第 3 条那条链。
19. **P2 明确不做**：部分发车、部分签收、签收时复核实收数量、拒收自动反冲、GPS 实时轨迹与轨迹回放、
    自动路线优化、电子签名图片、司机 App / 小程序配送端、可配置打印模板、自动退款与结算、退货入库单。
    这些都不阻塞主线事实链闭环；轨迹与司机端归后续配送子阶段（主线计划第 167 行同向）。
20. **迁移号与菜单号开工时重扫**：本裁决写就时 `db/migration/` 实际 max = V62，且远端 `main`
    与本地 HEAD 同为 `0dfb68a`，故 P2 从 **V63** 起；这只是一次快照，动手时仍须重扫，
    不得假定。菜单 id 在配送段（1000–1003 页面 / 1011–1016 线路按钮 / 1341–1342 范围与金额）
    实际占用重扫之后再定。

**Why:** L3 的风险不在状态机而在**事实归属**。实发量已经有了权威来源（分拣），库存账是追加式的，
订单状态机不许第三方扩展 —— 把这三条钉住，配送剩下的就只是「消费事实 + 产生出库」。
第 5、6、7 条之所以写成硬约束，是因为它们的反例都能让页面照常跑，只在库里留下事后解释不了的账。

**How to apply:** 任何新增的线路状态迁移入口都必须同时维护第 12 条的履约状态与第 14 条的不可逆守卫；
任何绕过第 4 条直接写库存的实现（哪怕只是「顺手把 `reserved_quantity` 减一下」）同时违反本裁决与 P0；
第 10 条作废的只是「无需改表结构」那半句，不要连带把「独立出库单」一起推翻。

## 未决事项

- **在途库存是否需要在余额上可见（2026-09-19 调拨波次提出）**。两步式调拨让货在途中
  **不属于任何仓库的余额**，因此「全仓总库存」在在途期间会暂时减少。当前只在单据上可见
  （调拨单状态 = 在途）。三种可能的收敛方式：① 引入一个虚拟「在途仓」并给它余额行；
  ② 在库存报表里增加「在途量」列（由调拨单聚合，不进余额表）；③ 保持现状，靠调拨单查询。
  在裁决前，**对账时必须把在途调拨单算进去**，否则总库存会对不上。
- **库存预留的触发点（2026-09-19 提出）**。预留能力（`InventoryReservationService`）已就绪，
  但**不能挂在销售订单确认上**：本业务的链路是「客户下单 → 订单 → 确认 → 聚合 → 采购需求 →
  采购单 → 收货 → 库存」，**库存在订单确认之后才产生**；在确认时校验可用量等于要求
  「货先到才能接单」，与「先接单、再采购」的设计前提冲突。
  （实测：把预留挂到确认上，W1–W6 的集成测试有 82 个用例报 `41011 可用库存不足`。）
  候选触发点：分拣/发货环节（那时货已到）、独立的「预留」操作、或收货后对已有库存自动预留。
  **现状（2026-09-25 更新）**：触发点仍是订单上的显式「预留库存」动作（菜单 620），未改为任何自动时机；
