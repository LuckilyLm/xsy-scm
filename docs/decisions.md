## 产品范围与最小交付原则（2026-10-19）

- 当前业务范围以 [原始 13 模块、44 条功能描述](requirements/产品功能需求基线.md)和[负责人已确认口径](requirements/2026-09-09-负责人确认口径.md)为准；描述模糊不等于授权实现参考产品的全部功能。蔬东坡仅作常用操作入口与交互参考。
- 同一模块先完成最小可用的增删改查、业务动作、状态查看及必要打印/导出，优先验证已有源码；只有现有操作不能满足原始文字时才补最小缺口，不从每个技术事实自动衍生新工作台、新权限模型或新 Flyway。
- 仓库、财务、权限、金额/数量、事务、必要数据库约束继续保留严格正确性；不得以“简化”为名跳过防重复入账、数据范围或账本守恒。
- 当前不自动推进 V159/V160 逐码出库/退回、混批拆包、复杂召回、EPCIS 和消费者公开溯源平台等扩展。V151～V158 既有数据结构与历史事实保留；若基础扫码确实无法满足业务演示，需先确定扫码对象、最小展示字段及最短流程，再评估是否需要进一步实现。
- 原始需求未决定的审批层级、参数阈值、全自动流程等，允许优先参考成熟产品的普通人工确认路径；涉及是否扣账、是否授权外部人员、是否对外公开数据等重大边界仍须获得明确确认。当前待办见 [MVP 收敛计划](next-development-plan.md)。

## 客户确认需求（2026-10-27）阶段一

- 商品销售单位缺省为“斤”：新建表单、服务端表单默认值与商品导入同一口径；显式提交空单位仍按校验失败处理，历史商品不回写。
- 客户分类、供应商分类是各自独立的业务分类（蔬菜/蛋/肉），不与客户类型、供应商类型混用；分类引用只做筛选和展示，不改变价格或结算口径。
- 最近采购价只作录单参考，按采购员数据范围读取，不写回订单、不参与当前定价。采购单位与销售单位不同且没有已配置的换算关系时，不直接当销售单位成本使用，也不做“售价低于采购价”的高低判断。
- 智能建议价 `PURCHASE_COST_LOSS_TAX_MARKUP` 以销售单位成本为基数：最近采购价能换算时优先，否则回退仓库加权平均成本；损耗率、税率缺失或越界时整行未定价，不以 0 兜底。
- 对账单打印使用已冻结的对账单版本，打印前按当前数据范围重新校验；客户专属模板只在“未显式选择模板”时生效，解析顺序为显式模板 → 客户绑定 → 类型默认模板。

## 销售订单导入（客户送货单版式，2026-10-27）

- 只保留客户送货单模板，旧的 12 列通用模板与行级导入结构一并下线；模板随后端 JAR 发布，下载入口与解析规则必须同源。
- 一张送货单生成一张订单。收货单位与日期取自表头上方的标签行，明细从表头下一行起读，遇到「合计」或签字栏结束；多工作表、模板外列、错误单元格、以及除销售金额外的公式均整批拒绝，避免漏单或读错值。
- 收货单位按客户名称精确匹配有效客户；重名或不存在时整批拒绝，不做模糊匹配或自动建档。收货人、电话、地址取客户档案，档案缺项即拒绝导入，导入行不能覆盖。
- 商品按「商品名称 + 规格 + 单位」匹配商品档案：规格为空时要求该商品名称只对应一个规格，单位必须等于销售单位。行内实数量即下单数量；销售金额只用于核对（实数量 × 销售单价，两位四舍五入），不参与下单金额。
- 销售单价视为人工定价：导入账号必须具备订单改价权限，否则含单价的送货单整批拒绝；改价原因由服务端统一记为「送货单导入」，不采信表格内容。单价留空时按系统定价，系统无可用价格则拒绝。
- 送货单日期作为期望送货日期，按 Asia/Shanghai 当日零点解释；行备注去重汇总后写入订单备注，超过 500 字符整批拒绝。

## 待确认订单改单（2026-10-27）

- 可改单状态放宽为草稿与待确认。待确认订单只有在没有支付意图、应收、库存预留、出库或分拣任务时才允许改单；一旦存在这些事实即失败关闭，避免改单与已发生的资金、库存事实脱节。
- 改单不重新定价：未改动的非人工改价行沿用提交时的报价并重新锁定，新增或改价行按表单值锁定；需要按最新价格重算仍走“批量核价”并留痕。标品实数量随下单量同步，非标品的称重结果不因改单被覆盖。
- 订单状态保持待确认，不回到草稿；改单记 `UPDATE` 操作日志。

## 订单锁单与发车后改单（2026-10-27）

- 锁单不新增订单状态：订单仍是已确认，只写 `locked_flag`、`locked_at`、`locked_by`、`lock_reason`、`auto_lock_at`，避免配送候选、商城展示、采购需求与既有状态机全部重判一个新状态。
- 发车出库时在订单上记 `dispatched_at`，7 天自动锁单从这一刻起算，不看配送履约状态（履约状态会被签收、异常等后续动作改写，反推不出发车时长）。
- 改单资格统一由后端判定：草稿、待确认照旧；已确认未发车、未锁的正常改单；已发车需要 `scm:order:edit-after-dispatch`，已锁单需要 `scm:order:edit-locked`。列表与详情的 `editable`/`editBlockedReason` 由后端给出，前端不自己拼状态与权限。
- 锁单与解锁是两个权限（`scm:order:lock` / `scm:order:unlock`），默认授予财务与管理员，避免同一角色既能锁又能随手解锁。手动锁单原因码固定为 `MANUAL`，自动锁单为 `AUTO_7_DAYS`，操作人手写原因记在操作日志。
- 已确认订单改单沿用行上已有的报价重新锁定，并按实际数量重算结算金额；非标品的称重实数量不从改单表单覆盖，人工实数量原因一并保留（数据库约束要求）。已冻结优惠的订单不允许直接改单，需要取消重下或加单；已分拣或已出库的订单不允许增删商品，需称重的新增商品也不允许直接加进已确认订单，统一走加单。
- 发车后改单单独记 `EDIT_AFTER_DISPATCH` 操作日志，锁单/解锁/自动锁单分别记 `LOCK`/`UNLOCK`/`AUTO_LOCK`。

## 称重实发量回写订单（2026-10-27）

- 分拣录入（手工或电子秤确认，两条路径都经 `SortingTaskService.enter`）把非标品的实称量回写到已确认订单行，同时重算行结算额与订单结算合计；签收应收按实发量 × 锁定单价生成，称多少就该结多少。
- 回写只发生在「已确认、未发车、需称重」三条件同时成立时：待确认订单的实发量由销售手工录入，标品实发量恒等于下单量，发车后改实发量会与已出库的分拣记录脱节。回写与分拣录入同一事务。
- 称出 0 不回写：数据库要求实发量大于 0，未交货少结的部分走退货或红字，不把订单行改成 0。
- 手工修改实发量放宽到已确认订单：已发车直接拒绝（40917），已锁单需要「锁单后改单」权限；修改后同步重算结算额并记 `ACTUAL_QUANTITY` 日志。

## 非标行先确认后称重（2026-10-28）

- 非标品允许在未录实重的情况下确认订单：实发量保持为空，行结算额与订单结算合计按**订购量 × 锁定单价暂计**，称重后由实际值覆盖。理由：现场是先确认订单、分拣时秤端才出实际重量，要求确认前先填估计实重等于让销售替秤报数。
- 标品仍必须带实发量确认；标品实发量恒等于下单量，不经过称重。
- 分拣计划量取「实发量有值且大于 0 就取实发量，否则取订购量」。建分拣任务不得因为实发量为空被拦，建单也不得改写订单实发量。
- 称重完成后由 `OrderActualQuantitySyncService` 回写实发量并重算结算额；应收按实发量生成，暂计只影响确认时的预估金额与授信检查。
- 授信检查对未称重非标行同样按订购量估算，与确认口径一致，不另立一套估值规则。
- 「先按订单做计划」的环节统一取**计划数量**（`PlannedQuantity`：实发量 > 0 就取实发量，否则取订购量）：授信、分拣计划量、采购需求生成与汇总预览、销售报表成交数量。采购 14:00 备货时还没到 20:00 的称重，采购需求必须按订购量生成，否则整批订单买不到货。
- 退货按已发运数量校验，未称重的行不能退（`ORDER_RETURN_QUANTITY_EXCEEDED`）：退货是对已发事实的红字，不是对计划量。

## 商品行备注（2026-10-28）

- 行备注属于商品行（去皮、切段、分袋），随行打印到客户分拣单/送货单；整单备注另存，两者不能互相顶替。
- Excel 导入与整单粘贴逐行保留备注，不汇总成整单备注；送货单导入不再把备注写到订单头。备注上限 200 字符（迁移 V211）。
- 前端录单明细表、订单详情、粘贴预览都按行展示与回填备注。

## 订单、对账与采购边界修正（2026-10-28）

- 整单粘贴预览必须落客户数据范围：越权客户直接拒绝（403），不能只返回匹配结果，否则可以用预览读别人的协议价。
- 对账单「包含过账」需要 `scm:finance:posting:query`：没有权限时勾选被拒，不勾选照常出单，避免从普通对账入口读到过账单据。
- 采购自动补价必须核对计价单位：只取同一 SKU、同一采购单位的最近已提交价；没有同单位参考价就保持待定价，不拿公斤价当斤价。
- 采购到期自动锁单前先在同一轮跑一次自动补价（各自独立 try/catch），避免锁单抢先把还能回填的待定价单锁死。

## 商城微信支付范围（2026-10-27 确认）

- 小程序不要求支持微信支付：客户只需下单生成订单并同步到后台，本次不做微信支付接入，`ScmPaymentProviderEnum.WECHAT` 继续只作占位，不据此新增支付渠道、回调或对账实现。
- 下单仍沿用现有结算方式（账期、余额、货到付款），是否可选由授信、余额与客户档案开关决定；因此某客户下不了单时先核对这三项配置，不视为需要接入微信支付。
- 若后续客户要求“无需任何结算方式即可下单”，再按新增结算方式的正式需求评估，不在此结论下自行扩展。

## 2026-10-28 客户现场确认

现场事实与纸面单据样式见 [2026-10-28 客户现场确认](requirements/2026-10-28-客户现场确认.md)。以下为当前有效规则，编号用于后续实现和评审引用。

- **D-1028-01 订单整单口径**：一张客户送货单对应一张销售订单，一个客户单头下多行商品；不按商品逐行建单。订单录入、整单粘贴、客户分拣单、客户送货单均以客户公司为整单单位。
- **D-1028-02 实称量唯一口径**：分拣实称量（手工录入或电子秤确认，均经 `SortingTaskService.enter`）是实发数量和结算金额的唯一来源；订单下单量不因超发自动修改。分拣单的实数量列留空供现场手写/核对，送货单读取订单当前实数量。
- **D-1028-03 20:00 打印**：客户分拣单（无价格、无金额、无合计）与客户送货单（含价格、实数量、金额合计、双方签字）是两种独立单据，均按客户绑定模板；按配送日期或线路批量打印当天全部客户，不设 10 单上限。线路级发货单继续只给司机，不合并。
- **D-1028-04 负库存范围**：负库存只按仓库级开关 `allow_negative_stock` 放行，且只影响销售出库 `SALES_OUT`；盘点、损溢、调拨、转换、赠品出库不受开关影响。不做虚拟库存或第二套台账，负库存只作为“货已发、单未入”的临时状态。现场按单仓运行，默认仓库为“鲜蔬源仓库”，该仓默认开启负库存。
- **D-1028-05 负库存单位与成本**：负库存余额的记账单位取显式出库单位；无显式单位时取该规格销售单位。负数量期间移动平均不参与加权：旧量小于等于 0 时入库直接采用本次入库价，新量小于等于 0 时保留原均价；已出库流水不追改。月末以负库存损耗估算报表收口，报表只读，不自动生成报损单。
- **D-1028-06 采购价窗口**：采购价允许在收货确认前补录，最多 7 天，窗口从采购单提交时间起算；超期由定时任务按最近一次已提交采购价回填并锁定，无历史价时保持待定价并提示。收货确认时任一行仍待定价则拒绝。已确认收货后的采购价不改库存成本，另立“采购成本更正”需求。
- **D-1028-07 采购锁单**：采购单支持人工锁单和提交后 7 天自动锁单；锁单不改变采购状态，只阻止补价/改价，收货仍可继续。锁后改价需要专门权限并写价格审计。锁单/解锁是两个权限。
- **D-1028-08 收款核销两模式**：支持自动 FIFO（按账单日期、单据 ID 顺序，只用收款剩余额逐笔分配，不超额）和手工选择两种模式；自动核销可先预览，单次目标数有上限，未分配余额留在收款单。两种模式共用同一分配核心和幂等键，不新建核销表。
- **D-1028-09 抹零**：抹零建模为 `WAIVER` 来源的核销事实，冲减应收未结额，不修改应收原始金额；更正追加 `REVERSE` 核销行并保留原记录，不删除历史。抹零只作用于正常应收，不冲红字/退款；对账单单独列示抹零，通用收款反向不得把 WAIVER 当收款反转。
- **D-1028-10 电子秤单位**：现场秤为内置 Windows 10 的 SH2100-T15 触摸终端，现有 .NET 秤端可直接安装，不需要另配主机；打印走同一台机器的 Windows 打印机。服务端保持“设备单位 = 销售单位”的硬校验，不做隐式换算；同一物理量纲的显式换算（kg↔斤）必须记录原始值、换算因子和业务值，件/包/箱禁止与重量换算。P0 优先现场把秤切到市斤（`sj`）；若只能输出 kg，按 1 kg = 2 斤显式换算。
- **D-1028-11 单据列顺序**：订单录入、客户分拣单、客户送货单共用列顺序：序号、商品名称、规格、单位、数量、实数量、单价（仅录入/送货单）、金额（仅录入/送货单）、备注。品牌列不实现；行备注不得用订单备注冒充。
- **D-1028-12 本轮不做**：过账/AB 特殊单据、自定义财务报表字段、检测报告手机端采集、批次/包装码深化、采购收货后成本回冲、自动接单截止与强制分批、超发容差阈值。以上均需另立需求，不在 P0 第一批顺带实现。独立退货单已按 D-1028-15 单独立项。
- **D-1028-13 单仓口径**：客户没有独立仓库流程，采购后直接分拣配送、不做入库；**仓库与分拣在同一地点**，系统只维护一个本地“鲜蔬源仓库”，订单、分拣、出库、库存都落在这个仓。客户没有配送点，分拣完成后由司机到仓库取货，因此不存在“一仓多点”或多仓调拨。新建/存量数据在一次部署中收敛为该仓，界面不再要求普通录单人员选仓；管理员仍可维护仓库主数据，但不为此扩展多仓流程。
- **D-1028-14 定价口径**：现场按**协议价**运行，协议价**按客户分组**维护：每个分组至少一个客户，组内客户对同一商品的**同一计量单位**执行同一价格；同一商品同一单位的**不同规格共用一条价格**，不按规格分别定价；跨单位（斤/箱/件）分别维护，不做隐式换算。分组与客户是个人/公司/集团类型无关，客户类型不参与定价。实际下单时仍可在订单行**对单个客户手动改价**（需原因，沿用既有改价留痕），这是分组价之上的例外而不是第二套价格。客户类型价与时价保留既有解析能力，但现场暂不使用，本轮不深化、不做界面引导、不纳入验收。取价优先级为**逐客协议价（个别例外）→ 客户分组价 → 客户类型价 → 时价 → 市场价**；停用分组不参与取价。分组至少一个客户由应用层校验；删除分组先把客户移出分组再软删除，历史价格保留在变更历史中。
- **D-1028-15 独立退货单**：客户退回来的货找不到原单时，允许直接按「客户 + 商品明细」建退货单，不关联销售订单。
  - 建单：明细按商品 SKU 选择，数量是本次申请退货的销售单位数量；退货单和明细都保存客户名称、商品名称与销售单位快照，列表和详情不再依赖原订单联接。
  - 取价：优先「该客户该商品该单位最近一次已确认成交价」；没有成交记录时走既有取价链（逐客协议价 → 客户分组价 → 客户类型价 → 时价 → 市场价）；仍无可用价格必须人工填价并填写原因。价格来源随行保存（最近成交 / 定价链来源 / 人工改价），审批时不再重新取价。
  - 入库：退回仓库由实物接收时指定；不绑定原出库行、不绑批次。库存单位取该仓该商品已有余额单位，没有余额时取商品销售单位；单位不一致且无换算关系时拒绝入库。入库成本取入库前该仓该商品的移动加权均价，没有余额按 0 计，不追溯原出库成本，也不改写历史出库流水。处置方式沿用入库存 / 报损。启用批次追踪的仓库因缺原出库行拒绝独立退货入库，需改走订单退货。
  - 财务：审批生成**客户级红字应收**——来源是这张独立退货单，`order_id` 与 `original_receivable_id` 均为空，客户与结算主体取客户档案。对账单把它作为负数事件冲减客户余额；账龄与核销按客户（含结算主体）先进先出抵减最早未结的正常应收，抵完为止，抵不完的部分保留为贷方余额。不修改原应收金额，不生成退款单（没有订单资金事实，多收的钱走客户预收或后续核销）。
  - 权限与日志：沿用现有退货查询/建单/审批/接收/驳回/撤销权限，不新增权限码。数据范围按客户负责业务员（`xsy_customer.seller_id`）落在订单业务员范围；操作日志允许挂在客户上，不再强制写订单号。

- **D-1028-16 过账特殊单据**：财务在系统里登记对外账目的**虚拟单据**，只留痕，不进正常业务流——不生成应收/应付、不参与核销、不改客户余额与账龄。`D-1028-12` 中「需另立需求」的过账项以本条立项。
  - 字段：过账单号（`PD` + 业务日 + 序号）、客户与结算主体快照、过账日期、过账金额（>0）、税点（0–100 的百分比，可空）、返款状态（未返款/部分返款/已返款）、备注。税点按纸质单据原样记录，**不据此计算税额**，系统不存 `tax_amount`。
  - 更正：过账表 append-only。登记错了走**作废**——追加一条作废事实（作废人、时间、原因必填），有效状态由「有没有作废行」推导，过账行本身不落 `status`。作废不可重复，作废后不可修改。
  - 修改：客户不可改（换客户等于换一张单，应作废后重新登记）；日期、金额、税点、返款状态、备注可改，改前改后都进操作日志（`POSTING_ADD / POSTING_UPDATE / POSTING_VOID`）。
  - 可见范围：页面只在财务目录下，菜单与权限只授超级管理员与 `SCM_FINANCE`；「隐藏」靠授权范围实现，不靠 `visible_flag` 对已授权的人隐藏入口。查询、登记、修改、作废各自独立权限码，导出沿用 `scm:finance:export`。数据范围按客户负责业务员（`xsy_customer.seller_id`）。
  - 对账：正式对账单可**选择**是否包含过账记录，默认不包含。包含时过账行进入明细时间线，但只带「过账金额」一列，应收/收款/核销/退款变动恒为 0，**不改变期初、期末净应收与未分配资金**；作废的过账不进对账单。`include_posting` 随冻结版本保存，打印与详情按同一口径读取。
  - 内部报表：过账列表本身就是完整的过账台账（日期、客户、返款状态、有效状态、单号/客户关键字），导出与列表同源，不另做一张口径可能不同的报表页。

## 工程边界

- SmartAdmin 负责认证、员工与组织、角色菜单权限、数据权限、日志、字典、文件、统一异常和后台 Layout；SCM 只实现供应链业务，不复制底座能力或旧版认证系统。
- Java 业务包使用 `com.xsy.scm`，依赖方向为 Controller → Service → Manager / Policy → DAO；跨域只读消费正式事实，不直接写其他业务域表。
- 新源码注释只说明代码本身看不出的约束，不写开发过程、测试统计或过期计划。UI 规则及代码质量约定见仓库根目录 `AGENTS.md` 与 `CONTRIBUTING.md`。
- PostgreSQL 是唯一正式数据库；不新增数据库外键。已应用的 Flyway migration 不得修改，数据库变更只追加新版本。

### 经营指标与可见范围

- 同名经营指标使用同一时间轴、状态和金额列；“今日销售额”按 `confirmed_at`、`CONFIRMED`、`settlement_total_amount`，创建轴须称“今日下单金额”；“今日采购额”按 `submitted_at`、已提交状态集合、`total_amount`，状态集合由采购枚举提供。
- 首页与大屏按业务归属和仓库授权相交收窄；报表保留页面权限与仓库范围策略。两种出口可以各有 SQL，但同名指标的业务口径应一致。若要统一报表与工作台的范围，须对整页查询单独作权限裁决。

## P0 基线收口裁决：角色模型、SCM 数据范围与 F0 附件收口

SCM 数据范围由 `ScmDataScopeService` 集中解析并显式传给 DAO。业务归属、仓库和操作人等范围按各自事实相交；用户筛选只能收窄，空范围失败关闭，扩权须由明确权限表达。读、写、下拉选项和幂等结果重放均重新检查当前对象范围；功能权限不能替代行级范围。SCM 不使用 SmartAdmin `@DataScope`。附件关系由通用 `support/file` 维护，业务对象授权决定读取权；服务端 URL 经 `FileService` 解析，商品图片只绑定 `public/` 文件。

- **商品图片导入（2026-10-24）**：批量导入不再要求文件名等于商品编码；上传后在预览表逐张（或批量）指定目标商品，服务端按「商品编码.jpg、商品编码-2.jpg…」生成展示名，存储 key 与其他商品图片引用不变。公开图片目录无论全局文件检测开关如何，都由后端按文件内容强制校验为 JPG/PNG/WebP/GIF/BMP（拒绝 SVG）；前端使用同一白名单提前拦截，单张上限沿用 `maxUploadFileSizeMb`（默认 20 MB）。

- **界面提示与操作层级（2026-10-24）**：`a-alert` 只用于错误、可操作的警告和瞬时状态（未保存、成功、定位锚点）；常驻解释性文案改为标题右侧或控件下方的 `.scm-note` 灰色小字，不做彩色胶囊条。状态在每个界面只出现一次：列表用状态列（或筛选器）帮助扫读和定位待办，详情在信息区用普通文字显示当前状态，动作条、标题旁和抽屉抬头不再重复贴状态；不同维度且都要看的状态（如在售状态与主档状态）可以并列，但同一状态不重复。详情页标题只放名称，状态与标签下沉为内容区的普通字段，不做标题旁的彩色标签；表格里的标签去描边，只保留淡色底与同色文字，避免一列状态看起来像一排按钮。同一区域只保留当前状态下真正要做的一个主按钮，其余次要动作收进「更多」；只剩下一个非危险次要动作时直接显示，不再点开只有一项的「更多」。破坏性动作不与其他按钮同权重平铺。表格横向滚动只固定右侧操作列，单号、余额等首屏字段不固定——多个冻结区会让滚动时出现被截断的空白带。侧栏 logo 区是 `fixed` 的，底色必须从侧栏继承（含 antd 的 `.ant-layout-sider-children` 包装层），不能透明也不能写死颜色，否则滚动菜单会从 logo 下面透出来；SCM 页和首页都要成立，不能只在外观层修。表单必须绑定稳定的 `:model` 对象：`reactive({字段})` 或固定的 `reactive` 模型，不能写 `:model="{ref}"`——后者每次渲染生成新快照，必填校验会读到空值。

- **两态字段用开关、详情走第一列（2026-10-29 负责人确认）**：只有两个取值的状态（供应商/仓库的启用与停用、商品的在售与下架）直接在该列用开关表达，不占操作列、也不放进「更多」；开关值由数据决定，确认框取消或请求失败时保持原状态，权限用 `hasPermission` 裁剪（`v-privilege` 对开关无效）。首列已是单号或名称详情入口的列表（客户、供应商、销售订单、采购单），「更多」里不再重复放「详情」；但入口列可以被列设置隐藏，因此当首列不在当前显示列里时，「更多」必须补回「详情」，不能让用户为了进详情先恢复列。开关按「目标状态」提交（由开关值决定），与当前状态相同的事件（键盘方向键会重复发 `change`）直接忽略，不能按当前状态取反，否则确认文案与实际结果相反。三态及以上（订单/采购状态、客户状态、优惠券生命周期）仍用状态标签与显式动作，不硬套开关。

- **后台视觉基调（2026-10-24）**：SCM 后台统一为「鲜蔬账台」外观：页底是极浅的菜叶灰，数据面纯白，结构用发丝线而不是卡片阴影；绿色只用于主操作、当前菜单和选中行。默认主题色改为园圃绿 `#15803D`（与客户侧商城同一支绿，白字对比度约 5:1）。表格表头不加底色、只用一条较深的发丝线；筛选条不再是一张独立白卡；详情页经营概览用主题淡色底。外观类只挂在 `business/scm/` 组件所在路由（`body.scm-module`），OA 与系统设置页保持 SmartAdmin 原貌；所有颜色取 `--scm-*` 变量，跟随用户切换主题色与夜间模式。

- **界面不展示实体编码（2026-10-24）**：客户、供应商、商品、商品规格、仓库、客户类型、活动、优惠券、模板、单位、标签、助记码等系统自动生成的编码属于内部标识，列表列、详情页信息区、选择器选项文案、卡片、确认弹窗和校验提示都不展示；页面之间通过 ID 传递，搜索框仍可按编码匹配。必须保留的是单据号（订单号、收货单号、付款单号等）、追溯码（分拣/包装码、批次号）、设备编码和税收分类编码。管理表单中由用户自定义的业务键（如优惠券编码、模板键）可以保留，因为它们是用户输入而非系统生成的展示负担。

2026-10-10 补充：客户写入和客户选择沿用当前客户负责人范围；余额人工更正与充值创建同时检查业务客户和结算主体。退款查询与支付意图查询同范围，幂等重放必须重新校验当前授权。在线充值以验签后的渠道成功事实为到账时点；同一次支付成功编排按渠道实收登记 Finance Receipt，并向创建时冻结的结算主体钱包追加唯一 CREDIT，重复回调和恢复重放不得重复记账。拒绝回调保留审计记录但不占用后续合法事件 ID。模拟支付和模拟回调仅供 `dev/test`，`pre/prod` 不注册模拟渠道。

商城资金接口只从登录会话确定当前业务客户，不接受客户端指定客户、结算主体或钱包账户。普通独立结算客户可见真实钱包余额；集团结算子客户及集团主体账号不展示共享钱包总额或集团授信总额。流水同时按当前客户与合法结算主体过滤，不下发账户主键、其他成员流水或内部更正原因。商城账单只展示当前客户拥有的正常应收，复用 Finance 净额口径；`creditLimit=0` 不解释为无限额度。

## P1 分拣管理裁决

分拣只写任务的已分拣数量，不回写订单数量或结算字段，不改库存、不生成出库。活动任务独占有效订单行；取消时释放明细，完成任务须为每条有效明细提交结果。重新打开须校验版本并保留数量与原因。配送候选订单须已确认且所有有效明细均被已完成任务覆盖。分拣员范围与仓库范围相交；打印只记录操作，不改任务状态。称重结果须由人工接受，一键处理不得替非标准品推断重量。

### 分次分拣与确认统计（2026-10-17）

- 分次人工记录是同一任务明细下追加的作业事实，必须有操作人、时间、数量、幂等键与行版本防重；未确认分次不回写分拣明细的 `sorted_quantity` / `result`，不参与配送资格、销售出库或财务事实。最终确认仍由已有明细录入命令显式执行，完成任务仍要求全部有效行已确认结果。
- 新记录按每次追加量累积；最终确认量若偏离事件累计量，须写原因并追加差额事件，原事件不删除。重开允许带原因调整已确认结果；跨人、跨仓和取消/完成后写入仍按既有权限与状态机拒绝。
- 只读“最终确认统计”只覆盖已完成任务，按最后确认人、仓库和销售单位分组；不将其误称为各参与者的劳动贡献或工资核算。分拣差异阈值和人员计件报酬没有业务定案，不能用页面默认数字代替裁决。

### 非标品电子秤接入边界（2026-10-15 待设备接口文档）

- 称重工作台从现有分拣任务中选择客户订单与商品规格，不新建另一套订单或分拣单。设备上报必须携带唯一事件键、设备编码、分拣任务和明细、原始重量、单位、稳定标记与采集时间；设备协议、连接方式与校准机制待厂家文档确定。
- 原始读数仅保存为设备事件。**人工接受稳定读数**后才复用 `SortingTaskService.enter` 写入已分拣量；非标品由操作员裁定 `NORMAL/SHORT/OUT_OF_STOCK/OVER`，非正常结果必须说明原因。上报端不得传入已分拣数量或直接触发订单、库存、财务变更。
- 接受读数要求设备单位与订单行冻结销售单位相同；尚未实现安全的单位换算，不允许把公斤、斤、件直接混用。历史上报事件的处理状态和操作者留痕，不允许通过再次上报覆盖原记录。
- 开发环境仅允许**前端本地只展示**模拟重量，不能形成设备事件或分拣事实。正式硬件认证、协议适配、设备绑定、实时推送、离线重连与采集容差阈值均需厂家接口文档及负责人确认后实施。

## P2 物流配送 L3 裁决

发车是销售出库的唯一生产入口，数量取已完成分拣结果；整条线路原子提交，任一订单不合格则整体拒绝。库存变更只经库存域命令，预留与出库在同一事务消费或释放。发车使用幂等键与线路版本，签收校验线路订单行版本和司机范围。签收只记录 `SIGNED` 或带原因的 `EXCEPTION`，不撤销出库；退货必须追加独立反向事实。打印不发车。当前路线地图只展示已确定停靠顺序；算路不可用时降级显示，不能改顺序、库存或线路状态。实时 GPS、部分签收和自动退款不在当前范围。

## P3 Finance R1 裁决

Finance 只读消费订单、采购、库存、配送和退货事实，不写这些业务表。财务记录是追加事实；更正追加反向记录，金额保持正数并由类型表达方向。自动应收、应付与触发业务事实同事务提交；收款登记不自动核销，冲正只允许在原事实未被核销使用时追加。订单、财务与库存不得形成第二套状态机。已确认退货不因红字应收余额不足而被阻断；退款付款须与完成的退款事实一致。

## 采购每日清单与快照

采购每日清单按 Asia/Shanghai 的采购单提交日统计，取前一自然日区间；纳入已提交、部分收货、已收货和短收关单，排除草稿、取消与删除数据。结果按商品、采购单位及采购单冻结的编码和名称分组，不跨单位求和；采购金额不代表财务应付。清单是生成时快照，重复生成不覆盖既有结果；后台任务使用 SmartAdmin 调度，查询与导出均按采购员和仓库授权范围相交。

采购订单行、收货、应付等历史快照保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。采购单位快照来自供应商商品关系，不得用商品销售单位替换；需求单位沿用销售订单行快照。采购单提交后不再回读供应商或商品主档；收货记录数量和重量，金额从采购行事实派生。

## 采购净需求、通知、打印与异常聚合

- 净采购按仓库、商品和单位分别计算，需求扣除同维度可用库存、有效在途未收数量及已有采购覆盖；单位之间不换算。计算只冻结输入、解释与建议，不改库存。生成需求引用同一冻结批次并具备幂等性；回看不得回表重算。
- 通知复用 SmartAdmin 站内信，不新增消息中心或外部渠道。库存预警按周期扫描 `NORMAL → LOW/HIGH`，异常持续期间不重复通知，恢复正常后再异常可重新通知；没有有效仓库授权接收人时不广播。消息跳转不授予数据访问权。
- 打印模板采用字段白名单约束的 JSON 模型，由服务端渲染；不允许任意 HTML、脚本或数据库字段。打印记录冻结模板与业务内容，重印读取原快照并按操作者当前权限重新过滤金额。打印和预览不触发提交、发车或分拣完成。
- 异常聚合只读现有分拣缺货/差异、订单实量差异、配送异常签收及退货/退款待处理和售后拒绝事实，不建工单状态机或自动补偿。分拣缺货由已记录的 `OUT_OF_STOCK` 结果识别；当前仓库库存只作附有记账单位的参考，不用于反推历史订单缺货，也不跨单位换算。筛选、列表、统计和导出共用事实口径与授权范围；处理仍回到源业务模块。退款单状态不等同于实际资金到账或返还。
- 换货按“先退货批准并完成实物接收，再建关联替换订单”执行；替换订单是独立草稿，按当前客户、地址、商品、定价、预留、配送及结算命令重新校验，不自动抵扣退货红字应收或退款。每张退货单最多关联一张替换订单，原订单与库存/财务事实不被改写。已出库订单的客户实收数量更正只追加带原销售单位、已出库基线、前后数量、原因和操作人的记录；不得超过正式实发量，不回写订单行、出库流水或财务，退货、补送、退款由人工分别走正式流程。

采购订单行、收货、应付等历史快照保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。业务状态变化追加或更新正式领域事实，报表快照不取代来源事实。

## 后续产品工作边界

- 收入以 Finance 正常应收事实确认；毛利成本取销售出库时冻结的库存流水单位成本，缺失时标记不完整，不用当前成本补算。退货成本只在实物验收回库后按原出库来源反向；可售回库与报损分别形成库存事实。
- 收入、出库成本和退货成本按各自事实发生时点统计，跨期不同步属于事件期毛利，不强行逐单配平。红字收入在实物接收前归为未分配仓库；接收后依原销售出库来源分摊。退货成本归属原销售出库仓，不按回库仓重新归属。
- 账期按冻结到期日计算。授信并发校验以服务端事实为准，额度为 0 表示未设金额上限，逾期仍可阻断；例外放行须有权限、原因和审计。集团关系冻结在单据与财务事实，不扩大数据范围。

- 客户与供应商对账区分债权债务、实际收付款、核销和未分配资金。冻结版本保存纳入的事实标识，后续迟录或反向更正生成新版本，不改旧快照；受限范围必须标记为部分范围，不得宣称是完整集团对账。

## 营销优惠生命周期、赠品与限时特价口径（2026-10-03 负责人确认）

本节补充固定优惠券、赠品与限时特价的状态及成本归属规则。

### 优惠券生命周期

```text
确认订单      AVAILABLE → RESERVED   （冻结优惠时占用）
正常签收      RESERVED  → USED       （与应收同一时点、同一事务）
异常签收      保持 RESERVED           （EXCEPTION 既不形成应收，也不算用掉）
部分/全额退款 保持 USED
现有订单取消  不处理券                （CONFIRMED 已是订单终态，cancel 碰不到 RESERVED）
未来撤销确认  RESERVED  → RELEASED   （当前无触发点，保留语义）
需要返券      重新 issue 一张新券，不复活旧券
```

- 券核销挂**正常签收**而不是退款：签收是订单级不可逆终态，也正是应收的形成时点，券「是否已被一笔真实成交使用过」与它对齐。
- **退款不恢复券**：退款反向的是金额（按冻结分摊），券回答的是权益是否已被使用过，两者不能混；允许 `USED → AVAILABLE` 会让「100 元订单用 20 元券、退款后券回来、再用于下一单」变成重复营销权益。若业务确需「全额退款返券」，另做重新发券（新实例），审计上才分得清「原券用掉了」与「补偿了一张新券」。
- `RELEASED` 是**历史终态**，不等于 `AVAILABLE`：它是「这张券被释放过」的痕迹。要把权益还给客户，应原券 `RELEASED` + 重新 `issue` 新券。
- 优惠券列表的累计张数按券实例统计：后台发放取 `ADMIN_ISSUE`，商城领取取 `MALL_CLAIM`，已使用取当前 `USED`（包含两种来源）。已知券让利只读已使用订单冻结快照的券优惠额，缺失快照单列数量，不把未知金额当作零。不按模板当前启停状态重算，也不把 `RESERVED` 算为已使用；当前没有时间窗口。

### 满赠（赠品）

- **不减订单收入**：赠品金额恒为 0，`FULL_GIFT` 的优惠额保持 0 是对的。
- **赠品必须走正式库存出库**，出库来源明确为促销赠品；赠品出库成本**计入该订单的履约成本**，因此销售毛利要扣掉赠品成本。
- **不把赠品塞成普通 `sales_order_item`**：那会污染采购需求、销售数量、销售额与客户购买商品分析。用独立冻结事实记录赠品（订单 / 活动 / SKU / 数量 / 单位 / 快照）。
- 赠品权益在**订单确认时冻结**（`order_promotion_gift`，快照不可变），出库、分拣、小票与成本归集都读它，不在各自环节重算活动规则。
- 门槛按**订单基础合计**判定，不按逐条作用后的剩余金额：同单另有满减不该把满赠门槛压没。
- **运行口径（2026-10-03 确认）**：赠品出库挂**发车**时点，与销售出库同一时点、同一仓库；赠品库存不足时**不阻断订单确认**，在出库时报错、由仓库补货后重试；赠品**进分拣清单与小票**（仓库照单备货），分拣不写回赠品数量。

### 限时特价

- **不改基础定价链**：协议价 → 客户类型价 → 市场价 保持不动，限时特价不参与这层的优先级竞争，也**不进 `PriceResolver`**。
- 它作为 Promotion 在**基础价之后**作用：`基础价解析 → 限时特价 → 满减/折扣 → 优惠券`。
- 冻结记录仍能回答「原基础价是多少、为什么卖这个价、按哪个活动哪一版、减了多少」：订单行金额仍是基础价口径，让利作为**独立事实**落 `order_discount.special_discount_amount` 与逐行分摊，**不把订单行的价格来源改成「限时活动」**。
- 保护规则：**限时特价只能把基础价往下压，不能抬高**（特价 ≥ 该行单价时让利为 0）。
- 分配口径：让利按**行**归集（`行基础金额 − 数量 × 特价`），不参与按金额比例分摊 —— 特价针对某个 SKU，摊到别的行上会让退款反向错行；同一行只让一次价（已被更靠前的特价命中过的行跳过），因此「按优先级顺序作用」在特价上依然成立，且每条活动记进快照的让利额之和恰好等于总让利。

## 微信小程序账号与退款分摊口径（2026-10-10 负责人确认）

- 下一单只允许延续当前选择的客户与配送仓，且客户收货信息从当前有效客户资料重取；若重取失败，清掉下一单的客户选择并要求重新选择。上一单的商品、数量、订单号、状态、版本、旧地址、人工改价、优惠、关联原单、补单原因、备注和锁定价格一律不可复制。每张订单仍走独立定价、下单、版本与幂等检查，不新增复制数据库命令。

## SDP-14 草稿订单批量核价边界（2026-10-17）

- 订单列表批量核价只接收当前列表已选中的 1～8 张草稿订单，只读请求逐单读取正式订单详情与客户定价预览，权限与负责人范围仍按正式订单和定价接口检查；报价仅是检查时点的参考，不锁价、不预留库存、不修改草稿订单。每张订单独立返回核价结果/失败原因，不因某一订单失败假装全部已核价。
- 人工改价行不被自动覆写；商品不可售或价格未知时阻止该单在批量核价窗口直接重算。若操作者逐单确认变更，必须具备 `scm:order:update` 与 `scm:pricing:resolve:query`，填写原因、核对最新草稿状态与订单版本，最终只走现有 `/scm/order/reprice` 由服务器再次定价、限制冻结事实并写操作日志。价格预览不能保证重算执行时金额不变，确认弹框必须说明这一点；不新增另一套价格写接口。
- 历史单复用为新单、订单草稿恢复此前已实现，不另建第二套复制命令。已确认订单的冻结价和结算事实绝不可通过此功能重写。

## SDP-08 查询与自定义导出列约束（2026-10-17）

- 个人常用筛选方案仅保存服务器允许的组合筛选谓词，不保存业务结果、日期、其它基本筛选、查询范围或用户的权限快照。按已认证操作人及业务页面双键隔离，每人每页最多20条，名称唯一，服务端创建时和读取后都重新按**当前**字段白名单验证，过期方案不得应用但允许本人删除。读写删除接口均要求页面查询权限，客户端不得提供操作人 ID 或数据库字段名。

- 商品、销售订单与采购分析的首批自定义导出列仅采用服务端声明的稳定字段键，字段名不参加 SQL 拼接；原业务查询、数据范围、成本可见性、行数上限和导出权限不得改变。自定义列只投影**已经由正式服务完成授权和业务过滤的结果**，不能再查一套宽松数据。
- 服务端元数据接口根据当前成本权限隐藏受限列；显式请求受限列时服务端再次拒绝。未传导出列参数保留原格式向后兼容；显式空列表、重复键、不认识的键、超过列数限额一律拒绝。
- 动态组合条件只支持服务端当前发布的字段、固定操作符和值类型；限8项，条件按 AND 收窄。条件映射到原业务查询 DTO，不用客户端传来的字段拼 SQL；与原有筛选对同一字段取不同值须拒绝，不得静默覆盖。只在明确试点的商品查询、销售订单明细和采购按商品查询/导出内生效，其它报表维度的查询语义不随之改变。

## SDP-07 内部采购询价实施边界（2026-10-17）

- 询价只从状态为 `READY` 的净需求计算批次派生；与原批次生成需求命令共用批次行锁，禁止对 `GENERATED` 批次再创建询价。按同批次商品规格与需求单位归并冻结建议量；任一归并来源行已关联当前有效采购需求则整组不可再建询价，不另算实时库存、不建立第二套需求账本。
- 权限同时受采购员归属和仓库范围约束，询价创建、报价登记、确认分别授权；员工代录报价只证明本系统登记事实，**不等于供应商登录提交或电子签署**。供应商端身份体系、安全认证和外部接口需要独立裁决。
- 报价行只追加修订版本，保留报价人、供应商、单位、价格和有效期；同供应商只对比最新有效修订，新增供应商报价必须在询价接收截止前；采购员选用报价可在接收截止后进行，但必须保证询价未被选用、版本一致、所选最新报价仍在有效期内，且供应商采购关系仍有效。询价单一次只能确认一条报价，保存不可变报价 ID，由数据库触发器校验报价属于该询价，不新增业务外键，也不改原报价。
- 报价单价不自动作为采购订单成交价。把已确认报价转为采购单并冻结价格来源、跨单位换算、供应商端确认流程另行实施；在正式人工确认采购单前不触碰订单、库存、资金事实。

## 采购收货批次与批次库存（2026-10-18）

- 批次追踪按**仓库开关**启用：只有新建且尚无库存的仓库可以开启，开启后不可关闭；存量仓库保持关闭，不做存量回填。开关只在创建时设置，编辑态只读。
- 批次仓的采购收货**必须逐行登记批次**，非批次仓不录批次且行为不变。收货行下挂的批次数量之和必须等于本次声明收货量，由数据库恒等式与命令校验双重保证。
- 内部批次号由系统发号（`LOT` + 北京时间业务日 + 全局序列），不进入前端编辑控件；**来源生产批号**由供应商或现场提供、原样保存、允许为空，不得冒充系统批次号，也不要求唯一。
- 批次是独立子账：`xsy_inventory_lot_balance` 与仓库 SKU 总账并存，不把总账按批次拆行。不变量为「同一仓库同一商品同一单位下，各批次余额之和等于总账余额」。
- 批次流水只追加，禁止改写或删除；更正只能追加补偿流水，沿用库存流水既有约定。
- 销售出库与赠品出库按**先进先出**自动分摊批次，现场不选批次；每条出库流水按批次拆成多条子账流水，子账数量之和等于总账流水数量。
- 销售退货（含拒收退回）必须**回原出库批次**：按原出库流水的批次关联回写，找不到原批次时拒绝并给出明确错误，不猜批次、不新建批次。
- 批次仓的盘点、调拨、损溢、规格转换在二期之前**一律拒绝**，避免出现没有批次语义的库存动作；非批次仓不受影响。
- 批次**不独立核算成本**：批次余额只记数量与单位，成本仍按仓库 + 商品规格的平均成本；批次毛利与批次成本另行裁决。
- 批次仓的记账单位仍是采购收货时的单位快照，不做单位换算，与现有「同一仓库同一商品只允许一个记账单位」的规则一致。
- 新增「批次库存」查询能力，权限只授给已具备库存查询权限的角色；批次来源批号按现有数据范围过滤，不因批次新增跨仓可见性。
- 后续 V152～V158 已实现 L2 独立包装码身份、分拣绑定、打印、作废及更正保护：`unit_code` 不透明、全局唯一、永不复用、不嵌日期，且**一码一批**不做混批；批次码不冒充逐包装码。仍需补逐码正式出库/退回与现场拆包规则。

## V158 包装码出库与并发保护（2026-10-19）

- 更正申请与批准均按原绑定的销售订单行查询**正式确认出库**；已经出库的订单行不允许解绑重绑（41525），已出库分拣行也不能事后补绑新码（41526）。出库后纠错必须走退货、售后或将来专门的单元级逆向补偿，不能通过更正单把客户已收实物的码释放。由于尚无单元级正式出库关联，以整个订单行为拦截粒度是有意保守，部分出库后也不能解绑该行的码。
- V158 不篡改 V157：数据库有效绑定触发器先 `FOR UPDATE` 锁包装码，确保直接并发 INSERT 也串行；正式出库行插入、出库单转为 `CONFIRMED` 与绑定/解绑触发器都锁同一 `xsy_sales_order_item` 行，然后复核正式出库状态；解绑触发器还必须检查申请单与单元/原绑定一致、申请待审批且非本人批准；作废状态变更触发器禁止直接将有有效绑定的码变为 VOID，避免「审批时无出库、提交时已经发车」和手工 SQL 绕过服务层。
- **尚未有逐码出库事实，批次级净出库不能证明某个已发码包装离场。** 发码额度改为「该批次累计发码量（包括已作废码）＋本次 ≤ 批次当前余额」，不再用批次净出库推测释放额度。这会让部分发货后的后续发码变得严格甚至无法继续；这是避免重复贴码的主动失败关闭，而不是完整的发码额度生命周期。未来必须先建设单元级出库和退回关联，才能凭逐码离场事实安全地释放额度。

## 包装码（一物一码）实施边界（2026-10-19）

- 包装码是**贴在实物上的身份**，与批次严格分层：**一码一批、不做混批**，一个批次可以有多个包装码；批次码不冒充逐包装码。
- `unit_code` 由系统发号、**不透明**（Base32 序号，前缀 U）、不嵌日期与业务含义、全局唯一、**永不复用**；作废只追加事件，原码保留。
- 发码总量受批次当前余额约束：包装码描述已经存在的实物，不能在库存之外凭空造出实物身份（超限 41504）。
- 一期发码入口是「包装码」页按批次发码（供应商预包装场景）；散装/称重品在分拣装箱时发码属于下一步，需要分拣域提供装箱事实后再接。
- 回放只读，回答「这个码从哪来、到哪去」：单元 → 批次 → 收货来源（收货单 / 供应商 / 确认时间）→ 出库去向（出库单号 / 时间 / 数量）。
- **V153 后客户维度可来自分拣绑定**：仅证明扫描绑定时承诺给哪张订单/哪个客户，不等于正式发车或签收；出库流水仍按批次分摊，不能从批次出库倒推“这枚码已经卖给了谁”。
- 包装码标签复用 `scm/print` 域的受控模板与冻结记录，新增 `TRACE_UNIT` 单据类型；默认模板用 80mm 热敏纸，只放码、批次、商品、包装量与绑定后的客户/订单号，不含价格与成本。
- 标签可以先贴后绑：未绑定时客户与订单号留空，标签仍表示实物身份；打印不代表已分配给任何客户。
- 包装码可以作废，但**只能作废未绑定的码**：已绑定的码代表一件承诺给客户的实物，作废会让回放自相矛盾，现场应先走退货或更正流程（41512）。
- 作废只把码标记为 VOID 并追加一条 VOID 事件，原码保留、永不复用；重复作废被拒（41513）。
- 分拣扫码绑定把包装码绑到**分拣任务行**而不是出库行：扫码发生在装箱现场，分拣行上已有客户与订单快照，出库单要到发车才生成。
- **一码一物，同一时刻至多一条有效绑定**：绑定行不可 UPDATE/DELETE；V157 更正单经他人审批后仅追加解绑事实，可在**原订单行尚未正式出库前**重新绑定，历史客户和原绑定不删除。V158 数据库锁与触发器确保直接 SQL 也不能并发双绑或出库后改绑。
- **绑定后不可直接作废**（V155 起）：已绑定的码代表一件已承诺给客户的实物，作废会让回放自相矛盾（41512）。
  绑错的处理走**更正单**（V157）：申请 → 他人审批 → 追加解绑事实（`xsy_trace_unit_unbind` + `UNBIND` 事件），
  仅在原绑定订单行未正式出库时，批准后该码回到可绑定状态、可以重新绑到正确的分拣行；出库后须走正式退货/售后补偿。申请与审批**不得是同一人**（41522），
  一条绑定只能被批准撤销一次；原绑定行与解绑事实都留在账上，**不提供无痕解绑**。
- 更正后「同一时刻只有一条有效绑定」由触发器 `xsy_assert_unit_bindable` 保证（V157 去掉了 `UNIQUE(unit_id)`），
  这样解绑—重绑才成立；分拣行的已绑数量只累计**有效**绑定。
- 绑定校验顺序即语义：码存在且有效 → 未绑过 → 商品规格与批次一致 → 该分拣行绑定总量不超过实拣量（41507–41509）。
- 回放的客户维度只来自**分拣绑定**，不由出库批次分摊倒推：批次是共同来源，不是某一袋的归属。
- 采购单分享用**令牌**授权，不用账号：令牌 32 字节随机、只存 SHA-256、有有效期（默认 7 天）、可撤销；
  一张采购单同一时刻只保留一条有效链接，重新分享会让旧码当场失效。
- 手机端回填**只追加事实**（`xsy_purchase_share_feedback`），不直接改写采购单：现场误填不能悄悄改掉已提交的单据，
  采用与否由后台人工确认。
- 集团共享结算的授权开关 `xsy_customer.shared_settlement_enabled` **默认关闭**，只有结算模式为 `GROUP` 的集团主体能置真；
  打开后允许后台为子客户执行集团钱包扣款，额度只看钱包余额，不叠加集团授信；小程序不提供资金写入口。
  首次扣款必须在结算主体行锁内复核当前开关，与关闭授权串行；已经成立的扣款幂等回放不再次扣钱，也不因开关关闭而伪装失败。
- 子客户仍然看不到集团的钱包余额与授信总额：共享结算的可选项只给「可用/不可用」，不给金额。

- 价格来源优先级固定为：客户协议价 → 客户类型价 → 时价 → 市场价。时价面向所有人，不能顶掉逐客约定与分组约定。
- 时价是**商品规格级**、按时间段生效，区间半开 `[start_at, end_at)`；同一规格的区间不允许重叠，
  重叠会让「现在按哪条算」没有唯一答案。首尾相接不算重叠。
- 时价只影响**下单与预览**的价格解析；已锁定价格的订单行不因时价变动而改价，来源记录为 `TIME_PRICE`。

- 客户推广码属于**客户**，归属业务员取该客户当时的 `seller_id` 快照：客户换业务员后，历史扫码仍能说清当时是谁的线索。
- 扫码只**记录来源**，不改任何归属；把人挂到业务员名下发生在后台建客户时（业务员按最近一次扫码归属预填，管理员可改）。
- 一个客户同一时刻只有一条有效推广码，重新生成让旧码立即失效；扫码记录只追加，不修改也不删除。

- 回填明细必须属于该采购单：令牌能看到的范围就是它能写的范围，不允许跨单写入。

- 回放里的「批次相关出库」是**批次级**事实：它能证明这一批货去了哪几张出库单，**不能**证明当前这一袋已经出库；
  单元级出库要等分拣/发车按包装码绑定出库行之后再补，界面不得把两者混为一谈。

### 一物一码扫码溯源与称重打通（2026-10-22）

- 扫码页面向客户与监管，凭据是标签上的 `public_token`，不是 `unit_code`：`unit_code` 由自增序列发号，
  相邻码可推算，不能当公开访问的凭据。`unit_code` 仍是员工侧主键。
- 公开页只返回脱敏字段（客户名、订单号），不返回内部主键、操作人与批次级出库明细；每次查询写
  `xsy_trace_public_query` 并按 IP 与令牌限流，用于发现枚举爬取。
- 包装码的批次归属只存在于发码环节，由现场选定（默认先进先出）。不给分拣行加 `lot_id`，也不建批次消耗账本：
  销售出库本就不按批次扣减，再建一张就是第二套账，且等于引入混批/拆包谱系。
  代价是贴错批次系统不拦，靠标签印批次号人工核对，风险显式接受。
- 重量写在包装码主体侧（一码一重），关联方向是 `unit.weighing_event_id → xsy_sorting_scale_event.id`：
  称重事件是追加的设备事实，不塞业务绑定列。
- 称重筐只发码、不立即绑定：`bind` 校验「已绑定量 + 本码数量 ≤ 实拣量」，而实拣量要等集合完成才写入，
  逐筐绑定会在第一筐就超量。绑定在明细完成时整批建立，装不下的码留在未绑定，不中断分拣完成——
  分拣完成是业务事实，追溯绑定是它的附属结果。
- 商品资质保留 `PRODUCT_QUALIFICATION` 与 `scm:trace:file:manage`；旧 `LOT_INSPECTION` 关系保留供内部查阅，
  不自动转换为已发布报告，也不再通过公开扫码接口展示或下载。出入库不挂附件，只在扫码页展示记录。
- 批次检测报告使用 `xsy_trace_inspection_report`，附件复用 `t_file_relation` 的 `TRACE_INSPECTION_REPORT`，
  `biz_id` 为报告 ID。仅关联已有已确认收货事实的真实批次，不修改采购、库存、分拣或包装码事实。
  管理权限为 `scm:trace:inspection:manage`，查看沿用包装码查看权或报告管理权，并叠加批次所属仓库范围。
- 报告状态为 `DRAFT / PUBLISHED / WITHDRAWN`；结论为 `QUALIFIED / UNQUALIFIED / UNDETERMINED`。
  按既有 SCM 枚举约定，Java 枚举名、数据库 CHECK 与接口字符串一致，中文由枚举 `desc` 与前端 SmartEnum 映射；
  未知值不按合格处理。过期是按有效期即时计算的展示状态，不增加生命周期枚举。
- 草稿可编辑，批次不能改绑；发布时必须有可读取的私有 PDF/图片，最多20个、单个不超过20MB。
  报告编号唯一；发布后内容冻结，仅可撤回，撤回记录保留且不重新发布。更正通过新报告记录处理。
  保存、发布、撤回在同一业务事务内追加操作人和时间，版本号与行锁拒绝旧页面覆盖。
- 公开查询仅返回当前包装码所属批次的已发布报告；不合格、未判定照实展示，不能显示合格标识。
  到期时间可空，非空时按时间点判断；录入与日期边界使用北京时间。过期报告保留检测信息及过期提示，
  不提供附件；撤回报告、草稿和作废包装码均不公开报告附件。商品资质不构成检测合格依据。
  公开页面及下载使用同一报告投影、禁止缓存；报告文件即使同时挂为商品资质，也不能从资质入口绕过发布控制。
- 标签二维码由前端生成，后端不引二维码库；链接规则只在 `TracePublicLinkBuilder` 定义一次，
  后台打印与秤端打标取同一个值。未配置 `scm.trace.public-base-url` 时标签只印码不印二维码。

### 设备请求与回填入口（2026-10-23）

- 设备心跳、读取本机配置仅校验设备身份，不建立员工权限；称重、完成和发码仍取设备仓库、当前员工范围、受指派人和有效租约的交集。员工授权失效与设备凭证失效分开处理，前者不能停用设备凭证。
- Windows 正式包装标签在本筐记录后、商品集合完成前由人工选择来源批次并请求平台发码；只能使用平台返回的包装码、批次与公开链接。打印请求先冻结快照，未知结果保留原操作号，补打追加尝试并检查平台码仍有效；本地演练凭条的 eventKey 不是正式包装身份。
- 采购现场回填由后台按原采购单归属分页查看，不从最近一条推断累计收货量；操作员核对后通过既有收货草稿和确认命令处理，不自动更改采购、库存与财务事实。
- 商品详情以“购物车数量”明确表达绝对数量编辑；服务端在行锁内插入或替换并验证最终数量。普通显式累加、快捷加购和绝对数量替换不得混用。

### 列表每页条数（2026-10-25）

- SCM 列表的下拉只给 `10 / 20`，默认 20；报表、分拣、客户详情的明细列表放宽到 `20 / 50`。不再提供 100 及以上，避免一次拉取过多数据拖慢翻页。
- 选项由 `src/constants/business/scm/pagination-const.ts` 统一维护，页面不写死数组；每页条数下拉加宽到能完整显示「20 条/页」。
- 后端分页参数仍按各接口自身上限校验（通用上限 500，排序 100 等），本规则先约束界面入口；内部取数（下拉选项、打印、日志）不受此限。

### 经营概览指标区（2026-10-25）

- 区间统计与当前时点共用一块底板，段标题带主色小标记；指标卡只放标签和数值，说明文字不再挂在个别卡片里（原先「已提交采购单 N 张」让两张卡显得格格不入）。
- 「已提交采购单数」独立成卡，与「已提交采购金额」并列；后端概览 SQL 的别名为 `submittedPurchaseOrderCount`，保证该字段能映射到 VO。
- 当前时点只有一条指标，用整行浅色横条显示标签、金额和「截至…｜有账面库存…行」，不再用一张孤立窄卡占用半行。

### 异常提示与装修存储自愈（2026-10-25）

- 未处理异常只写日志：接口统一返回「系统似乎出现了点小问题」，不再把 `e.toString()` 塞进 `msg`；前端拦截器再兜底，识别到 Java 异常原文或空消息时替换为「系统开小差了，请稍后重试」。
- 商城首页装修的草稿表和指针表是单行表。读取时缺行按「空草稿版本 0、无发布版本」返回；保存、发布、回滚前用 `ON CONFLICT (id) DO NOTHING` 补齐，避免历史数据被清理后出现空指针。

### 商城装修控制台（2026-10-25）

- 装修入口仍是一个菜单，后台用标签页分为首页、首页弹窗、公告、条款、关于我们、售后规则与店铺；主题、弹窗、单页与店铺各自独立保存，不要求一起发布。
- 首页五类组件（轮播、快捷入口、推荐商品、活动专题、公告）后台可配，客户端就按发布顺序全部渲染，不能在客户端静默过滤某几类；单图轮播不加 `circular`，避免生成副本残影。
- 分类/领券横滑是客户端固定入口，不占后台组件位：固定排在轮播之后；公告等组件仍按 `sortOrder` 渲染，所以把公告排在轮播前就显示在轮播上方。不要再为领券中心另配一个快捷入口组件，否则会和固定入口重复。
- 自定义主色只保存一个 `theme_color`；深浅色阶由后端 `MallThemeColors` 统一派生，后台预览与小程序共用同一套比例，避免两边配色对不上。主色必须满足白字对比度 2.5:1（比正文 4.5:1 宽松，否则常用品牌绿/橙都会被拒），否则拒绝保存；正文链接使用派生出的深色 `ink`，不用浅主色直接写字。
- 主题色跟着发布版本走：发布时草稿主色写入发布记录，回滚时配色随版式一起回滚，不会出现旧版式配新配色。`theme_color` 为空表示沿用 `theme_code` 预设。
- 首页弹窗是单行配置，最多 5 张图片，保存即生效；服务端只按启用状态与生效窗口过滤内容，「每日首次」与「每次进入」的频控由客户端按版本记录。版本变化后当天可再次展示，便于新活动当天上线。
- 富文本单页固定四个编码（ANNOUNCEMENT / TERMS / ABOUT / AFTER_SALE），草稿与发布内容分列存放；发布是复制草稿，不引入第二套版本历史。后台草稿永不出现在客户端，客户端只读已发布内容；未发布过按「页面不存在」处理。
- 富文本在保存时由服务端按 `SmartHtmlSanitizeUtil` 白名单清洗，客户端编辑器不是可信边界；公告、条款、关于我们、售后规则属于公开信息，与首页主题一样允许匿名读取。
- 店铺二维码只由已保存的 HTTPS 店铺链接生成，链接未保存或格式不对时不出码；后台展示的是「已保存链接」对应的二维码，避免扫到未保存地址。
