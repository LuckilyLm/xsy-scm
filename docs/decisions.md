# 当前项目决策

最后更新：2026-09-20

这些是当前仓库继续有效的简要边界。详细业务语义优先查阅
[`project-reference-examples/xsy-scm/`](../project-reference-examples/xsy-scm/)；实现约束以根目录 `AGENTS.md` 为准。

## 工程边界

- `xsy-scm-server/` 和 `xsy-scm-web/` 是 V2 正式实现；`xsy-scm-miniapp/` 冻结，只读参考。
- SmartAdmin 是系统底座；SCM 只实现供应链业务域，不复制旧认证、组织和权限实现。
- 后端使用 Java 21、Spring Boot、MyBatis-Plus、PostgreSQL、Flyway 和 Sa-Token；前端使用 Vue 3 + TypeScript。
- PostgreSQL 不使用数据库外键；关系完整性由服务层、事务、唯一约束和检查约束保证。
- 金额使用 `BigDecimal`，库存变化必须有可追溯流水，敏感变更需要审计。
- 不引入微服务、消息总线、Kubernetes 或第二套 UI / 状态 / HTTP 框架，除非另有明确决策。

## 参考与变更

- `project-reference-examples/xsy-scm/` 是需求、旧业务语义和参考页面的主要来源，保持只读。
- 参考内容不能直接覆盖当前 V2 技术栈、权限命名、数据库规则或已批准的业务实现。
- 新需求先在参考项目中定位来源，再在代码和本文件中记录当前项目的取舍；不要重新建立大批镜像文档。
- 验证入口 `verify.ps1` / `verify.sh` 共用 `tools/verify.py`；仅验证工具及其测试纳入 Git 白名单，TS 历史基线保存在 `xsy-scm-web/quality/`。类型门禁要求 SCM 零错误且全局不新增，不代表上游全量类型检查零错误。
- 采购单拆分保留事务编排在 `PurchaseOrderService`；行装配与分配对账共享请求行上下文，暂不继续拆出 Assembler，也不扩展到收货服务重构。
- B1 收货入库采用显式双模式：`DIRECT` 在确认收货事务内写入库存；`WAREHOUSE_CONFIRM` 在确认收货后保持 `PENDING`，由独立 putaway 命令完成物理入库。模式创建时必选，确认后不得切换。
- putaway 是独立生命周期和审计动作；库存流水 `occurred_at` 记录物理入库时刻，因此 `DIRECT` 取收货确认时刻，`WAREHOUSE_CONFIRM` 取仓库确认入库时刻。重复或非法状态统一拒绝，不重复写余额和流水。
- 仓库停用采用严格模式：正库存余额、在途采购单或待入库收货单任一存在即拒绝；停用仓库不能建立新的需求、采购单或收货单引用，既有历史记录仍可查询。
- B1 权限拆分为收货确认入库、仓库启用和仓库停用（菜单 822/823/824），不把三类动作合并到普通编辑权限。
- B2/B3 尚未形成批准方案；后续库存方向（损溢、调拨、单位转换、阈值预警、成本核算）必须另行裁决。
- 出库采用**独立出库单**，不挂在尚未开发的分拣 / 发货模块上：把出库挂上去会让库存能力被一个不存在的模块阻塞。
  发货模块落地后由发货确认去创建并确认出库单即可，无需改表结构。
- 预留**不进 `inventory_movement`**：那张表是物理数量账本（`quantity` 恒为正、方向编码在类型里），
  预留不改变物理数量。预留单独建表，并在 `inventory_balance.reserved_quantity` 上维护活状态计数。
- **出库与预留的可用量门槛**：可用量 = `quantity − reserved_quantity`。出库不得吃掉已预留的货，
  预留不得超出可用量。服务层给可读错误码（41011），DB 的 `ck_inventory_balance_available` 兜底。
- **盘点差异施加到「确认瞬间的账面量」，不是把账面改写成实盘数**（2026-09-19）。
  `delta = 实盘量 − 账面量快照`，`after = 确认瞬间账面量 + delta`。
  理由：保存草稿到确认之间很可能发生收货 / 出库（鲜活品仓里这是常态），直接改写会把那些真实变动
  悄悄抹掉，而抹掉的痕迹在任何报表里都看不出来。用「施加差异」的写法，期间变动被完整保留，
  且当期间无变动时 `after` 恰好等于实盘数 —— 符合直觉。两种量都在单据行上留痕，漂移可审计。
- 盘点**不建零余额行**：记账单位（Q13）只能来自余额行，因此从未入库过的 SKU 不能在盘点里凭空盘盈，
  必须先有入库事实（否则报 41023）。这不是能力缺失，而是刻意不让盘点成为「绕过入库、凭空造库存」的入口。
- 盘点差异为 0 的行**不写流水**：`quantity` 恒为正，写不出「零差异」流水；强行写一条 0 会让
  「一行一流水」的防重索引语义变脏。
- 同一 SKU 在盘点单里出现两次**直接拒绝**（41027），不做静默去重：重复行会让同一份差异被施加两次，
  而结果看起来完全正常（余额确实变了，只是变错了）。
- 盘盈 / 盘亏是**两个**流水类型而不是一个 `STOCKTAKE_ADJUST`：方向必须能从类型本身读出来，
  否则 `ck_inventory_movement_snap` 无法判定 `after` 该加还是该减。数量恒为正，方向编码在类型里。
- **报损报溢单独建表**，不与盘点调整 / 规格转换混在一张表里（参考项目 `t_stock_adjust` 是混的）：
  V2 的盘点是独立模块且状态机不同（`DRAFT/CONFIRMED`），规格转换尚未开发；
  把三种语义塞回一张表会让状态机无法统一。
- **报损报溢有审批状态机**：`PENDING`（创建即待审核）→ `COMPLETED`（写流水、调余额）/ `REJECTED`。
  「新建」与「审批」是**两个独立权限** —— 报损是把货从账上抹掉的动作，由同一人录单并批准就失去了制衡。
  「审批」与「驳回」也是两个独立权限（允许主管审批、由另一角色驳回是常见分工）。
- **报损报溢的 `update` / `delete` 都加状态守卫（仅 PENDING）**。参考项目对这两者没有状态守卫，
  会让「已完成（已写流水）」的单据被改内容或被删掉，账与单从此对不上。这是刻意比参考项目更严的地方。
- **审批用乐观锁**：审批请求必须携带审批人打开单据时读到的 `version`，不符则 40921。
  理由：审批是一道控制，审批人必须批准自己读到的内容；否则「打开 → 审批」之间被静默改掉数量，
  这道控制就形同虚设。而两个人同时改同一张待审核单据属于录单碰撞，与全仓其它单据一致，
  **不**引入乐观锁（保持一致比局部更严更重要）。
- **驳回必须填审核意见**（41037）：本波次没有消息通知，驳回是唯一会把「为什么不行」
  传达给录单人的渠道；允许空意见的驳回等于把沟通成本转移给录单人去反复试。
- **报损报溢不含 `weight`**：Q2 裁决「数量 = 采购单位口径（非标品实重即数量）」，双记账属分拣波次。
- 报损 / 报溢与盘亏 / 盘盈**不合并**成同一组流水类型：两者都改变库存，但业务含义与追责对象不同
  （盘亏是「账实不符」的结果，报损是「对已知损耗的申报」）。合并后「这个月损耗了多少」
  就无法从流水里直接读出来，而那正是报损存在的理由。
- **调拨是两步式（发出 → 在途 → 收货）**，不是一次事务内两边同时改（2026-09-19，V2 原创设计，
  参考项目**没有任何调拨实现**）。两条理由：① 语义正确 —— 货在卡车上时既不在源仓也不在目标仓，
  一步式会让「发出」那一刻目标仓就凭空多出库存，而那正是仓库最不能接受的账实不符；
  ② 并发安全 —— 两步各自只锁**一个仓库**的余额行，既有的「按 `(warehouse_id, sku_id)` 升序锁余额」
  纪律完全不用改；一步式要在同一事务里锁两个仓库的行，锁序规则就得升级为跨仓排序，
  而那是六条既有写入路径都要跟着改的事。
- **在途期间这批货不在任何余额行里**（`inventory_balance` 只表达「在仓库里的货」，没有虚拟在途仓），
  因此全仓总库存会暂时减少。这是两步式的必然结果，不是缺陷；要让它在余额上可见，
  需要引入「在途仓」这个虚拟仓库 —— **属未决事项**，见下方。
- **在途调拨不可取消**：货已经物理离开源仓，账上只能靠一张反向调拨单冲回，
  不能把状态改回草稿再删流水（会被 `trg_inventory_movement_append_only` 拒绝）。
- **调拨占两个来源类型**（`TRANSFER_OUT_ITEM` / `TRANSFER_IN_ITEM`）：这是被迫的 ——
  同一条调拨明细行会产生两条流水，而 `uk_inventory_movement_source_active` 只认
  `(source_document_type, source_document_item_id)`，共用一个来源类型会让第二条插不进去。
  该索引是 V19 冻结的 Q7/Q11 契约，不能为了调拨放宽它。
- **两仓记账单位必须一致**（41044），不做隐式换算：源仓按「箱」记账、目标仓按「kg」记账时，
  把 10 箱加成 10 kg 会得到一个没有物理意义的余额，而错误只会在未来盘点时以「账实不符」暴露。
  换算能力属「单位转换」波次。
- **调拨在途阻塞仓库停用**（41009，第四条停用阻塞条件），源仓与目标仓**都算**：
  源仓的货已经出去了但账上还没落地到目标仓，目标仓则还欠着一批要入库的货。
  草稿调拨不阻塞（还没动过库存，停用后发出会被 41048 拒绝）。
- **预警阈值不放在 `inventory_balance` 上，单独建 `inventory_warning_threshold`**
  （2026-09-19，与参考项目不同）。余额行是**派生状态**：它只能由流水产生，
  `InventoryBalanceDao` 里没有任何「建行 / 赋值」方法。若阈值放在余额表上，
  配置路径就必须为了写阈值而创建余额行 —— 那会造出「没有任何流水支撑的余额行」，
  直接破坏「余额是流水的净和」这条不变量。单独建表后配置路径完全不碰余额表。
  （V19 的契约断言「`inventory_balance` 不含 `warn_min` / `warn_max`」**没有被削弱**，
  它现在的含义更明确了：预警配置刻意不在余额表上。）
- **预警按 (仓库, SKU) 配置，不是只按 SKU**：参考项目的「单仓库」是 G-03 的范围限制
  而非业务规则；V2 已有跨仓调拨，两仓的合理下限本来就可能不同（前置仓 vs 中心仓）。
- **预警状态不落库，读时计算**（参考项目写「余额变动后校验」）。落库就意味着**六条**
  余额写入路径都要顺手维护它，而它完全可以由 `(阈值, 可用量)` 推导 —— 落库只会多出一个
  会漂移的副本。判定规则只在 `ScmInventoryWarningStatusEnum#evaluate` 实现一次；
  列表 SQL 里另有一份**过滤**谓词，两者的等价性由 IT 交叉验证。
- **判定基准是可用量（现有量 − 预留量），不是现有量**。下限的业务含义是「还够不够发货」：
  20 kg 在库但 18 kg 已预留给明天的订单时可用只有 2 kg，必须触发补货预警。
  上限同理：货已经被订走就不算积压。列表同时展示三个数量，用户能看出预警为什么触发。
- **取等号算正常**（「不低于下限」= 恰好等于下限是正常的），边界两侧都有断言钉住。
- **预警列表由配置驱动**：只列配置了阈值的 (仓库, SKU)。没有配置就没有预警 ——
  否则每个 SKU × 每个仓库都会因为「没有余额行 = 0 < 下限」而刷屏。
  配置了阈值却没有余额行时数量按 0 计并预警 —— 这是本能力唯一能表达
  「还没进过货就要补货」的方式。
- **预警不设「已读 / 已忽略」状态**：它只是 `(阈值, 可用量)` 的当前计算结果。
  引入已读会让预警与真实库存脱钩 —— 货补上了那条「已读」记录还在，货又少了它却已被忽略过。
- **本波次不做推送 / 通知**：项目没有任何消息机制，「提醒」落地为「一个随时可查的预警列表」。
  推送采购（补货）/ 销售（积压处理）属未决事项。

### 移动加权成本（V34，2026-09-20）

- **改变 Q3 的既有裁决：`inventory_balance` 新增 `avg_cost`**。Q3 原本定的是
  「成本事实由 `inventory_movement.unit_cost` 承载、余额表不加 `avg_cost`」。这条在只做数量账时成立，
  但移动加权**顺序相关**：均价取决于全部历史出入库的先后，而「出库那一刻的成本」必须在出库时确定。
  事后从流水反推需要重放整条历史，而重放的前提是出库流水都已经带成本 —— 那正是本波次要建立的东西，
  鸡生蛋。因此均价必须有一个**活状态**承载者，那就是余额行。
- **入库（`PURCHASE_IN`）是唯一会改变均价的路径**：
  `newAvg = (旧量·旧均价 + 入量·入价) / (旧量 + 入量)`，四舍五入到 4 位（`HALF_UP`）。
  取 `HALF_UP` 而不是 `HALF_EVEN`：四舍五入是财务口径默认，银行家舍入会让「同一批数据算两遍」
  的结果依赖末位奇偶，对账时无法解释。
- **出库不改变均价**（移动加权平均的性质），但**出库流水必须写当时的均价** —— 这是本波次的核心语义变更：
  出库 / 盘点 / 报损报溢 / 调拨转出 / 转换转出的 `unit_cost` 从 `NULL` 变成有值。
  写的是**出库那一刻**的均价，不是回填、不是当前均价。
- **入库分两类**：**盘盈 / 报溢**（`STOCKTAKE_GAIN` / `GAIN_REPORT`）不带来任何新的成本事实，
  按该 (仓库, SKU) 现有均价入账（等价于均价不变），不凭空创造损益；
  **调拨转入 / 转换转入**（`TRANSFER_IN` / `CONVERT_IN`）是同一批货换了个科目，
  成本必须**跟着货走**，取同一条明细行转出腿的成本，见下一节。
- **存量流水的 `unit_cost` 不回填**（Q7 append-only 禁止改历史行）。上线后历史出库流水的 `unit_cost`
  仍是 `NULL` —— 那**不是缺陷**，而是「该笔出库发生在成本核算上线之前」这一事实的忠实记录。
  对账时要按此解释，不要试图补齐。
- **期初 `avg_cost` 口径**：取该 (仓库, SKU) **最近一次 `PURCHASE_IN` 流水的 `unit_cost`**，
  没有采购入库则为 0。选它的理由：它是唯一有真实采购价格事实支撑的起点，且不需要引入任何新的输入数据。
  副作用是「最近一次采购价」会覆盖更早的价格，对历史库存的估价偏保守（不虚高）。
  业务若要求更精确的期初（如最近一次采购价 × 存量、或财务指定价），需另开一次数据修正迁移。
  **这条口径是本次采用的默认值，属可调整项。**
- **金额（`quantity × avg_cost`）在 SQL 里显式 `ROUND(..., 2)`**：`NUMERIC(18,4) × NUMERIC(18,4)`
  在 PG 里得到 scale 8，而 `BigDecimal` 走 `ToStringSerializer` 原样输出 → 前端会看到 `112.00000000`。
  金额是给对账看的，2 位是财务口径；均价保留 4 位不动（它是计算基数）。
- **`avg_cost` 为 `NOT NULL DEFAULT 0`**，不允许为空：「没有均价」与「均价为 0」在本业务里无法区分，
  而让调用方每次都判空会让八条写入路径都多一层分支。
- **`recomputeAvgCost` 必须在持有余额行锁之后调用**，且只用一次赋值（`updateAvgCost`），
  不做「读-改-写」—— 与 `quantity` 的增量更新同一纪律。

### 调拨 / 转换的成本平移与 0 成本余额修正（V37，2026-09-20）

- **调拨转入的成本取「同一条明细行的转出腿」，不取目标仓均价**。目标是**跨仓不变量**：
  `调出总成本 == 调入总成本`。此前按目标仓均价入账，目标仓**没有**该 SKU 的余额行时
  （行由 `insertOnConflictDoNothing` 现建、`avg_cost` 默认 0）成本会被**整体清零**，
  实测三笔调拨的转出腿 `unit_cost` = 6.20 / 132.00 / 2.60，转入腿全部 0.0000。
- **不新增「源成本快照」列**：转出腿落库时已经携带了 `unit_cost`，转入用
  `(TRANSFER_OUT_ITEM, 明细行 id)` 读回同一条流水即可。加一列等于把同一个事实存两处，
  还要额外规定哪一处是权威。读不到配对流水直接抛 `IllegalStateException` 让整单回滚 ——
  出现即说明有绕过命令层的写入，静默按 0 记账会把这种问题永久埋掉。
- **成本基准在锁行时一次取齐**（`lockCostBasis` 返回 `skuId -> (数量, 均价)`）：同一条明细的
  转入腿可能先于转出腿执行，到腿里再读均价会读到被本单前半段改过的值，两条腿于是不同源、
  总成本不守恒。
- **转换的转入单价 = 转出腿总成本 ÷ 目标腿数量**（`HALF_UP` 到 4 位，与 `avg_cost` 同精度）。
  折算率是人工声明的（一箱是 9.5 还是 10 kg 取决于供应商与批次），跨单位单价必然不同 ——
  **守恒的是总成本，不是单价**。
- **链式转换（A→B 且 B→C）的 B 不能取期初快照**：B 既收又发，真实账本上它的转出腿看到的是
  「进完之后」的加权均价；B 没有期初行时直接取 0，就是「调拨转入清零」的同一个缺陷。
  因此改为按**单据图**预解每个源 SKU 的成本基准：以锁行快照为期初，沿「谁转入到它」递归
  加权（记忆化；同一单据内互相引用时按期初均价收敛且不写缓存）。这类单据本身没有业务意义，
  不为它新增拒绝路径 —— 环上每条明细的两条腿仍共用同一个基准值，总成本依旧守恒。
- **V37 只重算 `avg_cost`，不改任何流水**（Q7 append-only）。`avg_cost` 是派生的活状态而非
  流水的净和，修正它不产生新的成本事实。候选集刻意收窄为 `quantity > 0 AND avg_cost = 0`
  （缺陷症状），逐行重放自己的流水并与重放结果逐行核对；重放不出来的行（转入腿找不到配对
  转出腿、或重放值与库里数量不符）**`RAISE EXCEPTION` 让迁移失败**，而不是按 0 继续 ——
  宁可卡住发布，也不要把一个算不出来的成本写进账。
- **口径**：盘盈 / 报溢转入仍按现有均价（不带来成本事实）；V34 上线前发生的出库腿
  `unit_cost` 为 `NULL`，按 0 参与加权 —— 那是「当时没有成本记录」的忠实重放，不是缺陷。

### 销售订单录入渠道（V35–V36，2026-09-20）

- 后台人工新增使用单一原子命令完成创建与推进：纯标品直接到 `CONFIRMED`；只要包含任一非标品，整单停在 `PENDING`。混合订单的标品由系统写入实数量，非标品等待电子秤或现有实重入口回写，全部实重齐备后再确认整单。
- Excel 导入是一种录入来源 `IMPORT`，不是第二套订单账。一行一个明细，按“导入订单标识”分组；先汇总全文件错误，只有全部通过才在一个事务内创建。任一订单失败，整批回滚。导入权限不隐含人工改价权限。
- 导入只接收模板单工作表，校验表头与实际单元格；空行不改变错误行号，公式/错误单元格不能录入。数量、人工单价读取实际数值而非显示格式；不可售、无价、金额超限等错误定位到行和字段。写入阶段业务失败必须先退出事务并完成回滚，再返回失败订单的行号，不能捕获异常后继续提交。
- 小程序订单本期仅确定接口边界，**未实现**客户端和 mall 后端。未来使用 uni-app Vue3 与 SmartAdmin Sa-Token 多 `userType`；服务端从登录身份派生客户，校验地址归属，通过结算预览返回 `priceFingerprint`，提交携带同一指纹和 `Idempotency-Key`，直接写同一 `sales_order` 并标记 `MALL`，不建 `mall_order` 或同步表。
- 商城提交必须满足可用库存。预览只作提示；正式提交必须在一个事务内锁定余额并建立预留，不能采用“先查询库存、再创建订单”的竞态实现。多仓规则未裁决前沿用唯一启用仓库约束。该商城规则不改变后台/Excel“先接单、再采购”的既有主链。
### 数据大屏（V28 建，V1 视觉版重构，2026-09-20）

- **「今日」必须是北京时间的今天**。`ScreenDataService.todayRange()` 原用 `ZoneOffset.UTC` 的日界，
  实际窗口是「北京时间 08:00 → 次日 08:00」：早上 07:00 下的单会被算进前一天，而 14:00 下的单
  恰好落在窗口内 —— 所以这个 bug 在下午几乎不可见。改为 `Asia/Shanghai` 日界，
  与 `demand_date` 的既有约定（`AT TIME ZONE 'Asia/Shanghai'`）一致。
- **库存健康度的四档互斥、之和等于总数**。设计稿把「缺货」画成与「预警」并列的一段（占比要凑满 100%），
  所以判定顺序是「缺货 → 未配置 → 三档」，而不是把缺货当作「低于下限」的子集另计：
  1. **缺货** —— 可用量 ≤ 0，**优先判定且不要求配了阈值**。理由：把缺货挂在阈值上会让
     「配了阈值但一件都没有」被算成「预警」而缺货段恒为 0；
  2. **未配置阈值** —— 有余额但没配阈值，**单独成档**。塞进「正常」会让健康度虚高
     （大屏看上去一片健康，实际什么都没评估过）；
  3. **预警 / 积压 / 正常** —— 完全交给 `ScmInventoryWarningStatusEnum.evaluate`，**取等号算正常**。
- **`totalSkuCount` 是「参与评估的行数」而不是 `product_sku` 总数**。取后者会让
  四档之和（13）与面板上显示的总数（14）对不上 —— 有一个 SKU 任何仓库都没有余额行。
- **口径单位是「(仓库, SKU)」而不是「SKU」**：阈值按 (仓库, SKU) 配，同一 SKU 在两个仓库
  可以一个正常一个缺货。面板文案写明「(仓库,SKU)」，避免与「SKU 总数」混淆。
- **大屏不自己编健康度算法**。判定只有 `ScmInventoryWarningStatusEnum.evaluate` 一份实现，
  大屏的 SQL 只提供「可用量 + 上下限」三个事实、不参与分类 ——
  一旦 SQL 里也写一份「正常/低于下限/高于上限」，两份规则漂移后大屏的健康度就会和预警列表对不上，
  而那种不一致比没有这个面板更糟。IT 里有交叉验证（大屏异常档 vs 预警列表总数，夹逼关系）。
- **商品排行按 SPU 归并**。原按 `sku_id` 分组，同一商品的多规格 SKU（如「智利车厘子」5 斤装 / 10 斤装）
  会在榜单里出现两条同名行，看起来像数据重复。榜单的口径是「商品」，所以按 `spu_id` 合并金额。
- **趋势接口一次返回全部序列**（`GET /scm/screen/data/trend?range=7d|30d`，8 条等长序列）。
  设计稿明确要求「不要大屏为了 7 张图调用十几个接口」；未知 `range` 兜底 7d ——
  大屏不应因为一个参数笔误而整块空白。
- **环比基数为 0 时显示「—」，不显示 0%**。昨天没营业、今天有 1 万，说「增长 0%」是错的，
  说「增长 ∞%」没有意义。「今日客户」「今日出库」没有同口径的历史序列，
  所以它们**恒显示「—」**而不是拿一个口径不同的数字算出看似合理的百分比。
- **各面板的数量类指标是跨单位求和**（kg + 箱 + 把 + 颗 + 托 + 件）。这是 V28 起的既有口径，
  设计稿也接受，但**不能当作重量或件数解读**，只适合看趋势与相对大小。
- **图表只在必要时用 ECharts**：排行用自定义条形（ECharts 类目轴做不出「序号+名称+金额一行、
  条形另起一行」的排布，10 条柱状图在 420px 面板里标签必然截断）；
  仓库分布用横向条形而不是饼图（饼图外置标签在 420px 下会被截断成「默…」）。
- **供应链地图第一阶段是抽象网络**：`warehouse` / `customer` 只有自由文本 `address`，
  没有经纬度也没有省市区结构化字段。按设计稿「第一阶段不要卡住大屏」，
  先做抽象网络占位，接高德时整体替换该组件，上层布局与接口不受影响。

### 商品中心优化 PCO-1：主档增强与辅助资料（V38–V39，2026-09-20）

- **`master_status` 只收窄「可选范围」，不改任何写入路径**。`DISABLED`（停止引用）的语义是
  「新单据选不到该商品」，落点只有 `ProductSkuOptionDao.options`；订单、采购、库存写入路径一行未动。
  曾考虑在写入侧也校验主档状态，那会让历史单据的补录与改单被自己的主数据挡住，
  属于把「引用控制」误用成「交易控制」。
- **单位字典只做取值来源，业务字段继续存名称快照**。`product_sku.sale_unit`、
  `supplier_sku.purchase_unit`、`inventory_balance.unit` 都是既有事实的组成部分，
  回写成 `uom_id` 会让历史流水的单位随字典变化而漂移。代价是字典必须保证**活动行内名称唯一**
  （`uk_scm_uom_name_active`），否则「按名称记账」会出现两个真值来源；也因此单位**编辑锁定编码与名称**，
  只能改量纲、精度和状态，退役走「停用」而不是删除，被引用的单位更是直接拒绝删除。
- **标签可以改名，停用只挡新绑定**。关系表存 `tag_id`，改名不影响已绑定商品的展示；
  停用标签仍保留历史绑定，所以批量摘标的下拉必须连选中商品已挂的停用标签一起给出（标注「已停用」），
  否则摘不掉。
- **批量维护是一个入口三种命令**（状态 / 分类 / 标签），逐行携带乐观锁版本，
  **预校验不通过整批不写**。半批成功会让运营无法判断哪些商品已改；失败行按行修正后原地重试。
  `failures` 最多回 50 行，超出只报条数，避免整批明细灌进响应。
- **商品删除保护刻意排除 `supplier_sku` 与客户可见性**。这两张是商品自身的辅助绑定，
  随商品一起清理是正当的；订单明细、采购明细、库存流水才是不可再生的业务事实，
  命中即 `40931` 拒绝并引导改用「停用 / 归档」。
- **归档必须下架**：`ck_product_spu_archived_off_shelf` 在数据库兜底，服务层同名校验只为了给出可解释错误。
  `status`（是否在售）与 `master_status`（主数据是否可用）保持正交，不合并成单个枚举，
  因为「下架但仍可引用」和「在售但停止新引用」是两种真实状态。
- **`/options` 类下拉数据源不单独开权限**，复用 `scm:product:query`。否则只读角色连筛选条件都渲染不出来，
  「页面能打开、写按钮被隐藏」这条验收就不成立。
- **本轮不做 Excel 导入导出与图片中心**（归入 PCO-2）：主档字段先稳定，导入模板与图集分组才有确定的列。
- **只读账号夹具拆成 `_read` 与 `_none`**。`_read` 带只读角色（全部页面菜单 + 只读按钮），
  已经无法验证「完全无权限」；`scm-inventory.spec.ts` 的「深链落到 404 + 查询也被拒」改用不挂角色的
  `_none`。两种语义互斥，不能再用同一个伴随账号承担。

## 未决事项

- **在途库存是否需要在余额上可见（2026-09-19 调拨波次提出）**。两步式调拨让货在途中
  **不属于任何仓库的余额**，因此「全仓总库存」在在途期间会暂时减少。当前只在单据上可见
  （调拨单状态 = 在途）。三种可能的收敛方式：① 引入一个虚拟「在途仓」并给它余额行；
  ② 在库存报表里增加「在途量」列（由调拨单聚合，不进余额表）；③ 保持现状，靠调拨单查询。
  在裁决前，**对账时必须把在途调拨单算进去**，否则总库存会对不上。
- **库存预留的触发点（2026-09-19 提出）**。预留能力（`InventoryReservationService`）已就绪，
  但**不能挂在销售订单确认上**：本业务的链路是「客户下单 → 订单 → 确认 → 聚合 → 采购需求 →
  采购单 → 收货 → 库存」，**库存在订单确认之后才产生**；在确认时校验可用量等于要求
  「货先到才能接单」，与「先接单、再采购」的设计前提冲突。
  （实测：把预留挂到确认上，W1–W6 的集成测试有 82 个用例报 `41011 可用库存不足`。）
  候选触发点：分拣/发货环节（那时货已到）、独立的「预留」操作、或收货后对已有库存自动预留。
  在裁决前，出库单是唯一会改变库存的入口；预留页只读。
- 多仓默认选择的完整业务规则（当前订单无仓库字段，靠「唯一启用仓库」解析，见 41018）。
- **期初 `avg_cost` 的口径是可调整的**（当前默认「最近一次采购入库单价，无历史则 0」）。
  若业务要求更精确（最近一次采购价 × 存量、财务指定价、按最早一次采购价），
  需另开一次数据修正迁移 —— 不能改 V34（已应用的迁移不可变）。
- 非管理员角色的数据范围与库存权限组合。
- F0-DEBT-01 的业务附件逐用户读取控制。
- W6-2 小程序的启动条件与迁移方案。
