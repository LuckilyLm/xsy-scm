# 当前决策索引

本文件是当前有效业务与架构决策的唯一事实源。已完成事项和历史推导由 Git 历史追溯；
当前实现状态与验证边界见[项目状态](status.md)。

## 工程边界

- SmartAdmin 负责认证、员工与组织、角色菜单权限、数据权限、日志、字典、文件、统一异常和后台 Layout；SCM 只实现供应链业务，不复制底座能力或旧版认证系统。
- Java 业务包使用 `com.xsy.scm`，依赖方向为 Controller → Service → Manager / Policy → DAO；跨域只读消费正式事实，不直接写其他业务域表。
- 新源码注释只说明代码本身看不出的约束，不写开发过程、测试统计或过期计划。UI 规则及代码质量约定见仓库根目录 `AGENTS.md` 与 `CONTRIBUTING.md`。
- PostgreSQL 是唯一正式数据库；不新增数据库外键。已应用的 Flyway migration 不得修改，数据库变更只追加新版本。

### 经营指标与可见范围

- 同名经营指标使用同一时间轴、状态和金额列；“今日销售额”按 `confirmed_at`、`CONFIRMED`、`settlement_total_amount`，创建轴须称“今日下单金额”；“今日采购额”按 `submitted_at`、已提交状态集合、`total_amount`，状态集合由采购枚举提供。
- 首页与大屏按业务归属和仓库授权相交收窄；报表保留页面权限与仓库范围策略。两种出口可以各有 SQL，但同名指标的业务口径应一致。若要统一报表与工作台的范围，须对整页查询单独作权限裁决。

## P0 基线收口裁决：角色模型、SCM 数据范围与 F0 附件收口

SCM 数据范围由 `ScmDataScopeService` 集中解析并显式传给 DAO。业务归属、仓库和操作人等范围按各自事实相交；用户筛选只能收窄，空范围失败关闭，扩权须由明确权限表达。读、写、下拉选项和幂等结果重放均重新检查当前对象范围；功能权限不能替代行级范围。SCM 不使用 SmartAdmin `@DataScope`。附件关系由通用 `support/file` 维护，业务对象授权决定读取权；服务端 URL 经 `FileService` 解析，商品图片只绑定 `public/` 文件。

2026-10-10 补充：客户写入和客户选择沿用当前客户负责人范围；余额人工更正与充值创建同时检查业务客户和结算主体。退款查询与支付意图查询同范围，幂等重放必须重新校验当前授权。在线充值以验签后的渠道成功事实为到账时点；同一次支付成功编排按渠道实收登记 Finance Receipt，并向创建时冻结的结算主体钱包追加唯一 CREDIT，重复回调和恢复重放不得重复记账。拒绝回调保留审计记录但不占用后续合法事件 ID。模拟支付和模拟回调仅供 `dev/test`，`pre/prod` 不注册模拟渠道。

商城资金接口只从登录会话确定当前业务客户，不接受客户端指定客户、结算主体或钱包账户。普通独立结算客户可见真实钱包余额；集团结算子客户及集团主体账号不展示共享钱包总额或集团授信总额。流水同时按当前客户与合法结算主体过滤，不下发账户主键、其他成员流水或内部更正原因。商城账单只展示当前客户拥有的正常应收，复用 Finance 净额口径；`creditLimit=0` 不解释为无限额度。

## P1 分拣管理裁决

分拣只写任务的已分拣数量，不回写订单数量或结算字段，不改库存、不生成出库。活动任务独占有效订单行；取消时释放明细，完成任务须为每条有效明细提交结果。重新打开须校验版本并保留数量与原因。配送候选订单须已确认且所有有效明细均被已完成任务覆盖。分拣员范围与仓库范围相交；打印只记录操作，不改任务状态。称重结果须由人工接受，一键处理不得替非标准品推断重量。

### 分次分拣与确认统计（2026-10-17）

- 分次人工记录是同一任务明细下追加的作业事实，必须有操作人、时间、数量、幂等键与行版本防重；未确认分次不回写分拣明细的 `sorted_quantity` / `result`，不参与配送资格、销售出库或财务事实。最终确认仍由已有明细录入命令显式执行，完成任务仍要求全部有效行已确认结果。
- 新记录按每次追加量累积；最终确认量若偏离事件累计量，须写原因并追加差额事件，原事件不删除。重开允许带原因调整已确认结果；跨人、跨仓和取消/完成后写入仍按既有权限与状态机拒绝。
- 只读“最终确认统计”只覆盖已完成任务，按最后确认人、仓库和销售单位分组；不将其误称为各参与者的劳动贡献或工资核算。分拣差异阈值和人员计件报酬没有业务定案，不能用页面默认数字代替裁决。

### 非标品电子秤接入边界（2026-10-15 待设备接口文档）

- 称重工作台从现有分拣任务中选择客户订单与商品规格，不新建另一套订单或分拣单。设备上报必须携带唯一事件键、设备编码、分拣任务和明细、原始重量、单位、稳定标记与采集时间；设备协议、连接方式与校准机制待厂家文档确定。
- 原始读数仅保存为设备事件。**人工接受稳定读数**后才复用 `SortingTaskService.enter` 写入已分拣量；非标品由操作员裁定 `NORMAL/SHORT/OUT_OF_STOCK/OVER`，非正常结果必须说明原因。上报端不得传入已分拣数量或直接触发订单、库存、财务变更。
- 接受读数要求设备单位与订单行冻结销售单位相同；尚未实现安全的单位换算，不允许把公斤、斤、件直接混用。历史上报事件的处理状态和操作者留痕，不允许通过再次上报覆盖原记录。
- 开发环境仅允许**前端本地只展示**模拟重量，不能形成设备事件或分拣事实。正式硬件认证、协议适配、设备绑定、实时推送、离线重连与采集容差阈值均需厂家接口文档及负责人确认后实施。

## P2 物流配送 L3 裁决

发车是销售出库的唯一生产入口，数量取已完成分拣结果；整条线路原子提交，任一订单不合格则整体拒绝。库存变更只经库存域命令，预留与出库在同一事务消费或释放。发车使用幂等键与线路版本，签收校验线路订单行版本和司机范围。签收只记录 `SIGNED` 或带原因的 `EXCEPTION`，不撤销出库；退货必须追加独立反向事实。打印不发车。当前路线地图只展示已确定停靠顺序；算路不可用时降级显示，不能改顺序、库存或线路状态。实时 GPS、部分签收和自动退款不在当前范围。

## P3 Finance R1 裁决

Finance 只读消费订单、采购、库存、配送和退货事实，不写这些业务表。财务记录是追加事实；更正追加反向记录，金额保持正数并由类型表达方向。自动应收、应付与触发业务事实同事务提交；收款登记不自动核销，冲正只允许在原事实未被核销使用时追加。订单、财务与库存不得形成第二套状态机。已确认退货不因红字应收余额不足而被阻断；退款付款须与完成的退款事实一致。

## 采购每日清单与快照

采购每日清单按 Asia/Shanghai 的采购单提交日统计，取前一自然日区间；纳入已提交、部分收货、已收货和短收关单，排除草稿、取消与删除数据。结果按商品、采购单位及采购单冻结的编码和名称分组，不跨单位求和；采购金额不代表财务应付。清单是生成时快照，重复生成不覆盖既有结果；后台任务使用 SmartAdmin 调度，查询与导出均按采购员和仓库授权范围相交。

采购订单行、收货、应付等历史快照保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。采购单位快照来自供应商商品关系，不得用商品销售单位替换；需求单位沿用销售订单行快照。采购单提交后不再回读供应商或商品主档；收货记录数量和重量，金额从采购行事实派生。

## 采购净需求、通知、打印与异常聚合

- 净采购按仓库、商品和单位分别计算，需求扣除同维度可用库存、有效在途未收数量及已有采购覆盖；单位之间不换算。计算只冻结输入、解释与建议，不改库存。生成需求引用同一冻结批次并具备幂等性；回看不得回表重算。
- 通知复用 SmartAdmin 站内信，不新增消息中心或外部渠道。库存预警按周期扫描 `NORMAL → LOW/HIGH`，异常持续期间不重复通知，恢复正常后再异常可重新通知；没有有效仓库授权接收人时不广播。消息跳转不授予数据访问权。
- 打印模板采用字段白名单约束的 JSON 模型，由服务端渲染；不允许任意 HTML、脚本或数据库字段。打印记录冻结模板与业务内容，重印读取原快照并按操作者当前权限重新过滤金额。打印和预览不触发提交、发车或分拣完成。
- 异常聚合只读现有分拣缺货/差异、订单实量差异、配送异常签收及退货/退款待处理和售后拒绝事实，不建工单状态机或自动补偿。分拣缺货由已记录的 `OUT_OF_STOCK` 结果识别；当前仓库库存只作附有记账单位的参考，不用于反推历史订单缺货，也不跨单位换算。筛选、列表、统计和导出共用事实口径与授权范围；处理仍回到源业务模块。退款单状态不等同于实际资金到账或返还。
- 换货按“先退货批准并完成实物接收，再建关联替换订单”执行；替换订单是独立草稿，按当前客户、地址、商品、定价、预留、配送及结算命令重新校验，不自动抵扣退货红字应收或退款。每张退货单最多关联一张替换订单，原订单与库存/财务事实不被改写。已出库订单的客户实收数量更正只追加带原销售单位、已出库基线、前后数量、原因和操作人的记录；不得超过正式实发量，不回写订单行、出库流水或财务，退货、补送、退款由人工分别走正式流程。

采购订单行、收货、应付等历史快照保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。业务状态变化追加或更新正式领域事实，报表快照不取代来源事实。

## 当前已明确的实现边界

- **商城首页装修（SDP-06）**：首页配置按白名单组件保存草稿，发布生成不可变版本并原子切换当前版本；回滚复制历史内容为新发布版本，保留完整发布记录。全局首页的草稿读取、客户内容预览、维护、发布、回滚和历史查询均要求客户全域数据范围，预览还需校验所选客户与仓库；功能权限分别限定查询、编辑和发布操作。组件的客户范围、有效时间、内部跳转与公开图片由服务端校验；外部网页仅允许 HTTPS 且域名命中 `scm.mall.home.allowed-external-hosts` 部署白名单（默认空，即不开放外链），小程序 WebView 域名还须在微信平台获准。客户侧只读取已发布版本，商品、活动与分类按当前客户可见性过滤；推荐商品的客户价和配送仓库存实时读取正式目录，不冻结在装修版本中。首次发布前沿用既有首页内容。

- 调拨页已提供“在途库存”只读报表（`/scm/inventory/transfer/in-transit`），在途量不计入任何仓库余额；不再列为缺少报表。
- 当前定价顺序为协议价 → 客户类型价 → 市场价；额外时价语义及活动价叠加仍需另行设计。
- 协议价启用固定价、市场价加固定金额、配送仓成本加价率和市场价加价率四种公式。市场价只取商品规格原始含税市场单价，成本只取本次配送仓库存移动加权成本并按销售单位换算；加价率统一为基准价 ×（1＋加价率），不是目标毛利率倒推。缺失有效基准价或换算关系时该协议价不可报价，不回退客户类型价或其他成本来源。金额以 BigDecimal 四位小数 HALF_UP 计算。
- 订单在报价时记录公式参数与依据，提交时校验依据未变化并冻结结果及版本；草稿和待确认订单只有员工经订单更新与价格查询授权、带版本和原因手动重算，已确认或已有资金、预留、分拣、出库等正式事实的订单不得重算。促销仍在基础价格之后独立计算，不覆盖历史冻结金额。
- 超收容差、少收关单、直接入库与仓库二次确认均已落地；采购库存对比预览不等于净采购建议。

## 地图当前边界

- M0 的地区、坐标和 CRS 字段及 M1 中国地图大屏已实现。客户、仓库、供应商和停靠点均已接入通用选点组件（供应商点位见 ADM-09）。
- `map-provider.ts` 根据 `VITE_AMAP_KEY` 加载高德 JSAPI，支持安全代理/安全码配置、Geocoder 与 Driving 插件；配置缺失可手工录入经纬度。代码可配置不代表生产环境已配置或获得商用授权。
- 配送路线展示使用高德驾车规划的道路路线。顺序事实来自 XSY 已保存的停靠点顺序：高德不决定顺序、不自动应用排线建议、不成为发车前置；算路失败降级为点间连线。实时 GPS 定位、轨迹采集/回放不纳入当前范围；历史轨迹表与数据保留。
- 坐标必须成对保存经纬度与 CRS，允许 `GCJ02` 和 `WGS84`；点位缺失处应断线并提示，不能跨过缺失点拼出完整路线。地图和选点遵守业务范围，不改变库存或线路状态。辅助排线仅生成建议，由操作者确认应用；实时路况、导航承诺和 GPS 不在当前范围。
- 商用服务商、授权、配额和部署路线在实施时核实，不沿用历史调研的版本、费用或预排迁移号。

## 后续产品工作边界

- 收入以 Finance 正常应收事实确认；毛利成本取销售出库时冻结的库存流水单位成本，缺失时标记不完整，不用当前成本补算。退货成本只在实物验收回库后按原出库来源反向；可售回库与报损分别形成库存事实。
- 收入、出库成本和退货成本按各自事实发生时点统计，跨期不同步属于事件期毛利，不强行逐单配平。红字收入在实物接收前归为未分配仓库；接收后依原销售出库来源分摊。退货成本归属原销售出库仓，不按回库仓重新归属。
- 账期按冻结到期日计算。授信并发校验以服务端事实为准，额度为 0 表示未设金额上限，逾期仍可阻断；例外放行须有权限、原因和审计。集团关系冻结在单据与财务事实，不扩大数据范围。
- 账龄按业务日截断的正常发生、红字和有效核销计算，实收款不直接冲减未核销余额；缺失的历史到期日单列，不从当前主档补算。查询、汇总和导出共用读模型并执行业务归属、仓库和财务权限交集。
- 客户与供应商对账区分债权债务、实际收付款、核销和未分配资金。冻结版本保存纳入的事实标识，后续迟录或反向更正生成新版本，不改旧快照；受限范围必须标记为部分范围，不得宣称是完整集团对账。
- 净采购建议按仓库、商品、单位和可用库存计算；报表、打印和异常聚合只读消费来源事实。站内通知只在状态从正常转为异常时发送，持续异常不重复发送，恢复正常后再次异常可重发。打印只记录打印事实，不触发业务状态迁移。

- **2026-10-17 蔬东坡对标补充裁决**：参考系统地图的区域、客户/仓库位置、站点分布、道路排线、打印和司机/车辆档案均可吸收；但**不建设地图上的车辆实时 GPS 定位、车载在线位置上传、实时轨迹/回放、车辆实时监控**，也不因为旧需求写过“线路轨迹记录”就启动实时车载采集。已确定停靠顺序计算出的静态道路路线可以显示；已存在历史轨迹数据表保持原状、不删除。参考方案中的实时车载视频若用于在线追车也不作为新功能实施。
- 促销在基础价后计算，订单确认时冻结优惠和分摊；预览只试算，确认时服务端重验并占券。支付通过 provider-neutral 契约接入；验签后的渠道成功才形成在线收款事实，余额以追加流水记账，COD 只在财务确认实际收款后形成资金事实。真实渠道必须单独验收。

- 推广归属默认保留首次有效绑定；订单助手只调用正式业务命令；商品溯源以批次及包装码建立可追溯关系，公开查询严格使用批准字段白名单。微信、地图、电子秤、外部支付及生产发布须各自验收。

## 营销优惠生命周期、赠品与限时特价口径（2026-10-03 负责人确认）

本节补充固定优惠券、赠品与限时特价的状态及成本归属规则。

### 优惠券生命周期

```text
确认订单      AVAILABLE → RESERVED   （冻结优惠时占用）
正常签收      RESERVED  → USED       （与应收同一时点、同一事务）
异常签收      保持 RESERVED           （EXCEPTION 既不形成应收，也不算用掉）
部分/全额退款 保持 USED
现有订单取消  不处理券                （CONFIRMED 已是订单终态，cancel 碰不到 RESERVED）
未来撤销确认  RESERVED  → RELEASED   （当前无触发点，保留语义）
需要返券      重新 issue 一张新券，不复活旧券
```

- 券核销挂**正常签收**而不是退款：签收是订单级不可逆终态，也正是应收的形成时点，券「是否已被一笔真实成交使用过」与它对齐。
- **退款不恢复券**：退款反向的是金额（按冻结分摊），券回答的是权益是否已被使用过，两者不能混；允许 `USED → AVAILABLE` 会让「100 元订单用 20 元券、退款后券回来、再用于下一单」变成重复营销权益。若业务确需「全额退款返券」，另做重新发券（新实例），审计上才分得清「原券用掉了」与「补偿了一张新券」。
- `RELEASED` 是**历史终态**，不等于 `AVAILABLE`：它是「这张券被释放过」的痕迹。要把权益还给客户，应原券 `RELEASED` + 重新 `issue` 新券。
- 优惠券列表的累计张数按券实例统计：后台发放取 `ADMIN_ISSUE`，商城领取取 `MALL_CLAIM`，已使用取当前 `USED`（包含两种来源）。已知券让利只读已使用订单冻结快照的券优惠额，缺失快照单列数量，不把未知金额当作零。不按模板当前启停状态重算，也不把 `RESERVED` 算为已使用；当前没有时间窗口。

### 满赠（赠品）

- **不减订单收入**：赠品金额恒为 0，`FULL_GIFT` 的优惠额保持 0 是对的。
- **赠品必须走正式库存出库**，出库来源明确为促销赠品；赠品出库成本**计入该订单的履约成本**，因此销售毛利要扣掉赠品成本。
- **不把赠品塞成普通 `sales_order_item`**：那会污染采购需求、销售数量、销售额与客户购买商品分析。用独立冻结事实记录赠品（订单 / 活动 / SKU / 数量 / 单位 / 快照）。
- 赠品权益在**订单确认时冻结**（`order_promotion_gift`，快照不可变），出库、分拣、小票与成本归集都读它，不在各自环节重算活动规则。
- 门槛按**订单基础合计**判定，不按逐条作用后的剩余金额：同单另有满减不该把满赠门槛压没。
- **运行口径（2026-10-03 确认）**：赠品出库挂**发车**时点，与销售出库同一时点、同一仓库；赠品库存不足时**不阻断订单确认**，在出库时报错、由仓库补货后重试；赠品**进分拣清单与小票**（仓库照单备货），分拣不写回赠品数量。

### 限时特价

- **不改基础定价链**：协议价 → 客户类型价 → 市场价 保持不动，限时特价不参与这层的优先级竞争，也**不进 `PriceResolver`**。
- 它作为 Promotion 在**基础价之后**作用：`基础价解析 → 限时特价 → 满减/折扣 → 优惠券`。
- 冻结记录仍能回答「原基础价是多少、为什么卖这个价、按哪个活动哪一版、减了多少」：订单行金额仍是基础价口径，让利作为**独立事实**落 `order_discount.special_discount_amount` 与逐行分摊，**不把订单行的价格来源改成「限时活动」**。
- 保护规则：**限时特价只能把基础价往下压，不能抬高**（特价 ≥ 该行单价时让利为 0）。
- 分配口径：让利按**行**归集（`行基础金额 − 数量 × 特价`），不参与按金额比例分摊 —— 特价针对某个 SKU，摊到别的行上会让退款反向错行；同一行只让一次价（已被更靠前的特价命中过的行跳过），因此「按优先级顺序作用」在特价上依然成立，且每条活动记进快照的让利额之和恰好等于总让利。

## 客户商城账号与退款分摊口径（2026-10-10 负责人确认）

- **混合支付及多成功交易退款按原资金比例分摊**（已确认，不再是待裁决事项）：一张业务退款按原订单各成功资金来源的**剩余可退本金比例**冻结分摊，尾差按确定性规则归集；不默认余额优先、在线优先、按时间顺序或按比例以外的其它顺序。余额来源退回原冻结结算钱包，在线来源对应原支付交易。
- **一个客户可绑定多个采购账号**：账号归属客户，不再限制「一客户一账号」；账号由后台管理员开通、停用与重置密码。V121 初建的一客一号唯一索引由 V122 移除，登录手机号仍全局唯一。

### 商城配送仓、购买量和地址坐标（2026-10-16 负责人确认）

- 商城库存按客户及收货地址确定的**单个配送仓**计算，优先客户已绑定配送仓；无匹配仓时不能提交。切换配送仓须重算商品库存、价格与购物车可下单量，当前仓缺货不合并其他仓库存。可售量为实际库存减已预占与独立冻结量，同一笔占用不得重复扣减。

- 商城收货地址统一使用高德地图服务，持久化省市区、详细地址和 GCJ-02 经度/纬度。地图搜索、选点和逆地理编码同源；外部坐标系在接口边界转换，高德 Key 只经环境配置注入，不写入源码。

## 商城结算约定与 COD 分笔（2026-10-15 确认）

## SDP-14 连续录单边界（2026-10-17）

- “创建并继续录单”只是既有后台新建订单命令的用户体验扩展，必须在 `create-and-progress` 成功后再清旧本地草稿并切换新表单；保存草稿、编辑现有订单均不进入连续录单。
- 下一单只允许延续当前选择的客户与配送仓，且客户收货信息从当前有效客户资料重取；若重取失败，清掉下一单的客户选择并要求重新选择。上一单的商品、数量、订单号、状态、版本、旧地址、人工改价、优惠、关联原单、补单原因、备注和锁定价格一律不可复制。每张订单仍走独立定价、下单、版本与幂等检查，不新增复制数据库命令。

## SDP-14 草稿订单批量核价边界（2026-10-17）

- 订单列表批量核价只接收当前列表已选中的 1～8 张草稿订单，只读请求逐单读取正式订单详情与客户定价预览，权限与负责人范围仍按正式订单和定价接口检查；报价仅是检查时点的参考，不锁价、不预留库存、不修改草稿订单。每张订单独立返回核价结果/失败原因，不因某一订单失败假装全部已核价。
- 人工改价行不被自动覆写；商品不可售或价格未知时阻止该单在批量核价窗口直接重算。若操作者逐单确认变更，必须具备 `scm:order:update` 与 `scm:pricing:resolve:query`，填写原因、核对最新草稿状态与订单版本，最终只走现有 `/scm/order/reprice` 由服务器再次定价、限制冻结事实并写操作日志。价格预览不能保证重算执行时金额不变，确认弹框必须说明这一点；不新增另一套价格写接口。
- 历史单复用为新单、订单草稿恢复此前已实现，不另建第二套复制命令。已确认订单的冻结价和结算事实绝不可通过此功能重写。

## SDP-08 查询与自定义导出列约束（2026-10-17）

- 个人常用筛选方案仅保存服务器允许的组合筛选谓词，不保存业务结果、日期、其它基本筛选、查询范围或用户的权限快照。按已认证操作人及业务页面双键隔离，每人每页最多20条，名称唯一，服务端创建时和读取后都重新按**当前**字段白名单验证，过期方案不得应用但允许本人删除。读写删除接口均要求页面查询权限，客户端不得提供操作人 ID 或数据库字段名。

- 商品、销售订单与采购分析的首批自定义导出列仅采用服务端声明的稳定字段键，字段名不参加 SQL 拼接；原业务查询、数据范围、成本可见性、行数上限和导出权限不得改变。自定义列只投影**已经由正式服务完成授权和业务过滤的结果**，不能再查一套宽松数据。
- 服务端元数据接口根据当前成本权限隐藏受限列；显式请求受限列时服务端再次拒绝。未传导出列参数保留原格式向后兼容；显式空列表、重复键、不认识的键、超过列数限额一律拒绝。
- 动态组合条件只支持服务端当前发布的字段、固定操作符和值类型；限8项，条件按 AND 收窄。条件映射到原业务查询 DTO，不用客户端传来的字段拼 SQL；与原有筛选对同一字段取不同值须拒绝，不得静默覆盖。只在明确试点的商品查询、销售订单明细和采购按商品查询/导出内生效，其它报表维度的查询语义不随之改变。

## SDP-07 内部采购询价实施边界（2026-10-17）

- 询价只从状态为 `READY` 的净需求计算批次派生；与原批次生成需求命令共用批次行锁，禁止对 `GENERATED` 批次再创建询价。按同批次商品规格与需求单位归并冻结建议量；任一归并来源行已关联当前有效采购需求则整组不可再建询价，不另算实时库存、不建立第二套需求账本。
- 权限同时受采购员归属和仓库范围约束，询价创建、报价登记、确认分别授权；员工代录报价只证明本系统登记事实，**不等于供应商登录提交或电子签署**。供应商端身份体系、安全认证和外部接口需要独立裁决。
- 报价行只追加修订版本，保留报价人、供应商、单位、价格和有效期；同供应商只对比最新有效修订，新增供应商报价必须在询价接收截止前；采购员选用报价可在接收截止后进行，但必须保证询价未被选用、版本一致、所选最新报价仍在有效期内，且供应商采购关系仍有效。询价单一次只能确认一条报价，保存不可变报价 ID，由数据库触发器校验报价属于该询价，不新增业务外键，也不改原报价。
- 报价单价不自动作为采购订单成交价。把已确认报价转为采购单并冻结价格来源、跨单位换算、供应商端确认流程另行实施；在正式人工确认采购单前不触碰订单、库存、资金事实。

## 采购收货批次与批次库存（2026-10-18）

- 批次追踪按**仓库开关**启用：只有新建且尚无库存的仓库可以开启，开启后不可关闭；存量仓库保持关闭，不做存量回填。开关只在创建时设置，编辑态只读。
- 批次仓的采购收货**必须逐行登记批次**，非批次仓不录批次且行为不变。收货行下挂的批次数量之和必须等于本次声明收货量，由数据库恒等式与命令校验双重保证。
- 内部批次号由系统发号（`LOT` + 北京时间业务日 + 全局序列），不进入前端编辑控件；**来源生产批号**由供应商或现场提供、原样保存、允许为空，不得冒充系统批次号，也不要求唯一。
- 批次是独立子账：`xsy_inventory_lot_balance` 与仓库 SKU 总账并存，不把总账按批次拆行。不变量为「同一仓库同一商品同一单位下，各批次余额之和等于总账余额」。
- 批次流水只追加，禁止改写或删除；更正只能追加补偿流水，沿用库存流水既有约定。
- 销售出库与赠品出库按**先进先出**自动分摊批次，现场不选批次；每条出库流水按批次拆成多条子账流水，子账数量之和等于总账流水数量。
- 销售退货（含拒收退回）必须**回原出库批次**：按原出库流水的批次关联回写，找不到原批次时拒绝并给出明确错误，不猜批次、不新建批次。
- 批次仓的盘点、调拨、损溢、规格转换在二期之前**一律拒绝**，避免出现没有批次语义的库存动作；非批次仓不受影响。
- 批次**不独立核算成本**：批次余额只记数量与单位，成本仍按仓库 + 商品规格的平均成本；批次毛利与批次成本另行裁决。
- 批次仓的记账单位仍是采购收货时的单位快照，不做单位换算，与现有「同一仓库同一商品只允许一个记账单位」的规则一致。
- 新增「批次库存」查询能力，权限只授给已具备库存查询权限的角色；批次来源批号按现有数据范围过滤，不因批次新增跨仓可见性。
- 二期再做包装码（一物一码）：`unit_code` 不透明、全局唯一、永不复用、不嵌日期，且**一码一批**不做混批；批次码不冒充逐包装码。

## 包装码（一物一码）实施边界（2026-10-19）

- 包装码是**贴在实物上的身份**，与批次严格分层：**一码一批、不做混批**，一个批次可以有多个包装码；批次码不冒充逐包装码。
- `unit_code` 由系统发号、**不透明**（Base32 序号，前缀 U）、不嵌日期与业务含义、全局唯一、**永不复用**；作废只追加事件，原码保留。
- 发码总量受批次当前余额约束：包装码描述已经存在的实物，不能在库存之外凭空造出实物身份（超限 41504）。
- 一期发码入口是「包装码」页按批次发码（供应商预包装场景）；散装/称重品在分拣装箱时发码属于下一步，需要分拣域提供装箱事实后再接。
- 回放只读，回答「这个码从哪来、到哪去」：单元 → 批次 → 收货来源（收货单 / 供应商 / 确认时间）→ 出库去向（出库单号 / 时间 / 数量）。
- **客户维度暂不进入回放**：出库流水按批次分摊，还没有单元级绑定；等分拣/发车按包装码绑定后再补，不能用批次分摊倒推「这个码卖给了谁」。
- 包装码标签复用 `scm/print` 域的受控模板与冻结记录，新增 `TRACE_UNIT` 单据类型；默认模板用 80mm 热敏纸，只放码、批次、商品、包装量与绑定后的客户/订单号，不含价格与成本。
- 标签可以先贴后绑：未绑定时客户与订单号留空，标签仍表示实物身份；打印不代表已分配给任何客户。
- 包装码可以作废，但**只能作废未绑定的码**：已绑定的码代表一件承诺给客户的实物，作废会让回放自相矛盾，现场应先走退货或更正流程（41512）。
- 作废只把码标记为 VOID 并追加一条 VOID 事件，原码保留、永不复用；重复作废被拒（41513）。
- 分拣扫码绑定把包装码绑到**分拣任务行**而不是出库行：扫码发生在装箱现场，分拣行上已有客户与订单快照，出库单要到发车才生成。
- **一码一物，绑定只追加**：一个包装码只能绑一次，绑错只能作废该码（追加 VOID 事件），不能改绑到别的客户；绑定行只追加，禁止 UPDATE/DELETE。
- 绑定校验顺序即语义：码存在且有效 → 未绑过 → 商品规格与批次一致 → 该分拣行绑定总量不超过实拣量（41507–41509）。
- 回放的客户维度只来自**分拣绑定**，不由出库批次分摊倒推：批次是共同来源，不是某一袋的归属。
