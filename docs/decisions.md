## 范围与工程

### 工程命名与模块边界（2026-11-05）

- 后端统一使用 `com.xsy.scm` 包根与 Maven groupId，父工程为 `xsy-parent`；`xsy-admin` 的系统管理代码位于 `com.xsy.scm.admin`，`xsy-base` 的公共能力位于 `com.xsy.scm.base`。供应链各业务域保留原职责及包结构，Spring 与 Mapper 统一扫描包根。
- 组件、配置资源和自有工具统一使用 XSY 名称。旧缓存类型与浏览器配置键通过明确映射读取，新增数据使用当前名称；任务执行类由新增迁移更新，既有迁移不回改。
- 改名不改变业务校验和数据范围；系统管理、公共能力与供应链领域的检查边界仍各自明确。第三方许可来源集中保留在根目录 `NOTICE.md` 与 `LICENSE`。

### 当前客户的简化业务流程（2026-10-31）

- 依据负责人确认的客户沟通纪要，优先适配客户现有 Excel 订单 → 核对价格 → 安排采购 → 分拣 → 送货 → 财务核对流程。销售订单、采购清单与送货单复用商品、规格、单位、数量及备注，避免重复录入；不能因纸面版式相同就把采购成本写入销售价格。
- 供应商报价可能滞后数天。录单同时展示该客户最近已确认销售单价、最近采购参考价及各自单位、日期、来源；历史价格只作人工参考，不自动覆盖有效协议价，一次特价不延续为下次协议价。销售价格的人工修改仍校验改价权限并记录原因。
- 非标商品对客销售通常按斤计价，采购可按捆、箱等实际单位记录；例如4捆×27元/捆为108元采购额。没有实际总斤数或已维护的单位换算关系时，不推算每斤采购成本。照片表格内价格是采购价，表格外手写数字是对客销售价。
- 当前客户不操作采购收货、入库或人工出库。采购核对直接保存实际数量与价格，产生应付；配送继续由系统自动追加发货记录，允许默认本地仓负库存。库存功能与批次溯源保留作可选能力，不构成当前客户录单、采购核对和报告上传的前置条件。
- 检测报告只需上传市场纸质报告的照片，后台独立入口查看、放大和移除。复用通用文件上传与报告附件关系，不要求批次、包装码、机构、结论、检测日期或发布操作。上传时间不冒充检测时间，图片内容不自动判定为合格。角色权限控制公司内的照片资料库；文件本身按 2026-11-02 的统一公开规则可读，原批次报告的公开查询与发布控制继续适用。

### 产品范围与最小交付原则（2026-10-19）

- 当前业务范围以 [原始 13 模块、44 条功能描述](requirements/产品功能需求基线.md)和[负责人已确认规则](requirements/2026-09-09-负责人确认规则.md)为准；描述模糊不等于授权实现参考产品的全部功能。蔬东坡仅作常用操作入口与交互参考。
- 同一模块先完成最小可用的增删改查、业务动作、状态查看及必要打印/导出，优先验证已有源码；只有现有操作不能满足原始文字时才补最小缺口，不从每个技术记录自动衍生新工作台、新权限模型或新 Flyway。
- 仓库、财务、权限、金额/数量、事务、必要数据库约束继续保留严格正确性；不得以“简化”为名跳过防重复入账、数据范围或账本守恒。
- 当前不自动推进 V159/V160 逐码出库/退回、混批拆包、复杂召回、EPCIS 和消费者公开溯源平台等扩展。V151～V158 既有数据结构与历史记录保留；若基础扫码确实无法满足业务演示，需先确定扫码对象、最小展示字段及最短流程，再评估是否需要进一步实现。
- 原始需求未决定的审批层级、参数阈值、全自动流程等，允许优先参考成熟产品的普通人工确认路径；涉及是否扣账、是否授权外部人员、是否对外公开数据等重大边界仍须获得明确确认。当前待办见 [项目状态与待办](status.md)。

### 客户确认需求（2026-10-27）阶段一

- 商品销售单位缺省为“斤”：新建表单、服务端表单默认值与商品导入同一套规则；显式提交空单位仍按校验失败处理，历史商品不回写。
- 客户分类、供应商分类是各自独立的业务分类（蔬菜/蛋/肉），不与客户类型、供应商类型混用；分类引用只做筛选和展示，不改变价格或结算规则。
- 最近采购价只作录单参考，按采购员数据范围读取，不写回订单、不参与当前定价。采购单位与销售单位不同且没有已配置的换算关系时，不直接当销售单位成本使用，也不做“售价低于采购价”的高低判断。
- 智能建议价 `PURCHASE_COST_LOSS_TAX_MARKUP` 以销售单位成本为基数：最近采购价能换算时优先，否则回退仓库加权平均成本；损耗率、税率缺失或越界时整行未定价，不以 0 兜底。
- 对账单打印使用已保存的对账单版本，打印前按当前数据范围重新校验；客户专属模板只在“未显式选择模板”时生效，解析顺序为显式模板 → 客户绑定 → 类型默认模板。

### 2026-10-28 客户现场确认

现场记录与纸面单据样式见 [2026-10-28 客户现场确认](requirements/2026-10-28-客户现场确认.md)。以下为当前有效规则，编号用于后续实现和评审引用。

- **D-1028-01 订单整单规则**：一张客户送货单对应一张销售订单，一个客户单头下多行商品；不按商品逐行建单。订单录入、整单粘贴、客户分拣单、客户送货单均以客户公司为整单单位。
- **D-1028-02 实称量唯一规则**：分拣实称量（手工录入或电子秤确认，均经 `SortingTaskService.enter`）是实发数量和结算金额的唯一来源；订单下单量不因超发自动修改。分拣单的实数量列留空供现场手写/核对，送货单读取订单当前实数量。
- **D-1028-03 20:00 打印**：客户分拣单（无价格、无金额、无合计）与客户送货单（含价格、实数量、金额合计、双方签字）是两种独立单据，均按客户绑定模板；按配送日期或线路批量打印当天全部客户，不设 10 单上限。线路级发货单继续只给司机，不合并。
- **D-1028-04 负库存范围**：负库存只按仓库级开关 `allow_negative_stock` 放行，且只影响销售出库 `SALES_OUT`；盘点、损溢、调拨、转换、赠品出库不受开关影响。不做虚拟库存或第二套台账；允许负库存时不以账面数量或其他订单的预留量阻断销售发货，预留记录保留并按来源释放。现场按单仓运行，默认仓库为“鲜蔬源仓库”，该仓默认开启负库存。
- **D-1028-05 负库存单位与成本**：负库存余额的记账单位取显式出库单位；无显式单位时取该规格销售单位。负数量期间移动平均不参与加权：旧量小于等于 0 时入库直接采用本次入库价，新量小于等于 0 时保留原均价；已出库流水不追改。月末以负库存损耗估算报表收口，报表只读，不自动生成报损单。
- **D-1028-06 采购价窗口**：采购价允许在收货确认前补录，最多 7 天，窗口从采购单提交时间起算；超期由定时任务按最近一次已提交采购价回填并锁定，无历史价时保持待定价并提示。收货确认时任一行仍待定价则拒绝。已确认收货后的采购价不改库存成本，另立“采购成本更正”需求。
- **D-1028-07 采购锁单**：采购单支持人工锁单和提交后 7 天自动锁单；锁单不改变采购状态，只阻止补价/改价，收货仍可继续。锁后改价需要专门权限并写价格审计。锁单/解锁是两个权限。
- **D-1028-08 收款核销两模式**：支持自动 FIFO（按账单日期、单据 ID 顺序，只用收款剩余额逐笔分配，不超额）和手工选择两种模式；自动核销可先预览，单次目标数有上限，未分配余额留在收款单。两种模式共用同一分配核心和防重复请求编号，不新建核销表。
- **D-1028-09 抹零**：抹零建模为 `WAIVER` 来源的核销记录，冲减应收未结额，不修改应收原始金额；更正追加 `REVERSE` 核销行并保留原记录，不删除历史。抹零只作用于正常应收，不冲红字/退款；对账单单独列示抹零，通用收款反向不得把 WAIVER 当收款反转。
- **D-1028-10 电子秤单位**：现场秤为内置 Windows 10 的 SH2100-T15 触摸终端，现有 .NET 秤端可直接安装，不需要另配主机；打印走同一台机器的 Windows 打印机。服务端保持“设备单位 = 销售单位”的硬校验，不做隐式换算；同一物理量纲的显式换算（kg↔斤）必须记录原始值、换算因子和业务值，件/包/箱禁止与重量换算。P0 优先现场把秤切到市斤（`sj`）；若只能输出 kg，按 1 kg = 2 斤显式换算。
- **D-1028-11 单据列顺序**：订单录入、客户分拣单、客户送货单共用列顺序：序号、商品名称、规格、单位、数量、实数量、单价（仅录入/送货单）、金额（仅录入/送货单）、备注。品牌列不实现；行备注不得用订单备注冒充。
- **D-1028-12 本轮不做**：过账/AB 特殊单据、自定义财务报表字段、独立员工移动端、批次/包装码深化、采购收货后成本回冲、自动接单截止与强制分批、超发容差阈值。以上均需另立需求，不在 P0 第一批顺带实现。独立退货单已按 D-1028-15 单独立项。
- **D-1028-13 单仓规则**：客户没有独立仓库流程，采购后直接分拣配送、不做入库；**仓库与分拣在同一地点**，系统只维护一个本地“鲜蔬源仓库”，订单、分拣、出库、库存都落在这个仓。客户没有配送点，分拣完成后由司机到仓库取货，因此不存在“一仓多点”或多仓调拨。新建/存量数据在一次部署中收敛为该仓，界面不再要求普通录单人员选仓；管理员仍可维护仓库主数据，但不为此扩展多仓流程。
- **D-1028-14 定价规则**：现场按**协议价**运行，协议价**按客户分组**维护：每个分组至少一个客户，组内客户对同一商品的**同一计量单位**执行同一价格；同一商品同一单位的**不同规格共用一条价格**，不按规格分别定价；跨单位（斤/箱/件）分别维护，不做隐式换算。分组与客户是个人/公司/集团类型无关，客户类型不参与定价。实际下单时仍可在订单行**对单个客户手动改价**（需原因，沿用既有改价留痕），这是分组价之上的例外而不是第二套价格。时价保留既有解析能力，但现场暂不使用，本轮不深化、不做界面引导、不纳入验收。取价优先级为**逐客协议价（个别例外）→ 客户分组价 → 时价 → 市场价**；停用分组不参与取价。分组至少一个客户由应用层校验；删除分组先把客户移出分组再软删除，历史价格保留在变更历史中。
- **D-1028-15 独立退货单**：客户退回来的货找不到原单时，允许直接按「客户 + 商品明细」建退货单，不关联销售订单。
  - 建单：明细按商品 SKU 选择，数量是本次申请退货的销售单位数量；退货单和明细都保存客户名称、商品名称与下单时的销售单位，列表和详情不再依赖原订单联接。
  - 取价：优先「该客户该商品该单位最近一次已确认成交价」；没有成交记录时走既有取价链（逐客协议价 → 客户分组价 → 时价 → 市场价）；仍无可用价格必须人工填价并填写原因。价格来源随行保存（最近成交 / 定价链来源 / 人工改价），审批时不再重新取价。
  - 入库：退回仓库由实物接收时指定；不绑定原出库行、不绑批次。库存单位取该仓该商品已有余额单位，没有余额时取商品销售单位；单位不一致且无换算关系时拒绝入库。入库成本取入库前该仓该商品的移动加权均价，没有余额按 0 计，不追溯原出库成本，也不改写历史出库流水。处置方式沿用入库存 / 报损。启用批次追踪的仓库因缺原出库行拒绝独立退货入库，需改走订单退货。
  - 财务：审批生成**客户级红字应收**——来源是这张独立退货单，`order_id` 与 `original_receivable_id` 均为空，客户与结算主体取客户档案。对账单把它作为负数事件冲减客户余额；账龄与核销按客户（含结算主体）先进先出抵减最早未结的正常应收，抵完为止，抵不完的部分保留为贷方余额。不修改原应收金额，不生成退款单（没有订单资金记录，多收的钱走客户预收或后续核销）。
  - 权限与日志：沿用现有退货查询/建单/审批/接收/驳回/撤销权限，不新增权限码。数据范围按客户负责业务员（`xsy_customer.seller_id`）落在订单业务员范围；操作日志允许挂在客户上，不再强制写订单号。

- **D-1028-16 过账特殊单据**：财务在系统里登记对外账目的**虚拟单据**，只留痕，不进正常业务流——不生成应收/应付、不参与核销、不改客户余额与账龄。`D-1028-12` 中「需另立需求」的过账项以本条立项。
  - 字段：过账单号（`XSY` + 雪花 ID）、客户与当时的结算主体、过账日期、过账金额（>0）、税点（0–100 的百分比，可空）、返款状态（未返款/部分返款/已返款）、备注。税点按纸质单据原样记录，**不据此计算税额**，系统不存 `tax_amount`。
  - 更正：过账表 append-only。登记错了走**作废**——追加一条作废记录（作废人、时间、原因必填），有效状态由「有没有作废行」推导，过账行本身不落 `status`。作废不可重复，作废后不可修改。
  - 修改：客户不可改（换客户等于换一张单，应作废后重新登记）；日期、金额、税点、返款状态、备注可改，改前改后都进操作日志（`POSTING_ADD / POSTING_UPDATE / POSTING_VOID`）。
  - 可见范围：页面只在财务目录下，菜单与权限只授超级管理员与 `SCM_FINANCE`；「隐藏」靠授权范围实现，不靠 `visible_flag` 对已授权的人隐藏入口。查询、登记、修改、作废各自独立权限码，导出沿用 `scm:finance:export`。数据范围按客户负责业务员（`xsy_customer.seller_id`）。
  - 对账：正式对账单可**选择**是否包含过账记录，默认不包含。包含时过账行进入明细时间线，但只带「过账金额」一列，应收/收款/核销/退款变动恒为 0，**不改变期初、期末净应收与未分配资金**；作废的过账不进对账单。`include_posting` 随保存后的版本记录，打印与详情按同一套规则读取。
  - 内部报表：过账列表本身就是完整的过账台账（日期、客户、返款状态、有效状态、单号/客户关键字），导出与列表同源，不另做一张规则可能不同的报表页。

### 工程边界

- XSY 负责认证、员工与组织、角色菜单权限、数据权限、日志、字典、文件、统一异常和后台 Layout；SCM 只实现供应链业务，不复制底座能力或旧版认证系统。
- Java 业务包使用 `com.xsy.scm`，依赖方向为 Controller → Service → Manager / Policy → DAO；跨域只读消费正式记录，不直接写其他业务域表。
- 新源码注释只说明代码本身看不出的约束，不写开发过程、测试统计或过期计划。UI 规则及代码质量约定见仓库根目录 `AGENTS.md` 与 `CONTRIBUTING.md`。
- PostgreSQL 是唯一正式数据库；不新增数据库外键。已应用的 Flyway migration 不得修改，数据库变更只能新增新版本。
- 数据库初始化按模块维护24份最终SQL（V1000.01～V1000.24），直接定义截至原V244的当前结构和系统默认数据，旧V/B脚本退出资源与制品，原文由Git追溯。已有V243/V244库必须先用显式工具核对完整历史和最终结构，再保留业务数据及原历史表、切换到1000.24基线；不自动接管非空库、不关闭Flyway校验、不用repair掩盖差异。已使用的模块SQL不能修改，后续上线差异追加V1001及更高版本。入口见[部署与升级](../deploy/README.md#模块初始化与旧库基线切换)。

### 数据库业务规则由后端执行（2026-11-05）

- V1001移除业务触发器、业务CHECK及专用触发器函数；保留主键、唯一、NOT NULL、字段类型与精度、默认值和索引，不增加数据库ENUM或外键。24份已使用的模块SQL继续保持原样，新库按模块初始化后正常执行V1001，旧库按已确认基线追加同一增量。
- 枚举、范围、配对、金额数量关系和引用有效性由表单校验、领域Service/Policy及命令执行；SCM Service入口复用Jakarta表单约束，导入和内部任务同样受校验。事务、乐观锁、防重复处理及数据范围继续保留。
- 客户未指定结算主体时，创建前分配主键并设为自身。应收按结算主体、应付按供应商在追加前保存账期和到期日，关联红字继承原来保存的资料，历史不随主档变化。
- 库存、财务及其他追加记录由仅允许新增记录的Mapper或仅暴露追加/读取的DAO保护；历史资料不能通过自定义SQL覆盖，更正继续追加反向记录。直接手工SQL不属于业务写入入口，不能依赖已移除的数据库保护。

### 当前已明确的实现边界

- **商城首页装修（SDP-06）**：首页配置按白名单组件保存草稿，发布生成不能修改的版本并原子切换当前版本；回滚复制历史内容为新发布版本，保留完整发布记录。全局首页的草稿读取、客户内容预览、维护、发布、回滚和历史查询均要求客户全域数据范围，预览还需校验所选客户与仓库；功能权限分别限定查询、编辑和发布操作。组件的客户范围、有效时间、内部跳转与公开图片由服务端校验；外部网页仅允许 HTTPS 且域名命中 `scm.mall.home.allowed-external-hosts` 部署白名单（默认空，即不开放外链），小程序 WebView 域名还须在微信平台获准。客户侧只读取已发布版本，商品、活动与分类按当前客户可见性过滤；推荐商品的客户价和配送仓库存实时读取正式目录，不保存在装修版本中。首次发布前沿用既有首页内容。

- **商城结算与库存规则（2026-10-25）**：商城按「先接单后采购」运行，库存量只影响商品页与购物车的展示（0 库存显示「预订」），不得作为结算预览或提交的拒绝条件。结算统一重验服务端 `sellable`、正式报价和起订/递增规则：`sellable=false` 视为不可售，价格为空或 0 元一律按「未报价」处理，不生成 0 元订单。购物车、结算预览与提交必须同一套规则，避免出现「能加购、能预览、提交才失败」。
- **富文本单页发布时保存的内容（2026-10-25）**：标题与正文必须来自同一次发布。发布时同时保存 `published_title` 与 `published_content`，客户端只读这两个字段；草稿标题修改后即使保存，也不得影响线上标题。发布校验与编辑器一致：正文有文字或有图片即可发布，纯图片公告不再被当作空白拒绝。

- 调拨页已提供“在途库存”只读报表（`/scm/inventory/transfer/in-transit`），在途量不计入任何仓库余额；不再列为缺少报表。
- 当前定价顺序为逐客协议价 → 客户分组价 → 时价 → 市场价；活动价叠加仍需另行设计。
- 协议价启用固定价、市场价加固定金额、配送仓成本加价率和市场价加价率四种公式。市场价只取商品规格原始含税市场单价，成本只取本次配送仓库存移动加权成本并按销售单位换算；加价率统一为基准价 ×（1＋加价率），不是目标毛利率倒推。缺失有效基准价或换算关系时该协议价不可报价，不回退其他价格来源或成本来源。金额以 BigDecimal 四位小数 HALF_UP 计算。
- 订单在报价时记录公式参数与依据，提交时校验依据未变化并保存结果及版本；待确认订单只有员工经订单更新与价格查询授权、带版本和原因手动重算，已确认或已有资金、预留、分拣、出库等正式记录的订单不得重算。促销仍在基础价格之后独立计算，不覆盖历史保存金额。
- **前端金额与数量精度（2026-10-24）**：销售/商城金额与销售单价按两位展示和录入，采购单价、成本、数量、费率保持四位；财务账本与结算（应收应付、收付款、核销、退款、余额、对账单）保持四位，因为存在四位精确相等校验。后端计算、存储与序列化仍为四位定点，Web 提交前统一归一为四位字符串；财务四位是前端展示例外，不改变 `BigDecimal 四位 HALF_UP` 计算规则。小程序对客展示统一两位：商品价格、购物车/结算/订单/售后、钱包余额与收支、账期账单与核销金额都按两位显示，数量保持四位，后台财务账本仍四位；后端计算、存储和四位相等校验不变。价格为 0 视为未报价显示「询价」，不显示 `¥0.00`。
- **数量录入不补零（2026-10-25）**：数量仍按四位定点校验、存储和提交，但录入框只显示实际需要的小数位，整数不再写成 `1.0000`（商城起订量、商城递增量已按此处理；表格数量列仍按四位展示）。数量必须大于 0 且不超过四位小数；后端 `@Digits(fraction = 4)` 仍是最终规则。
- 超收容差、少收关单、直接入库与仓库二次确认均已落地；采购库存对比预览不等于净采购建议。

### 后续产品工作边界

- 收入以 Finance 正常应收记录确认；毛利成本取销售出库时保存的库存流水单位成本，缺失时标记不完整，不用当前成本补算。退货成本只在实物验收回库后按原出库来源反向；可售回库与报损分别形成库存记录。
- 收入、出库成本和退货成本按各自记录发生时点统计，跨期不同步属于事件期毛利，不强行逐单配平。红字收入在实物接收前归为未分配仓库；接收后依原销售出库来源分摊。退货成本归属原销售出库仓，不按回库仓重新归属。
- 账期按入账时保存的到期日计算。授信并发校验以服务端记录为准，额度为 0 表示未设金额上限，逾期仍可阻断；例外放行须有权限、原因和审计。集团关系保存在单据与财务记录，不扩大数据范围。
- 账龄按业务日截断的正常发生、红字和有效核销计算，实收款不直接冲减未核销余额；缺失的历史到期日单列，不从当前主档补算。查询、汇总和导出共用读模型并执行业务归属、仓库和财务权限交集。
- 客户与供应商对账区分债权债务、实际收付款、核销和未分配资金。保存后的版本记录纳入的记录标识，后续迟录或反向更正生成新版本，不改原来保存的资料；受限范围必须标记为部分范围，不得宣称是完整集团对账。
- 净采购建议按仓库、商品、单位和可用库存计算；报表、打印和异常聚合只读消费来源记录。站内通知只在状态从正常转为异常时发送，持续异常不重复发送，恢复正常后再次异常可重发。打印只记录打印记录，不触发业务状态迁移。
- 地图点位必须成对保存经纬度及 CRS。道路路线按 XSY 已确认的停靠顺序显示，外部地图或距离 provider 只给建议，不自动排线或发车；缺少坐标或服务不可用时明确降级。电子秤遵守“设备事件 → 稳定读数 → 人工接受”，不让设备直接绕过分拣命令。
- **2026-10-17 蔬东坡对标补充裁决**：参考系统地图的区域、客户/仓库位置、站点分布、道路排线、打印和司机/车辆档案均可吸收；但**不建设地图上的车辆实时 GPS 定位、车载在线位置上传、实时轨迹/历史轨迹查看、车辆实时监控**，也不因为旧需求写过“线路轨迹记录”就启动实时车载采集。已确定停靠顺序计算出的静态道路路线可以显示；已存在历史轨迹数据表保持原状、不删除。参考方案中的实时车载视频若用于在线追车也不作为新功能实施。

- 推广归属默认保留首次有效绑定；订单助手只调用正式业务命令；商品溯源以批次及包装码建立可追溯关系，公开查询严格使用批准字段白名单。微信、地图、电子秤、外部支付及生产发布须各自验收。

### 表结构与字段收敛（2026-11-01）

- 1:1 关联不单独建表：换货关联收进退货单的 `replacement_order_id`，原单号由退货单自己的 `order_id` 得到；替换订单删除时把该列清空，唯一索引只约束非空值。
- 价格变更审计只保留一张 `xsy_price_operation_log`，用 `price_type`（协议价 / 客户分组价 / 时价）区分维度，`price_id` 指向该维度自己的价格表。新增价格维度只扩枚举，不再复制建表、建 DAO 和 UNION 查询。

### 交易单据取消草稿语义（2026-11-01）

- 销售订单、采购单、采购收货单、库存出库单、库存调拨单、库存盘点单和配送线路不再有 `DRAFT` 状态。新增即进入正式流程首态：销售订单/配送线路为 `PENDING`，采购单为 `SUBMITTED`，出库单为 `PENDING`（待出库），调拨单为 `PENDING`（待发货），盘点单/收货单为 `PENDING`（待确认）。

### 客户月费用批量登记与报告照片筛选（2026-11-02）

- 客户月成本费用支持按「同一月份 + 同一说明」批量登记多个客户；每行仍按单笔规则校验客户可见性、金额非负且不可全空。整批一个防重复请求编号、同一事务，任一行失败全部回滚，不留下半批费用。
- 同一批次不允许重复客户；需要给同一客户登记多笔不同说明时，分开两次登记。
- 检测报告照片按上传日期、报告名或上传人姓名筛选，上传日期统一按 `Asia/Shanghai` 业务日折算；筛选不改变原有「最近 50 条 + 游标」的翻页方式。

### 客户月利润对账规则（2026-11-02）

- 客户对账模板只有表头；主公式已由客户确认并落到报表：**对账金额 = 当月应收净额 + 有效过账金额**；**实付金额 = 当月收款净额**（`NORMAL` 加、`REVERSE` 减）；**未付金额 = 对账金额 − 实付金额**。
- **过账税金** = 有效过账金额 × 登记税点 / 100，未登记税点按 0 计。账本与过账表仍不落税额，只在报表派生。
- **开票金额**暂按对账金额展示（当前无销售发票台账）；**实际货款 = 对账金额 − 过账金额 − 过账税金**。
- **1% 专票税费 = 对账金额 × 1%**；**6% 服务费 = 对账金额 × 6%**；**利润 = 对账金额 − 实际商品成本 − 1% 专票税费 − 6% 服务费 − 运费 − 扣点**。成本未登记时利润为空。
- 专票税费与服务费各自按四位 HALF_UP 舍入，利润扣减这两项已舍入金额，查询、汇总与客户 Excel 使用同一套规则，避免导出列复算尾差。
- 月报查询、汇总及两种导出均要求外部账单查询权限，不能通过原值或派生利润旁路读取。对账日期列明确写查询自然月的起止期间；客户版十二列 Excel 按发生额输出，不冒充含期初余额的保存账务对账单，开票占位规则随文件说明保留。
- 以上均为报表派生列，不写回应收、收款、过账或费用记录；V207 的过账表本身仍只保存税点、不保存税额。客户给出正式公式后只改派生列，不改账本。
- 报表仍以「当月有应收或有月费用」的客户为取数范围；只有收款或只有过账的客户暂不单独成行，避免在正式规则未定前扩大对账范围。

### 文件与图片上传统一公开（2026-11-02）

### P0 基线收口裁决：角色模型、SCM 数据范围与 F0 附件收口

SCM 数据范围由 `ScmDataScopeService` 集中解析并显式传给 DAO。业务归属、仓库和操作人等范围按各自记录相交；用户筛选只能收窄，范围为空时拒绝访问，扩权须由明确权限表达。读、写、下拉选项和防重复处理结果重放均重新检查当前对象范围；功能权限不能替代行级范围。SCM 不使用 XSY `@DataScope`。附件关系由通用 `support/file` 维护；新上传公开文件按 `public/` 策略读取，存量私有文件仍按业务对象授权。服务端 URL 经 `FileService` 解析，商品图片只绑定 `public/image/` 文件。

- **商品图片导入（2026-10-24）**：批量导入不再要求文件名等于商品编码；上传后在预览表逐张（或批量）指定目标商品，服务端按「商品编码.jpg、商品编码-2.jpg…」生成展示名，存储 key 与其他商品图片引用不变。公开图片目录无论全局文件检测开关如何，都由后端按文件内容强制校验为 JPG/PNG/WebP/GIF/BMP（拒绝 SVG）；前端使用同一白名单提前拦截，单张上限沿用 `maxUploadFileSizeMb`（默认 20 MB）。

- **后台视觉与交互**：统一见根目录 [DESIGN.md](../DESIGN.md)，覆盖 SCM、系统管理与支撑工具的共用组件规范。

2026-10-10 补充：客户写入和客户选择沿用当前客户负责人范围；余额人工更正与充值创建同时检查业务客户和结算主体。退款查询与支付意图查询同范围，重复请求返回原结果必须重新校验当前授权。在线充值以验签后的渠道成功记录为到账时点；同一次支付成功协调按渠道实收登记 Finance Receipt，并向创建时保存的结算主体钱包追加唯一 CREDIT，重复回调和恢复重放不得重复记账。拒绝回调保留审计记录但不占用后续合法事件 ID。模拟支付和模拟回调仅供 `dev/test`，`pre/prod` 不注册模拟渠道。

商城资金接口只从登录会话确定当前业务客户，不接受客户端指定客户、结算主体或钱包账户。普通独立结算客户可见真实钱包余额；集团结算子客户及集团主体账号不展示共享钱包总额或集团授信总额。流水同时按当前客户与合法结算主体过滤，不下发账户主键、其他成员流水或内部更正原因。商城账单只展示当前客户拥有的正常应收，复用 Finance 净额规则；`creditLimit=0` 不解释为无限额度。

## 订单与定价

### 销售订单导入（客户送货单版式，2026-10-27）

- 只保留客户送货单模板，旧的 12 列通用模板与行级导入结构一并下线；模板随后端 JAR 发布，下载入口与解析规则必须同源。
- 一张送货单生成一张订单。收货单位与日期取自表头上方的标签行，明细从表头下一行起读，遇到「合计」或签字栏结束；多工作表、模板外列、错误单元格、以及除销售金额外的公式均整批拒绝，避免漏单或读错值。
- 合计或签字后仍检查剩余区域；除正常签字栏和空白外有其他内容时整批拒绝，不静默丢弃同工作表中的第二份单据。
- 收货单位按客户名称精确匹配有效客户；重名或不存在时整批拒绝，不做模糊匹配或自动建档。收货人、电话、地址取客户档案，档案缺项即拒绝导入，导入行不能覆盖。
- 商品按「商品名称 + 规格 + 单位」匹配商品档案：规格为空时要求该商品名称只对应一个规格，单位必须等于销售单位。行内实数量即下单数量；销售金额只用于核对（实数量 × 销售单价，两位四舍五入），不参与下单金额。
- 销售单价视为人工定价：导入账号必须具备订单改价权限，否则含单价的送货单整批拒绝；改价原因由服务端统一记为「送货单导入」，不采信表格内容。单价留空时按系统定价，系统无可用价格则拒绝。
- 送货单日期作为期望送货日期，按 Asia/Shanghai 当日零点解释；行备注逐行保存，上限 200 字符；整单备注独立维护，不由行备注汇总覆盖。

### 待确认订单改单（2026-10-27）

- 可改单状态限定为待确认。待确认订单只有在没有支付意图、应收、库存预留、出库或分拣任务时才允许改单；一旦存在这些记录即校验失败时拒绝操作，避免改单与已发生的资金、库存记录脱节。
- 改单不重新定价：未改动的非人工改价行沿用提交时的报价并重新锁定，新增或改价行按表单值锁定；需要按最新价格重算仍走“批量核价”并留痕。标品实数量随下单量同步，非标品的称重结果不因改单被覆盖。
- 改单后订单仍为待确认；改单记 `UPDATE` 操作日志。

### 订单锁单与发车后改单（2026-10-27）

- 锁单不新增订单状态：保持订单当前状态，只写 `locked_flag`、`locked_at`、`locked_by`、`lock_reason`、`auto_lock_at`，避免配送候选、商城展示、采购需求与既有状态机全部重判一个新状态。
- 发车出库时在订单上记 `dispatched_at`，7 天自动锁单从这一刻起算，不看配送履约状态（履约状态会被签收、异常等后续动作改写，反推不出发车时长）。
- 改单资格统一由后端判定：待确认照旧；已确认未发车、未锁的正常改单；已发车需要 `scm:order:edit-after-dispatch`，已锁单需要 `scm:order:edit-locked`。列表与详情的 `editable`/`editBlockedReason` 由后端给出，前端不自己拼状态与权限。
- 锁单与解锁是两个权限（`scm:order:lock` / `scm:order:unlock`），默认授予财务与管理员，避免同一角色既能锁又能随手解锁。手动锁单原因码固定为 `MANUAL`，自动锁单为 `AUTO_7_DAYS`，操作人手写原因记在操作日志。
- 已确认订单改单沿用行上已有的报价重新锁定，并按实际数量重算结算金额；非标品的称重实数量不从改单表单覆盖，人工实数量原因一并保留（后端业务规则要求）。已已确认优惠的订单不允许直接改单，需要取消重下或加单；已分拣或已出库的订单不允许增删商品，需称重的新增商品也不允许直接加进已确认订单，统一走加单。
- 发车后改单单独记 `EDIT_AFTER_DISPATCH` 操作日志，锁单/解锁/自动锁单分别记 `LOCK`/`UNLOCK`/`AUTO_LOCK`。

### 称重实发量回写订单（2026-10-27）

- 分拣录入（手工或电子秤确认，两条路径都经 `SortingTaskService.enter`）把非标品的实称量回写到已确认订单行，同时重算行结算额与订单结算合计；签收应收按实发量 × 锁定单价生成，称多少就该结多少。
- 回写只发生在「已确认、未发车、需称重」三条件同时成立时：待确认订单的实发量由销售手工录入，标品实发量恒等于下单量，发车后改实发量会与已出库的分拣记录脱节。回写与分拣录入同一事务。
- 称出 0 不回写：后端要求实发量大于 0，未交货少结的部分走退货或红字，不把订单行改成 0。
- 手工修改实发量放宽到已确认订单：已发车直接拒绝（40917），已锁单需要「锁单后改单」权限；修改后同步重算结算额并记 `ACTUAL_QUANTITY` 日志。

### 非标行先确认后称重（2026-10-28）

- 非标品允许在未录实重的情况下确认订单：实发量保持为空，行结算额与订单结算合计按**订购量 × 锁定单价暂计**，称重后由实际值覆盖。理由：现场是先确认订单、分拣时秤端才出实际重量，要求确认前先填估计实重等于让销售替秤报数。
- 标品仍必须带实发量确认；标品实发量恒等于下单量，不经过称重。
- 分拣计划量取「实发量有值且大于 0 就取实发量，否则取订购量」。建分拣任务不得因为实发量为空被拦，建单也不得改写订单实发量。
- 称重完成后由 `OrderActualQuantitySyncService` 回写实发量并重算结算额；应收按实发量生成，暂计只影响确认时的预估金额与授信检查。
- 授信检查对未称重非标行同样按订购量估算，与确认规则一致，不另立一套估值规则。
- 「先按订单做计划」的环节统一取**计划数量**（`PlannedQuantity`：实发量 > 0 就取实发量，否则取订购量）：授信、分拣计划量、采购需求生成与汇总预览、销售报表成交数量。采购 14:00 备货时还没到 20:00 的称重，采购需求必须按订购量生成，否则整批订单买不到货。
- 退货按已发运数量校验，未称重的行不能退（`ORDER_RETURN_QUANTITY_EXCEEDED`）：退货是对已发记录的红字，不是对计划量。

### 商品行备注（2026-10-28）

- 行备注属于商品行（去皮、切段、分袋），随行打印到客户分拣单/送货单；整单备注另存，两者不能互相顶替。
- Excel 导入与整单粘贴逐行保留备注，不汇总成整单备注；送货单导入不再把备注写到订单头。备注上限 200 字符（迁移 V211）。
- 前端录单明细表、订单详情、粘贴预览都按行展示与回填备注。

### SDP-14 待确认订单批量核价边界（2026-10-17）

- 订单列表批量核价只接收当前列表已选中的 1～8 张待确认订单，只读请求逐单读取正式订单详情与客户定价预览，权限与负责人范围仍按正式订单和定价接口检查；报价仅是检查时点的参考，不锁价、不预留库存、不修改待确认订单。每张订单独立返回核价结果/失败原因，不因某一订单失败假装全部已核价。
- 人工改价行不被自动覆写；商品不可售或价格未知时阻止该单在批量核价窗口直接重算。若操作者逐单确认变更，必须具备 `scm:order:update` 与 `scm:pricing:resolve:query`，填写原因、核对最新待确认状态与订单版本，最终只走现有 `/scm/order/reprice` 由服务器再次定价、限制保存记录并写操作日志。价格预览不能保证重算执行时金额不变，确认弹框必须说明这一点；不新增另一套价格写接口。
- 历史单复用为新单此前已实现，不另建第二套复制命令。已确认订单的保存价和结算记录绝不可通过此功能重写。

### 时价与锁价

- 价格来源优先级固定为：客户协议价 → 客户分组价 → 时价 → 市场价。时价面向所有人，不能顶掉逐客约定与分组约定。
- 时价是**商品规格级**、按时间段生效，区间半开 `[start_at, end_at)`；同一规格的区间不允许重叠，
  重叠会让「现在按哪条算」没有唯一答案。首尾相接不算重叠。
- 时价只影响**下单与预览**的价格解析；已锁定价格的订单行不因时价变动而改价，来源记录为 `TIME_PRICE`。

### 签收后改单与缺货打印（2026-11-02）

- 订单一旦有签收记录（`SIGNED` 或 `EXCEPTION`）就禁止直接改单，持「发车后改单」权限也不例外；数量或金额差异只能走退货或红字更正。应收在签收时按出库实发量生成，原单再改会让送货单、订单结算额与账面应收三份数对不上。
- 客户送货单的「实发量」取已完成分拣任务的正式结果，分拣为 0 的缺货行照印 0；行金额按「分拣量 × 锁定单价」计算，再按该行确认时保存的优惠分摊等比扣减，与应收明细同一算法；合计由逐行净额相加。订单行的 `actual_quantity` 仍不写 0（后端校验与既有入库规则不变），未分拣的行才回落到订单实发量/下单量。
- 采购缺口预览把本批可用库存下限截到 0：账面负库存照实展示，但不作为本批额外需求。负库存是历史欠账，不应让采购员按「负库存 + 本批需求」重复放大采购量。
- 采购分析按商品报表的三组记录各自归期：「计划采购」按原采购单提交日，「实采确认」按 `xsy_purchase_account.confirmed_at`，「采购价差净额」按 `xsy_purchase_cost_adjustment.occurred_at`（`INCREASE` 加、`DECREASE` 减）。10 月提交、11 月确认或更正的采购，其确认量和价差计入 11 月，不回填到 10 月；供应商/采购员/仓库/关键字筛选仍同时收窄三组记录，不修改采购订单金额与入库成本的既有规则。

## 采购与库存

### 代采费用不纳入系统（2026-11-05 客户确认）

- 采购照片底部“加3个点”为代采费用，客户明确系统不用体现；不新增代采费录入、费率计算或导入导出列。
- 不根据照片中的代采费用或含费合计自动反推商品单价、增加采购应付或调整成本。采购、销售及财务继续按既有已确认记录计算，该项不再作为功能缺口或待确认需求。

### 供应商采购单位统一取计量单位字典（2026-11-03）

- 供应商关联商品的「采购单位」只从启用的计量单位字典选择，不再手填；历史手填或已停用单位在编辑时保留原值并标注，避免旧关联保存时丢单位。
- 参考价仍是按采购单位计价的可空 4 位定点金额，前端用数值输入框录入，不按普通文本处理。
- 「优先采购」只表示首选供应商来源，用于供应商列表和同规格比价排序；不自动把采购单分配给该供应商，也不改变采购单选源逻辑。

### 订单、对账与采购边界修正（2026-10-28）

- 整单粘贴预览必须落客户数据范围：越权客户直接拒绝（403），不能只返回匹配结果，否则可以用预览读别人的协议价。
- 对账单「包含过账」需要 `scm:finance:posting:query`：没有权限时勾选被拒，不勾选照常出单，避免从普通对账入口读到过账单据。
- 采购自动补价必须核对计价单位：只取同一 SKU、同一采购单位的最近已提交价；没有同单位参考价就保持待定价，不拿公斤价当斤价。
- 采购到期自动锁单前先在同一轮跑一次自动补价（各自独立 try/catch），避免锁单抢先把还能回填的待定价单锁死。

### 采购每日清单与保存的数据

采购每日清单按 Asia/Shanghai 的采购单提交日统计，取前一自然日区间；纳入已提交、部分收货、已收货和短收关单，排除取消与删除数据。结果按商品、采购单位及采购单保存的编码和名称分组，不跨单位求和；采购金额不代表财务应付。清单是生成时保存的数据，重复生成不覆盖既有结果；后台任务使用 XSY 调度，查询与导出均按采购员和仓库授权范围相交。

采购订单行、收货、应付等历史数据保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。采购时的单位来自供应商商品关系，不得用商品销售单位替换；需求单位沿用销售订单当时的明细。采购单提交后不再回读供应商或商品主档；收货记录数量和重量，金额从采购行记录派生。

### 采购净需求、通知、打印与异常聚合

- 净采购按仓库、商品和单位分别计算，需求扣除同维度可用库存、有效在途未收数量及已有采购覆盖；单位之间不换算。计算只保存输入、解释与建议，不改库存。生成需求引用同一计算结果批次并支持防重复处理；回看不得回表重算。
- 通知复用 XSY 站内信，不新增消息中心或外部渠道。库存预警按周期扫描 `NORMAL → LOW/HIGH`，异常持续期间不重复通知，恢复正常后再异常可重新通知；没有有效仓库授权接收人时不广播。消息跳转不授予数据访问权。
- 打印模板采用字段白名单约束的 JSON 模型，由服务端渲染；不允许任意 HTML、脚本或数据库字段。打印记录保存模板与业务内容，重印读取原来保存的资料并按操作者当前权限重新过滤金额。打印和预览不触发提交、发车或分拣完成。
- 异常聚合只读现有分拣缺货/差异、订单实量差异、配送异常签收及退货/退款待处理和售后拒绝记录，不建工单状态机或自动补偿。分拣缺货由已记录的 `OUT_OF_STOCK` 结果识别；当前仓库库存只作附有记账单位的参考，不用于反推历史订单缺货，也不跨单位换算。筛选、列表、统计和导出共用记录规则与授权范围；处理仍回到源业务模块。退款单状态不等同于实际资金到账或返还。
- 换货按“先退货批准并完成实物接收，再建关联替换订单”执行；替换订单是独立新建订单（新建即待确认），按当前客户、地址、商品、定价、预留、配送及结算命令重新校验，不自动抵扣退货红字应收或退款。每张退货单最多关联一张替换订单，原订单与库存/财务记录不被改写。已出库订单的客户实收数量更正只能新增带原销售单位、已出库基线、前后数量、原因和操作人的记录；不得超过正式实发量，不回写订单行、出库流水或财务，退货、补送、退款由人工分别走正式流程。

采购订单行、收货、应付等历史数据保留事件发生时的价格、单位、结算主体及名称，不得由当前主档重算覆盖。业务状态变化追加或更新正式领域记录，报表保存的数据不取代来源记录。

### SDP-07 内部采购询价实施边界（2026-10-17）

- 询价只从状态为 `READY` 的净需求计算批次派生；与原批次生成需求命令共用批次行锁，禁止对 `GENERATED` 批次再创建询价。按同批次商品规格与需求单位归并保存建议量；任一归并来源行已关联当前有效采购需求则整组不可再建询价，不另算实时库存、不建立第二套需求账本。
- 权限同时受采购员归属和仓库范围约束，询价创建、报价登记、确认分别授权；员工代录报价只证明本系统登记记录，**不等于供应商登录提交或电子签署**。供应商端身份体系、安全认证和外部接口需要独立裁决。
- 报价行只能新增修订版本，保留报价人、供应商、单位、价格和有效期；同供应商只对比最新有效修订，新增供应商报价必须在询价接收截止前；采购员选用报价可在接收截止后进行，但必须保证询价未被选用、版本一致、所选最新报价仍在有效期内，且供应商采购关系仍有效。询价单一次只能确认一条报价，保存选中的报价 ID，之后不能修改，由采购服务在持有询价行锁时校验报价属于该询价，不新增业务外键，也不改原报价。
- 报价单价不自动作为采购订单成交价。把已确认报价转为采购单并保存价格来源、跨单位换算、供应商端确认流程另行实施；在正式人工确认采购单前不触碰订单、库存、资金记录。

### 采购分享与现场回填

- 采购单分享用**令牌**授权，不用账号：令牌 32 字节随机、只存 SHA-256、有有效期（默认 7 天）、可撤销；
  一张采购单同一时刻只保留一条有效链接，重新分享会让旧码当场失效。
- 手机端回填**只能新增记录**（`xsy_purchase_share_feedback`），不直接改写采购单：现场误填不能悄悄改掉已提交的单据，
  采用与否由后台人工确认。

## 分拣、设备与追溯

### P1 分拣管理裁决

分拣维护正式已分拣量，不修改订购量、不改库存、不生成出库；已确认、未发车的非标行按「称重实发量回写订单」规则同步实际数量与结算额。活动任务独占有效订单行；取消时释放明细，完成任务须为每条有效明细提交结果。重新打开须校验版本并保留数量与原因。配送候选订单须已确认且所有有效明细均被已完成任务覆盖。分拣员范围与仓库范围相交；打印只记录操作，不改任务状态。称重结果须由人工接受，一键处理不得替非标准品推断重量。

#### 分次分拣与确认统计（2026-10-17）

- 分次人工记录是同一任务明细下追加的作业记录，必须有操作人、时间、数量、防重复请求编号与行版本防重；未确认分次不回写分拣明细的 `sorted_quantity` / `result`，不参与配送资格、销售出库或财务记录。最终确认仍由已有明细录入命令显式执行，完成任务仍要求全部有效行已确认结果。
- 新记录按每次追加量累积；最终确认量若偏离事件累计量，须写原因并追加差额事件，原事件不删除。重开允许带原因调整已确认结果；跨人、跨仓和取消/完成后写入仍按既有权限与状态机拒绝。
- 只读“最终确认统计”只覆盖已完成任务，按最后确认人、仓库和销售单位分组；不将其误称为各参与者的劳动贡献或工资核算。分拣差异阈值和人员计件报酬没有业务定案，不能用页面默认数字代替裁决。

#### 非标品电子秤接入边界

- 称重工作台从现有分拣任务中选择客户订单与商品规格，不新建另一套订单或分拣单。设备上报必须携带唯一事件键、设备编码、分拣任务和明细、原始重量、单位、稳定标记与采集时间；秤端适配 SOHE RS232/厂家 HTTP 等协议；实际现场协议、连续输出、单位与校准仍需核对。
- 原始读数仅保存为设备事件。**人工接受稳定读数**后才复用 `SortingTaskService.enter` 写入已分拣量；非标品由操作员裁定 `NORMAL/SHORT/OUT_OF_STOCK/OVER`，非正常结果必须说明原因。上报端不得传入已分拣数量或直接触发订单、库存、财务变更。
- 接受读数要求设备单位与订单行保存销售单位相同；尚未实现安全的单位换算，不允许把公斤、斤、件直接混用。历史上报事件的处理状态和操作者留痕，不允许通过再次上报覆盖原记录。
- 开发环境仅允许**前端本地只展示**模拟重量，不能形成设备事件或分拣记录。Windows Agent 已有设备适配、绑定、实时流与离线队列；本地演练不代表真实设备或平台组合验收通过。采集容差阈值和计量标定不能用页面默认值代替确认。

### 采购收货批次与批次库存（2026-10-18）

- 批次追踪按**仓库开关**启用：只有新建且尚无库存的仓库可以开启，开启后不可关闭；存量仓库保持关闭，不做存量回填。开关只在创建时设置，编辑态只读。
- 批次仓的采购收货**必须逐行登记批次**，非批次仓不录批次且行为不变。收货行下挂的批次数量之和必须等于本次声明收货量，由采购收货命令校验保证。
- 内部批次号由系统发号（`LOT` + 北京时间业务日 + 全局序列），不进入前端编辑控件；**来源生产批号**由供应商或现场提供、原样保存、允许为空，不得冒充系统批次号，也不要求唯一。
- 批次是独立子账：`xsy_inventory_lot_balance` 与仓库 SKU 总账并存，不把总账按批次拆行。不变量为「同一仓库同一商品同一单位下，各批次余额之和等于总账余额」。
- 批次流水只能新增，禁止改写或删除；更正只能追加补偿流水，沿用库存流水既有约定。
- 销售出库与赠品出库按**先进先出**自动分摊批次，现场不选批次；每条出库流水按批次拆成多条子账流水，子账数量之和等于总账流水数量。
- 销售退货（含拒收退回）必须**回原出库批次**：按原出库流水的批次关联回写，找不到原批次时拒绝并给出明确错误，不猜批次、不新建批次。
- 批次仓的盘点、调拨、损溢、规格转换在二期之前**一律拒绝**，避免出现没有批次语义的库存动作；非批次仓不受影响。
- 批次**不独立核算成本**：批次余额只记数量与单位，成本仍按仓库 + 商品规格的平均成本；批次毛利与批次成本另行裁决。
- 批次仓的记账单位仍是采购收货时的当时的单位，不做单位换算，与现有「同一仓库同一商品只允许一个记账单位」的规则一致。
- 新增「批次库存」查询能力，权限只授给已具备库存查询权限的角色；批次来源批号按现有数据范围过滤，不因批次新增跨仓可见性。
- 后续 V152～V158 已实现 L2 独立包装码身份、分拣绑定、打印、作废及更正保护：`unit_code` 不透明、全局唯一、永不复用、不嵌日期，且**一码一批**不做混批；批次码不冒充逐包装码。仍需补逐码正式出库/退回与现场拆包规则。

### V158 包装码出库与并发保护（2026-10-19）

- 更正申请与批准均按原绑定的销售订单行查询**正式确认出库**；已经出库的订单行不允许解绑重绑（41525），已出库分拣行也不能事后补绑新码（41526）。出库后纠错必须走退货、售后或将来专门的单元级逆向补偿，不能通过更正单把客户已收实物的码释放。由于尚无单元级正式出库关联，以整个订单行为拦截粒度是有意保守，部分出库后也不能解绑该行的码。
- 包装码绑定、自动绑定与更正审批统一先锁业务行再锁包装码；正式出库锁相同订单行并持有到事务结束。持锁后重新检查码状态、有效绑定、累计绑定量及正式出库状态；解绑还校验申请与单元/原绑定一致、申请待审批且非本人批准。作废与绑定共用码锁，有有效绑定时拒绝作废。
- **尚未有逐码出库记录，批次级净出库不能证明某个已发码包装离场。** 发码额度改为「该批次累计发码量（包括已作废码）＋本次 ≤ 批次当前余额」，不再用批次净出库推测释放额度。这会让部分发货后的后续发码变得严格甚至无法继续；这是避免重复贴码的主动校验失败时拒绝操作，而不是完整的发码额度生命周期。未来必须先建设单元级出库和退回关联，才能凭逐码离场记录安全地释放额度。

### 包装码（一物一码）实施边界（2026-10-19）

- 包装码是**贴在实物上的身份**，与批次严格分层：**一码一批、不做混批**，一个批次可以有多个包装码；批次码不冒充逐包装码。
- `unit_code` 由系统发号、**不透明**（Base32 序号，前缀 U）、不嵌日期与业务含义、全局唯一、**永不复用**；作废只能新增事件，原码保留。
- 发码总量受批次当前余额约束：包装码描述已经存在的实物，不能在库存之外凭空造出实物身份（超限 41504）。
- 发码入口包括「包装码」页按批次发码，以及设备称重后人工选来源批次请求平台发码；均使用平台正式包装身份，现场验收状态见 status.md。
- 历史记录查询只读，回答「这个码从哪来、到哪去」：单元 → 批次 → 收货来源（收货单 / 供应商 / 确认时间）→ 出库去向（出库单号 / 时间 / 数量）。
- **V153 后客户维度可来自分拣绑定**：仅证明扫描绑定时承诺给哪张订单/哪个客户，不等于正式发车或签收；出库流水仍按批次分摊，不能从批次出库倒推“这枚码已经卖给了谁”。
- 包装码标签复用 `scm/print` 域的受控模板与保存记录，新增 `TRACE_UNIT` 单据类型；默认模板用 80mm 热敏纸，只放码、批次、商品、包装量与绑定后的客户/订单号，不含价格与成本。
- 标签可以先贴后绑：未绑定时客户与订单号留空，标签仍表示实物身份；打印不代表已分配给任何客户。
- 包装码可以作废，但**只能作废未绑定的码**：已绑定的码代表一件承诺给客户的实物，作废后历史记录会互相矛盾，现场应先走退货或更正流程（41512）。
- 作废只把码标记为 VOID 并追加一条 VOID 事件，原码保留、永不复用；重复作废被拒（41513）。
- 分拣扫码绑定把包装码绑到**分拣任务行**而不是出库行：扫码发生在装箱现场，分拣行上已有客户与当时的订单资料，出库单要到发车才生成。
- **一码一物，同一时刻至多一条有效绑定**：绑定行不可 UPDATE/DELETE；V157 更正单经他人审批后仅追加解绑记录，可在**原订单行尚未正式出库前**重新绑定，历史客户和原绑定不删除。绑定、解绑与发货由后端共用订单行锁，并在持锁后复核，禁止并发双绑或出库后改绑。
- **绑定后不可直接作废**（V155 起）：已绑定的码代表一件已承诺给客户的实物，作废后历史记录会互相矛盾（41512）。
  绑错的处理走**更正单**（V157）：申请 → 他人审批 → 追加解绑记录（`xsy_trace_unit_unbind` + `UNBIND` 事件），
  仅在原绑定订单行未正式出库时，批准后该码回到可绑定状态、可以重新绑到正确的分拣行；出库后须走正式退货/售后补偿。申请与审批**不得是同一人**（41522），
  一条绑定只能被批准撤销一次；原绑定行与解绑记录都留在账上，**不提供无痕解绑**。
- 更正后「同一时刻只有一条有效绑定」由后端持码锁后重新查询有效绑定保证（解绑后允许重绑，不能使用永久的 `UNIQUE(unit_id)`），
  这样解绑—重绑才成立；分拣行的已绑数量只累计**有效**绑定。
- 绑定校验顺序即语义：码存在且有效 → 未绑过 → 商品规格与批次一致 → 该分拣行绑定总量不超过实拣量（41507–41509）。
- 历史记录查询的客户维度只来自**分拣绑定**，不由出库批次分摊倒推：批次是共同来源，不是某一袋的归属。

### 采购回填归属与包装记录查询边界

- 回填明细必须属于该采购单：令牌能看到的范围就是它能写的范围，不允许跨单写入。

- 历史记录查询里的「批次相关出库」是**批次级**记录：它能证明这一批货去了哪几张出库单，**不能**证明当前这一袋已经出库；
  单元级出库要等分拣/发车按包装码绑定出库行之后再补，界面不得把两者混为一谈。

### 一物一码扫码溯源与称重打通（2026-10-22）

- 扫码页面向客户与监管，凭据是标签上的 `public_token`，不是 `unit_code`：`unit_code` 由自增序列发号，
  相邻码可推算，不能当公开访问的凭据。`unit_code` 仍是员工侧主键。
- 公开页只返回脱敏字段（客户名、订单号），不返回内部主键、操作人与批次级出库明细；每次查询写
  `xsy_trace_public_query` 并按 IP 与令牌限流，用于发现枚举爬取。
- 包装码的批次归属只存在于发码环节，由现场选定（默认先进先出）。不给分拣行加 `lot_id`，也不建批次消耗账本：
  销售出库本就不按批次扣减，再建一张就是第二套账，且等于引入混批/拆包谱系。

- 重量写在包装码主体侧（一码一重），关联方向是 `unit.weighing_event_id → xsy_sorting_scale_event.id`：
  称重事件是追加的设备记录，不塞业务绑定列。
- 称重筐只发码、不立即绑定：`bind` 校验「已绑定量 + 本码数量 ≤ 实拣量」，而实拣量要等集合完成才写入，
  逐筐绑定会在第一筐就超量。绑定在明细完成时整批建立，装不下的码留在未绑定，不中断分拣完成——
  分拣完成是业务记录，追溯绑定是它的附属结果。
- 商品资质保留 `PRODUCT_QUALIFICATION` 与 `scm:trace:file:manage`；旧 `LOT_INSPECTION` 关系保留供内部查阅，

  `biz_id` 为报告 ID。仅关联已有已确认收货记录的真实批次，不修改采购、库存、分拣或包装码记录。
  管理权限为 `scm:trace:inspection:manage`，查看沿用包装码查看权或报告管理权，并叠加批次所属仓库范围。
- 报告状态为 `DRAFT / PUBLISHED / WITHDRAWN`；结论为 `QUALIFIED / UNQUALIFIED / UNDETERMINED`。
  按既有 SCM 枚举约定，Java 枚举名、服务端校验与接口字符串一致，中文由枚举 `desc` 与前端 XsyEnum 映射；
  未知值不按合格处理。过期是按有效期即时计算的展示状态，不增加生命周期枚举。
- 草稿可编辑，批次不能改绑；发布时必须有可读取的 PDF/图片，最多20个、单个不超过20MB。
  报告编号唯一；发布后内容保存，仅可撤回，撤回记录保留且不重新发布。更正通过新报告记录处理。
  保存、发布、撤回在同一业务事务内追加操作人和时间，版本号与行锁拒绝旧页面覆盖。
- 公开查询仅返回当前包装码所属批次的已发布报告；不合格、未判定照实展示，不能显示合格标识。
  到期时间可空，非空时按时间点判断；录入与日期边界使用北京时间。过期报告保留检测信息及过期提示，
  不提供附件；撤回报告、草稿和作废包装码均不公开报告附件。商品资质不构成检测合格依据。
  公开报告页面及报告下载入口使用同一报告查询结果、禁止缓存；资质入口不返回受报告控制的附件关系。此处约束接口展示；按 2026-11-02 的公开上传规则，已公开对象 URL 本身可匿名读取，撤回和过期不撤销其公开可读性。
- 标签二维码由前端生成，后端不引二维码库；链接规则只在 `TracePublicLinkBuilder` 定义一次，
  后台打印与秤端打标取同一个值。未配置 `scm.trace.public-base-url` 时标签只印码不印二维码。

## 配送与地图

### P2 物流配送 L3 裁决

发车是销售出库的唯一生产入口，数量取已完成分拣结果；整条线路原子提交，任一订单不合格则整体拒绝。库存变更只经库存域命令，预留与出库在同一事务消费或释放。发车使用防重复请求编号与线路版本，签收校验线路订单行版本和司机范围。签收只记录 `SIGNED` 或带原因的 `EXCEPTION`，不撤销出库；退货必须追加独立反向记录。打印不发车。当前路线地图只展示已确定停靠顺序；算路不可用时降级显示，不能改顺序、库存或线路状态。实时 GPS、部分签收和自动退款不在当前范围。

- M0 的地区、坐标和 CRS 字段及 M1 中国地图大屏已实现。客户、仓库、供应商和停靠点均已接入通用选点组件（供应商点位见 ADM-09）。

## 财务与报表

### 财务月成本、费用与采购核对（2026-10-31 负责人确认）

- 客户利润的税费、服务费、运费、扣点按「客户 + 费用所属月份」登记实际金额，不推导费率或计税基数。多笔费用按月汇总；更正保留原记录，先追加作废记录再重新登记。费用不冒充收付款或核销，不修改客户应收余额。客户月利润的收入取当期正式应收与红字净额，商品成本由财务按客户、月份登记实际金额（含赠品和已分摊采购价差），不再依赖收货或库存均价。有效成本与费用多笔累加，空成本表示未登记，显式0表示已核实零成本；有销售记录但未登记成本时商品成本、毛利、扣费后利润均留空。费用不重复计入商品成本，已计入实际商品成本的价差不再额外扣一次。
- 财务核对实际采购数量与已补齐的采购价格后，可一键确认采购。该操作在一个事务内保存只能新增的实际采购确认保存的数据并生成应付，不创建收货单、入库单或库存流水。继续校验采购归属、仓库范围、成本权限、单位、价格、版本和防重复处理；零数量可表示某行未采购，但至少一行有实际采购。采购确认与旧收货入口互斥，采购单转入 ACCOUNTED（采购已确认）终态，不再列入待收货或在途采购；确认后不可取消采购或覆盖原单价。
- 采购确认或旧收货后发现采购价错误，在更正当期追加价差，不改原采购、收货、库存流水或已出具的历史报表。更正必须关联实际采购确认或旧收货明细并说明原因；不把当前采购价套回历史出库成本。
- 采购价差调增追加正常应付，调减按同一采购确认/收货明细的原应付及此前调增应付追加红字，可冲余额不足时整笔回滚。价差属于当期采购成本调整，供应商对账单包含原确认、价差调增、价差红字及核销。旧库存成本毛利表保留未分摊价差栏目；客户月利润只扣财务登记的实际商品成本，不自动分摊价差。客户月利润要求完整订单范围和成本权限，客户授权范围独立收窄，不要求仓库范围。
- 独立退货按自身客户、当时的商品资料参与毛利。批准时冲减收入，实物接收时按接收成本冲减销售成本；未接收部分归未分配仓库，已接收部分按接收数量归实际退回仓库。客户与订单负责人范围同时收窄到客户当前负责人，仓库范围继续取交集。
- 旧库存成本毛利查询中，出库时缺少采购成本依据的缺省零成本视为待确认，毛利不展示为完整金额；明确有采购成本依据的零成本仍可正常参与计算。后续补录入库不覆盖原出库成本。
- 负库存月度留存保存某一仓库的完整当前清单、费用估算与实际取数时间，同月可留存多个版本。月份由实际取数时点确定，历史月份只读已有留存，不允许用当前余额补造历史月末数据；留存、查看和导出均复核成本权限与仓库范围。留存不产生报损或库存调整记录。

### 经营指标与可见范围

- 同名经营指标使用同一时间轴、状态和金额列；“今日销售额”按 `confirmed_at`、已确认交易状态集合（已确认、已发车、已签收、签收异常）、`settlement_total_amount`，创建轴须称“今日下单金额”；“今日采购额”按 `submitted_at`、已提交状态集合、`total_amount`，状态集合由采购枚举提供。

### P3 Finance R1 裁决

Finance 只读消费订单、采购、库存、配送和退货记录，不写这些业务表。财务记录是追加记录；更正追加反向记录，金额保持正数并由类型表达方向。自动应收、应付与触发业务记录同事务提交；收款登记不自动核销，冲正只允许在原记录未被核销使用时追加。订单、财务与库存不得形成第二套状态机。已确认退货不因红字应收余额不足而被阻断；退款付款须与完成的退款记录一致。

### 订单资金全额核销与纯余额返还（2026-10-04）

- 负责人确认采用全额关联：支付 100、正常应收 70 时，订单专属资金核销 100，超额 30 单独显示，不自动退款或增加钱包。售后 RED 不改历史核销，人工 REVERSE 保持整笔纠错语义。
- 纯余额售后返还与退款完成在同一事务追加原钱包 CREDIT；每个资金来源唯一，累计不超过原消费本金，并与同来源渠道或人工退款互斥。混合及多交易退款按已确认的剩余可退本金比例分摊。
- 退款意图与分摊先提交，再在事务外调用渠道；恢复始终复用持久化退款编号，只有渠道明确报告“不存在”时才重新派发。查单异常不能当成不存在，也不能另建退款号。渠道实退与申请额不一致时保留审计记录，不伪造分摊成功、不自动补差；只有全部来源成功后才登记唯一退款付款。旧退款路径与新分摊路径互斥，不自动迁移历史退款。
- 恢复租约和审计在短事务中提交，外部查询不得持有订单数据库事务。部分资金来源失败可独立重试，但必须保留订单锁序、来源防重复处理与各来源数据库写入的事务边界。

### 集团共享钱包授权

- 集团共享结算的授权开关 `xsy_customer.shared_settlement_enabled` **默认关闭**，只有结算模式为 `GROUP` 的集团主体能置真；
  打开后允许后台为子客户执行集团钱包扣款，额度只看钱包余额，不叠加集团授信；小程序不提供资金写入口。

### 营销优惠生命周期、赠品与限时特价规则（2026-10-03 负责人确认）

本节补充固定优惠券、赠品与限时特价的状态及成本归属规则。

#### 优惠券生命周期

```text
确认订单      AVAILABLE → RESERVED   （已确认优惠时占用）
正常签收      RESERVED  → USED       （与应收同一时点、同一事务）
异常签收      保持 RESERVED           （EXCEPTION 既不形成应收，也不算用掉）
部分/全额退款 保持 USED
现有订单取消  不处理券                （确认后的各阶段不允许取消，cancel 碰不到 RESERVED）
未来撤销确认  RESERVED  → RELEASED   （当前无触发点，保留语义）
需要返券      重新 issue 一张新券，不复活旧券
```

- 券核销挂**正常签收**而不是退款：签收是订单级不可逆终态，也正是应收的形成时点，券「是否已被一笔真实成交使用过」与它对齐。
- **退款不恢复券**：退款反向的是金额（按保存分摊），券回答的是权益是否已被使用过，两者不能混；允许 `USED → AVAILABLE` 会让「100 元订单用 20 元券、退款后券回来、再用于下一单」变成重复营销权益。若业务确需「全额退款返券」，另做重新发券（新实例），审计上才分得清「原券用掉了」与「补偿了一张新券」。
- `RELEASED` 是**历史终态**，不等于 `AVAILABLE`：它是「这张券被释放过」的痕迹。要把权益还给客户，应原券 `RELEASED` + 重新 `issue` 新券。
- 优惠券列表的累计张数按券实例统计：后台发放取 `ADMIN_ISSUE`，商城领取取 `MALL_CLAIM`，已使用取当前 `USED`（包含两种来源）。已知券让利只读已使用订单历史资料的券优惠额，缺失保存的数据单列数量，不把未知金额当作零。不按模板当前启停状态重算，也不把 `RESERVED` 算为已使用；当前没有时间窗口。

#### 满赠（赠品）

- **不减订单收入**：赠品金额恒为 0，`FULL_GIFT` 的优惠额保持 0 是对的。
- **赠品必须走正式库存出库**，出库来源明确为促销赠品；赠品出库成本**计入该订单的履约成本**，因此销售毛利要扣掉赠品成本。
- **不把赠品塞成普通 `sales_order_item`**：那会污染采购需求、销售数量、销售额与客户购买商品分析。用单独保存赠品记录（订单 / 活动 / SKU / 数量 / 单位 / 保存的数据）。
- 赠品权益在**订单确认时保存**（`order_promotion_gift`，保存的数据不可修改），出库、分拣、小票与成本归集都读它，不在各自环节重算活动规则。
- 门槛按**订单基础合计**判定，不按逐条作用后的剩余金额：同单另有满减不该把满赠门槛压没。
- **运行规则（2026-10-03 确认）**：赠品出库挂**发车**时点，与销售出库同一时点、同一仓库；赠品库存不足时**不阻断订单确认**，在出库时报错、由仓库补货后重试；赠品**进分拣清单与小票**（仓库照单备货），分拣不写回赠品数量。

#### 限时特价

- **不改基础定价链**：逐客协议价 → 客户分组价 → 时价 → 市场价 保持不动，限时特价不参与这层的优先级竞争，也**不进 `PriceResolver`**。
- 它作为 Promotion 在**基础价之后**作用：`基础价解析 → 限时特价 → 满减/折扣 → 优惠券`。
- 保存记录仍能回答「原基础价是多少、为什么卖这个价、按哪个活动哪一版、减了多少」：订单行金额仍是基础价规则，让利作为**独立记录**落 `order_discount.special_discount_amount` 与逐行分摊，**不把订单行的价格来源改成「限时活动」**。
- 保护规则：**限时特价只能把基础价往下压，不能抬高**（特价 ≥ 该行单价时让利为 0）。
- 分配规则：让利按**行**归集（`行基础金额 − 数量 × 特价`），不参与按金额比例分摊 —— 特价针对某个 SKU，摊到别的行上会让退款反向错行；同一行只让一次价（已被更靠前的特价命中过的行跳过），因此「按优先级顺序作用」在特价上依然成立，且每条活动记进保存的数据的让利额之和恰好等于总让利。

### 微信小程序账号与退款分摊规则（2026-10-10 负责人确认）

- **混合支付及多成功交易退款按原资金比例分摊**（已确认，不再是待裁决事项）：一张业务退款按原订单各成功资金来源的**剩余可退本金比例**保存分摊，尾差按确定性规则归集；不默认余额优先、在线优先、按时间顺序或按比例以外的其它顺序。余额来源退回原保存结算钱包，在线来源对应原支付交易。
- **一个客户可绑定多个采购账号**：账号归属客户，不再限制「一客户一账号」；账号由后台管理员开通、停用与重置密码。V121 初建的一客一号唯一索引由 V122 移除，登录手机号仍全局唯一。
- **一个账号切换多个企业**（集团/多门店采购）为**后续独立功能**，本期不实现：当前账号只归属一个客户，切换企业需另立账号—企业授权模型，不并入本期商城账号。
- **常购商品接口以现有后端返回结构为准**：保留后端 `GET /scm/mall/catalog/frequent` 的现有约定（`List<MallProductVO>` 裸数组 + `days/limit` 参数），由前端修正请求参数与响应解析；不为此新增包装 VO 或分页字段。

### 商城结算约定与 COD 分笔（2026-10-15 确认）

#### 小程序仅下单（2026-10-27，客户确认）

- 小程序只承担订货、查询进度、取消与售后申请，不支持微信支付、余额扣款或充值；资金及结算由后台处理。钱包、账单入口从客户主导航隐藏，历史记录不删除。
- 新商城订单直接写正式销售订单，来源保持 `MALL`，服务端设置不可由编辑表单更改的 `mall_order_only=true`；历史订单默认 false。所有新订单统一提交至现有 `PENDING`，标准品也不在下单事务中自动确认。
- 客户下单不选择付款方式，不因余额不足、授信不足或未开通货到付款而拒绝订货；商品可售性、正式报价、数量、客户/地址/配送仓归属、防重复处理与价格指纹仍需校验。优惠只预选和试算，后台确认时再重验和占券。
- 新模式订单在后台确认时明确选择 `WALLET / CREDIT / COD`，在同一事务中保存约定并沿用原确认校验。不能以空值跳过校验，也不能把“未选择”自动当货到付款；确认不表示已收款。已有结算约定不能通过确认请求改写。
- 客户身份及负责人保存的数据继续由服务器决定；有负责人进入受限销售列表，无负责人进入现有待分配池。后台与客户读取同一订单，无额外同步账本。
- 已成功的下单请求再次提交时仍返回原订单；旧客户端传入的合法付款方式仅保留在请求指纹用于兼容，不采信为新订单的结算约定。旧客户端支付写入口统一拒绝；后台支付、集团结算、历史核销及退款规则保留。

#### 已有结算约定与财务处理

- 已选择结算方式的商城订单，后台支付入口也严格遵守原约定；当前没有“授权改结算方式”命令。历史结算方式为空的后台订单仍按原支付入口处理。
- COD 表示实际收款时机，不是资金形式；登记每笔实收时仍选择现金、银行转账等实际资金方式。
- COD 允许同一订单按实际到账分笔收款，每笔有独立的防重复处理来源和明确订单归属，合计核销不超过正常应收剩余。V131 的一订单一笔旧记录保持不变；V132 起新收款使用分笔来源。客户关系变更不改写原订单与应收保存的结算主体。
- 授信敞口在未开应收阶段只预占账期 `CREDIT` 订单；历史空结算方式订单继续沿用旧规则。已开正常应收无论原结算方式如何，仍按未结净额计入敞口。余额与 COD 订单在签收前不占用账期额度。

### 客户推广来源

- 客户推广码属于**客户**，归属业务员取该客户当时的 `seller_id` 保存的数据：客户换业务员后，历史扫码仍能说清当时是谁的线索。
- 扫码只**记录来源**，不改任何归属；把人挂到业务员名下发生在后台建客户时（业务员按最近一次扫码归属预填，管理员可改）。
- 一个客户同一时刻只有一条有效推广码，重新生成让旧码立即失效；扫码记录只能新增，不修改也不删除。

### 商城装修控制台（2026-10-25）

- 装修入口仍是一个菜单，后台用标签页分为首页、首页弹窗、公告、条款、关于我们、售后规则与店铺；主题、弹窗、单页与店铺各自独立保存，不要求一起发布。

## 界面、查询与打印

### 用户界面用语

- 面向用户的菜单、页面、操作记录、校验提示、导出和新打印统一采用业务用语：红字应收/应付称“应收扣减/应付扣减”，红字记录称“扣减记录”；核销称“账款抵扣”，反向/冲正称“撤销记录”；账龄称“账款到期情况”，过账称“外部账单记录”，毛额称“优惠前金额”。优惠券的核销称“使用”，不套用账款抵扣。
- 应收指客户应付给我们的货款，应付指我们应付给供应商的货款；扣减、账款抵扣与实际收付款分别表达。撤销收付款记录只更正系统记录，不表示自动退款或追回付款。外部账单只留存对外账目，不增加客户欠款，不登记实际收付款，也不参与账款抵扣。
- 报价单价与订单单价分别对应报价结果和订单保存的单价，不混成一个字段。优惠试算结果称“优惠后应付”，不能称“客户实付”；客户收货数量更正只记录数量，不能与实收款混淆。
- 价格指纹等提交校验信息不直接展示；精度要求写明“最多保留4位小数”及原有正负限制。履约称“配送进度/发货与签收”，授信额度称“赊欠额度”，净需求批次称“采购需求汇总”，净采购缺口称“还需采购数量”。取消预留、取消分拣分配和取消优惠券使用分别说明，不用同一个“释放”掩盖业务差别。
- 对账 Excel 与新打印共用中文类型名称；供应商的扣减称“应付扣减”，客户退货称“退货扣减”。收付款及抵扣的撤销记录导出为“撤销记录”，不直接输出 `REVERSE` 等内部代码。
- 仅变更显示名称，保留现有接口、权限码、枚举值、数据库字段、金额计算和追加记录规则。新打印采用当前文案；历史正式打印继续读取不能修改的记录，客户/供应商原始单据、历史操作原因和用户自建帮助内容不批量改写。

### SDP-14 订单辅助标签边界（2026-10-17）

- 订单标签是独立的人工分类，不承载状态、履约或财务含义；每张销售订单最多一个当前标签。设置新标签替换旧值，清空停用当前关联，操作不改变订单状态、版本、金额或库存。沿用现有关系表，以 `active` 标记当前关联并按 `order_id` 建立生效项唯一索引；原关联保留。历史多标签保留最近建立的一项，同一时间按标签编号倒序稳定选择。标签目录可维护多个可选项；单笔和批量订单分配均为单选。
- 标签查询复用 `scm:order:query`，创建/打标/取消还必须具有 `scm:order:update`；列表使用 `SalesOrderDao.query` 中已有的业务员授权范围，再与标签关联做 EXISTS 交集过滤。服务端批量变更最多20单，先按订单 ID 排序加行锁，再逐张核实业务员范围，任何一张不符合要求则事务整批失败，不接受客户端指定的负责人、订单状态或数据范围。重复设置同一标签或清空无标签订单不产生额外变更；旧 ADD 请求按替换处理，旧 REMOVE 只移除相同的当前标签，不刷新主订单版本和交易账本。
- 订单列表允许全状态选择用于打标，但“批量核价、批量删除待确认订单”必须全选待确认订单才能启用。标签创建者允许新增统一标签；标签目录归运营侧共有，暂不提供删除目录或修改历史名称，避免破坏已有订单展示。正式订单打印单据、模板权限及打印日志另行实施。

### SDP-08 查询与自定义导出列约束（2026-10-17）

- 个人常用筛选方案仅保存服务器允许的组合筛选谓词，不保存业务结果、日期、其它基本筛选、查询范围或用户的权限保存的数据。按已认证操作人及业务页面双键隔离，每人每页最多20条，名称唯一，服务端创建时和读取后都重新按**当前**字段白名单验证，过期方案不得应用但允许本人删除。读写删除接口均要求页面查询权限，客户端不得提供操作人 ID 或数据库字段名。

- 商品、销售订单与采购分析的首批自定义导出列仅采用服务端声明的稳定字段键，字段名不参加 SQL 拼接；原业务查询、数据范围、成本可见性、行数上限和导出权限不得改变。自定义列只查询结果**已经由正式服务完成授权和业务过滤的结果**，不能再查一套宽松数据。
- 服务端元数据接口根据当前成本权限隐藏受限列；显式请求受限列时服务端再次拒绝。未传导出列参数保留原格式向后兼容；显式空列表、重复键、不认识的键、超过列数限额一律拒绝。
- 动态组合条件只支持服务端当前发布的字段、固定操作符和值类型；限8项，条件按 AND 收窄。条件映射到原业务查询 DTO，不用客户端传来的字段拼 SQL；与原有筛选对同一字段取不同值须拒绝，不得静默覆盖。只在明确试点的商品查询、销售订单明细和采购按商品查询/导出内生效，其它报表维度的查询语义不随之改变。
