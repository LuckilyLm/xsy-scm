# 商城与小程序统一规划

状态：现行规划
更新日期：2026-09-11

## 1. 定位

商城用于下游客户自助下单，管理端负责商品、价格、客户可见性、营销内容和主题配置。微信小程序首发，H5 作为同一业务能力的另一客户端；两个客户端共享后端合同，不分别维护业务规则。

当前代码已经包含 `xsy-scm-miniapp`、Web 商城页面、商城客户身份、地址、购物车、目录、首页主题和下单基础能力。因此后续工作以稳定化和业务闭环为主，不再按“从零创建小程序”规划。

## 2. 技术与边界

- 管理端：React + Vite + TypeScript + Ant Design。
- 小程序：Taro + React + TypeScript，微信小程序首发，保留 H5 构建能力。
- 后端：复用 `product`、`customer`、`order`、`marketing`、`mall` 领域，商城客户端只消费面向客户的聚合接口。
- 客户身份与后台员工身份分离，不复用后台菜单权限作为商城授权模型。
- 价格、库存、促销资格和订单金额由后端权威计算，客户端不得自行决定成交结果。
- 不将 Ant Design、后台路由、Cookie 假设或管理端 DOM 组件移植到 Taro 页面。

## 3. 已有基础

- 商城客户注册、登录、会话和个人资料。
- 收货地址维护。
- 商品目录、搜索和分类入口。
- 购物车、订单预览、订单提交、订单列表与详情。
- 商城首页、主题配置和部分营销配置。
- Taro 微信小程序与 H5 构建基础。

这些能力属于工程基础，不等同于客户试运行完成。支付、完整售后、异常恢复、跨端一致性和真实浏览器验收仍需补齐。

## 4. 统一配置模型

后台只维护一套商城首页和主题配置：

```text
Web 管理端
  -> Marketing 管理运营内容
  -> Mall 聚合已发布且有效的客户端数据
  -> Web 商城 / Taro 小程序消费同一语义
```

职责：

- `marketing`：促销、优惠券、首页板块、常购和复购等运营配置。
- `mall`：客户身份、客户可见商品、客户价格、购物车、地址、订单和客户端聚合数据。
- 管理端：配置、排序、启停、有效期和预览。
- 客户端：展示和交互，不直接组合后台管理接口。

主题只控制颜色、背景、卡片、导航等表现，不创建促销，也不改变价格。未知主题值应回退到默认主题，不能阻断下单。

## 5. 分阶段交付

| 阶段 | 目标 | 关键验收 |
| --- | --- | --- |
| M0 身份与客户绑定 | 商城客户安全登录并绑定业务客户 | 会话隔离、客户停用生效、越权数据不可见 |
| M1 浏览与购物车 | 客户看到自己的商品和价格并维护购物车 | 可见性、价格、起订量和规格均由后端校验 |
| M2 下单闭环 | 预览并提交商城订单 | 防重复提交，地址与价格快照完整，进入统一销售订单域 |
| M3 跨端稳定化 | Web 与小程序统一首页、主题和异常语义 | 同一配置顺序一致，加载/空/错状态完整，关键浏览器流程通过 |
| M4 增强能力 | 支付、售后、活动深化、H5 发布 | 每项单独冻结业务规则，不阻塞内部供应链主闭环 |

正式客户试运行应在订单、采购、收货、库存和必要履约链路验收后进行。商城功能可以并行补测试，但不应抢占分拣、配送和结算主链路的优先级。

## 6. 交互与设计原则

- 使用 Mall Theme，不把活动视觉带入 ERP 页面。
- 首页支持搜索、Banner、分类、活动和商品列表，但避免建设通用低代码装修器。
- 商品卡明确规格、单位、价格、最小起订量、数量和金额反馈。
- 配置端采用表单、排序和手机预览，不复制外部产品品牌或未验证规则。
- 所有网络页面覆盖加载、空数据、失败、重试和会话过期。

## 7. 延后范围

- 真实在线支付和余额资金账户。
- AI 语音下单。
- 通用拖拽式页面装修器。
- 复杂会员、积分和裂变营销。
- 未经现场确认的打印、电子秤和硬件直连。

## 8. 验证门禁

- 后端相关测试和 Flyway 空库、升级验证通过。
- Web 执行 lint、typecheck、test、build。
- 小程序执行 lint、typecheck、微信小程序构建和 H5 构建。
- Playwright 至少覆盖登录、商品可见性、客户价格、购物车、订单预览、重复提交和订单查询。
- 浏览器控制台无未解释错误，关键请求无静默失败。
