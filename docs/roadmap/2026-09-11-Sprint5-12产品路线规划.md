# 鲜蔬源智链 Sprint 5–12 产品路线规划

状态：现行产品路线
基线日期：2026-09-11
适用范围：Sprint 5–12 产品设计、实施排序和阶段验收

## 1. 规划结论

项目已经具备商品、客户、协议价、销售订单、采购需求、采购单、分批收货、库存流水、RBAC、商城和小程序基础。Sprint 5–8 不能再按新建模块规划，应以补齐规则、状态耦合和验收缺口为主；Sprint 9–12 的分拣、配送、财务、经营分析和溯源仍是主要新增建设范围。

总推进原则：

```text
存量能力验收与收敛
-> 定价和订单履约控制
-> 采购与仓储深化
-> 分拣称重
-> 出库配送
-> 财务结算
-> 经营分析、溯源和开放接口
```

当前 Sprint 5–12 目标的工程基础约完成 35%–40%；按可试运行的端到端业务闭环约完成 25%–30%。百分比用于排期判断，不替代逐项验收。

## 2. 事实基线

### 2.1 已实现或具备基础

- 商品分类、SPU/SKU、上下架和客户商品可见性。
- 客户、客户类型、协议价、价格解析和价格操作记录。
- 销售订单创建、更新、提交、确认、取消、实际数量、退货和退款。
- 采购需求生成与分配、采购订单、分批收货、超收容忍、少收关闭、直接或确认后入库。
- 库存余额和追加式库存流水。
- 登录、会话、RBAC、菜单、字典、登录日志和系统操作日志。
- 商城客户、地址、目录、购物车、下单和主题/营销基础。
- Taro + React + TypeScript 小程序工程，支持微信小程序和 H5 构建。

### 2.2 尚未形成完整模块

- 分拣波次、分拣任务、称重记录、标签和缺货处理。
- 出库、装车、配送路线、司机任务、签收和配送异常。
- 应收、应付、收付款、核销、对账和利润。
- 批次、库区库位、盘点、调拨、保质期和移动加权成本。
- 经营 BI、损耗、业务追溯和 Open API。

### 2.3 验证边界

- 后端、Web 和小程序已有较完整的静态及构建门禁基础。
- 前端 Vitest 稳定执行和 Sprint 4 Playwright 浏览器主链路仍需形成当前版本证据。
- 历史测试通过只证明当时提交，不能替代每个 Sprint 合并后的回归。

## 3. 跨 Sprint 全局约束

- 技术栈保持 Java 21、Spring Boot、PostgreSQL、Flyway、MyBatis-Plus/MyBatis XML、React、Vite 和 TypeScript。
- 保持模块化单体，不引入微服务、消息中间件或分布式事务作为默认方案。
- 不修改已应用 Flyway，不创建数据库外键约束；通过服务校验、事务、唯一/检查约束、索引、审计和对账保障一致性。
- 金额使用 `DECIMAL/NUMERIC`，数量和重量保留业务所需精度，不使用浮点数承担结算。
- 订购数量、实际重量、出库数量、签收数量和结算数量分别保存，不互相覆盖。
- 库存变化必须产生追加式 movement，重要业务动作必须幂等且可审计。
- 后端负责价格、库存、状态和结算权威校验；前端隐藏按钮不能替代权限或并发控制。
- 当前 API 继续以 `/api/...` 为基线。是否引入 `/api/admin`、`/api/app` 版本化前缀另立兼容方案，不在单个 Sprint 全面改造。
- 每个 Sprint 先冻结业务规则，再形成实施计划；不把本文中的建议状态或表结构直接当成最终规格。

## 5. Sprint 5 现有质量门禁与价格中心收敛

**目标：** 不重复建设现有定价模块，先把当前版本变成可信基线，再补价格中心的高价值缺口。

范围：

- 修复或隔离 Vitest 挂起问题，补齐当前 Playwright 浏览器验收。
- 验证后台和商城客户商品可见性、协议价命中、缺价行为和价格锁定。
- 增加价格组、价格生效区间、批量调价/导入和价格历史查询设计。
- 统一客户协议价、客户类型价、基础售价和活动价的优先级；具体顺序必须经业务确认。
- 完善商品—供应商关系和默认采购员/默认供应商规则。

非目标：

- 不重写现有客户协议价 CRUD。
- 不在价格转换器或前端组件中实现结算规则。
- 不扩展完整营销引擎。

验收：

- 后端、Web、小程序门禁均有当前提交证据。
- Playwright 覆盖登录、客户可见商品、价格命中、下单预览和重复提交。
- 任一订单项能说明价格来源、锁定值和操作历史。
- 批量调价失败时具备明确的整批/逐行处理语义。

## 6. Sprint 6 订单生命周期与库存预占

**目标：** 把订单从“可增删改”提升为受库存、时间和履约状态约束的业务单据。

范围：

- 确认审核、驳回、截单、取消和改单边界。
- 分离订单业务状态、履约状态和结算状态，避免单字段承载全部含义。
- 建立库存预占、释放和缺口计算；并发请求不能重复占用库存。
- 建立异常订单池，覆盖缺价、库存不足、改价、取消冲突和履约中改单。
- 保留并扩展已有幂等和订单操作日志。

验收：

- 确认订单原子创建预占并计算采购缺口。
- 取消或合法减量会释放对应预占。
- 过截单时间、履约中改单和并发确认均由后端拒绝或进入明确审批路径。
- 退货退款不会静默覆盖原始数量和金额。

## 7. Sprint 7 采购询价与进度深化

**目标：** 在现有采购需求、采购订单和收货能力上补齐供应商选择和执行可视化。

范围：

- 采购需求结合可用库存、已预占、在途和安全库存形成建议采购量。
- 建立询价单、供应商报价、比价选择和采购价历史。
- 增加按供应商、采购员和品类的进度视图。
- 保留现有需求分配、采购单、分批收货、少收关闭和超收规则。
- 采购二维码或供应商移动协同只做最小闭环，供应商门户放入后续增强。

验收：

- 重复生成不会形成重复采购需求。
- 一个需求可以拆给多个供应商，采购单可追溯到来源需求和订单缺口。
- 报价选择保留当前报价、历史采购价和选择记录。
- 部分收货、少收关闭和取消不会抹掉已收货事实。

## 8. Sprint 8 仓储批次、库位、盘点与成本

**目标：** 在现有库存余额和流水基础上建立可运营的仓储与成本底座。

范围：

- 仓库、库区、库位和商品批次。
- 收货批次、生产日期、保质期和临期查询。
- 盘点、库存调整、报损报溢和库位移动。
- 预留 FEFO 出库批次建议。
- 建立统一 CostService 计算移动加权平均成本。

验收：

- 每次入库、移库、盘点和调整都能对应唯一库存流水。
- 重复事件不重复记账，失败事务不留下半成品余额。
- 库位移动前后仓库总库存不变。
- 盘盈盘亏经确认后才影响正式库存。
- 成本计算有边界、回滚和精度测试。

## 9. Sprint 9 分拣、称重、缺货与标签

**目标：** 将订单数量转换为实际交付数量，这是首个尚未建立的核心作业模块。

范围：

- 分拣波次和任务，支持按商品、客户订单两种视角。
- 标品快速确认，非标品人工称重；真实电子秤通过 device agent 后续接入。
- 分拣员、配送日期、线路、供应商和任务状态筛选。
- 容差、缺货、超差、人工更正及原因审计。
- 标签结构化数据和打印记录，首期不绑定具体打印机驱动。

验收：

- 同一履约批次不会重复生成有效分拣任务。
- 原订购数量保留，实际重量及每次更正可追溯。
- 超差、缺货和重复称重事件不能静默完成。
- 完成分拣后订单进入明确的待出库状态。

## 10. Sprint 10 出库、配送与签收

**目标：** 完成从待出库到客户签收的履约闭环。

范围：

- 出库确认、装车、配送计划、路线、司机、车辆和订单分配。
- 按区域、时间窗、订单数、重量、金额和车辆载重辅助排线；首期不做 AI 路径优化。
- 发车、到达、签收、部分签收、拒收和配送异常。
- 签收人、时间、数量、图片/签字和异常备注。
- 退货引用原订单项和实际签收数量。

验收：

- 出库与 `SALES_OUT` 库存流水原子提交，失败不得发车。
- 同一订单同一履约批次不能进入两个有效配送任务。
- 部分签收、拒收和退货均有明确后续状态和库存/财务影响入口。
- 司机只能访问分配给自己的任务。

## 11. Sprint 11 应收、应付、核销与利润

**目标：** 让客户欠款、供应商欠款、收付款和订单利润能够核对。

范围：

- 签收实际数量生成应收，采购实收生成应付。
- 收款、付款、部分核销、多单核销和撤销核销。
- 客户、供应商对账单以及按天、按月账期。
- 退款、退货、折让和数量差异的财务调整。
- 最终收入、实际出库成本和利润快照。

非目标：

- 不建设完整总账、会计科目、税务凭证和法定财务报表。

验收：

- 应收应付生成幂等，余额在核销和撤销后准确恢复。
- 对账单余额与业务明细一致。
- 利润使用最终交付收入和实际库存成本，不使用草稿金额。
- 已锁定利润快照不会因基础资料修改静默变化。

## 12. Sprint 12 损耗、经营 BI、溯源与 Open API

**目标：** 在闭环业务数据之上提供经营管理和受控外部接入。

范围：

- 采购差异、收货、仓储、分拣、配送和退货损耗。
- 销售、采购、库存、履约、应收应付、利润和损耗指标。
- 指标下钻到业务明细，不维护大屏专用事实副本。
- 商品—供应商—采购—批次—分拣—配送—签收追溯链。
- Open API 客户端、密钥、签名、scope、限流、幂等、调用日志和 webhook/outbox。

验收：

- 指标汇总能与业务明细核对，任一指标可追溯来源。
- 历史追溯事件不可被普通删除破坏。
- 外部重复订单不产生重复业务单据。
- 签名失败、过期时间戳、重放和无权限 scope 有稳定错误码。
- 完成从客户价格、下单到采购、收货、分拣、配送、结算和利润的端到端回归。

## 13. 跨 Sprint 状态衔接

```text
客户价格与可见商品
-> 订单确认与库存预占
-> 库存缺口形成采购需求
-> 采购单与分批收货
-> 批次库存与成本
-> 分拣称重与实际交付数量
-> 出库与配送签收
-> 应收应付与核销
-> 利润、损耗、BI 与追溯
```

跨领域状态由所属领域的显式动作推进。分拣、配送或财务模块不得直接更新销售订单表来绕过订单服务；应通过明确的应用服务合同和同一事务内的领域校验协作。

## 14. 每个 Sprint 的完成定义

- 先形成并批准该 Sprint 的业务规格，不保留关键规则占位符。
- Flyway 可在空库执行，也可从当前受支持版本升级；旧迁移未被修改。
- 核心状态机、幂等、并发、权限、精度和事务回滚具有自动化测试。
- 后端测试与打包通过；Web 执行 lint、typecheck、test、build；涉及小程序时执行对应门禁。
- 关键浏览器路径覆盖主流程、加载、空、错误、会话失效和越权。
- 无假数据依赖、静默失败、数据库外键、注解 SQL或未分页的大列表接口。
- 重要动作有操作日志，余额或状态可以从明细和流水核对。
- 验证结果单独写入 `docs/superpowers/verification/`，不能用计划文档中的预期替代。

## 15. 分支与交付建议

- 每个 Sprint 使用独立功能分支和小而可审查的提交。
- 数据库、后端、前端和测试可以拆为逻辑提交，但必须在 Sprint 合并前进行全链路回归。
- 已有模块采用扩展式迁移和兼容式 API，不为了统一命名大规模改写稳定代码。
- 商城与营销进入“控制扩张、补齐测试”的并行轨道，不能阻塞 Sprint 9–11 核心闭环。

## 16. 最终产品验收主链路

Sprint 12 完成时至少稳定演示：

1. 创建客户、账期和协议价。
2. 客户商城或后台下单，系统锁定价格。
3. 审核确认订单并预占库存。
4. 缺口形成采购需求，完成询价和采购单。
5. 供应商分批送货，仓库按实际数量或重量收货。
6. 库存批次、流水和成本一致更新。
7. 生成分拣任务，称重并保留实际交付数量。
8. 出库装车、配送并签收或部分退货。
9. 按实际业务生成应收、应付并完成部分或全部核销。
10. 生成对账、利润、损耗和追溯结果，Dashboard 可下钻到明细。

只有该链路稳定、幂等、权限受控且可审计，核心业务底座才算完成。
