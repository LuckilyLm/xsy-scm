## 2. 数据表设计（对应指令第 1、2、3 项）

### 2.1 `inventory_balance`（余额）

```sql
CREATE TABLE inventory_balance (
    id            BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id  BIGINT        NOT NULL,
    sku_id        BIGINT        NOT NULL,
    unit          VARCHAR(32)   NOT NULL,
    quantity      NUMERIC(18,4) NOT NULL DEFAULT 0,
    version       INTEGER       NOT NULL DEFAULT 0,
    deleted       BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at    TIMESTAMPTZ   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMPTZ   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by    VARCHAR(64),
    updated_by    VARCHAR(64),
    CONSTRAINT ck_inventory_balance_quantity CHECK (quantity >= 0),
    CONSTRAINT ck_inventory_balance_version  CHECK (version >= 0)
);

CREATE UNIQUE INDEX uk_inventory_balance_wh_sku_active
    ON inventory_balance (warehouse_id, sku_id) WHERE deleted = FALSE;
CREATE INDEX idx_inventory_balance_sku ON inventory_balance (sku_id);
```

设计说明：

- **粒度 = `(warehouse_id, sku_id)`**（A 源 spec §5.8、plan §10.1 与 V2 G-03 一致）；无 `batch_id`（G-03 永久不启用，不留死列）；
- **`unit` 列与单位不变量（Q13，已裁决新增）**：同一 `(warehouse_id, sku_id)` 的余额行**锁定一个记账单位**。
  首笔入库 `unit = InboundFact.unit`（= `purchase_unit_snapshot`）；后续同键入库 `fact.unit != balance.unit` →
  抛 `INVENTORY_UNIT_MISMATCH(41xxx)`，confirm 整体回滚。**禁止把不同单位的数量静默相加**——
  `SupplierSku.purchaseUnit` 是 supplier+sku 维度，同一 SKU 理论上可能存在不同采购单位，
  单位换算放到后续 Product Conversion / Inventory Unit 波次；W6-1 遇到单位冲突 = 显式失败而非静默汇总；
- **无商品快照列**：余额是**活状态**不是单据，展示用的编码/名称由查询服务联 `product_sku` / `product_spu` 实时取
  （与 W5 `warehouse` 列表同一取向）；单据侧的快照纪律不受影响；
- **无 `weight` 独立列**（Q2 已裁决）：W6-1 的数量语义是**采购单位口径**——标品数量 = 件数，非标品数量 = 实重（kg），
  一个 `quantity` 列已完整表达；「数量/重量双记账」是分拣波次的关注点，届时按需演进；
- **无成本列**（Q3 已裁决）：不落 `avg_cost` / `total_cost`；成本事实由 movement 的 `unit_cost` 快照承载（§11），
  移动加权平均延期到销售出库/财务波次；
- **无预警列**（Q4 已裁决）：`warn_min/warn_max` 随预警能力一起进未来波次；
- `quantity >= 0` CHECK 本期冻结（Q10 已裁决）：W6-1 唯一写路径是入库（正数增量），负库存问题在本阶段不可能发生，
  冻结 CHECK 使未来出库波次必须**显式**决策负库存策略才能绕过。

### 2.2 `inventory_movement`（流水，append-only）

```sql
CREATE TABLE inventory_movement (
    id                      BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id            BIGINT        NOT NULL,
    sku_id                  BIGINT        NOT NULL,
    movement_type           VARCHAR(32)   NOT NULL,
    source_document_type    VARCHAR(64)   NOT NULL,
    source_document_id      BIGINT        NOT NULL,
    source_document_item_id BIGINT        NOT NULL,
    quantity                NUMERIC(18,4) NOT NULL,
    unit_snapshot           VARCHAR(32)   NOT NULL,
    unit_cost               NUMERIC(18,4),
    before_quantity         NUMERIC(18,4) NOT NULL,
    after_quantity          NUMERIC(18,4) NOT NULL,
    occurred_at             TIMESTAMPTZ   NOT NULL,
    operator                VARCHAR(64),
    deleted                 BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at              TIMESTAMPTZ   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by              VARCHAR(64),
    CONSTRAINT ck_inventory_movement_type CHECK (movement_type IN ('PURCHASE_IN')),
    CONSTRAINT ck_inventory_movement_qty  CHECK (quantity > 0),
    CONSTRAINT ck_inventory_movement_snap CHECK (after_quantity = before_quantity + quantity),
    CONSTRAINT ck_inventory_movement_append_only CHECK (deleted = FALSE)
);
-- source_document_type 常量值 = PurchaseInventoryContract.SOURCE_DOCUMENT_TYPE = 'PURCHASE_RECEIPT_ITEM'

-- W5 TD §8.5 预留的源身份唯一索引（逐字落地）：
CREATE UNIQUE INDEX uk_inventory_movement_source_active
    ON inventory_movement (source_document_type, source_document_item_id)
    WHERE deleted = FALSE AND source_document_item_id IS NOT NULL;

CREATE INDEX idx_inventory_movement_wh_sku_occurred
    ON inventory_movement (warehouse_id, sku_id, occurred_at);
CREATE INDEX idx_inventory_movement_occurred ON inventory_movement (occurred_at);
CREATE INDEX idx_inventory_movement_source
    ON inventory_movement (source_document_type, source_document_id);
```

设计说明：

- **方向编码在类型里**（`PURCHASE_IN` 即「入」），不设 `direction` 列 —— AGENTS §7.5 的 11 个 movement 类型
  全部自带方向；`quantity` 恒为正（`> 0` CHECK），与 reference 的「direction + 正数」双表达相比少一列且不可矛盾；
- **append-only 的落法（Q7 已裁决硬化）**：表带 `deleted`（与 W5 §8.5 契约 SQL 的
  `WHERE deleted = FALSE` 谓词逐字一致），且 **`CHECK (deleted = FALSE)` 把 append-only 上升为 DB 约束**——
  任何 soft delete / update 历史流水的 SQL 在数据库层直接失败；未来冲销必须新增反向 movement。
  同时**没有 `version` / `updated_at` / `updated_by`**（对齐 `receipt_weighing_record` 的只追加纪律）；
  DAO 只提供 insert + select，服务层无任何更新路径；
- **`before_quantity / after_quantity` 快照**：沿用 reference 与 plan §10.3 的可追溯性核心语义，
  恒等式 `after = before + quantity` 由 CHECK 强制（plan §10.3「每条 PURCHASE_IN 必须满足」的 DB 化）；
- **`source_document_id`** = 收货单 id（`InboundFact.receiptId`）：头级溯源（列表页展示/跳转收货单用）；
  防重锚点只用 `source_document_item_id`（W5 §8.5 冻结的口径），`source_document_id` 不参与唯一索引；
- **无 `movement_no` 流水号**（推荐裁决）：人类可读溯源由 `source_document_id → receipt_no` 承担；
  自建流水号需要新增发号器与列，W6-1 无消费者。若负责人要求保留，加列属加法演进（§14 Q10）；
- **无 `biz_type/biz_id` 双层关联**：reference 的 `biz_type(1-6)+biz_id` 与 `flow_type` 语义重叠；
  V2 用 `movement_type + source_document_type/id/item_id` 三元组表达同一信息且类型安全；
- **`occurred_at`**：实时路径 = `receipt.confirmed_at`（确认时刻），backfill 路径同口径（§5），
  保证两条路径写入的时间语义一致、按时间回放与按 id 回放同序。

## 4. PURCHASE_IN 源身份与防重（对应指令第 4、10 项）

### 4.1 源身份（W5 §8.5 逐字兑现）

```text
source_document_type    = 'PURCHASE_RECEIPT_ITEM'   （PurchaseInventoryContract.SOURCE_DOCUMENT_TYPE）
source_document_item_id = purchase_receipt_item.id  （IDENTITY 主键，确认后不可变、软删不释放）
source_document_id      = purchase_receipt.id       （头级溯源，不参与防重）
```

### 4.2 三条路径互不重复入库（W5 §8.5 表格兑现）

| 路径 | 触发时机 | 防重机制 |
| --- | --- | --- |
| 历史 backfill | W6 启用前一次性回放 | `INSERT ... ON CONFLICT (source_document_type, source_document_item_id) DO NOTHING`（§5） |
| 未来实时 confirm | W6 上线后 confirm 事务内 `postInbound` | 唯一索引兜底 + claim 幂等（重放不进入写路径） |
| 重试 / 重复消费 | 手工重跑 backfill、接口重放 | 同一唯一索引（**DB 层兜底，不依赖应用层判重**） |

### 4.3 应用层行为

契约实现写入流水时使用 `INSERT ... ON CONFLICT ... DO NOTHING` 并检查受影响行数：

- 影响行数 = 1 → 正常入库，继续更新余额；
- 影响行数 = 0 → **该源事实已入库**。实时 confirm 路径下这属于不可能发生的数据异常
  （claim 幂等 + 状态机已挡住），直接抛 `InventoryErrorCode.INVENTORY_DUPLICATE_INBOUND`
  使事务回滚（fail-fast 暴露问题，**不静默吞掉**——A 源 spec §8.2「不能通过捕获异常后继续写入来掩盖库存不一致」）；
  backfill 路径下 0 是预期值（幂等跳过），由 backfill 执行器区分处理（§5）。

## 5. Backfill（W6 bootstrap，Q5 兑现）

取数口径（W5 TD §8.5 已冻结，直接使用）：

```sql
SELECT ri.id, ro.id AS purchase_order_id, ri.purchase_receipt_id, ro.warehouse_id, ri.sku_id,
       ri.purchase_unit_snapshot, ri.received_quantity, oi.purchase_price
FROM purchase_receipt_item ri
JOIN purchase_receipt     r  ON r.id  = ri.purchase_receipt_id AND r.deleted  = FALSE
JOIN purchase_order       ro ON ro.id = r.purchase_order_id   AND ro.deleted = FALSE
JOIN purchase_order_item  oi ON oi.id = ri.purchase_order_item_id AND oi.deleted = FALSE
WHERE r.status = 'CONFIRMED' AND ri.deleted = FALSE
ORDER BY ri.id ASC;                     -- 确定性顺序，便于对账
```

**载体（Q5 已裁决 + 修正）：data-only backfill 与首次库存 schema migration 同文件同波次执行
（`V19__scm_inventory.sql` 内、建表 DDL 之后），且必须在新 W6 应用开始接受业务请求前完成。**

**回放顺序（Q5 裁决修正，禁止仅按 `ri.id` 排序）**：

```sql
-- 窗口累计与 INSERT 输出统一使用同一顺序，保证 occurred_at 顺序与 before/after_quantity 回放顺序一致：
ORDER BY receipt.confirmed_at ASC, receipt.id ASC, receipt_item.id ASC
```

要点：

- **单位不变量前置检查（Q13）**：写入前校验同 `(warehouse_id, sku_id)` 的
  `COUNT(DISTINCT purchase_unit_snapshot)`；`> 1` → **migration FAIL**（`RAISE EXCEPTION`），
  不得静默汇总；
- 每行 `INSERT ... ON CONFLICT (source_document_type, source_document_item_id)
  WHERE deleted = FALSE AND source_document_item_id IS NOT NULL DO NOTHING`；
- `occurred_at = r.confirmed_at`、`operator = r.operator`（回放语义 = 「在确认时刻发生」）；
- `before_quantity` 用窗口函数推导：`SUM(received_quantity) OVER (
  PARTITION BY warehouse_id, sku_id ORDER BY r.confirmed_at ASC, r.id ASC, ri.id ASC
  ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)`，`after = before + quantity` 恒等式由此成立；
- 余额行由同一迁移按 `(warehouse_id, sku_id)` 从流水汇总生成
  （`INSERT ... SELECT ... ON CONFLICT DO NOTHING`），`unit` 取该组唯一单位（前置检查已保证）；
- 迁移内置对账断言：`Σ movement.quantity = Σ received_quantity` 且 `Σ balance.quantity = Σ movement.quantity`
  （按 `(warehouse_id, sku_id)` 分组双向 EXCEPT），不一致即迁移失败。

> 迁移可测（PG IT 直接跑 Flyway）、可重放（ON CONFLICT 幂等）、有审计（版本控制）。

## 6. 契约实现与 confirm 接线（对应指令第 5、6 项）

### 6.1 实现类

```java
package net.lab1024.sa.admin.module.scm.inventory.support;

@Component
@RequiredArgsConstructor
public class PurchaseInventoryContractImpl implements PurchaseInventoryContract {

    private final InventoryCommandService inventoryCommandService;

    @Override
    public void postInbound(InboundFact fact) {
        inventoryCommandService.postPurchaseInbound(fact);   // 加入调用方事务（不另开事务）
    }

    @Override
    public Availability queryAvailability(Long skuId, Long warehouseId) {
        // W6-1：无占用概念（reserve/release 未实现）→ available = balance.quantity
        // 余额行不存在 ≠ 未启用库存；W6 起返回非 null（区分语义由调用方自行判断）
        return inventoryCommandService.queryAvailability(skuId, warehouseId);
    }
}
```

- **替换 NoOp 的方式**：NoOp 类**不删除**（purchase 模块资产，避免 purchase 侧 diff），仅继续不注册；
  容器中出现唯一 Bean = `PurchaseInventoryContractImpl`；
- `InventoryCommandService.postPurchaseInbound` 不加 `@Transactional(propagation = REQUIRES_NEW)` ——
  **必须加入调用方事务**（默认 REQUIRED 即可），这是「同事务」要求的实现形态。

### 6.2 `InventoryCommandService.postPurchaseInbound` 内部序列

```text
1. 校验 fact（非空、quantity > 0、unit / occurredAt / operator 快照非空）
2. warehouse 引用守卫：WarehouseService.require(fact.warehouseId)（40485，服务层外键替代）
3. 余额行获取（§8 并发方案）：
   a. INSERT INTO inventory_balance (warehouse_id, sku_id, unit, quantity=0)
      VALUES (...) ON CONFLICT (warehouse_id, sku_id) WHERE deleted = FALSE DO NOTHING
   b. SELECT ... FOR UPDATE WHERE warehouse_id = ? AND sku_id = ? AND deleted = FALSE
4. 单位不变量（Q13）：fact.unit != balance.unit → 抛 INVENTORY_UNIT_MISMATCH，confirm 整体回滚
5. before = balance.quantity
6. INSERT inventory_movement（before/after 快照 + 源身份；occurred_at = fact.occurredAt()、
   operator = fact.operator() —— 禁止用 now()/ambient operator 替代已冻结的收货确认事实；
   ON CONFLICT DO NOTHING）
   ├─ 影响行数 = 0 → 抛 INVENTORY_DUPLICATE_INBOUND（回滚一切，§4.3）
   └─ 影响行数 = 1 → 继续
7. UPDATE inventory_balance SET quantity = quantity + fact.quantity, version = version + 1 ...
   WHERE id = balance.id（持行锁后自增，无丢失更新窗口）
8. 返回
```

`queryAvailability`：只读余额行（无锁或普通 SELECT），行不存在返回 `available = 0, reserved = 0`
（W6 起库存已启用，`null` 语义退场——与 W5 期间 NoOp 返回 null 的区别即「能力上线」）。

## 7. 事务边界（对应指令第 7 项）

```text
┌────────────────────────── PurchaseReceiptService.confirm 事务 ──────────────────────────┐
│  幂等 claim（INSERT 竞争）                                                              │
│  采购单锁 → 收货单锁 → 采购行锁 → 收货行锁（W5 冻结锁序，零改动）                        │
│  逐行：版本校验 → effective 计算 → 超收校验 → accumulateReceived → 对账快照 → 称重记录   │
│  采购单状态机 → 收货单 CONFIRMED → 操作日志                                              │
│  ┌──────────────── InventoryCommandService.postPurchaseInbound（×N，同事务）──────────┐  │
│  │  仓库引用守卫 → 余额 ON CONFLICT + FOR UPDATE → 流水 INSERT（源身份防重）→ 余额自增 │  │
│  └────────────────────────────────────────────────────────────────────────────────────┘  │
│  幂等 complete（result_data = 含库存结果的真实返回）                                      │
└──────────────────────────────────────────────────────────────────────────────────────────┘

```

- 库存服务**不新建事务**（REQUIRED 传播），不使用异步/事件/MQ（AGENTS §5：无复杂事件基础设施）；
- 幂等 `complete` 在库存写入之后 → 重放返回的结果保证「库存已入库」；
- backfill 走独立迁移事务（Flyway 单迁移单事务），与在线路径无交叠（ON CONFLICT 兜底）。

## 8. 并发与 PostgreSQL 锁（对应指令第 8、9 项）

### 8.1 全域锁序（在 W5 锁序末尾追加一段）

```text
采购单 → 收货单 → 采购行(id 升序) → 收货行(id 升序) → 库存余额 (warehouse_id, sku_id 字典序升序)
```

- 余额锁永远是**最后**获取的锁：库存域内部不获取任何采购/收货锁，锁图无环；
- 多行收货涉及多个 `(warehouse, sku)` 时，confirm 在调用契约前**先排序再调用**（§6.3），
  保证任意两个并发 confirm 事务的余额加锁顺序一致 —— 这是防死锁的关键，
  也是「confirm 侧排序」而非「实现侧内部缓冲」的原因（单次调用内锁定，事务状态不留在契约实现里）；
- 未来所有库存写路径（出库/调拨/盘点）必须复用同一规则：**先锁单据，后按 `(warehouse_id, sku_id)` 升序锁余额**。

### 8.2 并发首建余额（§9 项的完整方案）

场景：两个不同采购单的收货并发确认，同一个首次出现的 `(warehouse_id, sku_id)`。

```sql
-- 步骤 1（两事务并发执行）：竞争插入（冲突目标与部分唯一索引完全匹配，含 WHERE 谓词）
INSERT INTO inventory_balance (warehouse_id, sku_id, unit, quantity, created_by, updated_by)
VALUES (:wh, :sku, :unit, 0, :op, :op)
ON CONFLICT (warehouse_id, sku_id) WHERE deleted = FALSE DO NOTHING;

-- 步骤 2（两事务都会执行）：锁定胜利行
SELECT * FROM inventory_balance
WHERE warehouse_id = :wh AND sku_id = :sku AND deleted = FALSE
FOR UPDATE;   -- 输家在此等待赢家事务提交
```

- **Q11 已裁决修订**：统一使用与 partial unique index 完全匹配的
  `ON CONFLICT (列...) WHERE 谓词 DO NOTHING` 形态（该语法自 PG 9.5 起即支持 index predicate 匹配，
  「依赖 PG15+」是错误前提，已删除）；**业务代码不制造 PG 版本分支**，实际 PostgreSQL 版本只记录到验收证据；
  PG IT 必须真实验证该 SQL（§12）；
- 赢家/输家最终都拿到**同一行**的行锁 → 后续自增串行化，无丢失更新、无重复行；
- 不使用「catch unique violation 后重试整个事务」的复杂路径 —— ON CONFLICT 是原子的；
- IT 用两个并发线程 + CyclicBarrier 复现（§12）。

### 8.3 并发收货同一采购单

W5 既有纪律自动覆盖：`lockByOrderId` 的行锁使第二笔 confirm 串行等待，
看到第一笔的 `received_quantity` 后重新计算 `effective ≤ available` —— 库存侧因此也天然串行
（同一单的两个 confirm 不可能并发进入余额段）。IT 回归验证。

### 8.4 并发不同采购单、相同 SKU

两事务在各自单据锁（互不相干）后竞争同一余额行：靠 §8.1 的确定性余额排序 + 行锁串行化。
`before/after` 快照保证流水恒等式在并发下依然成立（before 在持锁后读取）。

### 8.5 乐观锁的角色

余额行同时有 `version` 列：本设计中余额更新只发生在**持有行锁之后**（`WHERE id = ...` 影响行数必须为 1），
version 是**纵深防御**（若未来出现未持锁的更新路径，`version` 条件会失败而非脏写），
不作为第一道并发机制。

## 9. BigDecimal 精度与数量语义（对应指令第 11、12 项）

### 9.1 精度规则

| 项 | 规则 |
| --- | --- |
| DB 列 | 数量/重量/单价 `NUMERIC(18,4)`（与 `purchase_*` 全域一致；**不采纳** reference 的 18,3） |
| Java 类型 | `BigDecimal`；新增算术（`before + quantity`）结果天然 4 位内，**不做二次取整** |
| API 传输 | 十进制字符串协议（W1–W5 既有 `ScmFixedScale4Serializer` 序列化形态），前端不参与计算 |
| 恒等式 | `after_quantity = before_quantity + quantity` 由 DB CHECK 强制（§2.2），不依赖应用层 |
| 输入校验 | 库存域**不接受任何用户提交的数量**（无写 API），数量唯一来源 = confirm 已校验的 `effective`（40083 校验已发生），库存侧只断言 `> 0` |

### 9.2 单位语义

| 项 | 规则 |
| --- | --- |
| `unit_snapshot` | = `purchase_order_item.purchase_unit_snapshot`（确认时刻快照，经 `InboundFact.unit` 传递）；标品 = 计数单位，非标品 = 采购重量单位（kg）——**同一列，语义由 SKU 的 `product_type` 决定** |
| **单位不变量（Q13）** | 同一 `(warehouse_id, sku_id)` 的**记账单位唯一**：首笔入库把 `unit` 写进余额行，之后同键入库的 `fact.unit` 必须等于 `balance.unit`，否则 `INVENTORY_UNIT_MISMATCH(41001)` + confirm 整体回滚。理由：`SupplierSku.purchaseUnit` 是 **supplier + sku** 维度，同一 SKU 经不同供应商入库时理论上可以是不同单位，**禁止静默相加** |
| 不做单位换算 | W6-1 无多单位/换算需求；`sale_unit` 与 `purchase_unit` 的差异不影响库存（库存始终以采购单位记账）；单位换算（Product Conversion / Inventory Unit 波次）**不在本期** |
| 展示 | 余额/流水页直接展示 `unit` / `unit_snapshot`；SKU 详情里的 `sale_unit` 不参与库存口径 |

> 审计提醒（Legacy Audit §7.3）：实现时**不得**用 confirm 循环里的 `weightUnit`（标品时为 null）作为库存单位，
> 必须统一取 `orderItem.getPurchaseUnitSnapshot()`。

## 11. 成本快照 / 加权平均边界（对应指令第 13 项）

```text
W6-1 记录成本事实：inventory_movement.unit_cost = confirm 时刻的 purchase_order_item.purchase_price
W6-1 不维护成本状态：balance 无 avg_cost / total_cost 列，不做加权平均重算，不产出任何成本报表
```

- 理由：加权平均的**消费者**（销售出库成本结转、毛利）全部在排除清单里；
  reference 的入库重算公式（`(beforeQty×beforeAvg + qty×price)/afterQty`，scale 4 HALF_UP）已收录在
  Legacy Audit §4.4，作为未来启用时的实现参考，而非本期实现；
- movement 的 `unit_cost` 是**事实快照**（该笔入库时的采购单价），可空性：`InboundFact.unitCost` 恒非空
  （`purchase_price NOT NULL >= 0`），列定义为可空是为未来无成本语义的 movement 类型（如盘盈）预留表达空间；
- 需求基线的「采购成本移动加权平均核算」落在后续财务/出库波次（Q3 追认后，本边界写入验收报告）。
