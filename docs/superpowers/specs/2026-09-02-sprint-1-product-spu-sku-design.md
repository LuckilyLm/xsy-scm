# Sprint 1 商品 SPU/SKU 纵向链路设计

> 历史参考：本文保留原始业务/设计语义。技术栈、实施状态和进度均为 legacy 快照；当前实现以 V2 对应波次的 target-design、approval 与验收报告为准。已删除的旧计划及验证记录可从 Git 历史恢复。

## 1. 背景与目标

Sprint 1 只跑通第一条真实技术链路：PostgreSQL → Spring Boot REST API → React 商品档案页面。交付范围以 `docs/architecture/xsy-scm-项目设计草案-v0.2.md` 第 20 节为准，并吸收已确认的 SPU/SKU 约束。

完成标准：用户可以在商品档案页面查询、新增、编辑、上下架和删除一个包含至少一个 SKU 的 SPU，刷新页面后仍能从 PostgreSQL 读取一致数据。

## 2. 范围

### 2.1 本 Sprint 包含

- PostgreSQL Flyway 迁移。

## 3. 开源参考策略

采用以下成熟经验：

- 参考 `YunaiV/ruoyi-vue-pro`：明确区分 SPU 与 SKU；SPU 聚合保存前校验 SKU；创建和更新处于同一事务；无多规格商品仍保留默认 SKU。
- 参考 `macrozheng/mall`：SKU 更新采用新增、更新、移除的差量同步，不通过全删再插导致 SKU ID 变化。
- 参考 `linlinjava/litemall`：保持 Sprint 1 商品模型轻量，避免提前引入完整商城能力。

明确不采用：

- 不整体复制任一商城或 ERP 工程。
- 不引入 Redis、消息队列、微服务、搜索引擎、营销和支付模块。
- 不复制 Mall4j 代码；其 AGPL-3.0 许可证不适合作为当前工程的直接代码来源。
- 前端继续使用 React + Ant Design + ProComponents，不改用参考项目的 Vue/Element 前端。
- 如后续确需复制 MIT/Apache-2.0 代码片段，必须保留来源和许可证声明；Sprint 1 默认只复用设计思想并按当前工程约束实现。

## 4. 领域模型与不变量

`ProductSpu` 是商品档案聚合根，`ProductSku` 只能通过所属 SPU 的应用服务创建或修改。商品分类是独立聚合，SPU 只保存分类标识。后续订单、价格、采购、库存和称重统一引用 `sku_id`，不得使用 `spu_id` 代替交易规格。

必须满足：

1. 每个未删除 SPU 至少存在一个未删除 SKU。
2. 每个 SPU 恰好有一个默认 SKU。
3. `spu_code`、`sku_code` 在未删除记录中分别唯一。
4. 非空条码在未删除 SKU 中唯一。
5. SKU 必须属于请求路径指定的 SPU，客户端不能修改归属。
6. SKU 市场价不得小于零。
7. 分类最多三级；SPU 只能选择启用的第三级分类。
8. 更新 SKU 时保留仍存在的 SKU ID，只新增新规格并软删除被移除规格。
9. 禁止移除全部 SKU；禁止删除最后一个未删除 SKU。
10. 乐观锁版本不一致时拒绝覆盖并返回明确冲突错误。

## 5. 数据库设计

数据库使用 PostgreSQL。所有关系列只建普通索引，不建外键；关联完整性由服务层校验和事务保证。金额/单价使用 `NUMERIC(18,4)`，不使用浮点类型。

### 5.1 `product_category`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `parent_id` | `BIGINT NULL` | 上级分类；根分类为空 |
| `category_code` | `VARCHAR(64)` | 分类编码 |
| `name` | `VARCHAR(100)` | 分类名称 |
| `level` | `SMALLINT` | 1–3 |
| `sort_order` | `INTEGER` | 同级排序 |
| `status` | `VARCHAR(16)` | `ENABLED` / `DISABLED` |
| `version` | `INTEGER` | 乐观锁 |
| `deleted` | `BOOLEAN` | 软删除 |
| 审计字段 | 时间与操作者 | 创建/更新时间，操作者可空 |

约束：未删除分类编码唯一；`level BETWEEN 1 AND 3`；`parent_id` 建索引。删除前校验无未删除子分类且无未删除 SPU。

### 5.2 `product_spu`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `spu_code` | `VARCHAR(64)` | SPU 编码 |
| `name` | `VARCHAR(150)` | 商品名称 |
| `alias` | `VARCHAR(150) NULL` | 搜索别名 |
| `category_id` | `BIGINT` | 第三级分类标识 |
| `description` | `VARCHAR(1000) NULL` | 简介 |
| `status` | `VARCHAR(20)` | `ON_SHELF` / `OFF_SHELF` |
| `version` | `INTEGER` | 乐观锁 |
| `deleted` | `BOOLEAN` | 软删除 |
| 审计字段 | 时间与操作者 | 创建/更新时间，操作者可空 |

约束：未删除 `spu_code` 唯一；`category_id` 建索引；名称建普通索引以支持首期检索。

### 5.3 `product_sku`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 主键 |
| `spu_id` | `BIGINT` | 所属 SPU |
| `sku_code` | `VARCHAR(64)` | SKU 编码 |
| `barcode` | `VARCHAR(64) NULL` | 条码 |
| `spec_name` | `VARCHAR(150)` | 人类可读规格名 |
| `spec_values` | `JSONB` | 规格快照；无规格时为空对象 |
| `sale_unit` | `VARCHAR(32)` | 斤、千克、袋、盒等 |
| `product_type` | `VARCHAR(20)` | `STANDARD` / `NON_STANDARD` |
| `market_price` | `NUMERIC(18,4)` | SKU 市场参考价 |
| `status` | `VARCHAR(20)` | `ON_SHELF` / `OFF_SHELF` |
| `is_default` | `BOOLEAN` | 默认 SKU 标识 |
| `sort_order` | `INTEGER` | 展示顺序 |
| `version` | `INTEGER` | 乐观锁 |
| `deleted` | `BOOLEAN` | 软删除 |
| 审计字段 | 时间与操作者 | 创建/更新时间，操作者可空 |

约束：未删除 `sku_code` 唯一；未删除非空条码唯一；每个 SPU 至多一个未删除默认 SKU 使用 PostgreSQL 部分唯一索引；`spu_id` 建 B-tree 索引。Sprint 1 不按规格快照检索，因此不预建 JSONB GIN 索引。每个 SPU 至少一个 SKU 和必须有默认 SKU 由应用事务保证。

### 5.4 首批基础表

`supplier`、`warehouse` 只包含主键、业务编码、名称、状态、版本、软删除和审计字段。`sys_user` 只包含主键、用户名、显示名、状态、版本、软删除和审计字段；登录未进入本 Sprint，因此不提前定义密码、令牌或其他认证凭据。三张表均不提供业务 API，也不与商品建立关系。

最终首批表共六张：

```text
sys_user
product_category
product_spu
product_sku
supplier
warehouse
```

## 6. 后端设计

### 6.1 模块结构

```text
com.xianshuyuan.scm
├─ common
│  ├─ api
│  ├─ exception
│  └─ persistence
└─ product
   ├─ controller
   ├─ service
   ├─ repository
   ├─ mapper
   ├─ entity
   ├─ dto
   ├─ vo
   └─ converter
```

`ProductApplicationService` 负责 SPU 聚合事务和不变量；SKU 不暴露可绕过 SPU 的独立写服务。Mapper 只处理持久化，不承载业务校验。

### 6.2 API

所有接口以 `/api` 为前缀，响应为 `{code,message,data}`；分页数据为 `{records,page,pageSize,total}`。

商品分类：

```http
GET    /api/product-categories/tree
POST   /api/product-categories
PUT    /api/product-categories/{id}
DELETE /api/product-categories/{id}
```

商品 SPU 聚合：

```http
GET    /api/products
GET    /api/products/{id}
POST   /api/products
PUT    /api/products/{id}
PUT    /api/products/{id}/status
DELETE /api/products/{id}
```

分页查询参数：`page`、`pageSize`、`keyword`、`categoryId`、`spuStatus`、`skuStatus`、`productType`。关键字匹配 SPU 编码、名称、别名、SKU 编码和条码。

新增/编辑请求包含 SPU 字段和 `skus` 数组。新增 SKU 不传 `id`；编辑时已有 SKU 必须回传 `id` 与 `version`。服务端根据 ID 做差量同步，并校验 ID 确实属于当前 SPU。

### 6.3 错误语义

- `400`：字段格式、价格、分类层级或 SKU 列表不合法。
- `404`：SPU、SKU 或分类不存在。
- `409`：编码/条码重复、版本冲突、删除被引用分类、试图移除全部 SKU。
- `500`：未预期错误；客户端不返回堆栈和数据库细节。

新增、修改、上下架和删除写入结构化应用日志，操作者在未接入登录前记为 `SYSTEM`。持久化通用操作审计在登录/权限阶段落地。

## 7. 前端设计

### 7.1 页面结构

使用 Admin Theme：56px 顶栏、80px 一级导航、约 140px 二级导航、24px 内容边距。一级导航激活“商品”，二级导航激活“商品档案”。不实现未在 Sprint 1 范围内的业务页面。

商品档案遵循：标题/Tab → 查询 → 工具栏 → ProTable → 汇总 → 分页。

### 7.2 列表语义

主表一行代表一个 SPU。列包括：SPU 编码、商品名称、分类、默认 SKU、SKU 数量、价格区间、SPU 状态、更新时间和操作。

行展开区域展示 SKU：SKU 编码、条码、规格名、销售单位、标品/非标品、市场价、上下架状态。金额和数量右对齐并使用等宽数字，状态居中，操作列固定在右侧。

### 7.3 新增与编辑

SPU/SKU 是复杂主从数据，使用 `DrawerForm`。上半部分编辑 SPU 基础信息，下半部分使用可编辑 SKU 表格：

- 初始自动生成一个默认 SKU 行。
- 可以新增、编辑、排序和移除 SKU。
- 不能移除最后一行。
- 默认 SKU 使用单选语义，任何时刻恰好一个。
- 无多规格商品的规格名默认为“默认规格”，规格快照为空对象。
- 提交按钮在请求期间禁用，避免重复提交。

删除使用危险色语义和二次确认。上下架是显式操作，不与编辑保存混合。

### 7.4 网络状态

列表和表单均处理 Loading、Empty、Error、Success、Retry；错误提示根据后端业务码翻译，不展示服务器堆栈。刷新查询保留分页和筛选条件。

## 8. 测试与验收

### 8.1 后端

- 单元测试覆盖 SPU 至少一个 SKU、唯一默认 SKU、分类层级、SKU 归属、价格非负和差量同步。
- 服务测试证明保留 SKU 的 ID 不变、移除 SKU 软删除、新 SKU 新增。
- API 测试覆盖统一响应、分页、校验错误、重复编码和乐观锁冲突。
- Flyway 在真实 PostgreSQL 18 上从空库执行成功；验证不存在外键，约束和索引存在。

### 8.2 前端

- 组件测试覆盖默认 SKU 自动创建、禁止删除最后一个 SKU、默认 SKU 单选和请求映射。
- 运行 `npm run lint`、`npm run typecheck`、`npm run test`、`npm run build`。

### 8.3 真实链路

1. 启动 PostgreSQL、后端和前端。
2. 页面读取 Flyway 演示数据。
3. 新增含两个 SKU 的 SPU，刷新后仍可查询。
4. 编辑其中一个 SKU 并新增另一个 SKU，确认原 SKU ID 未变化。
5. 通过 SPU 聚合编辑移除一个非默认 SKU，确认其不再出现在正常查询中。
6. 上下架商品并验证状态持久化。
7. 删除 SPU，确认 SPU/SKU 均为软删除。
8. 检查浏览器 Console、Network、Loading、Empty、Error、滚动和常见桌面分辨率。

## 9. 环境与安全

目标运行环境为 Java 21、Maven、Node.js 和 PostgreSQL 18。数据库 URL、用户名和密码通过环境变量注入；仓库只提交无秘密的示例配置。日志不得输出密码、连接串凭证或完整敏感响应。

当前本机 PostgreSQL 服务处于停止状态。实施阶段可启动本机服务用于验收，但不得修改生产数据库或删除既有数据库/数据目录。若需要创建 Sprint 验收数据库，必须使用独立的 `xsy_scm` 数据库。

## 10. 设计决策摘要

- 采用模块化单体和纵向切片，不引入微服务。
- 数据库表显式命名为 `product_spu` 与 `product_sku`。
- 所有 SPU 强制至少一个 SKU，后续交易统一引用 SKU。
- SKU 更新采用差量同步，ID 稳定。
- Sprint 1 使用 `JSONB` 保存规格快照，不提前建设完整规格属性系统。
- 价格属于 SKU；SPU 列表价格由 SKU 汇总得到，不冗余存储。
- 不使用数据库外键。
- 参考成熟开源实现，但不整体复制或扩张 Sprint 范围。
