### 纳入范围后需要重新评审的既有口径

纳入上述能力后，以下既有约定会与之冲突或需扩展，**应在对应模块开工前先行评审**：

1. **Q13 库存单位不变量** —— 现规定一个 `(warehouse_id, sku_id)` 只锁采购单位、混单位必须报错。
   **2026-09-20 已澄清：规格转换不影响 Q13**（它是跨 SKU 的，两个 SKU 各自仍只锁一个记账单位）。
   真正会推翻 Q13 的是「同一 `(仓库, SKU)` 多单位记账」，**需求里从未提出过，明确排除**。
   因此本条**不需要再评审**。
2. **Q7 append-only 流水** —— 出库、盘点、报损报溢、调拨**都必须新增反向或正向流水**，
   不得改删历史行；`inventory_movement` 需要扩展 `movement_type` 枚举而非新增可变字段。
3. **成本列缺失** —— 目前 `inventory_movement` 不含成本列，`inventory_balance` 无 `avg_cost`。
   移动加权成本落地需要新增列并明确「何时重算、以什么时点计价」。
4. **仓库停用阻塞规则** —— 现已按「正库存 / 在途采购单 / 待入库收货单」三条件阻塞。
   引入调拨后，还需把「在途调拨单」纳入阻塞判断。

## 六、判定口径与核实方法

判断某能力是否「已完成」，需同时满足：

1. 后端存在对应 service（`module/scm/<domain>/service/`）；
2. 前端存在对应视图（`views/business/scm/<domain>/`）或明确的接口消费方；
3. 数据库结构支持（表 / 列 / 枚举值存在）。

> **只有表存在不算实现。** 例如 `order_return` / `order_refund` 表与 service 同时存在，才算完成退货退款。

核对数据库实际能力（以库存流水类型为例）：

```sql
SELECT DISTINCT movement_type FROM xsy_v2.inventory_movement;
```

  ① **差异施加到确认瞬间的账面量**（不是把账面改写成实盘数），期间发生的收货 / 出库不被抹掉；
  ② **盘点不建零余额行**（记账单位只能来自余额行）。
  详见 [`../decisions.md`](../decisions.md)。
- 2026-09-19 报损报溢落地（V30）。本波次引入**审批状态机**（`PENDING → COMPLETED / REJECTED`），
  并确认了四条口径：① 「新建」与「审批」必须是两个独立权限（报损是抹掉库存的动作，需要制衡）；
  ② `update` / `delete` 加状态守卫（比参考项目更严，否则已写流水的单据会被改删）；
  ③ 审批用乐观锁（审批人必须批准自己读到的内容）；④ 驳回必须填审核意见。
- 2026-09-19 调拨落地（V31）。**参考项目没有任何调拨实现**，本波次是 V2 原创设计。
  核心裁决：**两步式（发出 → 在途 → 收货）**，理由一是语义正确（货在卡车上时不在任何仓）、
  二是并发安全（两步各只锁一个仓库的余额行，既有锁序纪律不用改）。
  另确认：调拨占两个来源类型（唯一索引所迫）、两仓单位必须一致（不做隐式换算）、
  在途调拨阻塞仓库停用（第四条停用条件）。
- 2026-09-19 阈值预警落地（V32）。**四处刻意与参考项目不同**：阈值独立建表
  （不放在余额表上，否则配置路径会造出「没有流水支撑的余额行」）、按 (仓库, SKU) 配置、
  状态读时计算不落库、基准是可用量而非现有量。本波次不改变库存。
  剩余项重新排序为：单位转换 → 移动加权成本。
