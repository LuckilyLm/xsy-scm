## 2. 核心判断

「地图」不是一个模块，而是四个能力，成本差别极大：

```text
① 行政区划归属（省 / 市 / 区）    →  纯数据问题，免费，且是所有地理可视化的前置
② 中国地图分布图（大屏）          →  开源已完全够用，0 新增依赖、0 费用
③ 街道底图 + 地址选点 + 地理编码  →  必须外部服务（地图数据本身有资质与授权壁垒）
④ 路网距离矩阵 + 多点排线         →  排线有成熟开源求解器；路网仍要外部数据
```

因此：**②③④ 中唯一真正 unavoidable 的付费项是 ③ 的底图与地理编码**，
而 ①② 现在就能做完且不欠任何外部依赖 —— 这是本方案的主排序依据，事实也验证了它：
M0 + M1 全程未引入外部服务、未新增任何依赖。

> 动工前大屏中间的「供应链网络」是 `supply-chain-map.vue` 里按数组下标画的内联 SVG
> （`nodeX()` 与固定中心点 `(50,46)`，无任何地理含义）。它缺的正是 ① 的数据而不是代码 ——
> ① 落地后该组件已整体换成 ECharts 省界底图 + 市级气泡，见 §4。

## 3. M0 地理数据地基（已实施，V40，无任何外部服务依赖）

**为什么先做它**：没有区划归属，②只能显示全国空白；没有坐标，③④ 无从谈起。
这是唯一的硬前置，且做完后无论 ③ 选哪家都不返工。

- **区划码表 `scm_region`**：`region_code` / `parent_code` / `region_name` / `region_level`
  / `center_lng` / `center_lat`，无外键、逻辑删除、乐观锁。
  **实际只建省 / 市两级（34 + 414 行），不是原计划的三级** —— 区县由业务表单人工选择后
  按「编码 + 名称快照」直接落库，服务端持有区县字典没有任何消费者；
  而省市两级必须有数据，因为①存量自由文本地址要保守解析到市，②大屏按市聚合要取质心。
  数据**不手抄、不自采**：编码与名称取自仓库内 `area-cascader/province-city-district.ts`
  （GB/T 2260 六位码，与前端选择器**逐字一致**，避免两套编码对不上），
  质心取阿里 DataV.GeoAtlas `areas_v3`（拉取日期 2026-09-21，无市级要素的省回落省质心），
  以 V40 的 data-only 种子入库。
- **结构化归属列**：`warehouse` / `customer` / `supplier` 各加
  `province_code` / `city_code` / `district_code` 与三个 `*_name` 快照（均可空），
  外加 `longitude NUMERIC(11,8)` / `latitude NUMERIC(10,8)` / `geom_crs VARCHAR(8)`。
  原 `address` 保留为详细地址自由文本，语义不变。
  约束落在 DB：CRS 白名单、经纬度取值域、**经纬度必须成对**、
  **`geom_crs` 只能伴随坐标存在**；并建 `(city_code) WHERE deleted = FALSE AND city_code IS NOT NULL`
  部分索引供大屏按市聚合。
- **坐标系标记 `geom_crs`**（`GCJ02` / `WGS84`，可空）：**这条不是可选项**。
  高德与腾讯用 GCJ-02，天地图 / OSM / MapLibre 用 WGS-84，两者混用会有百米级系统偏移，
  一旦多源补录就无法追溯。所有坐标写入必须同时落 CRS。
  当前口径：`scm_region` 质心一律按 GCJ-02 理解，业务坐标列全为 NULL（M2 才写入）。
- **地址→区划解析：在迁移里用一条保守 SQL 完成，不引入 Java `RegionMatcher`**（与原计划的差异）。
  理由：这段规则只服务一次性回填，没有运行时消费者，放进应用等于凭空多一个类和一套单测；
  放 SQL 里则三张表共用同一个 `FOREACH` 循环。规则刻意保守、宁缺勿错：
  只按区划**完整名称**（'杭州市' 而非 '杭州'）做 `strpos`，命中多个市时取**出现位置最早**者，
  市名全国不唯一（当前只有重庆市）时必须同时命中其省名，**只解析到市**，解析不出留 NULL。
  **不在迁移里跑网络请求**。
- **前端：复用既有 `area-cascader`，不建第二套选择器、后端不开区划查询接口**（与原计划的差异）。
  选择器自带全量省市区数据集且编码与 `scm_region` 同源同值，多一个接口只会多一个漂移点。
  新增 `common/scm-area.ts` 做「级联路径 ↔ 6 列」双向纯函数（可被 `node --test` 直接加载），
  客户 / 供应商 / 仓库三处抽屉的地址升级为「省市区三级 + 详细地址」。
  名称快照与编码来自**同一次选择**，不按编码事后反查 —— 区划会调整，快照要忠于当时。
- **`longitude` / `latitude` 本期不进表单**：选点属于 M2，本期只建列与约束，不接受半套坐标。
- **存量数据验收口径**：M0 的验收标准是「解析失败**可见**、可人工纠正」，不是「100% 解析成功」。
  这一条由 M1 的覆盖度字段与大屏「未归属」提示实际承载（见 §4）。

## 4. M1 大屏真实地图（已实施，0 新增依赖、0 费用）

- 底图数据：存档**省级**行政区划 GeoJSON 进仓库 ——
  `xsy-scm-web/public/screen/china-province.json`，576 KB / 35 要素，来源阿里 DataV.GeoAtlas
  （2026-09-21 拉取，属性只留 `adcode` 与 `name`，边界未自绘未删减，含南海诸岛要素）。
  **构建期资产，运行时只请求本站静态资源，不请求外部域名** —— 内网 / 离线部署照常可用。
  前端只 `fetch` 一次并缓存注册（`echarts.registerMap`），失败时清缓存并提供「重新加载底图」入口。
- 渲染：`geo` 组件 + `map` 系列（省界着色，`visualMap` 按客户数）+ `effectScatter`（市级气泡）。
  `use-echarts.ts` 现为 `import * as echarts from 'echarts'` 全量引入，`geo` / `map` 已在包内，
  **确实零新增依赖**；不升级到 echarts 6.1.0（项目规则：无编译需要不动依赖）。
- **省级节点与底图要素按 `adcode` 对齐，不按名称**（实施时才发现的必要修正）。
  字典沿用 `area-cascader` 的简称「香港」/「澳门」，官方边界数据用全称
  「香港特别行政区」/「澳门特别行政区」，按名称匹配会让这两省**静默不着色**
  （ECharts 不报错，图上只是没有颜色）。`adcode` 与 `province_code` 同为 GB/T 2260 六位码，
  是两份数据唯一稳定的共同身份；这条差异被
  `xsy-scm-web/test/screen-geo-contract.test.mjs` 钉成断言，防止匹配键被改回名称。
- **省级数值由后端从市级聚合行在 Java 侧上卷**，不是两条各自演算的 SQL：
  省界着色与市级气泡因此恒等，不会出现「图例与气泡对不上」的漂移。
- 图层语义（全部来自只读聚合，不写业务表、不建独立副本）：
  气泡大小 = **该市主档数**（客户 + 供应商 + 启用仓库，按面积开方缩放），着色 = 客户数；
  仓库口径与 KPI 面板一致，只统计 `ENABLED`。
- **覆盖度显性化**：接口同时返回 `coverage`（各 `*Total` 与 `*Located`），
  面板标题条用醒目色标出「未归属：客户 N · 供应商 N · 仓库 N」。
  地图上找不到的量必须被看见，否则用户会把分布图当成全部业务量。
- 后端新增一枚只读接口 `GET /scm/screen/data/geo`，沿用 `scm:screen:query`（V28），
  SQL 在 `ScreenDataMapper.xml` 按 `city_code` 聚合并走 V40 新建的部分索引；
  字典里查不到的编码**不成为气泡**（没有坐标画不出来），差额只体现在覆盖度里。
- 保留 V1 信息不丢：逐仓的「库存 / 今日出库」移到地图右侧栏，底部四格统计首格升级为「覆盖城市」。
- **本期未做**：`lines` 流向层（供应商 → 仓库 → 客户）。它需要跨域按单聚合，
  且在没有街道坐标（M2）的情况下只能画「省 → 省」的粗线，信息量低于代价；
  留到 M2 有真实点位后再评估。
- 地图合规：使用官方来源的完整行政区划边界（不自行删减、不自绘），存档来源与版本记录在
  `docs/decisions.md`；内部经营大屏仍需避免对外公开放映无审图号的地图 —— 见 §8 风险 R-3。

## 8. 风险与如实声明

- **R-1 配额即成本**：高德公开口径为「未认证 0 配额 / 个人约 15 万次每月 / 企业更高（本日核实上限约 900 万 / 100 QPS），超出走流量包或余额」。
  地理编码 + 路径规划 + 底图初始化的实际消耗要在上线前按订单量测算，不能默认「免费」。
- **R-2 商用授权无公开报价**：本文只给出 2021 年行业讨论的约 5 万元 / 年量级作参考，**签约前必须向厂商索取正式报价与授权范围**。
- **R-3 地图内容合规**：公开发布 / 对外放映的地图涉及测绘资质与审图号要求；内部 ERP 与内部大屏风险较低，
  但边界数据必须来自官方来源且不做删减，不自绘。
- **R-4 坐标系混用**：GCJ-02 与 WGS-84 混存会造成百米级偏移且不可追溯，`geom_crs` 是硬约束。
- **R-5 数据质量**：现网客户地址为自由文本，预计有不可解析比例；M0 的验收标准是「解析失败可见、可人工纠正」，不是「100% 解析成功」。
- **R-6 保守解析对港澳 generic 地名的潜在误匹配**（M0 实施时发现，现网 0 命中）。
  V40 Step 4 只按**市级名称整体出现**在地址里做匹配，而 `scm_region` 的市级字典含香港 / 澳门下辖的
  「东区 / 南区 / 北区 / 荃湾区 / 大堂区」等通名；地址里出现「长沙东区」这类片段就会被认作选中该市级编码。
  现网实测（`xsy_scm_b0`）落在 710000–829999 的解析结果为 **0 行**，所以本期不改行为；
  一旦后续补录数据出现这类误挂，收紧规则（要求市级名前带省级名，或剔除通名市级行）必须**新开 V41**，
  因为 V40 已应用到真实库且不可修改。
- **R-7 字典与官方边界数据的名称漂移**：`scm_region` 沿用 `area-cascader` 简称（「香港」/「澳门」），
