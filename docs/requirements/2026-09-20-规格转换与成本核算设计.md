# 规格转换与成本核算：设计口径

最后更新：2026-09-20
状态：**设计输入**（本文不代表已排期、已批准或已冻结）
适用范围：库存深化剩余两项 —— 规格转换（原称「单位转换」）、移动加权成本核算

## 一、先更正一处既有口径（重要）

`docs/requirements/2026-09-19-需求覆盖与待办清单.md` 与 `docs/decisions.md` 里此前写着
「单位转换会推翻 Q13 的『一个 `(仓库, SKU)` 只锁一个记账单位』」。**这个说法是错的**，
本文予以更正：

- 参考项目的「规格转换」（`ConvertTypeEnum`：`SPLIT 整件拆零` / `COMBINE 组合拆分`）
  流程是「**选择源规格与目标规格**（如整件 → 散装）」，产出「转换出」与「转换入」两条流水。
  **它是跨 SKU 的**：源 SKU 与目标 SKU 是两个不同的 `(warehouse_id, sku_id)`，
  各自仍然只锁一个记账单位。
- 因此 **Q13 不需要重述，也不会被推翻**。此前把它列为「开工前需重新评审的口径」是误判。

真正会动到 Q13 的，是另一件**没有被需求提出过**的事：让**同一个** `(仓库, SKU)`
同时按多个单位记账（例如同一 SKU 既按箱又按 kg 记余额）。**本设计不做这件事**，
理由见第四节「明确排除」。

## 二、规格转换（整件拆零 / 组合拆分）

### 2.1 业务形态

一次转换 = 一个仓库内、**一张单**、多行；每行是
「源 SKU 出 N（单位 U₁） → 目标 SKU 入 M（单位 U₂）」。

- **拆零（SPLIT）**：1 箱 → 10 kg（源数量少、目标数量多）
- **组合拆分（COMBINE）**：若干散装 → 1 个组合品（源数量多、目标数量少）

折算关系（N : M）**由单据显式声明**，不做自动推断。理由：折算率是业务事实
（一箱到底是 9.5 kg 还是 10 kg 取决于供应商与批次），系统猜不出来，猜错会直接污染两边余额。

### 2.2 表结构

```text
inventory_conversion（头）
  id, conversion_no, warehouse_id, convert_type(SPLIT|COMBINE),
  status(PENDING|COMPLETED|REJECTED), reason, remark,
  audited_at, auditor, audit_opinion, version, deleted, created_*/updated_*

inventory_conversion_item（行）
  id, conversion_id,
  source_sku_id, source_quantity, source_unit,
  target_sku_id, target_quantity, target_unit,
  remark, version, deleted, created_*/updated_*
```

- `source_unit` / `target_unit` **由单据显式声明**（不是从余额推导）：折算关系本身就含单位
  （1 箱 = 10 kg），让系统去猜等于把「箱」和「kg」的关系交给启发式。
- 单号前缀 `CVT`（与 `OUT`/`STK`/`LGR`/`TRF` 并列，互不相同）。
- **审批状态机与报损报溢同构**（`PENDING → COMPLETED / REJECTED`）：参考项目也是三态。
  转换会把两个 SKU 的余额同时改掉，比单纯报损影响面更大，更需要制衡。

### 2.3 流水与方向

新增两个流水类型（沿用「方向编码在类型里」的既有纪律，数量恒为正）：

| 类型 | 方向 | 写入哪个仓库的哪个 SKU |
| --- | --- | --- |
| `CONVERT_OUT` | 出 | 本仓的**源** SKU |
| `CONVERT_IN` | 入 | 本仓的**目标** SKU |

来源类型同样要拆两个（`CONVERT_OUT_ITEM` / `CONVERT_IN_ITEM`）——
**与调拨同一个原因**：同一条明细行会产生两条流水，而
`uk_inventory_movement_source_active` 只认 `(source_document_type, source_document_item_id)`，
共用一个类型第二条就插不进去。该索引是 V19 冻结的契约，不为新能力放宽。

`ck_inventory_movement_snap` 扩到**十方向分组**（入 5 个、出 5 个）：
`CONVERT_IN` 进「入」组、`CONVERT_OUT` 进「出」组。

### 2.4 审批通过时的执行顺序（本设计的核心难点）

一次转换要在**同一个事务**里改动**两行余额**（源 SKU 与目标 SKU），都在同一仓库。
因此：

1. **先把目标行建出来**（`insertOnConflictDoNothing`，入方向才允许建行），
   单位取单据声明的 `target_unit`；
2. **再把本次涉及的所有余额行按 `(warehouse_id, sku_id)` 升序统一加锁**
   —— 一行可能既是某行的源、又是另一行的目标，**必须先收集去重再排序**，
   不能「逐行先源后目标」，否则两行互为源/目标时会死锁；
3. 持锁后逐个施加增减（源减、目标加），并写两条流水；
4. 最后推进单据状态。

第 2 步是本能力与既有六条写入路径的**唯一实质差异**：
既有的六条路径每个事务只碰一行余额，锁序天然成立；本能力第一次碰两行，
必须显式排序。**这是必须写进 IT 的用例**（构造两行互为源/目标，验证不死锁、结果正确）。

### 2.5 边界与守卫

- **源 SKU 必须有余额行**，且可用量（现有量 − 预留量）足够 → 否则失败。
  与销售出库同一取向：出方向不建行。
- **源 SKU 的余额单位必须等于单据声明的 `source_unit`** → 否则失败（不做隐式换算）。
- **目标 SKU 已有余额行时，其单位必须等于 `target_unit`** → 否则失败；
  没有余额行则由本次转换**建立**（入方向允许建行）。
- **同一行的源 SKU 与目标 SKU 不得相同**（那不是转换，是原地来回加减）。
- 同一张单里同一个源 SKU 可以出现在多行（拆给不同目标），**但同一行内不得重复**；
  需要去重的是「余额行」而不是「SKU」（见 2.4 第 2 步）。
- **不保证守恒**：重量/成本守恒是参考项目的诉求，但 V2 目前没有重量列（Q2），
  也没有成本核算（Q3）。因此本波次**只保证数量按声明的折算关系变化**，
  不宣称重量或金额守恒。成本守恒等移动加权成本落地后再谈（见第三节）。

## 三、移动加权成本核算（最后一项）

### 3.1 现状与缺口

- `inventory_movement` 有 `unit_cost`（可空），目前**只有入库写入**（= 采购单价）；
  出库 / 盘点 / 报损报溢 / 调拨的流水**一律写 NULL**。
- `inventory_balance` **没有** `avg_cost`（Q3 裁决：成本事实由 movement 的 `unit_cost` 承载）。

### 3.2 落地要点（需要在开工前定口径）

1. **加列**：`inventory_balance.avg_cost`（以及是否需要 `total_cost`）。
   Q3 的「不加列」是**范围裁决**，不是永久否决 —— 但加列要说明为什么
   movement 的 `unit_cost` 不够：因为**出库时的成本必须在出库那一刻确定**，
   事后从流水反推需要重放全部历史，且移动加权本身是顺序相关的。
2. **计价时点**：入库时 `newAvg = (oldQty·oldAvg + inQty·inCost) / (oldQty + inQty)`；
   出库时按当时的 `avg_cost` 计入 `unit_cost`（**这是本项最大的一处语义变更**：
   出库流水从「无成本」变成「有成本」，且**存量历史流水的 `unit_cost` 仍是 NULL**，
   不能回填 —— Q7 append-only 禁止改历史行）。
3. **期初 `avg_cost` 口径**（原阻塞项，**2026-09-20 已按默认值落地**）：
   取该 (仓库, SKU) **最近一次 `PURCHASE_IN` 流水的 `unit_cost`**，无采购入库则为 0。
   这是唯一有真实采购价格事实支撑、且不需引入任何新输入数据的起点；副作用是历史库存估价偏保守
   （不虚高）。**属可调整项** —— 要更精确（最近一次采购价 × 存量 / 财务指定价）需另开数据修正迁移，
   V34 已应用不可变。
4. 受影响面：**七条写入路径全部**要顺手维护 `avg_cost`（采购入库重算，其余六条按现有均价入账），
   其中五条（出库 / 盘点 / 报损报溢 / 调拨转出 / 转换转出）还要把成本写进流水。

### 3.3 为什么排在最后

它会改「出库流水是否带成本」这条语义，而这条语义被前六波全部依赖。
在库存动作稳定之前定计价时点，等于在流沙上浇地基。

## 四、明确排除（不做的事）

- **同一 `(仓库, SKU)` 多单位记账**：不引入。它才是真正推翻 Q13 的那件事，
  而需求里没有提出过它；引入后「可用量」「预留量」「预警基准」全部要按单位分别维护，
  复杂度与收益不成比例。
- **自动折算率推断**：不做。折算率由单据显式声明。
- **跨仓转换**：不做。跨仓搬运是**调拨**（V31 已有），转换只在本仓内改规格。
  两者职责必须分清，否则会出现「用转换单搬货」这种绕过调拨在途语义的用法。

## 五、与既有能力的关系

| 既有能力 | 关系 |
| --- | --- |
| 调拨（V31） | 同样是「一次事务动两行余额」，但调拨是**跨仓**且**分两步**（各自只锁一仓）；转换是**同仓**且**一步**（锁两行，需排序）。两者互补，不可互相替代 |
| 报损报溢（V30） | 审批状态机直接复用同一形状（`PENDING → COMPLETED / REJECTED` + 审批乐观锁 + 驳回必须填意见） |
| 阈值预警（V32） | 转换会改变源/目标 SKU 的可用量，因此**可能触发或解除预警**；预警是读时计算的，无需额外联动 |
| Q13 单位不变量 | **不受影响**（跨 SKU），见第一节 |
| Q7 append-only | 转换同样只新增流水，修正靠反向转换单 |

## 六、待裁决项（开工前）

1. 折算率是否需要留痕历史（同一对 SKU 的折算率变化是否需要可追溯）？
2. 转换单是否允许**跨行引用同一 SKU 两次以上**（例如 A→B 与 A→C 同单）？
   本设计允许；若业务不允许，需要加一条单级校验。
3. 移动加权成本的**期初 `avg_cost`** 取值口径 —— **已落地**（V34 采用「最近一次采购入库单价，
   无历史则 0」；口径可调整，见 3.2 第 3 点）。
4. 出库流水的 `unit_cost` 从「NULL」变成「有值」后，既有的
   `InventoryMovementVO` 与前端展示是否需要区分「无成本事实」与「成本为 0」。
   **V34 的处理**：前端流水页继续用 `quantityText`（null → `—`），因此
   「历史流水（上线前出库）」显示 `—`、「成本为 0 的流水」显示 `0.0000` —— 三态天然成立，无需改类型。
