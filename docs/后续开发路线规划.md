# 鲜蔬源智链后续开发路线规划

日期：2026-09-10

状态：开发方向与文档整理计划已确认；各阶段业务细则仍需形成详细规格，不代表已实施或验收。

## 1. 目标与试运行范围

以内部业务闭环优先，面向少量客户、单个试点仓库，采用人工确认重量、人工配送签收和收付款登记。保留现有多仓数据结构，首期不扩展跨仓协同。

推进顺序：现有基础收口 → 采购收货规则升级 → 分拣与销售出库 → 配送签收 → 基础结算 → 试运行。

小程序需求与接口设计可以提前开展，正式客户试用安排在内部闭环验收之后。技术路线为 Taro + React + TypeScript，微信小程序首发，预留商城 H5，详见[小程序商城规划草案](小程序商城规划草案.md)。真实电子秤按后续现场需求接入。

## 2. 当前基础与证据边界

以下为 2026-09-10 规划调查结论，不替代当前版本运行验收：

- 已有商品、客户协议价、销售订单、采购收货、库存和认证权限基础实现。
- [Sprint 3 验证记录](superpowers/verification/2026-09-07-sprint-3-verification.md)记录历史自动化通过，但保留浏览器主链路验收缺口；调查时 E2E 文件尚未覆盖采购收货库存完整链路。
- 前端已存在认证基础代码，调查时入口与路由仍需完成登录守卫接线；[系统基础计划](superpowers/plans/2026-09-07-system-foundation-rbac.md)包含不同阶段历史结果，不能只取其中成功记录作为当前全量通过的证明。
- [最新登录权限后端补充](references/smartadmin/2026-09-10-登录权限后端补充.md)记录了编译与跳过测试的打包检查，权限合同变化仍需对应回归验证。
- [负责人确认口径](requirements/2026-09-09-负责人确认口径.md)覆盖旧规格中的采购生成、多次收货、超收和入库模式口径；现有实现不能直接视为已满足新需求。

## 3. 分阶段交付与依赖

| 阶段 | 重点交付 | 验收目标 |
| --- | --- | --- |
| P0 基础收口 | 登录、退出、强制改密、路由守卫；试点必需的用户角色授权入口与日志查询；处理现有回归问题 | 普通账号按权限完成现有订单采购主路径，越权 API 被拒绝，浏览器验收有实际证据 |
| P1 采购收货升级 | 按时间段人工生成；库存计算口径；多次收货；超收及少收关单；直接入库与二次确认入库 | 销售、采购、每次收货及库存流水可追溯；重复操作不重复采购或入库，未入库收货不增加库存 |
| P2 分拣出库 | 分拣任务、人工实际重量及修改原因、出库确认与 SALES_OUT 流水 | 保留订购数量，重量可审计；库存不足、重复提交及并发扣减受到后端约束 |
| P3 配送签收 | 配送任务、订单分配、司机车辆基础信息、人工发车签收与异常处理 | 订单可追踪至配送与签收，部分签收、拒收有明确处理路径 |
| P4 基础结算 | 应收应付、部分收付款登记、客户供应商对账 | 数量、金额和业务单据可核对，结算依据与未结余额可追溯，重复登记受保护 |
| P5 试运行 | 完整链路、权限、部署、备份恢复及阻断问题修复 | 一笔业务从销售录单走到收付款登记，库存、重量、金额和日志一致 |

阶段按依赖顺序实施，每阶段独立形成规格、实现与验收证据，通过后再进入依赖它的下一阶段。P0 实施期间可开展 P1 规则确认；不将全部后续模块合并成一个大版本。P 编号是本路线内部编号，不重命名既有 Sprint。

## 4. 详细设计前置决策与架构边界

| 阶段 | 必须先确认的业务规则 |
| --- | --- |
| P1 | 计算库存选项默认值、可用库存定义、计算及锁定时点、重复时间段生成策略；超收容差或审批；少收关单；两种入库模式的状态、权限和流水时点；旧收货单与确认批次兼容映射 |
| P2 | 分拣任务粒度、实际重量确认与更正、缺货处理、出库时点及撤销边界 |
| P3 | 部分签收、拒收与退货如何衔接，异常由谁处理及允许的状态变化 |
| P4 | 结算触发时点和数量依据、协议价缺失回退、退货与实重差异对账款的影响、首期结算方式 |

这些是前置决策，不是已确认业务规则；不能由开发人员静默补齐。负责人已确认的事实以需求文档为准。

- 延续 Java 21、React 和模块化单体。系统通用能力先调查本项目，再只读参考 SmartAdmin；供应链能力以本项目规格为准。
- 分拣确认、出库、发车、签收、收付款登记使用显式业务动作，由所属领域校验权限和状态，不跨模块直接修改订单状态。
- 分别保留订购数量、实际重量、出库数量和结算数量；金额计算由后端负责，不在页面或转换器中隐藏结算规则。
- 业务单据、库存余额、追加流水及幂等结果按必要边界原子提交。沿用新增 Flyway 迁移，不修改已应用迁移、不创建数据库外键，保留历史追溯。
- 首期暂缓小程序正式试用、真实电子秤、GPS 轨迹、营销、大屏、完整成本利润核算和总账；后续分别立项，不以占位页面作为交付。

## 5. 验收与下一步

测试按业务风险安排：采购重复生成与多次收货、超收与少收、两种入库模式；重量更正、库存不足、并发扣库、幂等和事务回滚；部分签收、拒收、部分收付款与数据追溯。

每阶段运行相关后端测试与构建、前端 lint/typecheck/test/build。浏览器覆盖普通账号关键主路径、会话失效、越权、加载、空状态和失败恢复；不为每个按钮重复建设 E2E。试运行前验证真实 PostgreSQL 业务链路和一次备份恢复演练。未执行项目必须注明原因，不用历史成功结果代替当前验收。

下一步安排 P0 基础收口，同时确认 P1 业务规则。本次仅形成规划文档，没有创建小程序工程、安装依赖、修改业务代码或执行运行时测试。
