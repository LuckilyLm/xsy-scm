# 鲜蔬源智链小程序商城规划草案

日期：2026-09-08
状态：待评审；用于范围与架构讨论，不代表已批准实施。
建议工程名：`xsy-scm-miniapp`

## 1. 定位与目标

建设一个面向下游客户的逻辑商城，由不同展示端承载；当前负责人确认手机端先做微信小程序。商城与现有管理后台共用商品、客户价格和销售订单体系，先完成“客户登录 → 选品 → 下单 → 查看订单与实重”的闭环，再增加支付、营销、报表和语音能力。

本草案不创建小程序工程，不改变当前 Sprint 范围，也不代表已有能力已通过商城端验收。

## 2. 功能范围

| 需求 | 规划 |
| --- | --- |
| 定制首页、新品推荐、不同商城主题 | 首期提供默认生鲜主题和简单首页配置，后续扩展主题模板 |
| 商品搜索、分类下单、购物车 | 首期核心 |
| 常用菜品、再来一单 | 首期纳入，提高重复采购效率 |
| 账期支付、货到付款、在线支付、余额充值 | 分阶段接入，必须配套服务端结算能力 |
| 下单商品汇总等客户报表 | 基础订单闭环后增加 |
| 抢购、促销、满减满赠、优惠券、限时特价 | 后续营销阶段 |
| 智能语音下单 | 独立后续阶段，识别结果必须经客户确认 |
| 客户查看订单实际称重数据 | 首期订单详情纳入，读取后台已确认的业务数据 |

功能清单中的“订单助手”面向员工，涉及改价、编辑订单、入库，应单独规划身份和入口，不混入客户商城首期。“针对订单入库”的具体业务含义需独立澄清，不能直接映射为库存修改操作。

## 3. SmartApp 参考结论

参考工程采用 UniApp + Vue 3 + Pinia，包含客户线索、公告、商品查询、表单等页面，偏员工业务操作，并非完整订货商城。

### 可借鉴

- 页面、API、请求封装、状态管理分层。
- 登录失效处理、下拉刷新、分页加载。
- 搜索筛选、详情页、附件上传、消息入口。

### 需要重新设计

- 参考登录绑定员工、部门；商城应绑定客户及其采购账号。
- 参考请求使用自己的响应码和 Token 约定；当前项目使用 `code/message/data`，建设中的后台认证使用 Session/CSRF。
- 参考商品页是查询列表，不包含完整客户价、购物车和结算流程。
- 参考工程依赖存在较早的版本锁定，不能整体复制依赖清单。

重点参考文件：

- `smart-app/package.json`
- `smart-app/src/pages.json`
- `smart-app/src/lib/smart-request.js`
- `smart-app/src/api/system/login-api.js`
- `smart-app/src/store/modules/system/user.js`

上述路径均相对于 `project-reference-examples/smart-admin-java17/`。参考目录保持只读。

## 4. 技术选型建议

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| Taro + React + TypeScript，推荐 | 延续项目 React 路线，可面向微信小程序及 H5 | 移动组件需要独立实现和多端验证 |
| UniApp + Vue 3 + TypeScript | 与 SmartApp 参考结构接近 | 增加 Vue 技术栈，需要明确项目规则例外 |
| 微信原生小程序 | 直接使用平台能力 | 后续公众号 H5 需要另外建设 |

Taro 官方支持 React 和小程序/H5 多端开发，参见 [Taro 官方介绍](https://taro-docs.jd.com/taro/docs)。具体版本及配套组件库在实施时锁定验证，本草案不指定版本。

负责人已确认手机端当前指微信小程序。商城仍保持一个逻辑商城；H5/公众号等其他展示端属于后续适配，不拆分商品、价格、订单和结算规则。

后台 Ant Design/ProComponents 组件不直接移植到小程序。可以复用业务概念、类型契约和纯工具逻辑，暂不为此拆共享包。请求层使用适配小程序的平台能力，不假设浏览器端 Axios、Cookie 或 DOM 行为能够直接沿用。

## 6. 后端与数据边界

建议在现有 Spring Boot 模块化单体内增加 `mall` 模块，对外提供 `/api/mall/**`，负责客户接口与业务编排，调用现有业务服务。商品、价格、订单和库存规则继续归属原业务域，不另建一套商城业务账。

```text
xsy-scm-miniapp
    → /api/mall/**
    → 商城身份校验与业务编排
    → product / customer / order 等现有业务域
    → 同一套业务数据库
```

| 已有基础 | 商城适配工作 |
| --- | --- |
| SPU/SKU、上下架 | 增加分页商品查询、详情和商城展示字段 |
| 客户商品可见性 | 商品查询、加购校验、提交均执行客户范围检查 |
| 协议价优先、市场价回退 | 列表、详情、结算统一调用价格解析 |
| 销售订单、提交锁价、实重 | 增加受限的客户下单与查询接口，复用状态流转 |
| 后台认证建设中 | 增加客户身份体系，隔离员工权限和客户权限 |

### 已发现的适配点

1. `OrderableSkuQueryService` 当前列表返回市场价，并采用全量列表方式。商城需要分页查询和客户有效价格，不能直接将该列表作为商城价格展示接口。
2. 当前 `SalesOrderSaveRequest` 允许传入 `customerId`、`source`。商城应使用受限请求模型，由服务端根据登录身份确定客户，并固定 `source=MALL`，不得允许客户端指定其他客户或人工改价。
3. 微信身份与业务客户身份需要绑定校验。商城凭证的签发、失效和传输方案应独立设计，与既有 Spring Security 集成，不因参考工程使用 Bearer Token 就替换后台认证方案。
4. 订单列表、详情、报表和售后操作均需服务端验证客户归属，不能只通过前端隐藏入口控制权限。

### 新增数据范围

- 客户登录身份与绑定关系。
- 客户收货地址及订单地址快照。
- 购物车及明细。
- 常购记录或收藏关系；具体语义在首期规格中明确。
- 商城首页配置。

具体表结构在详细设计中确定。使用新增 Flyway 迁移，不修改已应用迁移，不创建数据库外键；保留必要唯一约束、检查约束、关系列索引和事务边界。

## 7. 首期业务规则建议

- 默认面向已有企业客户，由后台确认客户绑定关系。
- 首期每个采购账号绑定一个客户；集团多单位切换后续扩展。
- 下单后沿用现有订单提交与审核流程，不由商城直接跳过审核。
- 商品列表价格用于展示，提交时由服务端重新校验可见性、上下架和有效价格并锁价。价格变化应明确反馈客户。
- “再来一单”重新校验上下架、可见性和当前价格，不复制历史锁价作为新订单价格。
- 非标品同时保留订购数量、实际数量，区分预估金额与已确定金额。客户读取后台已确认实重，不直接修改称重记录。
- 重复点击或网络重试不得生成重复订单；关键提交操作使用服务端幂等保护。
- 首期建议选择一种已确认的线下结算方式。账期需要额度及应收规则，货到付款需要收款状态衔接，不能只在页面上提供选项。
- 库存不足是否允许下单，应结合销售驱动采购模式确认，不能默认按现货零售商城拦截。

以上属于建议，尚未冻结为已批准业务规则。

## 8. 分阶段路线

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| M0：工程与身份 | 工程、环境配置、请求封装、客户绑定登录、基础导航 | 真机登录、退出、失效恢复；客户不能访问后台接口 |
| M1：选品下单 | 默认主题及简单首页配置、分类搜索、客户价、详情、购物车、地址、提交订单、订单列表详情、常购、再来一单 | 商城订单进入现有销售订单流程；后台更新的实重可被客户查看 |
| M2：客户服务 | 商品汇总报表、售后申请、配送信息、账单查询 | 客户只能查看自己的数据；对应后台业务已具备可用接口 |
| M3：支付与营销 | 在线支付、余额充值、优惠券、促销、主题配置 | 支付回调幂等、退款及对账、优惠计算一致 |
| M4：语音与扩展 | 语音选品下单、推广入口等 | 商品和规格歧义由客户确认，确认后再提交 |

M0—M4 是本草案内部阶段编号，不替换现有 Sprint 编号。

M2 依赖售后、配送、财务相应后台能力，不以空页面或模拟数据视为交付。M3 应进一步拆分支付与营销设计，明确非标品最终实重带来的补差、退款及结算时点。现有订单金额和退款记录不代表真实支付能力已完成。

## 9. 验证要求

实施时按风险选择测试，不为每个页面重复建设完整 E2E 套件。

- 工程检查：执行实际提供的 lint、类型检查、测试和微信小程序构建。
- 真实链路：微信开发者工具及真机验证登录、选品、提交、订单查询；H5 验证不能替代小程序验收。
- 权限：客户 A 不能访问客户 B 的商品专属价格、订单、地址和报表。
- 价格：协议价、市场价回退、提交前变价、再来一单重新定价。
- 订单：网络重试、重复提交、失效购物车项、后台审核及实重数据同步展示。
- 交互：加载、空状态、失败重试、登录过期、滚动和常用手机尺寸。
- 后端：对受影响业务运行编译、相关单元与集成测试及构建；数据库变更验证迁移和约束。

本次仅规划与文档整理，未进行运行时验证。

## 10. 详细设计前待确认

1. 是否接受 Taro + React + TypeScript，以及 `xsy-scm-miniapp` 命名。
2. 微信小程序首发是否足够；公众号 H5 是否必须同期交付。
3. 客户账号开通、微信绑定、审核及解除绑定的流程。
4. 单账号单客户是否满足首期，是否立即需要集团多单位切换。
5. 首期采用哪一种结算方式，以及对应收款、应收和对账边界。
6. 配送日期、截单时间、起送条件、运费规则。
7. 缺货能否下单、是否需要库存预占，以及与采购需求生成的关系。
8. 客户提交、取消、修改订单与后台审核的权限和时点。
9. 常用菜品是主动收藏、历史购买推导，还是两者并存。

## 11. 与当前建设节奏的关系

原项目草案将商城安排在 Phase 7。当前可以先完成设计；如需提前实施，应单独确认 M0/M1 范围，与正在建设的系统权限能力衔接，不自动扩展当前 Sprint。

首期重点是客户身份隔离、准确客户价和可靠下单。详细规格确认后，再拆解实施任务和迁移方案。
