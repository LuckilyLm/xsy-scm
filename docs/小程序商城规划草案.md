# 鲜蔬源智链小程序商城规划草案

日期：2026-09-08；更新：2026-09-10

状态：技术路线、微信首发及预留 H5 的方向已确认；业务细则仍待详细设计，不代表已实现或验收。

拟建工程名：`xsy-scm-miniapp`

## 1. 定位与目标

建设一个面向下游客户的逻辑商城，由不同展示端承载；当前负责人确认手机端先做微信小程序。商城与现有管理后台共用商品、客户价格和销售订单体系，先完成“客户登录 → 选品 → 下单 → 查看订单与实重”的闭环，再增加支付、营销、报表和语音能力。

本草案不创建小程序工程，不改变当前 Sprint 范围，也不代表已有能力已通过商城端验收。

## 2. 功能范围

| 需求 | 规划 |
| --- | --- |
| 定制首页、新品推荐、不同商城主题 | 首期采用默认生鲜主题；可运营首页配置及主题模板后续扩展 |
| 商品搜索、分类下单、购物车 | 首期核心 |

功能清单中的“订单助手”面向员工，涉及改价、编辑订单、入库，应单独规划身份和入口，不混入客户商城首期。“针对订单入库”的具体业务含义需独立澄清，不能直接映射为库存修改操作。

## 4. 已确认技术路线与复用边界

采用 **Taro + React + TypeScript，微信小程序首发，预留商城 H5**。不迁移现有管理后台，不要求 H5 同期正式交付。

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| Taro + React + TypeScript，已选择 | 延续项目 React 路线，可面向微信小程序及 H5 | 移动组件需要独立实现和多端验证 |
| UniApp + Vue 3 + TypeScript | 与 SmartApp 参考结构接近 | 增加 Vue 技术栈，需要明确项目规则例外 |
| 微信原生小程序 | 直接使用平台能力 | 后续公众号 H5 需要另外建设 |

Taro 官方支持 React 和小程序/H5 多端开发，参见 [Taro 官方介绍](https://taro-docs.jd.com/)。具体版本及配套组件库在工程启动时验证并锁定，不直接复制后台 React/Vite 版本。uni-app 也通过其组件、页面和平台 API 规范实现多端编译，不能直接编译现有 React 后台，参见 [uni-app 跨端原理](https://uniapp.dcloud.net.cn/tutorial/)。官方资料于 2026-09-10 规划调查时核对。

负责人已确认手机端当前指微信小程序。商城仍保持一个逻辑商城；H5/公众号等其他展示端属于后续适配，不拆分商品、价格、订单和结算规则。

后台 Ant Design/ProComponents 组件不直接移植到小程序。可以复用业务概念、类型契约和纯工具逻辑，暂不为此拆共享包。请求层使用适配小程序的平台能力，不假设浏览器端 Axios、Cookie 或 DOM 行为能够直接沿用。

| 内容 | 复用方式 |
| --- | --- |
| 商品、客户价格、订单、库存与结算规则 | 复用已有或后续交付的后端领域服务，维持一套业务账 |
| 类型、枚举、纯工具函数 | 筛选无浏览器依赖且语义相同的部分，不向客户暴露后台专用字段 |
| Ant Design、ProComponents、后台布局 | 独立建设移动界面，使用 Mall Theme |
| 请求、路由、认证与存储 | 使用小程序平台适配层，不直接沿用 Axios/Cookie/React Router 接线 |
| 新商城小程序与未来 H5 | 共用跨端页面和业务交互，登录、存储等平台差异集中封装 |

复用目标是新商城的小程序与未来 H5，以及适合共享的后端和纯逻辑，不承诺复用百分比。首期不建设通用共享包，出现真实重复后再提取。H5 构建预览可以辅助开发，但不是首发验收端。

## 6. 后端与数据边界

建议在现有 Spring Boot 模块化单体内增加 `mall` 模块，对外提供 `/api/mall/**`，负责客户接口与业务编排，调用现有业务服务。商品、价格、订单和库存规则继续归属原业务域，不另建一套商城业务账。

```text
xsy-scm-miniapp
    → /api/mall/**
    → 商城身份校验与业务编排
    → product / customer / order 等现有业务域
    → 同一套业务数据库
```

| 既有基础或规划依赖 | 商城适配工作 |
| --- | --- |
| SPU/SKU、上下架 | 增加分页商品查询、详情和商城展示字段 |
| 客户商品可见性 | 商品查询、加购校验、提交均执行客户范围检查 |
| 客户协议价基础，负责人已确认协议价优先 | 列表、详情、结算统一调用价格解析；协议价缺失回退仍需价格专项确认 |
| 既有销售订单与锁价基础，实际重量依赖分拣阶段交付 | 增加受限的客户下单与查询接口，复用状态流转，读取后台已确认实重 |
| 后台认证建设中 | 增加客户身份体系，隔离员工权限和客户权限 |

### 历史调查发现的适配点（实施前复核）

1. `OrderableSkuQueryService` 当前列表返回市场价，并采用全量列表方式。商城需要分页查询和客户有效价格，不能直接将该列表作为商城价格展示接口。
2. 当前 `SalesOrderSaveRequest` 允许传入 `customerId`、`source`。商城应使用受限请求模型，由服务端根据登录身份确定客户，并固定 `source=MALL`，不得允许客户端指定其他客户或人工改价。
3. 微信凭证交换由后端完成，微信身份与业务客户身份需要绑定校验。商城凭证的签发、失效和传输方案应独立设计，与既有 Spring Security 集成，不因参考工程使用 Bearer Token 就替换后台认证方案。
4. 订单列表、详情、报表和售后操作均需服务端验证客户归属，不能只通过前端隐藏入口控制权限。

### 新增数据范围

- 客户登录身份与绑定关系。
- 客户收货地址及订单地址快照。
- 购物车及明细。
- 常购记录或收藏关系；M3 详细设计明确具体语义。
- 商城首页配置；后续运营扩展阶段设计。

具体表结构在详细设计中确定。使用新增 Flyway 迁移，不修改已应用迁移，不创建数据库外键；保留必要唯一约束、检查约束、关系列索引和事务边界。

## 7. 首期业务规则建议

- 默认面向已有企业客户，由后台确认客户绑定关系。
- 首期每个采购账号绑定一个客户；集团多单位切换后续扩展。
- 下单后沿用现有订单提交与审核流程，不由商城直接跳过审核。
- 商品列表价格用于展示，提交时由服务端重新校验可见性、上下架、数量和有效价格并锁价。价格变化须由客户明确确认后继续提交。
- “再来一单”重新校验上下架、可见性和当前价格，不复制历史锁价作为新订单价格。
- 非标品同时保留订购数量、实际数量，区分预估金额与已确定金额。客户读取后台已确认实重，不直接修改称重记录。
- 重复点击或网络重试不得生成重复订单；关键提交操作使用服务端幂等保护。
- 首期不接入在线支付及余额充值，结算方式沿用内部闭环确认后的业务规则。账期需要额度及应收规则，货到付款需要收款状态衔接，不能只在页面上提供选项。
- 库存不足是否允许下单，应结合销售驱动采购模式确认，不能默认按现货零售商城拦截。

客户归属隔离、服务端校验、价格变化确认及提交幂等是本次确认的接口边界；开户绑定、单账号单客户、审核时点、结算及缺货规则仍属建议或待确认项，不能视为已冻结业务规则。

## 8. 分阶段路线

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| M0：工程与客户身份 | 工程、平台适配、登录、客户绑定、基础导航 | 真机登录、退出、失效恢复；客户身份与员工权限隔离 |
| M1：选品与购物车 | 默认主题、分类搜索、商品详情、客户有效价格、购物车、收货地址 | 客户商品可见性正确，失效商品和价格变化有明确提示 |
| M2：下单与订单查询 | 结算确认、幂等提交、订单列表详情、已确认实重展示 | 商城订单进入现有销售流程，重复提交不重复建单 |
| M3：复购与服务 | 常购、再来一单、配送信息、账单查询 | 复购重新校验当前价格，客户只访问自身数据，信息来自真实后台业务 |
| M4：后续扩展 | H5 正式适配、在线支付、余额充值、营销、运营首页配置、设备关联展示；报表、售后与语音作为后续专项 | 各专项单独设计验收，不纳入首发；支付回调幂等及对账，语音结果须客户确认 |

M0—M4 是本草案内部阶段编号，不替换现有 Sprint 编号；本次更新替代旧 M1—M4 划分。首发闭环为 M0—M2，M3 随后迭代，M4 分专项推进。

M2 的实重展示依赖内部 P2 分拣能力，M3 的配送和账单依赖 P3/P4，不以空页面或模拟数据视为交付。M4 应分别设计 H5、支付、营销等专项，明确非标品最终实重带来的补差、退款及结算时点。现有订单金额和退款记录不代表真实支付能力已完成。

## 9. 验证要求

实施时按风险选择测试，不为每个页面重复建设完整 E2E 套件。

- 工程检查：执行实际提供的 lint、类型检查、测试和微信小程序构建。
- 真实链路：微信开发者工具及真机验证登录、选品、提交、订单查询；H5 验证不能替代小程序验收。
- 权限：客户 A 不能访问客户 B 的商品专属价格、订单、地址和报表。
- 价格：协议价优先、专项确认后的缺价回退、提交前变价确认、再来一单重新定价。
- 订单：网络重试、重复提交、失效购物车项、后台审核及实重数据同步展示。
- 交互：加载、空状态、失败重试、登录过期、滚动和常用手机尺寸。
- 后端：对受影响业务运行编译、相关单元与集成测试及构建；数据库变更验证迁移和约束。

本次仅规划与文档整理，未进行运行时验证。

## 10. 详细设计前待确认

已确认：Taro + React + TypeScript、`xsy-scm-miniapp` 工程名、微信首发并预留 H5；不要求 H5 同期交付。

1. 客户协议价缺失时的回退及无有效价格处理，遵循价格专项，不默认市场价回退。
