  - **复核修正（同日，按负责人复核意见）**：
    ① **取消幂等重放打通**：原实现在调用正式订单服务**之前**做状态机前置判定，首次取消成功后订单已 `CANCELLED`，同一幂等键重试会被前置判定挡成「不允许取消」；且 `SalesOrderService.cancel` 的重放分支无条件调用面向员工的 `salesOrderQueryService.detail()`，商城客户会被员工范围挡住。现改为：订单已 `CANCELLED` 时跳过前置判定、直接交给幂等记录与状态机回答；重放分支的归属校验按 `enforceEmployeeScope` 分流（管理端仍走员工范围，商城侧由 `MallOrderService.requireOwnedOrder` 先判归属）。
    ② **签收信息回填**：`MallOrderQueryService` 原只取履约状态，`signedAt` / `signReason` 一直是空；现改为读取生效线路订单整行并回填，详情页不再出现「已签收却显示未签收」。
    ③ **金额标签改正**：订单列表原写「实付金额」但取的是 `orderedTotalAmount`（订货金额），与账期/货到付款/实重结算都不同；改为「预计订单金额」，接入真实支付事实后再单独展示已付金额。
    ④ **切换分类竞态**：`switchTab` 会因在途请求被 `loading` 早退，且旧响应会覆盖新分类；现引入请求序号，切分类总发新请求、旧响应一律丢弃，翻页仍等待上一页。
    ⑤ **异常配送不再当正常完成**：`EXCEPTION` 仍归「已完成」页签（异常单必须有归属，否则客户在列表找不到），但列表打「配送异常」标、详情给横幅并展示签收原因；是否单独出一个状态与页签属产品口径，**留待第二阶段配送功能统一裁决**。
  - **复核修正后验证**：后端商城单测 **16/16**（`MallOrderServiceTest` 增到 6 项，含「已取消订单的幂等重放仍能到达幂等记录」）；小程序契约测试 **18/18**；`build:mp-weixin` 通过；改动文件 eslint 无告警。
  - **第二轮复核修正（同日，幂等指纹与前端状态）**：
    ① **取消幂等指纹去掉 `version`**：幂等组件除比对 `Idempotency-Key` 还比对请求内容哈希，而 `OrderCancelForm` 带 `version`；第一次取消成功后版本前进，同一键重试的哈希就变了，会报幂等冲突而不是重放。现商城入口改用只绑定「订单 + 原因」的指纹（客户身份已在幂等 scope 的操作者里），管理端仍按整表单参与指纹、版本规则不变。指纹用 `LinkedHashMap` 而非 `Map.of`——后者迭代顺序在不同 JVM 间会变，哈希会漂移。
    ② **下单幂等预检提前到价格校验之前**：原顺序是「查价 → 校验指纹 → 幂等」，第一次下单成功但响应丢失时，重试若遇到变价会被 `CHECKOUT_PRICE_CHANGED` 挡住，客户以为没下成、实际订单已存在。现新增 `ScmIdempotencyService.peekCompleted`（只读、不占键），命中已成功的同键同指纹请求直接回放原订单；**新请求仍严格校验当前价格**。
    ③ **结算预览失败不再允许提交**：新增 `previewReady`，重新预览先作废旧指纹与金额，失败时清空并提示「金额获取失败，点击重试」，`canSubmit` 与提交守卫都要求本次预览成功，避免拿旧金额下单。
    ④ **配送日期改用 Asia/Shanghai**：原 `new Date().toISOString().slice(0, 10)` 取的是 UTC 日期，中国时间凌晨会少一天，客户能选到昨天；新增 `utils/mall-date.js` 的 `shanghaiDate()`（固定 +8，不依赖小程序支持不完整的 Intl）。
  - **第二轮复核修正后验证**：后端定向单测 **20/20**（新增 `SalesOrderCancelFingerprintTest` 2 项、`MallCheckoutServiceTest` 增到 4 项）；小程序契约测试 **20/20**；`build:mp-weixin` 通过；改动文件 eslint 无告警（顺带修掉结算页既有的 `textarea` 自闭合告警）。
  - **第三轮复核修正（同日，幂等身份与结算前端）**：
    ① **下单幂等指纹不再依赖可变的收货地址**：原实现直接拿 `SalesOrderAddForm`（含地址内容快照）当幂等请求，而地址会被同一客户的其他采购账号编辑；第一次下单成功、响应丢失后重试，服务端重新读到的地址已变，哈希随之改变，原订单回放不出来。现由 `MallCheckoutService.idempotencyRequest` 构造只含稳定字段的指纹（客户、**地址 ID**、备注、期望配送日期、按 SKU 排序的规格与数量），`SalesOrderService.createFromMall` / `replayMallOrder` 改为接收该指纹；地址内容仍在建单时照常冻结进订单快照。
    ② **预览发现不可售项时禁止提交**：`preview` 早已返回 `unavailableSkuIds` / `availableCount`，但页面只更新金额、未据此拦截，服务端金额已排除不可售行 → 客户可拿「少了钱的金额」提交。现新增 `unavailableItems`，预览结果里非 `AVAILABLE` 的项全部计入，`canSubmit` 与提交守卫都要求其为空，并展示不可售原因与「返回购物车」入口，明细行也标出不可售（不再显示 `¥` 空价）。
    ③ **预览加请求序号**：连续触发预览时旧响应后到会覆盖新金额与价格指纹，与订单列表同类竞态。现引入 `previewSeq`，旧响应一律丢弃，且旧请求不会把仍在进行中的最新预览标记为已结束。
  - **第三轮复核修正后验证**：后端定向单测 **21/21**（`MallCheckoutServiceTest` 增到 5 项，新增「地址被其他采购账号编辑后幂等身份不变、但建单快照确实变了」）；小程序契约测试 **22/22**（新增不可售拦截、预览请求序号两项）；`build:mp-weixin` 通过；改动文件 eslint 无告警。
  - **第四轮复核修正（同日，幂等预检顺序）**：`submit()` 原顺序是「读地址 → 建表单 → 幂等预检」，因此**地址被删除**时同键重试会先抛 40484「地址不存在」，把一笔已成功的订单藏起来——与「排在价格校验之后」是同一类遗漏。现幂等指纹只取请求里的地址 ID、不需要先读出地址，预检整体前移到读地址之前；只有真正的新请求才继续校验地址与价格。后端定向单测 **20/20**（`MallCheckoutServiceTest` 增到 7 项，新增「地址被删除后同键重试仍回放原订单且不读地址/不读商品」与「无原订单时地址不存在仍拒绝」）。
  - **商城主链端到端联调 ✅ 2/2（2026-10-12，隔离库 `xsy_mall_20261012_01`，`MallOrderFlowPgIT`）**：真实 PostgreSQL + 真实服务，不 mock 商城域，用例事务回滚、未留数据（复查 MALL 订单 / 商城账号 / 购物车行 / 商城地址均为 0 行）。链路与结论：
    - **主链**：后台开通商城账号 → 客户登录（真实密码校验 + 账号状态 + 客户可交易性）→ 首次登录强制改临时密码 → 目录可见性与客户价（基类 SKU 只有市场价，落 `MARKET` 兜底档 1.2000）→ 加购 → 建收货地址 → 结算预览（金额 2.4000 + 价格指纹 + 不可售清单为空）→ 下单（`orderSource=MALL`、非标品停留 `PENDING`）→ 同键重试回放原订单不重复建单 → 已下单规格从购物车移除 → 客户订单中心展示 `PENDING` 且可取消 → 后台全量范围可见 → **订单业务员本人（非超管）可见并录实重后确认** → 客户侧展示分类前进为 `PREPARING`、不再可取消。
    - **未分配业务员客户的可见性（本轮要验的风险）**：客户**未分配业务员**时订单 `seller_id` 为空，`seller_id IN (...)` 天然排除 NULL → **普通业务员在后台看不到该单**；客户自己（按 `customerId` 收窄）与全量范围操作者均可见。已用用例钉住该口径；若产品要求「未分配单人人可见」，需改范围口径而不是改测试。
