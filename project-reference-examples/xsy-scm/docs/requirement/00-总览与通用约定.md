> 本文档是 XSY-SCM 供应链管理系统需求文档的总入口。

## 1. 项目背景与系统边界

| 项 | 内容 |
| --- | --- |
| 项目 | XSY-SCM 供应链管理系统（基于官方 SmartAdmin v3.30.0 / Java17 + Spring Boot 3 二次开发） |
| 后端 | `xsy-scm-server`（`xsy-scm-base` + `xsy-scm-server`） |
| PC 管理后台 | `xsy-scm-web`（Vue 3 + TypeScript） |
| 移动端 | `xsy-app`（UniApp Vue3，目标 H5 / 微信小程序 / Android / iOS） |
| 数据库 | MySQL 8，库名 `supply_chain` |
| 编码铁律 | 见仓库根目录 `AGENTS.md`（本文档所有规则均不得与其冲突） |

系统覆盖「商品 → 客户下单 → 订单 → 采购 → 库存 → 分拣 → 配送 → 财务」的生鲜 / 农副产品供应链主链路，并包含 C 端下单商城与 B 端订单助手两端入口。

## 3. 通用字段规范

每张业务表必备字段（遵循 `AGENTS.md`「数据规则」）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `{module}_id` | BIGINT | 业务主键（以项目现有生成器为准） |
| `{module}_no` | VARCHAR | 业务编号，走编号生成器，全局唯一 |
| `status` | TINYINT | 业务状态，与后端 Enum、前端常量一一对应 |
| `create_time` / `update_time` | DATETIME | 创建 / 更新时间 |
| `create_by` / `update_by` | BIGINT | 创建 / 更新人 |
| `deleted_flag` | TINYINT | 逻辑删除（0 否，1 是） |

约束：

- 不得依赖 MySQL 物理外键，实体关系由业务层维护。
- 状态字段一律使用 Enum，禁止在业务代码散落 `0/1/2` 字面量。
- 除字典、日志类表外，业务表默认逻辑删除，不做物理删除。

## 4. 金额 / 重量 / 数量精度

| 类型 | Java | MySQL | 说明 |
| --- | --- | --- | --- |
| 金额 | `BigDecimal` | `DECIMAL(18,2)` | 禁止 `double` / `float` |
| 单价 | `BigDecimal` | `DECIMAL(18,4)` | 时价、协议价、加权平均成本需更高精度 |
| 重量 | `BigDecimal` | `DECIMAL(18,3)` | **内部统一单位 kg**，仅在展示层换算为斤 / 吨等 |
| 数量 | `BigDecimal` | `DECIMAL(18,3)` | 非标品按重计量，支持小数 |

所有涉及金额的计算（小计、优惠、运费、退款、利润）必须使用 `BigDecimal`。

### 4.1 舍入规则（G-04 已定）

- 中间计算保留 **4 位小数**（与 `DECIMAL(18,4)` 一致）；
- **最终金额一律 `HALF_UP`（四舍五入）保留 2 位小数（到分）**；
- 订单金额、订单明细金额、应收 / 应付、收款 / 付款、各类报表统一适用，确保订单与财务对得上。

### 4.2 币种与组织（G-07 已定）

- **单币种 CNY、单组织**：不引入汇率字段与多组织架构。
- 所有金额字段均为人民币金额，字段与报表不体现币种；二期如需扩展再评估。

## 5. 状态机通用约定

- 所有业务状态以 Enum 定义，状态值含义写入数据库字段注释。
- 状态流转必须：校验当前状态合法性 → 记录流转日志 → 更新状态，禁止绕过状态机直接改库。
- 终态（已完成 / 已取消 / 已作废）不允许再正向流转；确需变更时走**冲销 / 反向单据**流程，而不是改回中间态。
- 状态值新增或修改时，必须同步更新：数据库注释、后端 Enum、前端常量、API 文档。
- 状态流转优先复用现有机制记录，不额外自建流水表（库存流水、财务流水等业务流水除外，属业务数据）。

## 6. 编号规则（已确认口径）

- 单据编号统一走项目编号生成器（SmartAdmin Serial Number），禁止各模块自行拼接 `前缀 + 日期 + 随机数`。
- **业务单据：`前缀 + yyyyMMdd + 4 位流水`，流水按日重置**，如 `XSD202609070001`。
- **主数据编码（商品、客户）：`前缀 + 6 位流水`，不按日重置**，如 `SP000001`。
- 并发场景必须保证编号唯一（依赖数据库唯一约束 / 锁 / 生成器机制）。

## 7. 审计与日志

必须留审计日志的操作（遵循 `AGENTS.md`「业务规则」）：

改价、取消、退款、收货、盘点、报损报溢、客户账期修改、客户价格修改、配送状态修改。

审计内容至少包含：操作时间、操作人、IP / 设备、修改前值、修改后值、业务类型、操作类型。

实现方式：优先复用 SmartAdmin **DataTracer**，不逐表自建 `xxx_change_log`（审计要求确有差异的模块单独说明）。

## 8. 权限与数据范围

- 复用 SmartAdmin `@DataScope`：部门数据范围、员工数据范围、自定义策略。
- 典型隔离：业务员只看自己的客户与订单；采购员只看自己的采购单；客户（C 端）只看自己的数据。
- 权限校验必须在后端生效，前端隐藏按钮不构成权限控制。
- 自定义数据范围的 SQL 必须防注入，禁止拼接用户可控 SQL。

## 9. 不允许物理删除的数据

以下业务数据原则上不允许物理删除，改用「状态作废 + 冲销单据」：

订单、采购单、库存流水、退款单、配送单、财务收款 / 付款记录。

## 10. 库存口径（全局约束）

遵循 `AGENTS.md`：库存 = **余额 + 流水**，任何模块不得自行 `UPDATE` 库存余额，必须统一走库存业务层。

涉及出入库的场景（采购收货、订单发货、分拣、盘点、报损报溢、退货）都必须生成对应库存流水，由库存业务层更新余额并重算加权平均成本。

## 11. 术语表

| 术语 | 含义 |
| --- | --- |
| 标品 | 规格固定、可按件计量的商品 |
| 非标品 | 需按实际重量计量的商品（如生鲜称重） |
| 多规格 | 同一 SPU 下多个 SKU（规格 / 单位） |
| 时价 | 随行情波动、按生效时间调整的价格 |
| 协议价 | 与特定客户约定的价格 |
| 账期 | 客户先货后款的结算周期（按金额或按时间） |
| 实重 | 收货 / 分拣 / 配送环节实际称重得到的重量 |
| 分拣 | 按单品或按客户订单拣货配货的过程 |
| 线路 | 按区域 / 时间 / 订单量规划的配送路线 |
| 加权平均价 | 库存成本按入库单价加权平均的核算方式 |
| 一物一码 | 单件商品 / 批次绑定唯一二维码用于溯源 |

## 13. 已确认口径（决策记录）

> 以下为业务方已拍板的口径，需求文档据此生效，各模块「待确认」中对应条目同步标记。

| 编号 | 口径 | 决策 | 影响 |
| --- | --- | --- | --- |
| G-01 | 单据编号 | `前缀 + yyyyMMdd + 4 位流水`，按日重置；商品 / 客户编码 `前缀 + 6 位流水` 不重置 | 全部单据，见 §6 |
| G-02 | 金额含税 | **全部不含税**。单据与报表金额均为不含税金额，税额单独计算或暂不处理 | 01/04/05/09 及所有金额字段 |
| G-03 | 仓库与批次 | **单仓库、不启用批次与保质期**。表结构预留 `warehouse_id` / `batch_id` 字段但暂不使用，后续可平滑扩展 | 06 库存 |
| 01-01 | 取价优先级 | **协议价 > 促销价 > 分级价 > 时价 > 基础价，不叠加** | 01 商品、04 订单、11 商城 |
| 06-04 | 加权平均成本 | **每次入库时实时重算**，保证成本与利润实时准确 | 06 库存、09 财务 |
| 09-01 | 应收生成时点 | **订单签收后**生成（实重已确定、金额已核算） | 04 订单、09 财务 |
| 09-02 | 应付生成时点 | **采购收货入库后**生成（按实际入库数量与金额） | 05 采购、09 财务 |
| 13-01 | 溯源颗粒度 | **按批次**（一码一批），不按单件赋码 | 13 溯源 |
| G-04 | 舍入规则 | **中间计算保留 4 位，最终金额 `HALF_UP` 四舍五入到分**，全口径统一 | 04/09 及所有金额字段 |
| G-05 | 称重设备 | **一期实重手工录入，预留设备对接接口**，不绑定具体硬件型号 | 05/06/07 |
| G-06 | C 端载体 | **微信小程序为主，同一套 `xsy-app`（UniApp）代码同时发布 H5** | 11 |
| G-07 | 币种与组织 | **单币种 CNY、单组织**，不引入汇率与多组织架构 | 全部 |

### 13.1 口径落地要求

- 所有金额字段注释需标明「不含税」。
- 库存相关表一律保留 `warehouse_id`（默认单一仓库）与 `batch_id`（暂不使用），避免后续扩展改表结构。
- 取价逻辑必须记录取价依据（命中哪种价格），写入订单明细 `price_type`，保证可追溯。
- 应收 / 应付的生成时点必须在状态机中明确标注，禁止提前或延后生成。
